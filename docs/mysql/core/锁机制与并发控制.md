# MySQL 锁机制与并发控制：从行锁到死锁预防

## 一、并发问题与锁的必要性

### 1.1 并发场景下的数据问题

当多个事务同时访问相同的数据时，如果没有适当的并发控制机制，会产生各种数据一致性问题。

#### 丢失更新（Lost Update）

```
时间线:
  T1: 事务 A BEGIN
  T2: 事务 A SELECT balance FROM accounts WHERE id=1 → 1000
  T3: 事务 B BEGIN
  T4: 事务 B SELECT balance FROM accounts WHERE id=1 → 1000
  T5: 事务 A UPDATE accounts SET balance = balance + 500 WHERE id=1 → 1500
  T6: 事务 A COMMIT
  T7: 事务 B UPDATE accounts SET balance = balance + 300 WHERE id=1 → 1300
  T8: 事务 B COMMIT
  结果: balance 最终为 1300，事务 A 的更新（+500）丢失了！
```

#### 脏读

```
事务 A 修改了数据但未提交，事务 B 读取了未提交的数据。
如果事务 A 回滚，事务 B 读取的数据就是无效的"脏数据"。
```

#### 不可重复读

```
事务 A 在两次读取同一行数据之间，事务 B 修改并提交了该行。
导致事务 A 两次读取得到不同结果。
```

#### 幻读

```
事务 A 两次执行相同条件的查询，在两次查询之间，事务 B 新增/删除了满足条件的行。
导致事务 A 两次查询得到不同的结果集（像幻觉一样）。
```

### 1.2 锁的必要性

锁机制是解决并发问题的核心手段。它通过在数据访问前对数据加锁，确保同一时刻只有一个事务能修改特定数据，从而避免数据不一致。

```
锁的核心思想:
  - 互斥性：同一时刻只能有一个事务持有某数据的排他锁
  - 有序性：通过锁的获取顺序，保证并发操作的可预测性
  - 超时性：锁不能无限期持有，避免死锁
```

### 1.3 锁与事务的关系

```
事务是锁的持有者:
  ┌──────────────────────────────────┐
  │          事务生命周期              │
  │  BEGIN → 加锁 → 操作 → 解锁 → COMMIT │
  └──────────────────────────────────┘

锁的作用范围:
  ├── 锁只在事务内有效
  ├── COMMIT 或 ROLLBACK 后自动释放锁
  ├── 不同隔离级别下锁的行为不同
```

## 二、锁的分类

### 2.1 按锁的粒度分类

| 锁类型 | 锁定范围 | 开销 | 并发性能 |
|--------|---------|------|---------|
| **行锁（Row Lock）** | 单行记录 | 最小 | 最高 |
| **页锁（Page Lock）** | 一个数据页（16KB） | 中等 | 中等 |
| **表锁（Table Lock）** | 整张表 | 最大 | 最低 |

### 2.2 按锁的功能分类

#### 独占锁（Exclusive Lock，X Lock）

- **排他锁**，也称为写锁
- 一个数据行只能有一个 X 锁
- 持有 X 锁的事务可以读取和修改数据
- **阻止**其他事务获取同一数据行的任何锁

```sql
-- 加独占锁的语句:
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = 2000 WHERE id = 1;
DELETE FROM accounts WHERE id = 1;
INSERT INTO accounts(id, balance) VALUES(1, 1000);
```

#### 共享锁（Shared Lock，S Lock）

- **共享锁**，也称为读锁
- 一个数据行可以有多个 S 锁
- 持有 S 锁的事务只能读取数据，不能修改
- **阻止**其他事务获取同一数据行的 X 锁

```sql
-- 加共享锁的语句:
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
```

#### 锁的兼容性矩阵

| | X 锁（排他） | S 锁（共享） |
|---|---|---|
| **X 锁（排他）** | ❌ 冲突 | ❌ 冲突 |
| **S 锁（共享）** | ❌ 冲突 | ✅ 兼容 |

#### 意向锁（Intention Lock）

意向锁是**表级锁**，表示事务准备在表中的某些行上获取锁。

**意向排他锁（Intention Exclusive Lock，IX Lock）：**
- 事务打算在表中的某些行上加 X 锁
- 与所有表级锁冲突，但与其他意向锁兼容

**意向共享锁（Intention Shared Lock，IS Lock）：**
- 事务打算在表中的某些行上加 S 锁
- 与排他表锁冲突，但与其他意向锁和共享表锁兼容

**意向锁的作用：**

```
假设有表级共享锁 (Table S Lock):
  - 如果没有意向锁，需要检查表中每一行的锁
  - 有了意向锁，只需要检查表级意向锁是否兼容
  - 大大减少了锁检查的开销

锁兼容性矩阵（包含意向锁）:
         │   X    │   IX   │   S    │   IS   │
  ───────┼────────┼────────┼────────┼────────┤
  X      │   ❌   │   ❌   │   ❌   │   ❌   │
  IX     │   ❌   │   ✅   │   ❌   │   ✅   │
  S      │   ❌   │   ❌   │   ✅   │   ✅   │
  IS     │   ❌   │   ✅   │   ✅   │   ✅   │
```

### 2.3 按锁的实现分类

| 锁类型 | 说明 |
|--------|------|
| **行锁** | 锁定单行记录，InnoDB 的主要锁类型 |
| **Gap Lock** | 锁定一个范围，但**不包含**记录本身 |
| **Next-Key Lock** | 行锁 + Gap Lock，锁定记录和记录之前的范围 |
| **Insert Intention Lock** | 插入意向锁，特殊的间隙锁 |
| **Auto-Increment Lock** | 自增锁，用于自增列 |

## 三、行锁、表锁、页锁

### 3.1 行锁（Row Lock）

行锁是 InnoDB 中**最基本**的锁类型，锁定单行记录。

```
行锁的特点:
  ├── 粒度最小，并发性能最高
  ├── 开销最小
  ├── 仅在需要时锁定
  └── 实际是加在索引记录上
```

**行锁的工作方式：**

```
数据行:
  ┌────┬──────────┬──────┐
  │ id │ balance  │ lock │
  ├────┼──────────┼──────┤
  │ 1  │ 1000     │  -   │  ← 无锁
  │ 2  │ 2000     │  X   │  ← 事务 A 持有 X 锁
  │ 3  │ 3000     │  -   │  ← 无锁
  └────┴──────────┴──────┘

事务 B 请求 id=2 的 X 锁 → 被阻塞（等待事务 A 释放）
事务 C 请求 id=1 的 X 锁 → 立即获取（无冲突）
```

### 3.2 表锁（Table Lock）

表锁锁定整张表，开销大但实现简单。

**表锁的类型：**

| 锁类型 | 说明 |
|--------|------|
| 表读锁（Table Read Lock） | 所有事务只能读，不能写 |
| 表写锁（Table Write Lock） | 只有持有锁的事务能读写 |

```sql
-- 显式加表锁
LOCK TABLES accounts READ;           -- 加表读锁
LOCK TABLES accounts WRITE;          -- 加表写锁
UNLOCK TABLES;                       -- 释放锁

-- MyISAM 引擎在执行 SELECT/UPDATE/INSERT 时自动加表锁
-- InnoDB 使用行锁，不显式加表锁（但 DDL 操作仍会加元数据锁）
```

**元数据锁（Metadata Lock，MDL）：**

```
InnoDB 在执行 DDL 操作时会加 MDL 锁：
  - ALTER TABLE → 加 MDL 排他锁
  - SELECT 语句 → 加 MDL 共享锁
  - MDL 锁在事务提交后释放

MDL 锁的作用:
  - 保证表结构在查询过程中不会被修改
  - 防止 DDL 和 DML 的冲突
```

```sql
-- MDL 锁冲突示例
会话 A:
  BEGIN;
  SELECT * FROM accounts;  -- 加 MDL 共享锁
  
会话 B:
  ALTER TABLE accounts ADD COLUMN age INT;  -- 等待 MDL 排他锁，被阻塞
  
会话 A:
  COMMIT;  -- 释放 MDL 锁
  
会话 B:
  -- 此时才能获取 MDL 锁并执行 ALTER TABLE
```

### 3.3 页锁（Page Lock）

页锁锁定一个数据页（InnoDB 中为 16KB）。

```
页锁的场景:
  ┌─────────────────────────────────────┐
  │ 页 (16KB)                            │
  │  ├── 记录 1 (id=1, balance=1000)     │
  │  ├── 记录 2 (id=2, balance=2000)     │
  │  ├── 记录 3 (id=3, balance=3000)     │
  │  └── 记录 4 (id=4, balance=4000)     │
  └─────────────────────────────────────┘
  
如果是页锁，锁定的是整个页，即同时锁定 4 条记录
InnoDB 实际使用的是行锁（索引记录锁），而非页锁
```

### 3.4 锁的升级与降级

```
锁的兼容性:
  - S 锁 → 可以升级为 X 锁（如果没有冲突）
  - X 锁 → 无法降级为 S 锁
  - S 锁 → 可以被多个事务共享

锁的获取顺序:
  1. IS 锁 → IX 锁 → S 锁 → X 锁（升级）
  2. IS 锁 → S 锁
  3. IX 锁 → X 锁
```

## 四、间隙锁（Gap Lock）

### 4.1 什么是间隙锁

间隙锁锁定的是**索引记录之间的间隙**，而不是记录本身。它的作用是防止其他事务在锁定范围内**插入新记录**。

### 4.2 间隙锁的可视化

```
假设存在以下索引值: 10, 20, 30, 40

间隙锁锁定的范围:
  (-∞,10)  (10,20)  (20,30)  (30,40)  (40,+∞)
  
  如果锁定间隙 (20,30):
  - 不包含值 20 和 30 本身
  - 阻止其他事务插入 20~30 之间的值（如 25）
```

### 4.3 间隙锁的作用

间隙锁的主要作用是**防止幻读**。

```
场景：在可重复读隔离级别下

数据: id=10, id=20, id=30

事务 A:
  BEGIN;
  SELECT * FROM accounts WHERE id > 15 FOR UPDATE;  
  -- 锁定范围 (15, +∞)
  -- Next-Key Lock 锁定: (15,20], (20,30], (30,+∞)
  
事务 B:
  INSERT INTO accounts(id, balance) VALUES(25, 1000);
  -- 被阻塞！因为 (20,30) 范围被锁定
  
事务 A:
  COMMIT;
  
事务 B:
  -- 此时才能插入
```

### 4.4 间隙锁的开启与关闭

```sql
-- 间隙锁仅在可重复读（RR）隔离级别下生效
-- 在读已提交（RC）隔离级别下，间隙锁不会生效

-- 查看当前隔离级别
SELECT @@session.tx_isolation;

-- 设置为读已提交（禁用间隙锁）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### 4.5 间隙锁的范围示例

```
索引值: 10, 20, 30, 40

不同查询条件下的间隙锁范围:

条件: id = 20（唯一索引）
  锁定: 行锁（仅 id=20）
  间隙锁: 无

条件: id = 20（非唯一索引）
  锁定: Next-Key Lock (10,20]
  间隙锁: (10,20)

条件: id > 20
  锁定: Next-Key Lock (20,30], (30,40], (40,+∞)
  间隙锁: (20,30), (30,40), (40,+∞)

条件: id >= 20
  锁定: Next-Key Lock (20,30], (30,40], (40,+∞)
  间隙锁: (20,30), (30,40), (40,+∞)

条件: id < 20
  锁定: Next-Key Lock (-∞,10], (10,20]
  间隙锁: (-∞,10), (10,20)

条件: id <= 20
  锁定: Next-Key Lock (-∞,10], (10,20]
  间隙锁: (-∞,10), (10,20)

条件: id BETWEEN 20 AND 30
  锁定: Next-Key Lock (10,20], (20,30], (30,40]
  间隙锁: (10,20), (20,30), (30,40]
```

## 五、临键锁（Next-Key Lock）

### 5.1 什么是临键锁

临键锁是 **行锁 + 间隙锁** 的组合，锁定一条索引记录和该记录**之前的间隙**。它是 InnoDB 在可重复读隔离级别下防止幻读的核心机制。

### 5.2 临键锁的结构

```
临键锁 = 间隙锁 (前间隙) + 行锁 (当前记录)

索引值: 10, 20, 30, 40

记录 20 的 Next-Key Lock:
  ├── 间隙 (10, 20)  ← 间隙锁（不允许插入）
  └── 记录 20         ← 行锁（排他/共享）
  
  表示为: (10, 20]  ← 左开右闭区间
```

### 5.3 临键锁的工作原理

#### 防止幻读示例

```
数据初始状态: id=10, balance=1000
             id=20, balance=2000
             id=30, balance=3000

事务 A (RR 隔离级别):
  BEGIN;
  SELECT * FROM accounts WHERE id > 15 FOR UPDATE;
  -- 加 Next-Key Lock:
  --   (10,20]  → 锁定记录 20 和间隙 (10,20)
  --   (20,30]  → 锁定记录 30 和间隙 (20,30)
  --   (30,+∞)  → 锁定间隙 (30,+∞)
  -- 结果: 返回 id=20, id=30
  
事务 B:
  INSERT INTO accounts(id, balance) VALUES(25, 2500);
  -- 尝试在间隙 (20,30) 中插入
  -- 被间隙锁阻塞！
  
  INSERT INTO accounts(id, balance) VALUES(5, 500);
  -- 尝试在间隙 (-∞,10) 中插入
  -- 该间隙没有被锁定 → 成功！（因为 id > 15 不需要锁住 10 以下的范围）

事务 A:
  SELECT * FROM accounts WHERE id > 15 FOR UPDATE;
  -- 结果仍然是 id=20, id=30（没有幻读）
  COMMIT;
```

### 5.4 临键锁的特殊情况

#### 唯一索引的等值查询

```sql
-- 如果是唯一索引/主键的等值查询
-- InnoDB 会将 Next-Key Lock 降级为行锁

SELECT * FROM accounts WHERE id = 20 FOR UPDATE;  -- id 是主键
-- 仅加行锁在 id=20，不加间隙锁
```

#### 无匹配记录的等值查询

```sql
-- 查询不存在的记录
SELECT * FROM accounts WHERE id = 25 FOR UPDATE;
-- 仍然会加间隙锁 (20,30)，防止其他事务插入 id=25
```

#### 外键检查

```
InnoDB 在外键检查时也会使用 Next-Key Lock:
  - 检查引用是否存在时，使用临键锁
  - 防止在检查期间被引用的记录被删除
```

### 5.5 临键锁的优化建议

```sql
-- 建议 1：使用唯一索引进行等值查询
-- 唯一索引的等值查询会降级为行锁，减少锁范围
SELECT * FROM orders WHERE order_no = 'ORD001' FOR UPDATE;  -- order_no 是唯一索引

-- 建议 2：使用读已提交隔离级别
-- RC 级别下不使用 Gap Lock，仅使用行锁
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 建议 3：精确查询条件
-- 避免不必要的范围查询
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- 精确查询
-- 而不是
SELECT * FROM accounts WHERE id BETWEEN 1 AND 1 FOR UPDATE;  -- 范围查询
```

## 六、插入意向锁

### 6.1 什么是插入意向锁

插入意向锁（Insert Intention Lock）是一种**特殊的间隙锁**，表示事务有意向在某个间隙中插入数据。

### 6.2 插入意向锁的特点

```
插入意向锁的核心特点:
  ├── 特殊的间隙锁（更宽松）
  ├── 多个事务可以在同一间隙持有插入意向锁
  ├── 与临键锁和其他间隙锁冲突
  └── 实现了"插入不阻塞插入"的优化
```

### 6.3 工作示例

```
索引值: 10, 20, 30

事务 A:
  BEGIN;
  INSERT INTO accounts(id, balance) VALUES(15, 1500);
  -- 在间隙 (10,20) 中插入
  -- 获取插入意向锁在 (10,20)
  
事务 B:
  BEGIN;
  INSERT INTO accounts(id, balance) VALUES(16, 1600);
  -- 也在间隙 (10,20) 中插入
  -- 也获取插入意向锁在 (10,20)
  -- 多个插入意向锁兼容 → 不阻塞！
  
事务 A:
  COMMIT;
  
事务 B:
  COMMIT;
  -- 两个插入都成功了
```

### 6.4 插入意向锁与 Gap Lock 的冲突

```
事务 A:
  BEGIN;
  SELECT * FROM accounts WHERE id = 15 FOR UPDATE;
  -- id=15 不存在
  -- InnoDB 在间隙 (10,20) 加 Gap Lock
  
事务 B:
  BEGIN;
  INSERT INTO accounts(id, balance) VALUES(16, 1600);
  -- 尝试在 (10,20) 中获取插入意向锁
  -- Gap Lock 与插入意向锁冲突 → 被阻塞！
  
事务 A:
  COMMIT;
  -- 释放 Gap Lock
  
事务 B:
  -- 现在才能获取插入意向锁并插入
```

### 6.5 插入意向锁的意义

插入意向锁实现了**在同一间隙内的并发插入**，避免了不必要的锁冲突，是 InnoDB 在并发性能上的重要优化。

## 七、自增锁

### 7.1 自增锁概述

自增锁（Auto-Increment Lock）是 InnoDB 中用于**自增列**的特殊锁机制。

### 7.2 自增锁的工作原理

```sql
-- 假设有表
CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT,
    amount DECIMAL(10,2)
);

-- 当执行 INSERT 时:
INSERT INTO orders(user_id, amount) VALUES(1, 100);
```

**工作流程：**

```
1. InnoDB 请求自增锁（表级锁）
2. 获取一个或多个自增 ID（根据 innodb_autoinc_lock_mode）
3. 释放自增锁
4. 执行实际的 INSERT 操作
```

### 7.3 自增锁模式

```sql
-- 查看当前模式
SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode';
```

| 模式 | 说明 | 特点 |
|------|------|------|
| 0（传统模式） | 每次分配一个 ID，表级锁 | 性能低，兼容性好 |
| 1（连续模式） | 一次性分配指定数量的 ID | 性能较高，可能产生间隙 |
| 2（交错模式） | 一次性分配足够多的 ID | 性能最高，间隙更大 |

### 7.4 不同模式的对比

```
模式 0: 传统模式
  INSERT ... VALUES (1), (2), (3)
  → 获取 3 次自增锁，分别分配 ID 1, 2, 3
  → 每次 INSERT 都需要获取锁

模式 1: 连续模式
  INSERT ... VALUES (1), (2), (3)
  → 获取 1 次自增锁，分配 ID 1, 2, 3
  → 批量分配，减少锁获取次数
  → 但如果事务回滚，ID 会丢失（产生间隙）

模式 2: 交错模式
  INSERT ... VALUES (1), (2), (3)
  → 获取 1 次自增锁，分配 ID 1-100（预分配）
  → 性能最高，间隙也最大
```

### 7.5 自增锁的配置

```sql
-- 设置自增模式
SET GLOBAL innodb_autoinc_lock_mode = 2;  -- 推荐使用模式 2

-- 设置自增步长和偏移
SET GLOBAL auto_increment_increment = 1;
SET GLOBAL auto_increment_offset = 1;
```

## 八、死锁的产生与检测

### 8.1 什么是死锁

死锁是指两个或多个事务互相持有对方需要的锁，并无限期等待对方释放锁的状态。

### 8.2 死锁产生的四个必要条件

1. **互斥条件**：一个资源每次只能被一个事务使用
2. **请求与保持条件**：一个事务因请求资源而阻塞时，对已获得的资源保持不放
3. **不剥夺条件**：一个事务已获得的资源，在未使用完之前不能强行剥夺
4. **循环等待条件**：若干事务之间形成一种头尾相接的循环等待资源关系

### 8.3 死锁示例

```
初始状态:
  accounts 表: id=1, id=2

事务 A:                              事务 B:
  BEGIN;                               BEGIN;
  UPDATE accounts SET balance=100       UPDATE accounts SET balance=200
  WHERE id=1;                          WHERE id=2;
  -- 获取 id=1 的 X 锁                  -- 获取 id=2 的 X 锁
  
  UPDATE accounts SET balance=100       UPDATE accounts SET balance=200
  WHERE id=2;                          WHERE id=1;
  -- 请求 id=2 的 X 锁                 -- 请求 id=1 的 X 锁
  -- 被阻塞（事务 B 持有 id=2 的锁）     -- 被阻塞（事务 A 持有 id=1 的锁）
  
  ... 死锁！ ...
```

#### 死锁示意图

```
    事务 A ──等待──► id=2 (被事务 B 持有)
      ▲                    │
      │                    ▼
      └──等待── 事务 B ◄── id=1 (被事务 A 持有)
      
    形成循环等待 → 死锁！
```

### 8.4 InnoDB 的死锁检测

#### 检测机制

InnoDB 使用**等待图（Wait Graph）** 进行死锁检测：

```
等待图:
  事务 A ──等待──► 锁 L2 (被事务 B 持有)
  事务 B ──等待──► 锁 L3 (被事务 C 持有)
  事务 C ──等待──► 锁 L1 (被事务 A 持有)
  
  → 形成环 A → B → C → A → 检测到死锁！
```

#### 检测流程

```
1. 事务 T1 请求锁 L，但被事务 T2 阻塞
2. InnoDB 检查等待图中是否存在 T1 → T2 → ... → T1 的环路
3. 如果检测到环路（死锁），选择一个事务作为"牺牲者"
4. 回滚牺牲者的事务，释放其持有的锁
5. 其他事务继续执行
```

#### 检测时机

InnoDB 在以下时机进行死锁检测：
- 当一个事务等待锁时
- 当锁等待图发生变化时
- 使用深度优先搜索（DFS）算法检测环路

### 8.5 死锁的处理

#### InnoDB 的默认处理

```
当检测到死锁时:
  1. 选择回滚代价最小的事务作为牺牲者
     （通常是执行的修改操作最少的事务）
  2. 回滚牺牲者的事务
  3. 返回错误：
     ERROR 1213: Deadlock found when trying to get lock;
                 try restarting transaction
  4. 应用层需要捕获错误并重试
```

### 8.6 死锁的预防策略

#### 策略 1：固定加锁顺序

```sql
-- ❌ 反例：不同事务以不同顺序加锁
-- 事务 A: UPDATE ... WHERE id=1; UPDATE ... WHERE id=2;
-- 事务 B: UPDATE ... WHERE id=2; UPDATE ... WHERE id=1;
-- → 可能死锁！

-- ✅ 正例：所有事务按 id 从小到大加锁
-- 事务 A: UPDATE ... WHERE id=1; UPDATE ... WHERE id=2;
-- 事务 B: UPDATE ... WHERE id=1; UPDATE ... WHERE id=2;
-- → 不会死锁！
```

#### 策略 2：使用唯一索引

```sql
-- ✅ 使用唯一索引精确锁定
SELECT * FROM accounts WHERE id = ? FOR UPDATE;
-- id 是主键/唯一索引，每次只锁定一行
```

#### 策略 3：缩短事务

```sql
-- ❌ 长事务：持有锁时间过长
BEGIN;
-- 大量业务逻辑
UPDATE ...;
-- 更多业务逻辑
COMMIT;

-- ✅ 短事务：尽快提交
-- 业务逻辑放在事务外处理
BEGIN;
UPDATE ...;
COMMIT;
```

#### 策略 4：使用较低的隔离级别

```sql
-- 读已提交隔离级别不使用 Gap Lock，减少锁冲突
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

#### 策略 5：使用乐观锁

```sql
-- 使用版本号或时间戳实现乐观锁
UPDATE accounts 
SET balance = 2000, version = version + 1
WHERE id = 1 AND version = 5;
-- 如果更新失败，重试
```

#### 策略 6：死锁重试机制

```java
// Java 中的死锁重试示例
public void transferMoney(int fromId, int toId, BigDecimal amount) {
    int maxRetries = 5;
    int retryCount = 0;
    
    while (retryCount < maxRetries) {
        try {
            // 执行转账（可能抛出 DeadlockLoserDataAccessException）
            accountService.transfer(fromId, toId, amount);
            return;  // 成功，退出
        } catch (DeadlockLoserDataAccessException e) {
            retryCount++;
            // 随机等待后重试
            try {
                Thread.sleep(100 + Math.random() * 200);
            } catch (InterruptedException ie) {
                Thread.currentThread().interrupt();
            }
        }
    }
    throw new RuntimeException("死锁重试次数超限");
}
```

## 九、悲观锁与乐观锁

### 9.1 悲观锁（Pessimistic Locking）

**核心思想：** 假设并发冲突一定会发生，提前加锁防止冲突。

```sql
-- 悲观锁实现
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- 提前加 X 锁
-- 处理业务逻辑
UPDATE accounts SET balance = 2000 WHERE id = 1;
COMMIT;
```

**特点：**
- 适合**写多读少**的场景
- 锁冲突概率高
- 数据一致性强
- 并发性能较差

### 9.2 乐观锁（Optimistic Locking）

**核心思想：** 假设并发冲突很少发生，提交时才检查是否有冲突。

```sql
-- 乐观锁实现（使用版本号）
-- 表结构
CREATE TABLE accounts (
    id BIGINT PRIMARY KEY,
    balance DECIMAL(10,2),
    version INT DEFAULT 0  -- 版本号
);

-- 读取数据
SELECT id, balance, version FROM accounts WHERE id = 1;
-- → id=1, balance=1000, version=5

-- 业务处理（修改 balance）
new_balance = balance - 100;  -- 900

-- 提交时检查版本号
UPDATE accounts 
SET balance = 900, version = 6
WHERE id = 1 AND version = 5;
-- 如果其他事务已修改，version 不再是 5，更新失败
-- 应用层可以重试
```

**特点：**
- 适合**读多写少**的场景
- 锁冲突概率低
- 不会阻塞其他事务
- 需要应用层处理冲突

### 9.3 悲观锁 vs 乐观锁

| 对比维度 | 悲观锁 | 乐观锁 |
|---------|--------|--------|
| 核心假设 | 冲突一定发生 | 冲突很少发生 |
| 实现方式 | FOR UPDATE / LOCK IN SHARE MODE | 版本号 / 时间戳 |
| 锁冲突 | 高 | 低 |
| 并发性能 | 较低 | 较高 |
| 数据一致性 | 强 | 取决于实现 |
| 使用复杂度 | 简单 | 需要重试机制 |
| 适用场景 | 写密集 | 读密集 |

### 9.4 乐观锁的其他实现方式

#### 使用时间戳

```sql
-- 添加更新时间戳列
ALTER TABLE accounts ADD COLUMN updated_at DATETIME 
    DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP;

-- 查询时获取时间戳
SELECT id, balance, updated_at FROM accounts WHERE id = 1;

-- 提交时检查时间戳
UPDATE accounts 
SET balance = 900 
WHERE id = 1 AND updated_at = '2024-01-15 10:30:00';
```

#### 使用唯一约束

```sql
-- 在业务表上添加唯一约束
ALTER TABLE orders ADD CONSTRAINT uk_order_no UNIQUE (order_no);

-- 利用唯一约束的原子性防止并发重复创建
INSERT INTO orders(order_no, ...) VALUES ('ORD001', ...);
-- 如果重复插入，会违反唯一约束，应用层捕获异常后处理
```

## 十、SELECT ... FOR UPDATE 与 LOCK IN SHARE MODE

### 10.1 SELECT ... FOR UPDATE

```sql
-- 语法
SELECT * FROM table_name WHERE condition FOR UPDATE;
```

**行为：**
- 对查询到的每一行加**排他锁（X Lock）**
- 其他事务不能对这些行加任何锁
- 其他事务的更新、删除、FOR UPDATE 操作都会被阻塞
- 在事务提交/回滚后释放锁

```sql
-- 示例
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
-- 获取 id=1 的 X 锁

UPDATE accounts SET balance = 2000 WHERE id = 1;
-- 基于锁定的数据进行修改

COMMIT;
-- 释放 X 锁
```

### 10.2 LOCK IN SHARE MODE

```sql
-- 语法
SELECT * FROM table_name WHERE condition LOCK IN SHARE MODE;
```

**行为：**
- 对查询到的每一行加**共享锁（S Lock）**
- 其他事务可以读取这些行，但不能修改
- 其他事务可以再加 S 锁（共享锁可共存）
- 其他事务的 FOR UPDATE、UPDATE、DELETE 操作都会被阻塞

```sql
-- 示例
BEGIN;
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;
-- 获取 id=1 的 S 锁

-- 其他事务可以读：
SELECT * FROM accounts WHERE id = 1;  -- 快照读，不阻塞
SELECT * FROM accounts WHERE id = 1 LOCK IN SHARE MODE;  -- S 锁，不阻塞

-- 其他事务不能写：
UPDATE accounts SET balance = 2000 WHERE id = 1;  -- 阻塞
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- 阻塞

COMMIT;
-- 释放 S 锁
```

### 10.3 两种锁的对比

| 对比维度 | FOR UPDATE | LOCK IN SHARE MODE |
|---------|-----------|-------------------|
| 锁类型 | 排他锁（X） | 共享锁（S） |
| 其他读 | ✅ 快照读可 | ✅ 快照读可 |
| 其他共享锁 | ❌ 阻塞 | ✅ 兼容 |
| 其他排他锁 | ❌ 阻塞 | ❌ 阻塞 |
| 适用场景 | 需要修改数据 | 仅需读取但不想被修改 |
| 升级 | 已是 X 锁，无需升级 | 需要升级为 X 锁时可能死锁 |

### 10.4 使用建议

```
FOR UPDATE:
  - 适用于需要"读取并修改"的场景
  - 例如：库存扣减、金额转账
  - 更安全，避免了 S 锁升级 X 锁的死锁问题

LOCK IN SHARE MODE:
  - 适用于"只读取但不想被修改"的场景
  - 例如：读取配置、读取状态
  - 允许并发读取，但不允许修改
```

## 十一、InnoDB 锁的实现机制

### 11.1 锁的内部结构

InnoDB 的锁是**加在索引记录上**的，每条锁记录包含以下信息：

```
锁记录结构:
  ├── 锁类型 (X Lock / S Lock / Gap Lock / Next-Key Lock)
  ├── 索引记录位置 (Space ID + Page No + Record No)
  ├── 持有锁的事务 ID
  ├── 等待该锁的事务队列
  └── 锁的创建时间
```

### 11.2 锁的获取流程

```
事务 T 请求获取记录 R 的锁:
  │
  ├── 检查记录 R 是否有锁
  │   ├── 无锁 → 直接获取
  │   └── 有锁 → 检查兼容性
  │       ├── 兼容 → 共享锁可以同时获取
  │       └── 冲突 → 进入等待队列
  │
  ├── 如果进入等待队列:
  │   ├── InnoDB 将事务 T 挂起
  │   ├── 当锁释放时，唤醒等待队列中的事务
  │   └── 事务 T 被唤醒，重新尝试获取锁
  │
  └── 超时处理:
      └── 超过 innodb_lock_wait_timeout 秒后返回错误
```

### 11.3 锁的释放时机

```
锁在以下时机释放:
  ├── 事务 COMMIT 时
  ├── 事务 ROLLBACK 时
  ├── 语句执行完成（隐式提交的语句）
  └── 死锁回滚时

注意:
  - 锁在整个事务内有效
  - 即使语句执行完成，锁也不会立即释放
  - 必须等到事务提交或回滚
```

### 11.4 锁与索引的关系

```
锁的本质是加在索引记录上的:
  ├── 如果查询使用了索引，锁加在命中的索引记录上
  ├── 如果查询没有使用索引，InnoDB 会扫描所有索引记录并加锁
  │   → 相当于全表锁！
  └── 因此：合理使用索引可以缩小锁的范围
```

#### 无索引导致的锁升级

```sql
-- 假设 name 列没有索引
UPDATE users SET balance = balance + 100 WHERE name = '张三';
-- InnoDB 扫描所有记录，对每条记录加 X 锁
-- 实际效果相当于全表锁！

-- 创建索引后
CREATE INDEX idx_name ON users(name);
UPDATE users SET balance = balance + 100 WHERE name = '张三';
-- 只锁定 name='张三' 的记录
```

## 十二、锁等待与锁超时

### 12.1 锁等待机制

```
当事务 T1 请求的锁被事务 T2 持有时:
  1. InnoDB 将 T1 放入锁等待队列
  2. T1 进入挂起状态，等待 T2 释放锁
  3. T2 提交或回滚后，释放锁
  4. InnoDB 从等待队列中取出 T1
  5. T1 被唤醒，获取锁并继续执行
```

### 12.2 锁等待超时

```sql
-- 查看锁等待超时时间
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
-- 默认 50 秒

-- 修改超时时间
SET GLOBAL innodb_lock_wait_timeout = 30;

-- 超时后返回错误:
-- ERROR 1205: Lock wait timeout exceeded;
--            try restarting transaction
```

### 12.3 锁等待的排查

```sql
-- 查看当前锁等待
SELECT 
    r.trx_id waiting_trx_id,
    r.trx_mysql_thread_id waiting_thread,
    r.trx_query waiting_query,
    b.trx_id blocking_trx_id,
    b.trx_mysql_thread_id blocking_thread,
    b.trx_query blocking_query
FROM information_schema.innodb_lock_waits w
INNER JOIN information_schema.innodb_trx b 
    ON b.trx_id = w.blocking_trx_id
INNER JOIN information_schema.innodb_trx r 
    ON r.trx_id = w.requesting_trx_id;
```

### 12.4 强制终止锁等待

```sql
-- 查找阻塞线程
SELECT * FROM information_schema.innodb_trx\G

-- 查看线程 ID
SHOW PROCESSLIST;

-- 终止阻塞线程
KILL <thread_id>;
-- 注意：KILL 会回滚该事务，释放其持有的锁
```

## 十四、高并发场景下的锁优化

### 14.1 优化原则

1. **减少锁的范围**：使用精确的查询条件，避免锁定不必要的行
2. **缩短锁的时间**：尽快提交事务，减少锁持有时间
3. **降低隔离级别**：在适当的场景使用读已提交隔离级别
4. **固定加锁顺序**：避免循环等待，预防死锁
5. **使用乐观锁**：减少锁争用

### 14.2 具体优化措施

#### 1. 使用唯一索引精确锁定

```sql
-- ✅ 好：使用唯一索引
SELECT * FROM orders WHERE order_no = 'ORD20240015' FOR UPDATE;
-- 锁定一行

-- ❌ 差：使用非唯一条件
SELECT * FROM orders WHERE user_id = 123 AND status = 0 FOR UPDATE;
-- 锁定多行（可能是几十、几百行）
```

#### 2. 批量处理使用 LIMIT

```sql
-- ❌ 一次性锁定大量行
SELECT * FROM accounts WHERE balance > 10000 FOR UPDATE;

-- ✅ 分批处理
-- 第 1 批
SELECT * FROM accounts WHERE balance > 10000 ORDER BY id LIMIT 100 FOR UPDATE;
-- 第 2 批
SELECT * FROM accounts WHERE balance > 10000 AND id > last_id 
ORDER BY id LIMIT 100 FOR UPDATE;
```

#### 3. 使用 RC 隔离级别

```sql
-- 在读多写少的场景
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- 减少 Gap Lock，降低锁冲突
```

#### 4. 使用乐观锁替代悲观锁

```sql
-- 库存扣减场景
UPDATE products 
SET stock = stock - 1, version = version + 1
WHERE id = 123 AND version = 5 AND stock > 0;

-- 如果影响行数为 0，重试
```

#### 5. 热点行拆分

```sql
-- 假设库存表只有一行（热点）
-- products: id=1, stock=10000

-- 拆分多行分散热点
CREATE TABLE products_split (
    id INT,
    stock INT,
    PRIMARY KEY (id)
);

INSERT INTO products_split(id, stock) VALUES
(1, 2000), (2, 2000), (3, 2000), (4, 2000), (5, 2000);

-- 扣减时随机选择一个分片
UPDATE products_split SET stock = stock - 1 
WHERE id = ? AND stock > 0;
```

#### 6. 使用队列削峰

```sql
-- 直接更新（高并发时锁争用）
UPDATE products SET stock = stock - 1 WHERE id = 1;

-- 引入消息队列
-- 1. 扣减请求发送到消息队列
-- 2. 消费者从队列消费并更新库存
-- 3. 批量更新，减少锁获取次数
```

### 14.3 锁监控体系

### 14.4 实战案例：电商秒杀系统

#### 问题分析

秒杀场景下，大量并发请求同时扣减同一件商品的库存，导致严重的锁争用。

#### 优化方案

```sql
-- 方案 1：乐观锁（适合冲突概率低的场景）
UPDATE products 
SET stock = stock - #{quantity}
WHERE id = #{id} AND stock >= #{quantity};
-- 返回影响行数判断是否成功

-- 方案 2：Redis 预扣减 + 异步落库
-- Step 1: Redis 原子操作扣减库存
DECR stock_key  #{quantity}
-- Step 2: 异步将变更同步到 MySQL（批量）

-- 方案 3：库存分片 + 乐观锁
-- 将库存拆分到多行
UPDATE products_shard 
SET stock = stock - #{quantity}
WHERE id = #{shard_id} AND stock >= #{quantity};

-- 方案 4：队列削峰
-- 秒杀请求进入队列，消费者逐步处理
```

#### 代码示例

```java
// 基于 Redis + MySQL 的库存扣减
@Service
public class InventoryService {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @Autowired
    private InventoryMapper inventoryMapper;
    
    // Redis 预扣减
    public boolean deductStock(Long productId, int quantity) {
        String key = "stock:" + productId;
        Long remain = redisTemplate.opsForValue().decrement(key, quantity);
        return remain >= 0;
    }
    
    // MySQL 最终扣减（异步）
    @Async
    public void syncToMysql(Long productId, int quantity) {
        int maxRetries = 3;
        int retryCount = 0;
        
        while (retryCount < maxRetries) {
            try {
                int updated = inventoryMapper.deductStockWithVersion(
                    productId, quantity, expectedVersion);
                if (updated > 0) {
                    return;  // 成功
                }
                retryCount++;
                // 重新读取版本号并重试
            } catch (Exception e) {
                retryCount++;
            }
        }
    }
}
```
