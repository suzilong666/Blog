# MySQL 存储引擎详解：从 InnoDB 架构到引擎选择策略

## 一、MySQL 存储引擎概述

### 1.1 什么是存储引擎

存储引擎（Storage Engine）是 MySQL 的核心组件，负责数据的**实际存储和读取**。它定义了数据如何存储、如何索引、如何查询以及如何保证数据完整性。

MySQL 的独特之处在于采用了**插件化的存储引擎架构**：不同的存储引擎可以有不同的数据存储方式、索引类型、事务支持和锁定机制，用户可以根据业务需求选择最合适的引擎。

### 1.2 MySQL 架构分层

```
┌─────────────────────────────────────────────────────────┐
│                     客户端/连接层                          │
│  (连接处理、用户认证、权限管理)                             │
├─────────────────────────────────────────────────────────┤
│                     SQL 接口层                             │
│  (SQL 解析、查询缓存、优化器)                             │
├─────────────────────────────────────────────────────────┤
│                      存储引擎层                            │
│  ┌──────────┬──────────┬──────────┬──────────┬────────┐ │
│  │ InnoDB   │ MyISAM   │ Memory   │  Merge   │  CSV   │ │
│  └──────────┴──────────┴──────────┴──────────┴────────┘ │
├─────────────────────────────────────────────────────────┤
│                      物理存储层                            │
│  (磁盘文件、日志文件、内存缓存)                            │
└─────────────────────────────────────────────────────────┘
```

### 1.3 存储引擎的分类

| 分类 | 代表引擎 | 特点 |
|------|---------|------|
| **事务型引擎** | InnoDB | 支持事务、行锁、外键 |
| **非事务型引擎** | MyISAM, Memory | 不支持事务，性能高 |
| **特殊用途引擎** | Merge, CSV, Archive | 特定场景优化 |


```
| Memory     | YES     | ...        | NO   | NO         |
```

## 二、InnoDB 引擎架构

### 2.1 InnoDB 整体架构

InnoDB 是 MySQL 中最重要的存储引擎，也是 MySQL 5.5+ 的**默认引擎**。它以完整的事务支持、行级锁定和崩溃恢复能力成为大多数应用的首选。

```
┌─────────────────────────────────────────────────────────────┐
│                        前端模块                               │
│  ┌─────────────┬─────────────┬─────────────┬──────────────┐ │
│  │   查询执行    │   事务管理    │   锁定管理    │   数据字典   │ │
│  └─────────────┴─────────────┴─────────────┴──────────────┘ │
├─────────────────────────────────────────────────────────────┤
│                        缓冲池模块                             │
│  ┌─────────────┬─────────────┬─────────────┬──────────────┐ │
│  │  Buffer Pool │  Log Buffer │  Insert Buffer │  Adaptive    │ │
│  │  (数据缓存)   │  (日志缓存)  │  (插入缓存)    │  Hash Index  │ │
│  └─────────────┴─────────────┴─────────────┴──────────────┘ │
├─────────────────────────────────────────────────────────────┤
│                        存储模块                               │
│  ┌─────────────┬─────────────┬─────────────┬──────────────┐ │
│  │   数据存储    │   索引存储    │   日志存储    │   外键存储   │ │
│  └─────────────┴─────────────┴─────────────┴──────────────┘ │
├─────────────────────────────────────────────────────────────┤
│                        后台线程                               │
│  ┌─────────────┬─────────────┬─────────────┬──────────────┐ │
│  │  Master     │  IO Thread  │  Purge      │  Page Cleaner│ │
│  │  Thread     │  (异步IO)    │  Thread     │  Thread      │ │
│  └─────────────┴─────────────┴─────────────┴──────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 数据文件组织

#### 系统表空间（ibdata）

```
ibdata1:
  ├── 数据字典元数据
  ├── Double Write Buffer
  ├── 插入缓冲（Insert Buffer）
  ├── 回滚段（Rollback Segment）
  └── 其他系统信息
```

```sql
-- 查看系统表空间配置
SHOW VARIABLES LIKE 'innodb_data_file_path';
SHOW VARIABLES LIKE 'innodb_data_home_dir';
```

#### 独立表空间

```sql
-- MySQL 5.6+ 默认开启独立表空间
SET GLOBAL innodb_file_per_table = ON;
```

开启后，每个表使用独立的 `.ibd` 文件：

```
数据库目录/
  ├── ibdata1          ← 系统表空间
  ├── undo_001         ← Undo 表空间（MySQL 5.7+）
  ├── undo_002
  ├── mysql.ibd        ← 系统表的独立表空间
  ├── performance_schema/
  └── my_database/
       ├── users.frm   ← 表结构定义
       ├── users.ibd   ← 表数据（聚簇索引 + 二级索引）
       └── orders.ibd
```

#### Redo Log 文件

```
Redo Log 文件组:
  ib_logfile0: 0 ~ 48MB（默认大小）
  ib_logfile1: 0 ~ 48MB
  
  两个文件交替使用，循环写入
```

```sql
-- 查看 Redo Log 配置
SHOW VARIABLES LIKE 'innodb_log_file_size';
SHOW VARIABLES LIKE 'innodb_log_files_in_group';
```

#### Undo 表空间

```
Undo 表空间（MySQL 5.7+）:
  undo_001: 存放回滚段
  undo_002: 存放回滚段
  
  可以配置多个 Undo 表空间以提升并发
```

```sql
-- 查看 Undo 表空间
SHOW VARIABLES LIKE 'innodb_undo_tablespaces';
-- 默认 0（使用系统表空间的 Undo）
-- 设置为 2 表示使用独立的 undo_001 和 undo_002
```

### 2.3 后台线程详解

| 线程 | 功能 | 说明 |
|------|------|------|
| **Master Thread** | 主循环线程 | 负责异步刷新、合并插入缓冲、切换 Undo 页等 |
| **IO Thread** | 异步 I/O 线程 | 负责预读、脏页刷盘等 I/O 操作 |
| **Purge Thread** | 清理线程 | 清理已提交事务的 Undo Log |
| **Page Cleaner Thread** | 页清理线程 | 将 Buffer Pool 中的脏页刷入磁盘 |
| **Lock Wait Thread** | 锁等待线程 | 处理锁等待和死锁检测 |

#### Master Thread 工作流程

```
Master Thread 每 1 秒执行一次:
  1. 刷新 Redo Log 到磁盘（即使事务未提交）
  2. 合并 Insert Buffer 到主索引
  3. 刷新至多 100 个脏页到磁盘
  4. 如果没有活跃事务，删除无用的 Undo 页
  
每 10 秒执行一次:
  1. 刷新至多 300 个脏页到磁盘
  2. 切换日志文件（如果需要）
  3. 刷新所有缓冲池
```

### 2.4 InnoDB 核心特性总结

| 特性 | 说明 |
|------|------|
| **ACID 事务** | 完整支持原子性、一致性、隔离性、持久性 |
| **行级锁定** | 细粒度锁定，高并发性能 |
| **外键约束** | 支持外键关系，保证数据完整性 |
| **聚簇索引** | 主键索引即数据存储，查询效率高 |
| **MVCC** | 多版本并发控制，实现非锁定读 |
| **崩溃恢复** | 基于 Redo Log 和 Undo Log 的自动恢复 |
| **自适应哈希索引** | 自动为高频访问数据构建哈希索引 |
| **插入缓冲** | 优化非唯一索引的插入性能 |
| **Double Write** | 防止部分写失效 |

## 三、InnoDB 的缓冲池（Buffer Pool）

### 3.1 Buffer Pool 概述

Buffer Pool 是 InnoDB 中**最大最核心**的内存组件，用于缓存数据页和索引页。合理配置 Buffer Pool 对 MySQL 性能至关重要。

### 3.2 Buffer Pool 内存结构

```
Buffer Pool 内存布局:
  ┌───────────────────────────────────────────────────┐
  │                Buffer Pool 总大小                  │
  │  ┌────────────────────┬────────────────────────┐ │
  │  │    空闲页 (Free List)  │    脏页 (LRU List)      │ │
  │  │                    │                        │ │
  │  │   等待被使用的页    │   最近最少使用的页        │ │
  │  └────────────────────┴────────────────────────┘ │
  │  ┌────────────────────┬────────────────────────┐ │
  │  │    数据页          │    自适应哈希索引          │ │
  │  │   (16KB/页)        │   (动态内存分配)          │ │
  │  └────────────────────┴────────────────────────┘ │
  └───────────────────────────────────────────────────┘
```

### 3.3 页管理机制

#### LRU 算法（最近最少使用）

Buffer Pool 使用**改良版 LRU 算法**管理页的生命周期：

```
LRU List 结构:
  头部 (最近使用) → [热数据区] → [冷数据区] → 尾部 (最久未使用)
  
  冷数据区占比由参数 innodb_lru_scan_depth 控制
  默认 37% 的页位于冷数据区
```

**页的加载过程：**

```
1. 用户查询所需数据
  ↓
2. 检查 Buffer Pool 中是否存在该页
   ├── 存在 → 直接返回（命中缓存）
   └── 不存在 → 从磁盘读取到 Buffer Pool
                  ↓
               如果 Buffer Pool 已满
               → 从 LRU List 尾部淘汰最久未使用的页
               → 加载新页到 LRU List 头部
```

#### 脏页刷新机制

```
数据修改流程:
  1. 读取数据页到 Buffer Pool
  2. 在 Buffer Pool 中修改数据
  3. 该页变为"脏页"（Dirty Page）
  4. 脏页被加入 LRU List 的脏页区域

脏页刷新触发条件:
  ├── Master Thread 定期刷新（后台异步）
  ├── Redo Log 空间不足（必须刷新）
  ├── Buffer Pool 空间不足（需要淘汰脏页）
  ├── 数据库关闭时（全部刷新）
```

### 3.4 Buffer Pool 配置建议

```sql
-- 查看当前配置
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
-- 默认 128MB

-- 推荐配置（专用数据库服务器）
-- 通常设置为物理内存的 60% ~ 80%
SET GLOBAL innodb_buffer_pool_size = 8G;

-- 查看 Buffer Pool 状态
SHOW ENGINE INNODB STATUS\G
```

#### 命中率监控

```sql
-- 查询 Buffer Pool 命中率
SELECT 
    SUM(CASE WHEN EVENT_NAME LIKE '%read%' THEN COUNT_STAR ELSE 0 END) AS total_reads,
    SUM(CASE WHEN EVENT_NAME LIKE '%create%' THEN COUNT_STAR ELSE 0 END) AS disk_reads
FROM performance_schema.events_waits_summary_global_by_event_name;

-- 更精确的命中率计算
SELECT 
    (pages_made_young * 100.0 / (pages_made_young + pages_not_made_young)) AS hit_ratio
FROM information_schema.INNODB_BUFFER_POOL_STATS;
```

**命中率建议：** 应保持在 **99% 以上**，低于 95% 说明 Buffer Pool 可能太小。

### 3.5 多 Buffer Pool 实例

```sql
-- MySQL 5.7+ 支持多 Buffer Pool 实例
-- 减少锁竞争，提升并发性能

-- 查看和设置实例数
SHOW VARIABLES LIKE 'innodb_buffer_pool_instances';
-- 默认 1

-- 建议：设置为 CPU 核数
SET GLOBAL innodb_buffer_pool_instances = 4;
SET GLOBAL innodb_buffer_pool_size = 8G;  -- 每个实例 2G
```

### 3.6 Buffer Pool 预热

MySQL 可以在启动时预加载数据到 Buffer Pool，减少冷启动影响：

```sql
-- 开启自动预热
SET GLOBAL innodb_buffer_pool_dump_at_shutdown = ON;  -- 关闭时导出
SET GLOBAL innodb_buffer_pool_load_at_startup = ON;   -- 启动时加载

-- 手动预热特定表
-- 可以通过全表查询将数据加载到 Buffer Pool
SELECT * FROM orders;
```

## 四、InnoDB 的数据存储文件

### 4.1 页（Page）管理

页是 InnoDB 存储的**最小分配单元**，默认大小为 16KB。

```
页结构 (16KB):
  ┌───────────────────────────────────────────────────────┐
  │ 页标题 (Page Header) - 38 字节                        │
  │  ├── 页号 (Page Number)                                │
  │  ├── 页类型 (Page Type)                                │
  │  ├── 上一页指针                                        │
  │  └── 下一页指针                                        │
  ├───────────────────────────────────────────────────────┤
  │ 数据区 (Data Area)                                    │
  │  ├── 记录 1                                            │
  │  ├── 记录 2                                            │
  │  ├── ...                                               │
  │  └── 记录 N                                            │
  ├───────────────────────────────────────────────────────┤
  │ 页尾 (Page Trailer) - 8 字节                          │
  │  ├── 页校验和 (Checksum)                               │
  │  └── 上一页/下一页校验和                                │
  └───────────────────────────────────────────────────────┘
```

### 4.2 页类型

| 页类型 | 说明 |
|--------|------|
| **数据页（INDEX）** | 存储表中的行数据（B+ 树叶子节点） |
| **索引页** | 存储 B+ 树的非叶子节点 |
| **系统页（SYSTEM）** | 存储数据字典信息 |
| **Undo 日志页** | 存储 Undo Log |
| **插入缓冲页** | 存储 Insert Buffer 数据 |
| **自适应哈希索引页** | 存储自适应哈希索引数据 |

### 4.3 行格式

InnoDB 支持多种行格式：

#### Compact 行格式（默认）

```
记录结构:
  ┌────────────┬─────────────┬─────────────┬──────────────────────┐
  │ 记录头      │ 隐藏字段     │ 可变长度字段  │ NULL 标记             │
  │ (5 字节)   │ (DB_TRX_ID)  │             │                      │
  │            │ (DB_ROLL_PTR)│             │                      │
  ├────────────┴─────────────┴─────────────┴──────────────────────┤
  │ 实际数据区 (按列顺序存储)                                        │
  └─────────────────────────────────────────────────────────────────┘
```

隐藏字段说明：
- `DB_TRX_ID`：最后一次修改该行的事务 ID（6 字节）
- `DB_ROLL_PTR`：指向 Undo Log 中旧版本的指针（7 字节）
- 对于聚簇索引，还有 `DB_ROW_ID`：隐含的主键值（6 字节，仅在无主键时存在）

#### Dynamic 行格式

```sql
-- Dynamic 行格式的特点：
-- 1. 变长字段（BLOB, TEXT）仅存储 20 字节的指针
-- 2. 实际数据存储在溢出页（Off-page）
-- 3. 节省 Buffer Pool 空间

CREATE TABLE t_dynamic (
    id BIGINT PRIMARY KEY,
    data BLOB
) ENGINE=InnoDB ROW_FORMAT=DYNAMIC;
```

### 4.4 数据页内部结构

```
数据页内部:
  ┌──────────────────────────────────────────┐
  │ 页标题 (38 字节)                          │
  ├──────────────────────────────────────────┤
  │ 空闲空间 (Free Space)                     │
  ├──────────────────────────────────────────┤
  │ 记录区 (Records)                          │
  │  ├── 记录 1                               │
  │  ├── 记录 2                               │
  │  └── ...                                  │
  ├──────────────────────────────────────────┤
  │ 记录指针数组 (Record Pointer Array)       │
  │  ├── 指向记录 1 的偏移量                    │
  │  ├── 指向记录 2 的偏移量                    │
  │  └── ...                                  │
  ├──────────────────────────────────────────┤
  │ 页尾 (8 字节)                             │
  └──────────────────────────────────────────┘
```

## 五、MyISAM 引擎

### 5.1 MyISAM 概述

MyISAM 是 MySQL 的**早期默认引擎**，以其简单、高效、适合读密集场景而著称。虽然不支持事务，但在某些特定场景下仍有优势。

### 5.2 存储结构

每个 MyISAM 表由三个文件组成：

```
users 表的文件:
  ├── users.frm    ← 表结构定义
  ├── users.MYD    ← 数据文件 (MyISAM Data)
  └── users.MYI    ← 索引文件 (MyISAM Index)
```

#### 数据文件（.MYD）

```
数据文件结构:
  ┌──────────┬──────────┬──────────┬──────────┐
  │ 记录 1    │ 记录 2    │ 记录 3    │ ...      │
  └──────────┴──────────┴──────────┴──────────┘
  
特点:
  1. 数据以堆方式存储，无序
  2. 删除记录时标记为"可重用"
  3. 不支持事务和 MVCC
```

#### 索引文件（.MYI）

```
索引文件结构:
  ┌──────────────────────────────────────────┐
  │ 索引头部 (Index Header)                   │
  ├──────────────────────────────────────────┤
  │ B+ 树索引                                 │
  │  ├── 主键索引                              │
  │  ├── 辅助索引 1                            │
  │  └── 辅助索引 2                            │
  ├──────────────────────────────────────────┤
  │ 行指针数组                                │
  │  └── 指向 .MYD 文件中记录的物理位置         │
  └──────────────────────────────────────────┘
```

### 5.3 MyISAM 核心特性

| 特性 | 说明 |
|------|------|
| **不支持事务** | 无 ACID 特性，不能回滚 |
| **不支持行锁** | 仅支持表锁，并发性能差 |
| **不支持外键** | 无外键约束 |
| **崩溃安全性差** | 崩溃后需要 `REPAIR TABLE` 修复 |
| **全表扫描快** | 简单的存储结构，读取效率高 |
| **占用空间小** | 无事务日志、无 MVCC 开销 |
| **支持压缩** | `myisampack` 工具压缩只读表 |
| **全文索引** | 早期全文索引的主要提供者 |

### 5.4 MyISAM 适用场景

- ✅ **读多写少的场景**：如日志表、统计报表
- ✅ **数据仓库**：ETL 过程中的中间表
- ✅ **只读或偶尔更新的数据**：如配置表、字典表
- ❌ **高并发写入**
- ❌ **需要事务的业务**
- ❌ **外键约束**

### 5.5 MyISAM 表的维护

```sql
-- 检查表
CHECK TABLE users;

-- 修复表
REPAIR TABLE users;

-- 优化表（回收空间）
OPTIMIZE TABLE users;

-- 分析表（更新索引统计）
ANALYZE TABLE users;
```

## 六、Memory 引擎

### 6.1 Memory 引擎概述

Memory 引擎（之前称为 Heap 引擎）将数据存储在**内存**中，具有极快的读写速度，但数据在 MySQL 重启后会丢失。

### 6.2 核心特性

| 特性 | 说明 |
|------|------|
| **数据存储在内存** | 极快的访问速度 |
| **数据不持久** | MySQL 重启后数据丢失 |
| **支持的索引** | 仅支持哈希索引和 B+ 树索引 |
| **不支持事务** | 无事务安全 |
| **表锁** | 仅支持表级锁 |
| **固定长度行** | VARCHAR 等变长类型按最大长度存储 |

### 6.3 适用场景

- ✅ **临时表**：存储会话级临时数据
- ✅ **缓存表**：缓存热点数据（配合持久化方案）
- ✅ **中间计算结果**：存储复杂查询的中间结果
- ❌ **需要持久化的数据**
- ❌ **大数据量场景**：受内存限制

### 6.4 Memory 引擎的使用

```sql
-- 创建 Memory 表
CREATE TABLE cache_data (
    key VARCHAR(100) PRIMARY KEY,
    value TEXT,
    expire_time INT,
    INDEX idx_key USING HASH (key)
) ENGINE = MEMORY;

-- 注意：Memory 表重启后数据清空
-- 但 .frm 文件（表结构）会保留

-- 查看 Memory 表大小
SELECT * FROM information_schema.MEMORY_TABLE_STATISTICS;
```

### 6.5 与临时表的对比

| 特性 | Memory 表 | 临时表 |
|------|----------|--------|
| 生命周期 | 显式删除或重启 | 会话结束时自动删除 |
| 可见性 | 全局可见 | 仅当前会话可见 |
| 创建方式 | CREATE TABLE | CREATE TEMPORARY TABLE |
| 存储位置 | 内存 | 内存（溢出到磁盘） |

```sql
-- 临时表示例
CREATE TEMPORARY TABLE temp_results (
    id INT,
    score DECIMAL(10,2)
);

-- 临时表在当前会话可见，会话结束后自动删除
```

## 七、Merge 引擎

### 7.1 Merge 引擎概述

Merge 引擎是一种**虚拟引擎**，它将多个结构相同的 MyISAM 表组合成一个逻辑表，实现分表（Partition）的效果。

### 7.2 核心原理

```
users_all (Merge 引擎)
  ├── users_2023 (MyISAM)
  ├── users_2024 (MyISAM)
  └── users_2025 (MyISAM)
```

### 7.3 创建 Merge 表

```sql
-- 创建分表
CREATE TABLE users_2023 (
    id INT NOT NULL AUTO_INCREMENT,
    name VARCHAR(50),
    created_at DATE,
    PRIMARY KEY (id),
    KEY idx_created (created_at)
) ENGINE = MyISAM;

CREATE TABLE users_2024 (
    id INT NOT NULL AUTO_INCREMENT,
    name VARCHAR(50),
    created_at DATE,
    PRIMARY KEY (id),
    KEY idx_created (created_at)
) ENGINE = MyISAM;

-- 创建 Merge 表
CREATE TABLE users_all (
    id INT NOT NULL AUTO_INCREMENT,
    name VARCHAR(50),
    created_at DATE,
    PRIMARY KEY (id),
    KEY idx_created (created_at)
) ENGINE = MERGE 
UNION = (users_2023, users_2024) 
INSERT_METHOD = LAST;  -- 插入到最后一个表
```

### 7.4 Merge 引擎的限制

- 所有分表的结构必须**完全相同**
- 不支持 `REPLACE`、`AUTO_INCREMENT` 等特性
- 查询性能略低于单个表
- 不支持 ALTER TABLE 操作

### 7.5 适用场景

- ✅ 日志归档（按年/月分表）
- ✅ 历史数据查询
- ❌ 需要高并发的在线业务
- ❌ 需要事务的场景

## 八、CSV 引擎

### 8.1 CSV 引擎概述

CSV 引擎将数据存储为标准的 **CSV 格式文件**，可以用任何文本编辑器打开和编辑。

### 8.2 核心特性

| 特性 | 说明 |
|------|------|
| **数据以 CSV 格式存储** | 可直接用 Excel、文本编辑器打开 |
| **不支持索引** | 全表扫描 |
| **不支持事务** | 无事务安全 |
| **不支持主键** | 无唯一约束 |
| **适合数据交换** | 便于与其他系统交换数据 |

### 8.3 使用示例

```sql
-- 创建 CSV 表
CREATE TABLE product_export (
    id INT NOT NULL,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    stock INT
) ENGINE = CSV;

-- 查询表结构
SELECT * FROM product_export;

-- 对应的 CSV 文件 (product_export.CSV):
-- "id","name","price","stock"
-- 1,"iPhone 15",799.00,100
-- 2,"MacBook Pro",1999.00,50
```

### 8.4 CSV 引擎的使用场景

- ✅ 数据导出/导入
- ✅ 与其他系统的数据交换
- ❌ 在线业务系统
- ❌ 大数据量查询

## 九、Archive 引擎

### 9.1 Archive 引擎概述

Archive 引擎是专门为**归档存储**设计的引擎，具有极高的压缩比，但仅支持 INSERT 和 SELECT 操作。

### 9.2 核心特性

| 特性 | 说明 |
|------|------|
| **高压缩比** | 压缩率可达 70%~90% |
| **仅支持 INSERT 和 SELECT** | 不支持 UPDATE 和 DELETE |
| **不支持索引** | 全表扫描 |
| **不支持事务** | 无事务安全 |
| **适合冷数据归档** | 存储访问频率低的历史数据 |

### 9.3 使用示例

```sql
-- 创建 Archive 表
CREATE TABLE orders_archive (
    id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    total_amount DECIMAL(12,2),
    status TINYINT,
    created_at DATETIME,
    PRIMARY KEY (id)
) ENGINE = ARCHIVE;

-- 插入数据
INSERT INTO orders_archive 
SELECT * FROM orders WHERE created_at < '2023-01-01';

-- 查询归档数据
SELECT COUNT(*) FROM orders_archive;
```

### 9.4 适用场景

- ✅ 历史数据归档
- ✅ 日志归档
- ✅ 审计日志存储
- ❌ 需要频繁更新的数据
- ❌ 需要快速查询的数据

## 十、存储引擎的选择依据

### 10.1 选择决策矩阵

| 需求维度 | 推荐引擎 | 理由 |
|---------|---------|------|
| 需要事务 | **InnoDB** | 唯一完整支持 ACID |
| 高并发读写 | **InnoDB** | 行级锁，MVCC |
| 大量写入 | **InnoDB** | 插入缓冲优化 |
| 读多写少 | MyISAM / InnoDB | 均可，看其他需求 |
| 全文检索 | InnoDB | MySQL 5.6+ 支持全文索引 |
| 历史归档 | Archive | 高压缩比 |
| 数据导出 | CSV | 通用格式 |
| 临时数据 | Memory | 极快速度 |
| 分表场景 | Merge / InnoDB 分区 | Merge 或分区表 |
| 空间数据 | InnoDB | 支持空间索引 |

### 10.2 InnoDB vs MyISAM 详细对比

| 特性 | InnoDB | MyISAM |
|------|--------|--------|
| 事务支持 | ✅ 完整支持 | ❌ 不支持 |
| 行级锁 | ✅ 支持 | ❌ 仅表锁 |
| 外键约束 | ✅ 支持 | ❌ 不支持 |
| MVCC | ✅ 支持 | ❌ 不支持 |
| 聚簇索引 | ✅ 支持 | ❌ 不支持 |
| 崩溃恢复 | ✅ 自动恢复 | ❌ 需要修复 |
| 全文索引 | ✅ MySQL 5.6+ | ✅ 支持 |
| 空间索引 | ✅ 支持 | ✅ 支持 |
| B+ 树索引 | ✅ 支持 | ✅ 支持 |
| Hash 索引 | ✅ 自适应 | ❌ 不支持 |
| 压缩 | ✅ 页压缩 | ✅ 表压缩 |
| 存储空间 | 较大 | 较小 |
| 插入速度 | 较快 | 快 |
| 读取速度 | 快（聚簇索引） | 快 |

### 10.3 选择建议

#### 默认选择 InnoDB

在绝大多数场景下，**InnoDB 是最佳选择**：
- MySQL 5.5+ 的默认引擎
- 功能最完善，社区支持最好
- 性能在各方面都很均衡
- 未来 MySQL 的发展方向

#### 特殊场景考虑

```sql
-- 场景 1：日志表（大量写入，偶尔查询）
CREATE TABLE access_log (
    id BIGINT AUTO_INCREMENT,
    log_time DATETIME,
    user_id BIGINT,
    action VARCHAR(50),
    INDEX idx_time (log_time)
) ENGINE = InnoDB;  -- 仍然推荐 InnoDB（支持高并发写入）

-- 场景 2：配置表（读多写少，数据量小）
CREATE TABLE sys_config (
    config_key VARCHAR(50) PRIMARY KEY,
    config_value VARCHAR(500),
    description VARCHAR(200)
) ENGINE = InnoDB;  -- InnoDB 足够用

-- 场景 3：归档表（数据量大，极少查询）
CREATE TABLE orders_archive (...) ENGINE = ARCHIVE;

-- 场景 4：临时计算表
CREATE TEMPORARY TABLE temp_calc (...) ENGINE = Memory;
```

## 十一、查看与修改存储引擎的语法

### 11.1 查看引擎

```sql
-- 查看所有引擎
SHOW ENGINES;

-- 查看表状态
SHOW TABLE STATUS LIKE 'users'\G

  AND TABLE_NAME = 'users';
```

### 11.2 修改引擎

```sql
-- 修改单个表的引擎
ALTER TABLE users ENGINE = InnoDB;

-- 注意：修改引擎会重建表，大数据量时耗时很长
-- 建议在低峰期执行

-- 批量修改
-- 可以使用存储过程生成 ALTER 语句
```

### 11.3 默认引擎

```sql
-- 查看默认引擎
SELECT @@default_storage_engine;

-- 修改默认引擎
SET GLOBAL default_storage_engine = InnoDB;

-- 新建表时不指定引擎，将使用默认引擎

CREATE TABLE test (id INT);                   -- 使用默认引擎
```

### 11.4 迁移引擎注意事项

```sql
-- 从 MyISAM 迁移到 InnoDB
-- 1. 备份数据
mysqldump -u root -p database_name > backup.sql

-- 2. 修改引擎
ALTER TABLE table_name ENGINE = InnoDB;

-- 3. 验证数据完整性
SELECT COUNT(*) FROM table_name;

-- 4. 注意事项：
--    - 外键约束可能需要调整
--    - 全文索引语法可能不同
--    - 空间索引存储结构不同
```

## 十三、存储引擎插件机制

### 13.1 插件化架构

MySQL 采用插件化架构设计，存储引擎以**插件**形式加载。这种设计使得：

- 可以在运行时加载/卸载存储引擎
- 第三方可以开发自定义存储引擎
- 不同引擎可以独立演进

### 13.2 插件管理

```sql
-- 查看已安装的插件
SHOW PLUGINS;

-- 安装引擎插件
INSTALL SONAME 'example_engine';

-- 卸载引擎插件
UNINSTALL PLUGIN example_engine;

-- MySQL 8.0 中，InnoDB 是内置插件，无需安装
```

### 13.3 开发自定义引擎

MySQL 提供了存储引擎开发接口（`handlerton` 和 `handler` 类），允许开发者实现自定义的存储引擎。

```cpp
// 存储引擎的核心接口
class handler : public Sql_alloc {
public:
    // 打开/关闭表
    virtual int open(const char *name, int mode, uint test_if_locked);
    virtual int close(void);
    
    // 行操作
    virtual int write_row(uchar *buf);
    virtual int update_row(const uchar *old_row, uchar *new_row);
    virtual int delete_row(const uchar *buf);
    virtual int read_row(uchar *buf);
    
    // 索引操作
    virtual int index_init(uint idx, bool sorted);
    virtual int index_read(uchar *buf, const uchar *key, uint key_len, enum ha_rkey_function find_flag);
    
    // 事务支持
    virtual int external_lock(THD *thd, int lock_type);
    virtual int commit(THD *thd);
    virtual int rollback(THD *thd);
    
    // ... 其他接口
};
```

## 十四、InnoDB 性能优化实践

### 14.1 关键配置参数

```ini
# my.cnf 推荐配置（8GB 内存服务器）

# Buffer Pool 配置
innodb_buffer_pool_size = 6G           # 物理内存的 75%
innodb_buffer_pool_instances = 4        # CPU 核数
innodb_log_buffer_size = 16M            # Redo Log 缓冲区

# Redo Log 配置
innodb_log_file_size = 256M             # Redo Log 文件大小
innodb_log_files_in_group = 2           # 文件数量
innodb_flush_log_at_trx_commit = 1      # 每次提交刷盘

# 页相关配置
innodb_page_size = 16KB                 # 页大小
innodb_lru_scan_depth = 1024            # LRU 扫描深度

# 并发配置
innodb_thread_concurrency = 0            # 0=自动，推荐值
innodb_read_io_threads = 4              # 读 I/O 线程
innodb_write_io_threads = 4             # 写 I/O 线程

# 表空间
innodb_file_per_table = ON              # 独立表空间
innodb_open_files = 4000                # 最大打开文件数
```

### 14.2 监控脚本

```sql
-- InnoDB 状态监控
SHOW ENGINE INNODB STATUS\G

-- 关键指标解读:
-- 1. TRANSACTIONS: 活跃事务数量
-- 2. BUFFER POOL AND MEMORY: Buffer Pool 使用情况
-- 3. I/O THREADS: I/O 线程状态
-- 4. FILE I/O: 文件读写统计
-- 5. INSERT BUFFER: 插入缓冲状态
-- 6. ADAPTIVE HASH INDEX: 自适应哈希索引状态
-- 7. LOG: Redo Log 状态
-- 8. ROW LOCK: 锁等待信息
-- 9. DEADLOCK: 死锁信息
```

### 14.3 常见性能问题排查

| 问题 | 排查方法 | 解决方案 |
|------|---------|---------|
| Buffer Pool 太小 | 检查命中率 < 99% | 增大 innodb_buffer_pool_size |
| Redo Log 太小 | 检查 `log waits` | 增大 innodb_log_file_size |
| 锁等待严重 | `SHOW ENGINE INNODB STATUS` | 优化事务，减少锁范围 |
| 长事务过多 | `INNODB_TRX` 表 | 缩短事务，定期提交 |
| 磁盘 I/O 瓶颈 | `SHOW GLOBAL STATUS` 中的 `Innodb_buffer_pool_reads` | 增加内存，优化查询 |
