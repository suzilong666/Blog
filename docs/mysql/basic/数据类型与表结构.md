# 数据类型与表结构

## 一、整数类型

### 1.1 整数类型概览

MySQL 提供了五种整数类型，它们的区别在于存储范围和所需存储空间不同：

| 类型 | 存储大小 | 最小值（有符号） | 最大值（有符号） | 最小值（无符号） | 最大值（无符号） |
|------|---------|----------------|----------------|----------------|----------------|
| TINYINT | 1 字节 | -128 | 127 | 0 | 255 |
| SMALLINT | 2 字节 | -32768 | 32767 | 0 | 65535 |
| MEDIUMINT | 3 字节 | -8388608 | 8388607 | 0 | 16777215 |
| INT | 4 字节 | -2147483648 | 2147483647 | 0 | 4294967295 |
| BIGINT | 8 字节 | -9223372036854775808 | 9223372036854775807 | 0 | 18446744073709551615 |

### 1.2 有符号与无符号

默认情况下，整数类型是**有符号**的（SIGNED），可以存储正数和负数。使用 `UNSIGNED` 关键字声明无符号类型，只能存储非负数。

```sql
CREATE TABLE products (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    stock INT UNSIGNED NOT NULL DEFAULT 0,
    price DECIMAL(10, 2) UNSIGNED NOT NULL,
    age TINYINT UNSIGNED,
    total_viewers BIGINT UNSIGNED DEFAULT 0
);
```

**底层原理**：
- 有符号整数使用**一个字节的最高位**作为符号位（0 表示正数，1 表示负数）
- 无符号整数的所有位都用于存储数值
- 以 TINYINT 为例：1 字节 = 8 位
  - 有符号：1 位符号 + 7 位数值 → 范围 -128 到 127
  - 无符号：8 位数值 → 范围 0 到 255

### 1.3 选择整数类型的原则

1. **满足需求的最小类型**：存储越小，性能越好（索引更小、内存占用更少）
2. **考虑增长空间**：预估数据增长，避免后期修改类型（ALTER TABLE 成本高）
3. **主键选择**：
   - 推荐使用 `BIGINT UNSIGNED AUTO_INCREMENT` 作为主键
   - INT 主键在分布式系统中可能不够用
4. **避免使用 FLOAT/DOUBLE 存储整数**：使用整数类型精确存储

### 1.4 ZEROFILL 属性

`ZEROFILL` 在显示时用零填充。同时，列会自动变为 `UNSIGNED`。

```sql
CREATE TABLE example (
    id INT ZEROFILL
);

INSERT INTO example VALUES (42);
SELECT id FROM example;  -- 显示为 0000000042
```

**注意**：`ZEROFILL` 在 MySQL 8.0 中已被弃用，不建议使用。建议在应用层处理格式化。

## 二、浮点数类型

### 2.1 FLOAT 与 DOUBLE

MySQL 提供两种浮点类型用于存储近似数值：

| 类型 | 存储大小 | 精度 | 范围（有符号） |
|------|---------|------|--------------|
| FLOAT | 4 字节 | 约 7 位有效数字 | -3.402823466E+38 到 -1.175494351E-38 |
| DOUBLE | 8 字节 | 约 15 位有效数字 | -1.7976931348623157E+308 到 -2.2250738585072014E-308 |

```sql
CREATE TABLE measurements (
    sensor_id INT PRIMARY KEY,
    temperature FLOAT,
    latitude DOUBLE,
    longitude DOUBLE
);
```

### 2.2 DECIMAL 精确小数类型

`DECIMAL` 是 MySQL 中用于存储精确小数的类型，特别适合金融计算。

```sql
DECIMAL(M, D)
```

- `M`：最大位数（精度），范围 1-65，默认 10
- `D`：小数位数，范围 0-30，默认 0
- `M - D`：整数部分位数

```sql
CREATE TABLE products (
    price DECIMAL(10, 2),    -- 最大值 99999999.99
    discount DECIMAL(5, 3),  -- 最大值 99.999
    total_amount DECIMAL(15, 2)  -- 最大值 999999999999.99
);
```

### 2.3 浮点数 vs 精确小数

**浮点数的精度问题**：

```sql
CREATE TABLE test_float (
    f_val FLOAT,
    d_val DOUBLE,
    dec_val DECIMAL(10, 2)
);

INSERT INTO test_float VALUES (0.1, 0.1, 0.1);
INSERT INTO test_float VALUES (0.2, 0.2, 0.2);

SELECT f_val + f_val, d_val + d_val, dec_val + dec_val FROM test_float;
-- FLOAT: 0.20000000298023224  (不精确)
-- DOUBLE: 0.20000000000000001 (不精确)
-- DECIMAL: 0.20 (精确)
```

**底层原理**：
- FLOAT/DOUBLE 使用二进制浮点数表示，遵循 IEEE 754 标准
- 十进制小数 0.1 无法精确表示为二进制，只能近似
- DECIMAL 使用字符串形式存储，每位数字使用二进制编码（BCD 编码的变体），保证精确

### 2.4 选择建议

- **金融数据**：必须使用 `DECIMAL`，如价格、余额、税率
- **科学计算/测量**：使用 `FLOAT` 或 `DOUBLE`，接受微小误差
- **需要精确比较**：使用 `DECIMAL`，FLOAT/DOUBLE 不适合 `=` 比较
- **性能考虑**：`DECIMAL` 的计算比 `FLOAT/DOUBLE` 慢，但在大多数业务场景中差异可忽略

## 三、字符串类型

### 3.1 字符串类型概览

| 类型 | 存储大小 | 最大长度 | 说明 |
|------|---------|---------|------|
| CHAR(M) | M 字节 | 255 字符 | 固定长度字符串 |
| VARCHAR(M) | L + 1~2 字节 | 65535 字节 | 可变长度字符串 |
| TINYTEXT | L + 1 字节 | 255 字节 | 短文本 |
| TEXT | L + 2 字节 | 65535 字节 | 普通文本 |
| MEDIUMTEXT | L + 3 字节 | 16MB | 中等文本 |
| LONGTEXT | L + 4 字节 | 4GB | 长文本 |
| BINARY(M) | M 字节 | 255 字节 | 固定长度二进制 |
| VARBINARY(M) | L + 1~2 字节 | 65535 字节 | 可变长度二进制 |
| TINYBLOB | L + 1 字节 | 255 字节 | 短二进制 |
| BLOB | L + 2 字节 | 65535 字节 | 普通二进制 |
| MEDIUMBLOB | L + 3 字节 | 16MB | 中等二进制 |
| LONGBLOB | L + 4 字节 | 4GB | 长二进制 |

其中 `L` 表示实际数据长度，额外的 1-4 字节用于存储长度信息。

### 3.2 CHAR 固定长度字符串

`CHAR(M)` 存储固定长度的字符串。如果存储的字符串长度小于 M，MySQL 会在右侧填充空格。

```sql
CREATE TABLE users (
    username CHAR(10),
    country_code CHAR(2)
);

INSERT INTO users VALUES ('john', 'US');
SELECT username, LENGTH(username) FROM users;
-- username: 'john      ' (后面有6个空格)
-- LENGTH: 10
```

**CHAR 的使用场景**：
- 长度固定的编码类字段：如 `country_code CHAR(2)`、`currency CHAR(3)`、`postal_code CHAR(6)`
- 短字符串（M < 50）且长度差异不大的场景
- 需要 `[CHAR 列] = [CHAR 列]` 精确比较的场景

**注意**：
- MySQL 8.0 默认使用 `utf8mb4`，一个字符最多占 4 字节
- `CHAR(10)` 最多占用 40 字节（10 字符 × 4 字节/字符）
- 索引长度限制：`utf8mb4` 下索引最大长度为 767 字节，即 `CHAR(191)` 或 `VARCHAR(191)`

### 3.3 VARCHAR 可变长度字符串

`VARCHAR(M)` 存储可变长度的字符串，长度范围为 1 到 M。

```sql
CREATE TABLE users (
    username VARCHAR(50),
    email VARCHAR(100),
    bio VARCHAR(500)
);

INSERT INTO users VALUES ('john', 'john@example.com', 'A short bio');
```

**VARCHAR 的存储机制**：
- 存储时实际占用：`实际字符串长度 + 长度前缀（1-2 字节）`
- 如果字符串长度 < 256，使用 1 字节存储长度
- 如果字符串长度 >= 256，使用 2 字节存储长度
- 不填充空格，按实际长度存储

**VARCHAR 的使用场景**：
- 长度不固定的字符串：姓名、地址、描述等
- 大多数字符串字段的首选类型
- 需要合理预估最大长度，避免频繁修改

**VARCHAR 的 M 参数**：
- M 表示最大字符数，不是字节数
- `VARCHAR(50)` 最多存储 50 个字符
- 实际占用的字节数取决于字符集：
  - `latin1`：1 字节/字符 → 最多 50 字节
  - `utf8`：最多 3 字节/字符 → 最多 150 字节
  - `utf8mb4`：最多 4 字节/字符 → 最多 200 字节

### 3.4 VARCHAR 与 CHAR 的选择

| 对比项 | CHAR | VARCHAR |
|--------|------|---------|
| 长度 | 固定 | 可变 |
| 存储效率 | 浪费空间 | 节省空间 |
| 查询性能 | 略快（对齐访问） | 略慢（需要读取长度前缀） |
| 尾部空格 | 自动填充 | 不填充 |
| 最大长度 | 255 字符 | 65535 字节（约 16383 utf8mb4 字符） |

**选择建议**：
- 如果长度固定且较短（如邮编、国家代码），使用 CHAR
- 如果长度不固定，使用 VARCHAR
- 不要为 VARCHAR 设置过大的 M 值（如 VARCHAR(10000)），会影响索引和排序性能

### 3.5 TEXT 与 BLOB

TEXT 和 BLOB 类型用于存储大量数据，与 VARCHAR/VARBINARY 的主要区别：

| 特性 | VARCHAR/VARBINARY | TEXT/BLOB |
|------|-------------------|-----------|
| 最大长度 | 65535 字节 | 65535 ~ 4GB |
| 能否指定长度 | 必须 | 不能 |
| 默认值 | 可以 | 不能（MySQL 8.0.13+ 支持） |
| 排序规则 | 继承表默认 | 继承表默认 |
| 索引支持 | 可以 | 可以（前缀索引） |
| 存储位置 | 行内或溢出页 | 通常存储在溢出页 |

**TEXT 的使用场景**：
- 文章内容、产品描述、评论等长文本
- 存储超过 VARCHAR 合理范围的文本数据

**BLOB 的使用场景**：
- 存储二进制数据：图片、音频、视频、文档等
- 注意：小文件（< 1MB）可以直接存 BLOB，大文件建议存文件系统+路径引用

### 3.6 二进制类型选择

```sql
-- 存储图片缩略图（小文件）
CREATE TABLE products (
    id INT PRIMARY KEY,
    thumbnail BLOB  -- 最大 64KB
);

-- 存储图片（中等文件）
CREATE TABLE products (
    id INT PRIMARY KEY,
    image MEDIUMBLOB  -- 最大 16MB
);

-- 存储大文件
CREATE TABLE documents (
    id INT PRIMARY KEY,
    file_data LONGBLOB  -- 最大 4GB
);
```

### 3.7 字符串比较与排序

**比较规则（Collation）**：

```sql
-- 查看支持的排序规则
SHOW COLLATION;

-- 常用排序规则
utf8mb4_general_ci       -- 通用，大小写不敏感，重音不敏感
utf8mb4_unicode_ci       -- Unicode 标准，更精确的排序
utf8mb4_bin              -- 二进制比较，区分大小写
utf8mb4_0900_ai_ci       -- MySQL 8.0 新默认，更精确
```

**ci 与 bin 的区别**：
- `ci`（Case Insensitive）：大小写不敏感，`'A' = 'a'` 为 TRUE
- `bin`（Binary）：大小写敏感，`'A' = 'a'` 为 FALSE

```sql
SELECT 'Apple' = 'apple' COLLATE utf8mb4_general_ci;  -- 1 (TRUE)
SELECT 'Apple' = 'apple' COLLATE utf8mb4_bin;          -- 0 (FALSE)
```

## 四、日期时间类型

### 4.1 日期时间类型概览

| 类型 | 存储大小 | 格式 | 范围 | 精度 |
|------|---------|------|------|------|
| DATE | 3 字节 | 'YYYY-MM-DD' | '1000-01-01' 到 '9999-12-31' | 天 |
| TIME | 3 字节 | 'HH:MM:SS' | '-838:59:59' 到 '838:59:59' | 秒 |
| DATETIME | 5 字节 | 'YYYY-MM-DD HH:MM:SS' | '1000-01-01 00:00:00' 到 '9999-12-31 23:59:59' | 秒 |
| TIMESTAMP | 4 字节 | 'YYYY-MM-DD HH:MM:SS' | '1970-01-01 00:00:01' UTC 到 '2038-01-19 03:14:07' UTC | 秒 |
| YEAR | 1 字节 | 'YYYY' | '1901' 到 '2155' | 年 |

### 4.2 DATE 类型

`DATE` 用于存储日期，不包含时间部分。

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    birth_date DATE,
    join_date DATE NOT NULL
);

INSERT INTO users VALUES (1, '1990-05-15', '2023-01-01');
SELECT birth_date FROM users;  -- '1990-05-15'
```

### 4.3 TIME 类型

`TIME` 用于存储时间或时间间隔。范围比 24 小时更大，可以表示经过的时间。

```sql
CREATE TABLE schedules (
    id INT PRIMARY KEY,
    start_time TIME,
    duration TIME,
    end_time TIME
);

INSERT INTO schedules VALUES (1, '09:00:00', '01:30:00', '10:30:00');
INSERT INTO schedules VALUES (2, '08:00:00', '25:00:00', '09:00:00');  -- 25小时
```

### 4.4 DATETIME 类型

`DATETIME` 存储日期和时间，不考虑时区。

```sql
CREATE TABLE orders (
    id INT PRIMARY KEY,
    order_time DATETIME NOT NULL,
    delivery_time DATETIME
);

INSERT INTO orders VALUES (1, '2024-03-15 14:30:00', '2024-03-16 10:00:00');
```

**DATETIME 的特点**：
- 存储时不转换时区
- 适合需要精确时间戳且无时区转换需求的场景
- 存储开销比 TIMESTAMP 大（5 字节 vs 4 字节）

### 4.5 TIMESTAMP 类型

`TIMESTAMP` 存储日期和时间，会进行时区转换。

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP
);
```

**TIMESTAMP 的特点**：
- 存储时转换为 UTC 时间
- 读取时转换为当前时区
- 范围有限（1970-2038），存在 2038 问题
- 自动更新功能：`DEFAULT CURRENT_TIMESTAMP` 和 `ON UPDATE CURRENT_TIMESTAMP`

**DATETIME vs TIMESTAMP**：

| 对比项 | DATETIME | TIMESTAMP |
|--------|----------|-----------|
| 存储大小 | 5 字节 | 4 字节 |
| 时区处理 | 不转换 | 存储为 UTC，读取时转换 |
| 范围 | 1000-9999 | 1970-2038 |
| 自动更新 | 需手动设置 | 支持自动更新 |
| 适用场景 | 时区无关的时间 | 需要时区转换的时间 |

### 4.6 YEAR 类型

`YEAR` 用于存储年份。

```sql
CREATE TABLE products (
    id INT PRIMARY KEY,
    production_year YEAR,
    model_year YEAR(4)  -- 4位年份，默认4位
);

INSERT INTO products VALUES (1, 2024, 2024);
```

### 4.7 小数秒精度

所有日期时间类型都支持小数秒，精度最高微秒（6 位）。

```sql
CREATE TABLE events (
    id INT PRIMARY KEY,
    created_at DATETIME(3),      -- 毫秒精度
    updated_at TIMESTAMP(6)      -- 微秒精度
);

INSERT INTO events VALUES (1, '2024-03-15 14:30:00.123', '2024-03-15 14:30:00.123456');
```

### 4.8 日期时间选择建议

1. **优先使用 DATETIME**：范围更广，不受时区影响，MySQL 8.0 默认推荐
2. **需要自动时间戳**：使用 TIMESTAMP 或 DATETIME 配合 `DEFAULT CURRENT_TIMESTAMP`
3. **只存日期**：使用 DATE
4. **只存时间**：使用 TIME
5. **年份**：使用 YEAR，或直接使用 INT

## 五、JSON 类型

### 5.1 JSON 类型简介

MySQL 5.7.8+ 原生支持 JSON 类型，提供 JSON 数据的验证、存储和查询功能。

```sql
CREATE TABLE products (
    id INT PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    attributes JSON,
    metadata JSON
);

INSERT INTO products VALUES
(1, 'Laptop',
 '{"brand": "Dell", "model": "XPS 15", "specs": {"cpu": "i7", "ram": 16, "storage": "512GB"}, "colors": ["silver", "black"]}',
 '{"created_by": "admin", "tags": ["electronics", "computer"]}'
);
```

### 5.2 JSON 函数

**JSON 提取函数**：

```sql
-- 提取 JSON 字段
SELECT id, JSON_EXTRACT(attributes, '$.brand') AS brand
FROM products WHERE id = 1;
-- 'Dell'

-- 使用 -> 简写
SELECT id, attributes->'$.brand' AS brand FROM products WHERE id = 1;

-- 提取并去除引号
SELECT id, attributes->>'$.brand' AS brand FROM products WHERE id = 1;
-- Dell (不带引号)

-- 提取嵌套字段
SELECT id, attributes->'$.specs.cpu' AS cpu FROM products WHERE id = 1;
-- 'i7'

-- 提取数组元素
SELECT id, attributes->'$.colors[0]' AS color FROM products WHERE id = 1;
-- 'silver'
```

**JSON 构造函数**：

```sql
-- 构造 JSON 对象
SELECT JSON_OBJECT('name', 'John', 'age', 30);
-- {"name": "John", "age": 30}

-- 构造 JSON 数组
SELECT JSON_ARRAY(1, 2, 3, 4);
-- [1, 2, 3, 4]

-- 聚合生成 JSON 数组
SELECT JSON_ARRAYAGG(name) FROM users;

-- 聚合生成 JSON 对象
SELECT JSON_OBJECTAGG(id, name) FROM users;
```

**JSON 修改函数**：

```sql
-- 设置 JSON 字段
UPDATE products
SET attributes = JSON_SET(attributes, '$.brand', 'HP', '$.weight', '1.8kg')
WHERE id = 1;

-- 移除 JSON 字段
UPDATE products
SET attributes = JSON_REMOVE(attributes, '$.specs.storage')
WHERE id = 1;

-- 替换 JSON 字段值
UPDATE products
SET attributes = JSON_REPLACE(attributes, '$.brand', 'Lenovo')
WHERE id = 1;
```

**JSON 搜索函数**：

```sql
-- 检查 JSON 是否包含路径
SELECT JSON_CONTAINS_PATH(attributes, 'ONE', '$.brand') FROM products;

-- 检查 JSON 是否包含特定值
SELECT JSON_CONTAINS(attributes, '"Dell"', '$.brand') FROM products;

-- 搜索 JSON（MySQL 8.0+）
SELECT * FROM products WHERE JSON_SEARCH(attributes, 'one', 'Dell', NULL, '$.brand') IS NOT NULL;
```

### 5.3 JSON 类型的优势

1. **原生验证**：MySQL 自动验证 JSON 格式有效性，无效 JSON 会报错
2. **高效存储**：内部使用二进制格式存储，比文本 JSON 更紧凑
3. **函数支持**：提供丰富的 JSON 操作函数
4. **索引支持**：可以对 JSON 字段生成虚拟列并建立索引

### 5.4 JSON 类型的使用场景

- 存储灵活的扩展属性（如产品规格、用户配置）
- 存储 API 返回的 JSON 数据
- 多值属性存储（比 ENUM/SET 更灵活）

**注意**：
- JSON 列无法直接建立索引，需要通过虚拟列 + 索引实现
- 对于结构固定的数据，仍建议使用规范化的表结构
- JSON 查询性能通常低于普通列查询

```sql
-- 通过虚拟列索引优化 JSON 查询
ALTER TABLE products
    ADD COLUMN brand VARCHAR(50) GENERATED ALWAYS AS (attributes->>'$.brand') STORED,
    ADD INDEX idx_brand (brand);

-- 查询时可以使用索引
SELECT * FROM products WHERE brand = 'Dell';
```

## 六、ENUM 和 SET 类型

### 6.1 ENUM 类型

`ENUM` 是枚举类型，只能存储预定义值中的一个。

```sql
CREATE TABLE orders (
    id INT PRIMARY KEY,
    status ENUM('pending', 'processing', 'shipped', 'delivered', 'cancelled')
        DEFAULT 'pending',
    priority ENUM('low', 'medium', 'high', 'urgent') DEFAULT 'medium'
);
```

**ENUM 的存储原理**：
- ENUM 在内部存储为整数索引
- 1 字节：最多 255 个值
- 2 字节：256-65535 个值
- 索引从 1 开始，0 保留给空字符串（无效值）
- 存储效率高，查询速度快

```sql
INSERT INTO orders VALUES (1, 'pending', 'high');
SELECT status = 'pending' FROM orders;  -- 1 (TRUE)

-- 可以用整数查询
SELECT * FROM orders WHERE status = 1;  -- 查询 status = 'pending' 的记录
```

**ENUM 的优缺点**：
- **优点**：存储紧凑、查询高效、约束性强
- **缺点**：修改枚举值需要 ALTER TABLE、不适合频繁变化的选项

### 6.2 SET 类型

`SET` 是集合类型，可以存储预定义值中的多个组合。

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    username VARCHAR(50),
    permissions SET('read', 'write', 'delete', 'admin') DEFAULT 'read'
);

INSERT INTO users VALUES (1, 'john', 'read,write');
INSERT INTO users VALUES (2, 'admin_user', 'read,write,delete,admin');
```

**SET 的存储原理**：
- SET 在内部存储为位图（bitmask）
- 1 字节：最多 8 个值
- 2 字节：9-16 个值
- 3 字节：17-24 个值
- 4 字节：25-32 个值

每个值对应一个二进制位：
- 'read' = 1 (0001)
- 'write' = 2 (0010)
- 'delete' = 4 (0100)
- 'admin' = 8 (1000)

```sql
-- 'read,write' 存储为 3 (0011)
-- 'read,write,delete,admin' 存储为 15 (1111)
```

**SET 的查询**：

```sql
-- 查询具有 'write' 权限的用户
SELECT * FROM users WHERE permissions LIKE '%write%';
-- 或
SELECT * FROM users WHERE FIND_IN_SET('write', permissions);
-- 或使用位运算
SELECT * FROM users WHERE permissions & 2;
```

### 6.3 ENUM vs SET vs JSON

| 对比项 | ENUM | SET | JSON |
|--------|------|-----|------|
| 存储值数量 | 1 个 | 多个（组合） | 任意 JSON |
| 存储大小 | 1-2 字节 | 1-8 字节 | 变长 |
| 查询性能 | 快 | 快 | 较慢 |
| 灵活性 | 低 | 中 | 高 |
| 修改成本 | ALTER TABLE | ALTER TABLE | 无需修改表结构 |

## 七、NULL 值处理

### 7.1 NULL 的概念

NULL 不是零值或空字符串，而是"未知"或"不适用"的标记。

**NULL 的特性**：
- NULL 不参与算术运算，任何值与 NULL 运算结果为 NULL
- NULL 不参与比较，不能用 `=` 或 `!=` 判断
- NULL 在 `ORDER BY` 中默认排在最前（最小值）
- NULL 在索引中被视为最小值

### 7.2 NULL 的判断

```sql
-- 正确的 NULL 判断方式
SELECT * FROM users WHERE phone IS NULL;
SELECT * FROM users WHERE phone IS NOT NULL;

-- 错误的 NULL 判断方式（结果永远为 NULL）
SELECT * FROM users WHERE phone = NULL;
SELECT * FROM users WHERE phone != NULL;
```

### 7.3 NULL 相关函数

```sql
-- ISNULL() 函数
SELECT ISNULL(NULL);   -- 1
SELECT ISNULL('hello'); -- 0

-- IFNULL() 函数：如果为 NULL 返回默认值
SELECT IFNULL(phone, '未填写') FROM users;

-- COALESCE() 函数：返回第一个非 NULL 值
SELECT COALESCE(home_phone, work_phone, mobile_phone, '无电话') FROM users;

-- NULLIF() 函数：如果两个值相等返回 NULL
SELECT NULLIF(5, 5);   -- NULL
SELECT NULLIF(5, 3);   -- 5
```

### 7.4 NULL 与聚合函数

```sql
-- NULL 被聚合函数忽略
SELECT COUNT(*) FROM users;           -- 统计所有行
SELECT COUNT(phone) FROM users;       -- 只统计 phone 非 NULL 的行
SELECT SUM(salary) FROM users;        -- 忽略 salary 为 NULL 的行
SELECT AVG(phone) FROM users;        -- 忽略 phone 为 NULL 的行
SELECT MAX(salary) FROM users;        -- 忽略 salary 为 NULL 的行
SELECT MIN(salary) FROM users;        -- 忽略 salary 为 NULL 的行

-- 只有当所有值都为 NULL 时，聚合函数返回 NULL
SELECT AVG(NULL) FROM users;          -- NULL
```

### 7.5 NULL 的最佳实践

1. **尽量避免使用 NULL**：使用 `NOT NULL DEFAULT ''` 或 `NOT NULL DEFAULT 0` 替代
2. **主键列不允许 NULL**：主键必须能唯一标识每行
3. **外键列建议 NOT NULL**：保证参照完整性
4. **需要区分"不适用"和"零值"时使用 NULL**：如 `discount` 为 0 表示无折扣，NULL 表示不参与折扣活动

## 八、字符集与排序规则

### 8.1 字符集基础

**字符集（Character Set）**：定义了字符与二进制编码之间的映射关系。

**排序规则（Collation）**：定义了字符的比较和排序规则。

```sql
-- 查看所有字符集
SHOW CHARACTER SET;

-- 查看所有排序规则
SHOW COLLATION;
```

### 8.2 MySQL 常用字符集

| 字符集 | 最大字节数/字符 | 说明 |
|--------|---------------|------|
| latin1 | 1 | 西欧字符集，不支持中文 |
| gbk | 2 | 中文简体，Windows 默认 |
| big5 | 2 | 中文繁体 |
| utf8 | 3 | UTF-8 编码，不支持 emoji |
| utf8mb4 | 4 | UTF-8 完整编码，支持 emoji 和所有 Unicode 字符 |

**utf8 vs utf8mb4**：
- MySQL 的 `utf8` 实际是 `utf8mb3`，最多 3 字节/字符，不支持 4 字节的 emoji 和生僻字
- `utf8mb4` 是真正的 UTF-8，最多 4 字节/字符
- 强烈建议使用 `utf8mb4`，避免 emoji 存储问题

### 8.3 字符集的四级层次

MySQL 的字符集设置分为四个层次，从大到小依次覆盖：

```
服务器级 → 数据库级 → 表级 → 列级
```

```sql
-- 服务器级
SHOW VARIABLES LIKE 'character_set_server';
SHOW VARIABLES LIKE 'collation_server';

-- 数据库级
SHOW CREATE DATABASE shop;

-- 表级
SHOW CREATE TABLE users;

-- 列级
SHOW FULL COLUMNS FROM users;
```

### 8.4 字符集设置

```ini
# my.cnf / my.ini
[mysqld]
character-set-server = utf8mb4
collation-server = utf8mb4_unicode_ci

[client]
default-character-set = utf8mb4

[mysql]
default-character-set = utf8mb4
```

```sql
-- 动态修改当前会话
SET NAMES utf8mb4;
-- 等价于
SET character_set_client = utf8mb4;
SET character_set_connection = utf8mb4;
SET character_set_results = utf8mb4;
```

### 8.5 字符集对存储的影响

```sql
-- CHAR/VARCHAR 的存储大小依赖字符集
CREATE TABLE test (
    c_char CHAR(10),      -- utf8mb4: 最多 40 字节
    v_char VARCHAR(10)    -- utf8mb4: 最多 40 字节 + 长度前缀
);

-- 索引长度限制
-- InnoDB 单个索引键最大长度：767 字节
-- utf8mb4 下：767 / 4 = 191 字符
-- 因此 VARCHAR(200) 在建索引时会报错
-- 解决方案：使用前缀索引
ALTER TABLE users ADD INDEX idx_name (name(100));
```

### 8.6 排序规则的影响

```sql
-- ci（Case Insensitive）排序规则：大小写不敏感
SELECT 'a' = 'A' COLLATE utf8mb4_general_ci;  -- 1 (TRUE)

-- bin 排序规则：区分大小写
SELECT 'a' = 'A' COLLATE utf8mb4_bin;  -- 0 (FALSE)

-- 不同排序规则的排序差异
SELECT * FROM users ORDER BY name COLLATE utf8mb4_bin;  -- A < B < a < b
SELECT * FROM users ORDER BY name COLLATE utf8mb4_general_ci;  -- a < A < b < B
```

## 九、列约束

### 9.1 NOT NULL 约束

`NOT NULL` 约束确保列不接受 NULL 值。

```sql
CREATE TABLE users (
    id INT NOT NULL AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    remark VARCHAR(500) NULL,  -- 可以为 NULL
    PRIMARY KEY (id)
);
```

**NOT NULL 的底层原理**：
- InnoDB 在每行记录中为每列预留 1 个比特用于存储 NULL 信息
- 即使列声明为 `NOT NULL`，该比特仍然存在，只是必须为 0
- `NOT NULL` 约束在插入/更新时检查，如果违反则报错

### 9.2 DEFAULT 约束

`DEFAULT` 约束为列指定默认值。

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    status ENUM('active', 'inactive') NOT NULL DEFAULT 'active',
    login_count INT NOT NULL DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**DEFAULT 的使用注意**：
- `DEFAULT CURRENT_TIMESTAMP`：自动设置创建时间
- `ON UPDATE CURRENT_TIMESTAMP`：自动更新修改时间
- `DEFAULT` 值必须与列的数据类型兼容
- TEXT/BLOB 列在 MySQL 8.0.13+ 支持 DEFAULT

### 9.3 UNIQUE 约束

`UNIQUE` 约束确保列或列组合的值在表中唯一。

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL,
    -- 联合唯一约束
    UNIQUE KEY uk_email (email)
);
```

**UNIQUE 与 PRIMARY KEY 的区别**：

| 特性 | PRIMARY KEY | UNIQUE |
|------|-------------|--------|
| 能否为 NULL | 不能 | 可以（但通常不建议） |
| 数量 | 每表一个 | 每表多个 |
| 索引类型 | 聚簇索引（InnoDB） | 二级索引 |
| 自动创建 | 是 | 是 |

### 9.4 PRIMARY KEY 约束

`PRIMARY KEY` 约束定义主键，用于唯一标识每行记录。

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    -- 或
    PRIMARY KEY (id)
);

-- 复合主键
CREATE TABLE user_roles (
    user_id INT NOT NULL,
    role_id INT NOT NULL,
    PRIMARY KEY (user_id, role_id)
);
```

**主键设计原则**：
1. **选择短数据类型**：主键越小，索引效率越高
2. **避免业务主键**：使用无意义的自增 ID 作为主键
3. **InnoDB 主键必须**：如果不指定主键，MySQL 会选择唯一非空索引或生成 6 字节的隐藏主键
4. **不要频繁修改**：主键一旦创建不应修改
5. **推荐 INT/BIGINT UNSIGNED AUTO_INCREMENT**：性能和空间的最佳平衡

### 9.5 AUTO_INCREMENT 约束

`AUTO_INCREMENT` 用于自动生成唯一递增的整数值。

```sql
CREATE TABLE users (
    id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY
);
```

**AUTO_INCREMENT 的特点**：
- 每张表只能有一个自增列
- 自增列必须是主键或唯一索引的一部分
- 自增列必须是整数类型（TINYINT 到 BIGINT）
- 默认起始值为 1，步长为 1

```sql
-- 修改起始值
ALTER TABLE users AUTO_INCREMENT = 100;

-- 查询当前自增值
SHOW TABLE STATUS LIKE 'users';

-- 设置全局自增参数
SET GLOBAL auto_increment_increment = 1;  -- 步长
SET GLOBAL auto_increment_offset = 1;     -- 起始偏移
```

**AUTO_INCREMENT 的原理**：
- InnoDB 通过 `auto-increment counter` 机制管理自增值
- 自增计数器存储在内存中，表元数据中记录持久化值
- 当插入数据时，InnoDB 锁定计数器，分配唯一值，然后释放锁
- 事务回滚不会回收自增值（可能导致跳号）

## 十、表的物理存储结构

### 10.1 InnoDB 行存储结构

InnoDB 存储引擎以页（Page）为单位组织数据，默认页大小为 16KB。

```
┌──────────────────────────────────────────────┐
│              InnoDB 页结构 (16KB)              │
├──────────────────────────────────────────────┤
│  Page Header (38 字节)                        │
│  - 页号、上一页/下一页指针、事务信息等          │
├──────────────────────────────────────────────┤
│  Infimum + Supremum (26 字节)                  │
│  - 页内记录的最小/最大虚拟记录                  │
├──────────────────────────────────────────────┤
│  User Records (数据区)                         │
│  - 实际存储的行记录                            │
├──────────────────────────────────────────────┤
│  Free Space (空闲区)                           │
├──────────────────────────────────────────────┤
│  Page Directory (目录区)                       │
│  - 槽位指针，指向数据区的记录                  │
└──────────────────────────────────────────────┘
```

### 10.2 InnoDB 行记录格式

InnoDB 默认使用 Dynamic 行格式（MySQL 5.7+）。

```
┌──────────────────────────────────────────────┐
│              InnoDB 行记录结构                  │
├──────────────────────────────────────────────┤
│  Extra Info (5 字节)                           │
│  - 记录头、标志位                              │
├──────────────────────────────────────────────┤
│  Transaction ID (6 字节)                      │
│  - 最后修改该行的事务 ID                       │
├──────────────────────────────────────────────┤
│  Roll Pointer (7 字节)                        │
│  - 指向 Undo Log 中的历史版本                  │
├──────────────────────────────────────────────┤
│  Column Data (列数据区)                        │
│  - 实际的列值                                  │
│  - 变长列（VARCHAR、TEXT）存储实际长度          │
│  - 变长列的溢出页指针（超过阈值时）            │
├──────────────────────────────────────────────┤
│  NULL Bitmap (NULL 位图)                       │
│  - 标记哪些列的值为 NULL                       │
└──────────────────────────────────────────────┘
```

**Dynamic 行格式的特点**：
- 变长列（VARCHAR、VARBINARY、TEXT、BLOB）的前 768 字节存储在数据页中
- 超过 768 字节的部分存储在溢出页（Off-Page Storage）
- 相比 Compact 格式，减少了数据页的空间占用

### 10.3 聚簇索引与非聚簇索引

**聚簇索引（Clustered Index）**：
- InnoDB 的主键索引即是聚簇索引
- 数据按主键的物理顺序存储
- 叶子节点直接存储完整的行数据
- 每张表只能有一个聚簇索引

```
聚簇索引结构：

          [主键值, 指针]
         /              \
    [主键值, 指针]    [主键值, 指针]
    /        \        /        \
  [行数据]  [行数据] [行数据]  [行数据]
```

**二级索引（Secondary Index）**：
- 非主键索引都是二级索引
- 叶子节点存储：索引列值 + 主键值
- 查找数据需要两步：先通过二级索引找到主键，再通过主键在聚簇索引中找到完整行

```
二级索引结构：

          [索引值, 指针]
         /              \
    [索引值, 指针]    [索引值, 指针]
    /        \        /        \
  [索引值, 主键] [索引值, 主键] [索引值, 主键] [索引值, 主键]
```

**回表查询**：通过二级索引获取主键值，再回聚簇索引获取完整行的过程称为"回表"。

### 10.4 文件结构

InnoDB `file-per-table` 模式下，每张表对应两个文件：

```
/var/lib/mysql/database_name/
├── table_name.frm     -- 表结构定义（列、索引、约束等元数据）
├── table_name.ibd     -- 表数据（聚簇索引 + 所有二级索引 + 数据）
└── ...
```

**.frm 文件**：
- 存储表的结构定义
- 包含列名、类型、约束、索引定义等
- 即使使用共享表空间，.frm 文件也是独立的

**.ibd 文件**：
- 存储表的所有数据和索引
- 采用 B+ 树结构组织
- 包含聚簇索引（主键）和所有二级索引
- 新文件初始大小为 96KB

### 10.5 表空间管理

**系统表空间（System Tablespace）**：
- 由 `ibdata1` 等文件组成
- 存储系统信息（数据字典、双写缓冲区、撤销日志等）
- 也可以存储表数据（取决于 `innodb_file_per_table` 设置）

**独立表空间（Per-Table Tablespace）**：
- 每张表使用独立的 `.ibd` 文件
- 优点：单表膨胀不影响其他表、可以单独备份恢复
- 缺点：打开表时需要打开文件描述符，大量表可能超出操作系统限制

**Undo 表空间**：
- 存储撤销日志
- MySQL 5.7+ 使用独立的 undo 表空间文件
- `undo_001`、`undo_002` 等文件
