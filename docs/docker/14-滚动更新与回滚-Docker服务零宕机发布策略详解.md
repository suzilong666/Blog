# 14-滚动更新与回滚-Docker服务零宕机发布策略详解

## 引言

传统发布方式往往带来停机风险。容器化部署后，滚动更新和回滚策略让你在不中断服务的情况下发布新版本，并在出现问题时快速恢复。

本文把发布策略拆成“滚动更新”“回滚”和“结合监控”的三部分，帮助你构建零宕机发布流程。

## 1. 什么是滚动更新？

滚动更新的核心思路是：逐个或分批替换实例，而不是一次性替换全部。

优势包括：

- 保持部分实例持续可用；
- 降低发布风险；
- 便于快速回滚。

## 2. Docker 中的滚动更新

在 Docker Swarm 中，可以使用：

```bash
docker service update --image myapp:2.0 --update-parallelism 1 --update-delay 10s myapp
```

参数说明：

- `--update-parallelism`：每次并行更新的实例数；
- `--update-delay`：每批更新之间的等待时间。

这让你可以在保持可用性的同时渐进替换。

## 3. 回滚策略

回滚的前提是：

- 镜像使用明确版本标签；
- 发布过程可控；
- 监控及时发现异常。

Swarm 回滚命令：

```bash
docker service update --rollback myapp
```

这会把服务恢复到上一个稳定版本。

## 4. 结合监控和健康检查

真正安全的发布，不仅靠版本标签，还要靠健康检查和实时监控。

- `HEALTHCHECK` 保证容器实例只有在真正可用时才被认为正常；
- 监控告警帮助你在新版本出现异常时及时中止发布；
- 结合日志和指标判断是否执行回滚。

## 5. 实践建议

### 5.1 小批量发布

一次更新少量实例，观察是否有异常，再继续下一批。这样即使出现问题，影响范围也小。

### 5.2 版本标签策略

使用语义化版本或时间戳标签，避免 `latest` 导致回滚和追踪困难。

### 5.3 发布前验证

在测试或预发布环境先执行完整更新流程，验证健康检查、服务发现和回滚流程。

### 5.4 预留故障恢复路径

确保你有回滚命令、旧版本镜像和配置快照，避免在发布时才慌忙查找。

## 6. 常见误区

- 认为“只要更新了镜像就能自动平滑发布”。实际上还需要健康检查和发布策略；
- 认为“回滚只是再启动旧版本”。回滚前要先判断问题原因，避免重复失败；
- 认为“少量实例更新就可以忽略监控”。恰恰相反，监控是判断是否继续发布的关键。

## 小结

滚动更新和回滚不是可选项，而是容器化发布的基础能力。通过明确版本、分批发布、结合健康检查和监控，你能把发布从“高风险操作”转成“可控流程”。这才是真正的零宕机发布策略。
