# 18-容器漂移与注册中心-Consul-Nacos适配

## 引言

容器环境下实例不断变动，IP 地址和地址列表会随时改变。微服务若依赖固定地址，就会变得脆弱难维护。

注册中心为动态服务发现提供了解决方案，本篇文章用 Consul 和 Nacos 说明为什么它们是容器化微服务的必要组件。

## 1. 容器漂移为何是问题

在容器环境中，实例会因为：

- 自动扩容/缩容；
- 容器重启；
- 节点下线；
- 部署更新。

这些动作会导致服务地址不断改变。如果应用仍依赖静态 IP，就会出现连接失败、配置不一致和服务不可用。

## 2. 注册中心的价值

注册中心负责：

- 服务注册；
- 服务发现；
- 健康状态管理；
- 动态路由。

服务启动时注册自己，调用方通过注册中心查询可用实例，从而避免硬编码地址。

## 3. Consul 与 Nacos 选型

### Consul

- 轻量灵活；
- 支持服务发现、配置中心、健康检查；
- 适合多语言、多平台场景。

### Nacos

- 与 Spring Cloud 生态结合紧密；
- 提供服务发现、配置管理；
- 适合 Java 微服务。

## 4. 实际适配方式

### Consul 场景

1. 服务启动时注册自身地址；
2. 依赖服务通过 Consul 查询可用实例；
3. 利用健康检查剔除不可用实例；
4. 使用 Consul DNS 或 HTTP API 访问服务。

### Nacos 场景

1. 服务注册到 Nacos；
2. 客户端从 Nacos 拉取服务列表；
3. 使用 Nacos 提供的命名空间、分组、健康检查；
4. 与 Spring Cloud Gateway、Spring Cloud Alibaba 集成。

## 5. 与 Docker/编排平台的结合

容器编排平台本身也提供服务发现功能。注册中心的优势在于：

- 独立于编排平台；
- 支持更多协议与客户端；
- 提供配置管理和多语言适配。

在 Docker Swarm、Kubernetes、甚至纯 Docker 环境中，Consul/Nacos 都可以作为通用服务发现层。

## 6. 工程化建议

- 尽量让服务通过名称而非 IP 调用；
- 把健康检查结果同步到注册中心；
- 使用注册中心做动态配置；
- 避免直接依赖宿主机 DNS 或静态配置。

## 7. 常见误区

- 认为编排平台自带服务发现就够。很多场景仍然需要更稳定的注册中心；
- 认为只用一个 IP 列表就能解决。地址列表会随容器漂移变化；
- 认为注册中心只适合大规模系统。即便中小规模系统，也能显著提升动态服务的稳定性。

## 小结

容器漂移让服务地址变得动态，注册中心是应对这种动态性的基础设施。Consul 适合轻量多语言场景，Nacos 适合 Java/Spring Cloud 场景。把服务发现与健康检查结合起来，才能让容器化微服务真正稳定运行。
