# 20-从传统物理机到Docker化改造的8个避坑指南

把传统应用迁移到 Docker，不是简单地“把程序装进容器里”就算完成了。很多团队在迁移过程中，都会被依赖关系、网络设计、数据持久化、配置管理和发布流程这些问题拖住。真正的难点，往往不在于技术能不能实现，而在于迁移能不能被有序、可控地完成。

第一个常见误区，是一上来就想把所有服务都容器化。对于一些历史较长、依赖复杂、基础设施耦合严重的系统，这种做法往往会把迁移过程变成一场“大而全”的重构。更稳妥的方式，是先从最小可独立运行的服务开始切分，再逐步扩展。

第二个误区，是把隐式依赖当成理所当然。很多传统应用依赖宿主机上的工具、库、配置文件或运维脚本，这些在容器化后往往会被忽略。迁移前必须先梳理清楚依赖边界，并尽量把它们显式化，避免后续出现莫名其妙的启动失败。

第三个误区，是把数据和容器绑定得过深。容器拥有短暂生命周期，数据库文件、日志、上传内容和配置文件如果直接写在容器里，迁移和重建时就会非常麻烦。更好的做法是把持久化数据交给数据卷或外部存储。

第四个误区，是没有提前规划网络和端口。服务之间的通信方式、对外暴露端口、域名映射及服务发现机制，都应该在迁移前明确下来，否则上线过程会非常痛苦。

第五个误区，是把配置写死在镜像里。镜像应该尽量保持通用，运行时配置应该通过环境变量、挂载文件或配置中心动态注入。只有这样，应用才更适合跨环境部署。

最后，容器化改造最应该做的，不是一次性“上规模”，而是先通过小范围试点验证流程、监控和回滚机制，再逐步扩大到生产环境。Docker 化改造真正的挑战，正是从“能不能运行”转向“能不能持续、稳定、可控地运行”。
