# Redis 底层数据结构实现：从 SDS 到 QuickList 的深度剖析

## 一、Redis 数据结构概述

### 1.1 Redis 为什么要自研数据结构

Redis 是一款高性能的内存数据库，其核心竞争力在于**极致的执行效率**。为了实现这一目标，Redis 没有直接使用 C 语言标准库或现有的数据结构库，而是**自行实现了一套高效的数据结构**。

这些自定义数据结构的设计目标包括：

| 设计目标 | 说明 |
|---------|------|
| **高效的内存使用** | 动态调整内存大小，避免浪费 |
| **快速的查询速度** | 实现 O(1) 或 O(log n) 的操作 |
| **灵活的编码方式** | 根据数据规模自动选择最优编码 |
| **二进制安全** | 支持存储任意二进制数据 |
| **兼容性设计** | 在效率和兼容性之间取得平衡 |

### 1.2 Redis 数据结构总览

Redis 主要使用了以下六种底层数据结构：

```
┌─────────────────────────────────────────────────────────────┐
│                    Redis 底层数据结构                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │   SDS 字符串  │  │   哈希表     │  │   跳表      │         │
│  │  (Simple    │  │  (Hash     │  │  (Skip     │         │
│  │   Dynamic   │  │   Table)   │  │   List)    │         │
│  │   String)   │  │            │  │            │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
│                                                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │  压缩列表    │  │  整数集合    │  │  快速列表    │         │
│  │  (ZipList)  │  │  (IntSet)  │  │  (QuickList)│         │

```

### 1.3 数据结构与 Redis 类型的关系

Redis 的五种基本类型（String、Hash、List、Set、Sorted Set）在底层会根据不同情况选择合适的数据结构来实现：

| Redis 类型 | 可能的底层实现 | 选择依据 |
|-----------|--------------|---------|
| **String** | SDS | 直接使用 |
| **Hash** | ZipList / Hash Table | 字段数量和值的大小 |
| **List** | QuickList (3.2+) | 混合 ZipList 和 LinkedList |
| **Set** | IntSet / Hash Table | 是否为整数集合 |
| **Sorted Set** | ZipList / Skip List | 元素数量 |
| **Stream** | ListPack (5.0+) | 专门为流设计 |

## 二、SDS（Simple Dynamic String）

### 2.1 为什么不使用 C 字符串

C 语言中的字符串是以 `\0` 结尾的字符数组，这种设计存在以下问题：

| 问题 | C 字符串 | SDS 解决方案 |
|------|---------|-------------|
| **获取长度** | 需要遍历字符串，O(n) | 直接存储长度，O(1) |
| **缓冲区溢出** | 不确定空间大小，易溢出 | 动态分配空间，自动扩展 |
| **二进制安全** | 遇到 `\0` 截断 | 以显式长度为准，支持二进制 |
| **重复分配** | 每次修改都需重新分配 | 空间预分配，减少 realloc |

**C 字符串的问题示例：**

```c
// C 字符串获取长度需要遍历
char* str = "Hello, Redis!";
size_t len = strlen(str);  // O(n) 遍历字符串

// 二进制数据无法存储
char* binary_data = "data\0binary";  // 存储到 \0 处就结束了
printf("%s", binary_data);  // 只输出 "data"

// 缓冲区溢出风险
char buffer[10];
strcpy(buffer, "This string is too long!");  // 缓冲区溢出！
```

### 2.2 SDS 结构定义

SDS 的底层实现位于 Redis 源码的 `sds.h` 文件中，其结构定义如下：

```c
typedef struct sdshdr {
    int len;      // 已使用的字符串长度
    int free;     // 剩余可用空间长度
    char buf[];   // 实际存储数据的字符数组
} sdshdr;
```

#### SDS 结构示意图

```
┌─────────────┬─────────────┬──────────────────────────────────────┐
│    len       │    free      │              buf[]                    │
│  (已用长度)  │  (剩余空间)  │                                        │
├─────────────┼─────────────┼──────────────────────────────────────┤
│     13      │     16      │ [H][e][l][l][o][,][ ][R][e][d][i][s] │
│             │             │ [!][\0]   ...   ...   ...   ...      │
└─────────────┴─────────────┴──────────────────────────────────────┘
 ↑                              ↑                                    │
 └── len 指向有效数据长度        └── buf 实际存储内容，以 \0 结尾       │
```

**SDS 与 C 字符串的兼容性：**

SDS 的 `buf` 字段仍然以 `\0` 结尾，这使得 SDS 可以直接使用 C 字符串的函数（如 `printf`），实现了**向后兼容**。

### 2.3 SDS 的核心优势

#### 常数时间获取字符串长度

```c
// SDS 获取长度，O(1)
sds mystr = sdsnew("Hello, Redis!");
size_t len = sdslen(mystr);  // 直接读取 len 字段

// C 字符串获取长度，O(n)
char* str = "Hello, Redis!";
size_t len = strlen(str);  // 遍历整个字符串
```

#### 避免缓冲区溢出

```c
// SDS 自动扩展空间
sds s = sdsnew("Hello");
// 内部: len=5, free=?, buf=["Hello\0"]

s = sdscat(s, ", Redis!");  // 自动分配足够的空间
// 内部: len=13, free=? 
// 不会发生缓冲区溢出
```

#### 二进制安全

```c
// SDS 可以存储任意二进制数据
char binary_data[] = {'d', 'a', 't', 'a', '\0', 'b', 'i', 'n', 'a', 'r', 'y'};
sds s = sdsnewlen(binary_data, 11);  // 显式指定长度

// SDS 内部以 len 为准，\0 只是结束符，不是分隔符
sdslen(s);  // 返回 11，而不是 4
```

#### 兼容 C 字符串

```c
// SDS 可以直接作为 C 字符串使用
sds s = sdsnew("Hello, Redis!");
printf("%s", s);  // 直接传递，不需要转换

// 获取 C 字符串指针
const char* c_str = sdscstr(s);  // 但不需要这样做，SDS 本身就是 char* 类型
```

### 2.4 SDS 空间预分配策略

为了减少内存重分配的次数，SDS 采用了**空间预分配**策略：

#### 扩展时的分配规则

当 SDS 需要扩展时，会根据以下规则预分配额外空间：

```c
// sdsMakeRoomFor 函数的预分配逻辑
sds sdsMakeRoomFor(sds s, size_t addlen) {
    // ... 
    size_t newlen = sdslen(s) + addlen;
    
    if (newlen < SDS_MAX_PREALLOC) {
        // 如果新长度小于 SDS_MAX_PREALLOC (1024*1024 = 1MB)
        // 分配 2 倍的新长度
        newlen *= 2;
    } else {
        // 如果新长度超过 1MB
        // 分配新长度 + 1MB
        newlen += SDS_MAX_PREALLOC;
    }
    // ...
}
```

#### 预分配示意图

```
扩展前:
  ┌─────┬─────┬──────────────────────┐
  │ len │free │         buf[]         │
  ├─────┼─────┼──────────────────────┤
  │  10 │   5 │ [data][...][\0]      │
  └─────┴─────┴──────────────────────┘

需要追加 20 字节:
  新长度 = 10 + 20 = 30
  30 < SDS_MAX_PREALLOC (1MB)
  预分配 = 30 * 2 = 60

扩展后:
  ┌─────┬─────┬──────────────────────────────────────────────────┐
  │ len │free │                    buf[]                           │
  ├─────┼─────┼──────────────────────────────────────────────────┤
  │  30 │  30 │ [新data][...][\0]  ...  ...  ...  ...  ...  ...  │
  └─────┴─────┴──────────────────────────────────────────────────┘
```

### 2.5 SDS 操作的时间复杂度

| 操作 | 时间复杂度 | 说明 |
|------|-----------|------|
| `sdslen()` | O(1) | 直接读取 len 字段 |
| `sdsnew()` | O(n) | 复制字符串内容 |
| `sdscat()` | O(n) | 追加并可能扩展空间 |
| `sdscpy()` | O(n) | 复制并可能扩展空间 |
| `sdstrim()` | O(n) | 遍历去除指定字符 |
| `sdsrange()` | O(n) | 截取子字符串 |

### 2.6 SDS 对 Redis 性能的贡献

SDS 的设计对 Redis 的高性能至关重要：

1. **O(1) 的长度获取**：`STRLEN` 命令直接读取 `len` 字段，无需遍历
2. **减少内存重分配**：预分配策略使 `APPEND` 操作的平均时间复杂度为 O(1)
3. **二进制安全**：支持存储图片、序列化数据等二进制内容
4. **避免缓冲区溢出**：减少安全漏洞的风险

## 三、哈希表（Hash Table）

### 3.1 哈希表在 Redis 中的应用

哈希表是 Redis 最重要的数据结构之一，被广泛用于：

- **数据库核心结构**：Redis 的每个数据库都是一个哈希表
- **Hash 类型的底层实现**：当 Hash 对象字段较多时使用哈希表
- **字典实现**：Redis 的 `dict` 结构就是一个哈希表

### 3.2 Redis 字典（dict）结构

Redis 使用 `dict` 结构作为其核心哈希表实现，定义在 `dict.h` 中：

```c
typedef struct dict {
    dictType *type;      // 字典类型，包含一组操作函数
    void *privdata;      // 私有数据，传给类型特定的函数
    dictht table[2];     // 两个哈希表，用于渐进式 rehash
    int rehashidx;       // rehash 进度标记，-1 表示未在 rehash
    int iterators;       // 正在使用的迭代器数量
} dict;
```

#### 哈希表结构（dictht）

```c
typedef struct dictht {
    dictEntry **table;   // 哈希表数组
    unsigned long size;  // 哈希表大小（必须是 2 的幂）
    unsigned long sizemask;  // size - 1，用于快速取模
    unsigned long used;  // 已使用的节点数量
} dictht;
```

#### 哈希表节点（dictEntry）

```c
typedef struct dictEntry {
    void *key;           // 键
    union {
        void *val;       // 指针值
        uint64_t u64;   // 无符号 64 位整数
        int64_t s64;    // 有符号 64 位整数
        double d;       // 浮点数
    } v;
    struct dictEntry *next;  // 冲突链表的下一个节点
} dictEntry;
```

### 3.4 哈希算法

Redis 使用 MurmurHash2 算法作为其哈希函数，该算法由 Austin Appleby 发明，具有以下特点：

- **高性能**：比 MD5、SHA 等加密算法快得多
- **低碰撞率**：雪崩效应好，碰撞概率低
- **非加密**：不需要安全保证，追求速度

```c
// Redis 中使用的哈希函数
unsigned int dictGenHashFunction(const unsigned char *buf, int len) {
    // 使用 MurmurHash2 算法
    // ...
}

// 计算键在哈希表中的位置
// 利用 sizemask 进行快速取模（位运算比取模快）
index = hash(key) & sizemask;  // 等同于 hash(key) % size
```

### 3.5 哈希冲突解决：链地址法

Redis 使用**链地址法**解决哈希冲突。当多个键映射到同一位置时，通过链表串联：

```
哈希表:
  ┌──────────┬─────────────────────────────────────┐
  │ 位置 index│ 链表                                 │
  ├──────────┼─────────────────────────────────────┤
  │    0     │ NULL → 无冲突                         │
  ├──────────┼─────────────────────────────────────┤
  │    1     │ ┌─────────────┐                      │
  │          │ │ entry("A")  │                      │
  │          │ │ next: ──────┼──►┌─────────────┐    │
  │          │ └─────────────┘    │ entry("B")  │    │
  │          │                    │ next: ──────┼──►┌─────────────┐
  │          │                    └─────────────┘    │ entry("C")  │
  │          │                                       │ next: NULL  │
  │          │                                       └─────────────┘
  ├──────────┼─────────────────────────────────────┤
  │    2     │ ┌─────────────┐                      │
  │          │ │ entry("D")  │                      │
  │          │ │ next: NULL  │                      │
  │          │ └─────────────┘                      │
  └──────────┴─────────────────────────────────────┘

查询过程:
  1. 计算 hash(key) & sizemask 得到位置
  2. 遍历该位置的链表
  3. 逐个比较 key 是否匹配
  4. 找到则返回，否则继续或返回 NULL
```

### 3.6 渐进式 Rehash 机制

#### 为什么需要渐进式 Rehash

当哈希表的负载因子（`used / size`）过高或过低时，需要进行扩容或收缩。但如果一次性完成 rehash，对于大型哈希表会造成**阻塞问题**。

Redis 采用**渐进式 rehash** 来解决这个问题，将 rehash 分散到多次操作中完成。

#### 渐进式 Rehash 过程

```
Rehash 开始前:
  table[0]: size=4, used=4, rehashidx=-1
  ┌────┬────┬────┬────┐
  │ A  │ B  │ C  │ D  │
  └────┴────┴────┴────┘

第一步: 创建 table[1]
  table[0]: size=4, used=4
  ┌────┬────┬────┬────┐
  │ A  │ B  │ C  │ D  │
  └────┴────┴────┴────┘
  
  table[1]: size=8, used=0
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │NULL│NULL│NULL│NULL│NULL│NULL│NULL│NULL│
  └────┴────┴────┴────┴────┴────┴────┴────┘

渐进式 Rehash（每次 rehash 一个索引位置）:
  rehashidx=0: 迁移 table[0][0] → table[1]
  rehashidx=1: 迁移 table[0][1] → table[1]
  rehashidx=2: 迁移 table[0][2] → table[1]
  rehashidx=3: 迁移 table[0][3] → table[1]
  
  每次 rehash 完成后，rehashidx++
  
  当 rehashidx == table[0].size 时，rehash 完成
  释放 table[0]，table[1] 成为新的 table[0]
```

#### Rehash 期间的读写操作

在渐进式 rehash 期间，Redis 的读写操作会同时操作两个哈希表：

```c
// 查找操作：先查 table[0]，没找到再查 table[1]
dictEntry *dictFind(dict *d, const void *key) {
    // 先在 table[0] 中查找
    entry = dictFindInHashTable(d->table[0], key);
    if (entry) return entry;
    
    // 如果在 rehash，还要查 table[1]
    if (d->rehashidx != -1) {
        entry = dictFindInHashTable(d->table[1], key);
        if (entry) return entry;
    }
    return NULL;
}

// 插入操作：直接插入 table[1]
// 删除操作：同时从两个表中删除
```

#### 触发 Rehash 的条件

**扩容条件：**
- 当负载因子 `used / size >= 1` 时，且未在执行 BGSAVE 或 BGWRITEAOF
- 当负载因子 `used / size >= 5` 时，无论是否在执行子进程任务

**收缩条件：**
- 当负载因子 `used / size < 0.1` 时

```c
// 扩容时机判断
int dictRehash(dict *d, int n) {
    // 当负载因子过大时触发扩容
    if (d->used >= d->table[0].size && 
        !(d->iterator & DICT_HT_REHASH_AVOID)) {
        // 执行 rehash
    }
}
```

### 3.7 哈希表的时间复杂度

| 操作 | 平均时间复杂度 | 说明 |
|------|--------------|------|
| 查找 | O(1) | 无冲突或冲突很短 |
| 插入 | O(1) | 平均情况 |
| 删除 | O(1) | 平均情况 |
| 遍历 | O(n) | 需要遍历所有节点 |

## 四、跳表（Skip List）

### 4.1 跳表的引入

跳表是一种基于**有序链表**的数据结构，通过在链表上建立**多级索引**，实现了类似二分查找的效率。

Redis 使用跳表作为**有序集合（Sorted Set）**的底层实现之一，相比红黑树，跳表的实现更简单，范围查询更高效。

### 4.2 跳表的结构

#### 跳表节点结构

```c
typedef struct zskiplistNode {
    sds ele;                        // 成员对象
    double score;                   // 分值，用于排序
    struct zskiplistNode *backward; // 后退指针
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // 前进指针
        unsigned long span;            // 跨度
    } level[];                          // 层数组
} zskiplistNode;
```

#### 跳表整体结构

```
typedef struct zskiplist {
    struct zskiplistNode *header, *tail;  // 头尾节点
    unsigned long length;                  // 跳表长度
    int level;                             // 最大层数
} zskiplist;
```

```
Span 示例 (Level 1):
  header ──► node A:  span = 1 (跨越了 A)
  node A ──► node C:  span = 2 (跨越了 B, C)
  node C ──► tail:    span = 2 (跨越了 D, tail)
```

### 4.4 跳表的查询过程

跳表的查询过程类似于**二分查找**，从最高层开始，逐层向下：

```
查询 score=25 的节点:

Level 3:
  header ──────────────────────────────────────────► tail
  |                                                ^
  | 25 < tail.score, 继续

Level 2:
  header ─────────────► node C ──────────────────► tail
  |                     |                         ^
  | 25 > C.score(30)? 不，25 < 30，在 C 前面

Level 1:
  header ───► node A ──► node C ──────────────────► tail
  |            |          |                       ^
  | 25 > A.score(10)? 是
  | 25 > C.score(30)? 不，25 < 30，在 C 前面

Level 0 (找到精确位置):
  header ──► node A ──► node B ──► node C ──► node D ──► tail
                         |
                         | 25 > B.score(20)? 是
                         | 25 < C.score(30)? 是 → 找到了！
                         ↓
                      node B (score=20)
                      node C (score=30) → 目标位置在 B 和 C 之间
```

### 4.5 跳表的插入过程

#### 插入位置的确定

插入节点前需要先找到合适的位置，同时记录每一层的前驱节点：

```c
// 插入前的查找过程
zskiplistNode *update[ZSKIPLIST_MAXLEVEL];  // 记录每一层的前驱
unsigned long rank[ZSKIPLIST_MAXLEVEL];     // 记录排名

// 从最高层开始向下查找
for (int i = z->level - 1; i >= 0; i--) {
    // 记录当前排名
    rank[i] = (i == z->level - 1) ? 0 : rank[i + 1];
    
    // 在当前层向前遍历，直到找到合适位置
    while (x->level[i].forward && 
           (x->level[i].forward->score < score ||
            (x->level[i].forward->score == score && 
             compare(x->level[i].forward->ele, ele) <= 0))) {
        rank[i] += x->level[i].span;
        x = x->level[i].forward;
    }
    
    // 记录前驱节点
    update[i] = x;
}
```

#### 随机层数生成

跳表通过**随机算法**决定新节点的层数，层数越高的节点越稀疏：

```c
// 随机生成层数
int zslRandomLevel(void) {
    int level = 1;
    // 有 1/4 概率继续增加层数
    while ((random() & 0xFFFF) < (ZSKIPLIST_P * 0xFFFF))  // ZSKIPLIST_P = 0.25
        level += 1;
    return (level < ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;
}
```

**层数分布概率：**
- 1 层：100%（所有节点）
- 2 层：25%（1/4 概率）
- 3 层：6.25%（1/16 概率）
- 4 层：1.56%（1/64 概率）
- ...
- 32 层：几乎不可能

#### 插入操作示意图

```
插入 score=25, ele="e" 的节点:

1. 查找插入位置，获取 update 数组:
  update[0] = node B (Level 0 的前驱)
  update[1] = node A (Level 1 的前驱)
  update[2] = header (Level 2 的前驱)
  update[3] = header (Level 3 的前驱)

2. 随机生成层数: level = 2

3. 创建新节点:
  new_node: score=25, ele="e", level[0], level[1]

4. 更新各层的指针:
  Level 0: new_node→forward = update[0]→forward
           update[0]→forward = new_node
           
  Level 1: new_node→level[1].forward = update[1]→level[1].forward
           update[1]→level[1].forward = new_node

5. 更新 span 和 backward 指针
```

### 4.6 跳表的删除过程

```
删除 score=25 的节点:

1. 查找待删除节点和其前驱:
  update[0] = node B
  update[1] = node A
  ...

2. 逐层删除:
  for i = 0 to level-1:
    update[i]->level[i].forward = node->level[i].forward

3. 更新 span 值

4. 更新 backward 指针

5. 如果最高层变空，减少跳表的 level
```

### 4.7 跳表的时间复杂度

| 操作 | 平均时间复杂度 | 最坏情况 |
|------|--------------|---------|
| 查找 | O(log n) | O(n) |
| 插入 | O(log n) | O(n) |
| 删除 | O(log n) | O(n) |
| 范围查询 | O(log n + m) | O(n) |
| 按排名查询 | O(log n) | O(n) |

### 4.8 跳表与红黑树的对比

| 特性 | 跳表 | 红黑树 |
|------|------|--------|
| **实现复杂度** | 简单，代码量少 | 复杂，代码量大 |
| **查找效率** | O(log n) | O(log n) |
| **插入效率** | O(log n)，平均更优 | O(log n)，常数因子大 |
| **删除效率** | O(log n)，平均更优 | O(log n)，常数因子大 |
| **范围查询** | 高效，基于 span 计算排名 | 需要中序遍历 |
| **内存占用** | 略高（多层指针） | 较低（固定指针） |
| **并发友好** | 更容易实现无锁并发 | 困难 |
| **旋转操作** | 不需要 | 需要复杂的旋转和变色 |

**Redis 选择跳表的原因：**
1. **实现简单**：跳表的代码量约为红黑树的 1/3
2. **范围查询高效**：利用 span 字段可以快速计算排名
3. **插入删除高效**：跳表的常数因子比红黑树小
4. **易于扩展**：更容易支持并发操作

## 五、压缩列表（ZipList）

### 5.1 压缩列表概述

压缩列表（ZipList）是 Redis 为**节约内存**而设计的一种特殊编码结构，用于存储小数据量的 List、Hash 和 Sorted Set。

### 5.2 压缩列表的设计目标

| 目标 | 说明 |
|------|------|
| **极致的内存节省** | 连续内存，无指针开销 |
| **快速的随机访问** | 通过偏移量快速定位 |
| **支持多种编码** | 整数和字符串的灵活编码 |
| **兼容性** | 可快速转换为其他结构 |

### 5.3 压缩列表结构

```c
typedef struct zlentry {
    unsigned int prevrawlen;  // 前一个节点的长度（用于反向遍历）
    unsigned int len;         // 当前节点数据长度
    unsigned char encoding;   // 编码方式
    unsigned char* data;      // 实际数据
} zlentry;
```

#### 压缩列表整体结构

```
压缩列表整体布局:

┌──────────┬──────────┬──────────┬──────────┬──────────┬─────┐
│ zlbytes  │ zltail   │ zllen    │ entry 1  │ entry 2  │ ... │
│ (4字节)  │ (4字节)  │ (2字节)  │          │          │     │
└──────────┴──────────┴──────────┴──────────┴──────────┴─────┘
                                                                   ┌─────┐
                                                                   │zlend│
                                                                   │(1字节)│
                                                                   └─────┘

字段说明:
- zlbytes: 压缩列表占用的总字节数
- zltail: 最后一个节点的起始偏移（用于快速访问尾部）
- zllen: 压缩列表包含的节点数量
- entry: 各个数据节点
- zlend: 结束标记，值为 0xFF

entry 内部结构:
  ┌─────────────┬──────────┬──────────────┬──────────────────────┐
  │ prevrawlen  │ len      │ encoding     │ data                 │
  │ (1-5字节)   │ (1-5字节) │ (1字节)      │ (变长)               │
  └─────────────┴──────────┴──────────────┴──────────────────────┘
  
  prevrawlen: 前一个节点的总长度（用于反向遍历）
  len: 当前节点数据部分的长度
  encoding: 数据编码方式
  data: 实际存储的数据
```

### 5.4 编码方式详解

压缩列表支持两种编码方式：**整数编码**和**字符串编码**。

#### 整数编码

为不同范围的整数选择合适的字节数：

| 编码类型 | 字节数 | 取值范围 |
|---------|--------|---------|
| INT8 (11000000) | 1 | -128 ~ 127 |
| INT16 (11010000) | 2 | -32768 ~ 32767 |
| INT24 (11110000) | 3 | -8388608 ~ 8388607 |
| INT32 (11020000) | 4 | -2^31 ~ 2^31-1 |
| INT64 (11030000) | 8 | -2^63 ~ 2^63-1 |
| ENCINT (11111111) | 变长 | 0~12 用 1 字节，13~255 用 2 字节 |

#### 字符串编码

```
字符串编码 (0xxxxxx):
  最高位为 0，低 7 位表示字符串长度
  最大支持 127 字节的字符串

长字符串编码 (10xxxxxx):
  最高位为 10，后 6 位 + 后续字节表示长度
  支持更长的字符串
```

### 5.5 压缩列表操作

#### 查找操作

```
查找过程:
  1. 从第一个 entry 开始，逐个遍历
  2. 解码 entry 的数据
  3. 比较是否匹配
  4. 如果不匹配，根据 prevrawlen 跳转到下一个 entry
  5. 直到找到目标或到达 zlend
```

#### 插入操作

```
插入新 entry:
  1. 确定插入位置
  2. 计算新 entry 的 prevrawlen、len 等字段
  3. 为新 entry 分配空间
  4. 更新相关 entry 的 prevrawlen（连锁更新！）
  5. 更新 zlbytes、zltail、zllen
```

#### 删除操作

```
删除 entry:
  1. 定位待删除的 entry
  2. 移除该 entry
  3. 更新后续 entry 的 prevrawlen
  4. 更新 zlbytes、zllen
```

### 5.6 连锁更新问题

压缩列表插入或删除时可能触发**连锁更新**（Cascade Update）。

#### 连锁更新原因

当 entry 的 `prevrawlen` 字段需要变化时（从 1 字节变为 5 字节），会导致后续所有 entry 的起始位置变化，进而需要更新它们的 `prevrawlen`。

```
连锁更新示例:

初始状态 (所有 prevrawlen 都是 1 字节):
  ┌─────┬─────┬─────┬─────┐
  │  A  │  B  │  C  │  D  │
  └─────┴─────┴─────┴─────┘
  prevrawlen: 1 字节

在 A 前插入新节点 X，X 的长度超过 253 字节:
  prevrawlen_B 需要从 1 字节变为 5 字节
  → B 的总长度增加 4 字节
  → C 的 prevrawlen 需要更新
  → D 的 prevrawlen 需要更新
  → 连锁更新开始！
```

#### 连锁更新的时间复杂度

连锁更新的最坏时间复杂度为 **O(n²)**，但实际中：
- 只有当 entry 长度跨越特定阈值时才会触发
- 大多数情况下，连锁更新在几步内就会终止
- 平均时间复杂度仍然是 O(n)

### 5.7 压缩列表升级为双向链表

当压缩列表不再节省内存时（连锁更新过于频繁或元素过大），Redis 会将其升级为**双向链表**。

#### 升级条件

对于 List 类型：
- 元素数量超过 128 个
- 任意元素长度超过 64 字节

```c
// 升级判断
if (list->length > 128 || 
    element->len > 64) {
    // 升级为双向链表
    list->encoding = OBJ_ENCODING_LINKEDLIST;
    // 遍历压缩列表，逐个转换为链表节点
    listConvertZiplistToList(list);
}
```

#### 升级过程

```
压缩列表:
  ┌─────┬─────┬─────┬─────┐
  │  A  │  B  │  C  │  D  │
  └─────┴─────┴─────┴─────┘

升级为双向链表:
  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │  node A  │◄►│  node B  │◄►│  node C  │◄►│  node D  │
  └──────────┘  └──────────┘  └──────────┘  └──────────┘
```

### 5.8 压缩列表的优缺点

| 优点 | 缺点 |
|------|------|
| 内存紧凑，无指针开销 | 插入和删除可能触发连锁更新 |
| 连续内存，对缓存友好 | 查找需要线性遍历 |
| 支持多种编码方式 | 不适合大量或大尺寸元素 |
| 可以快速升级 | 反向遍历依赖 prevrawlen |

## 六、整数集合（IntSet）

### 6.1 整数集合概述

整数集合（IntSet）是 Redis 为**存储整数集合**而设计的专用数据结构，当 Set 类型只包含整数且元素数量较少时，Redis 会使用 IntSet 而非哈希表。

### 6.2 整数集合结构

```c
typedef struct intset {
    uint32_t encoding;  // 编码方式
    uint32_t length;    // 元素数量
    int8_t contents[];  // 存储元素的数组（按升序排列）
} intset;
```

#### 整数集合结构示意图

```
intset 结构:
  ┌────────────┬──────────┬──────────────────────────────────────────┐
  │ encoding   │ length   │            contents[]                     │
  ├────────────┼──────────┼──────────────────────────────────────────┤
  │ INT16      │    5     │ [10][20][30][40][50]                       │
  │ (2字节)    │          │  每个元素占 2 字节                          │
  └────────────┴──────────┴──────────────────────────────────────────┘

不同编码方式下的存储:
  INT16: 每个元素 2 字节，范围 -32768 ~ 32767
  INT32: 每个元素 4 字节，范围 -2^31 ~ 2^31-1
  INT64: 每个元素 8 字节，范围 -2^63 ~ 2^63-1
```

### 6.3 编码方式与升级机制

#### 编码方式

整数集合支持三种编码方式，按存储范围从小到大排列：

| 编码类型 | 每个元素字节数 | 取值范围 |
|---------|--------------|---------|
| `INTSET_ENC_INT16` | 2 | -32768 ~ 32767 |
| `INTSET_ENC_INT32` | 4 | -2^31 ~ 2^31-1 |
| `INTSET_ENC_INT64` | 8 | -2^63 ~ 2^63-1 |

#### 升级机制

当插入的整数超出当前编码的范围时，会触发**升级操作**，转换为更大的编码：

```
升级过程 (INT16 → INT32):

升级前:
  encoding: INT16 (2 字节/元素)
  contents: [10][20][30]  (每个占 2 字节)

插入 value = 40000 (超出 INT16 范围):
  1. 判断需要升级到 INT32
  2. 重新分配内存: 元素数 * 4 字节
  3. 将现有元素转换为 INT32 格式
  4. 插入新元素

升级后:
  encoding: INT32 (4 字节/元素)
  contents: [10][20][30][40000]  (每个占 4 字节)
```

#### 升级的时间复杂度

升级操作需要重新分配内存并复制所有元素，时间复杂度为 **O(n)**。但由于升级是单向的（不会降级），且触发条件特殊，实际性能影响较小。

### 6.4 整数集合的查找操作

整数集合内部元素按**升序排列**，可以使用**二分查找**提高效率：

```c
// 二分查找
static uint8_t intsetSearch(intset *is, int64_t value, uint32_t *pos) {
    int min = 0, max = intlen(is) - 1, mid;
    
    while (min <= max) {
        mid = (min + max) / 2;
        int64_t cur = intsetGet(is, mid);
        
        if (value > cur) min = mid + 1;
        else if (value < cur) max = mid - 1;
        else return 1;  // 找到
    }
    
    *pos = min;  // 插入位置
    return 0;     // 未找到
}
```

#### 查找示意图

```
二分查找 value=30:

  contents: [10][20][30][40][50]
  
  min=0, max=4
  mid=2: contents[2]=30 == value → 找到！

查找 value=25:
  
  min=0, max=4
  mid=2: contents[2]=30 > 25 → max=1
  mid=0: contents[0]=10 < 25 → min=1
  mid=1: contents[1]=20 < 25 → min=2
  min > max → 未找到，pos=2
```

### 6.5 整数集合的插入操作

```c
// 插入元素
intset *intsetAdd(intset *is, int64_t value, uint8_t *success) {
    uint32_t pos;
    uint8_t enc = intsetEncodingOfValue(value);
    
    // 检查是否需要升级编码
    if (enc > intsetEncoding(is)) {
        is = intsetUpgradeAndAdd(is, value);
    } else {
        // 查找插入位置
        if (intsetSearch(is, value, &pos)) {
            *success = 0;  // 已存在
        } else {
            // 扩展数组空间
            is = intsetResize(is, intlen(is) + 1);
            // 移动后续元素，腾出位置
            intsetMoveTail(is, pos, pos + 1);
            // 插入新元素
            intsetSet(is, pos, value);
            is->length++;
            *success = 1;
        }
    }
    return is;
}
```

### 6.6 整数集合的时间复杂度

| 操作 | 时间复杂度 | 说明 |
|------|-----------|------|
| 查找 | O(log n) | 二分查找 |
| 插入 | O(n) | 移动元素，可能触发升级 |
| 删除 | O(n) | 移动元素 |
| 遍历 | O(n) | 线性遍历 |

### 6.7 整数集合与哈希表的转换

当整数集合不再高效时，会转换为哈希表：

#### 转换条件

- 元素数量超过 512 个
- 插入了非整数值

```c
// 升级判断
if (intset->length > 512 || 
    !isAllIntegers(new_value)) {
    // 转换为哈希表
    set->encoding = OBJ_ENCODING_HT;
    // 遍历 intset，逐个添加到哈希表
    setConvertIntsetToHashTable(set);
}
```

### 6.8 整数集合的优势

| 优势 | 说明 |
|------|------|
| **内存高效** | 紧凑存储，无指针开销 |
| **查找快速** | 二分查找 O(log n) |
| **有序性** | 元素天然有序，支持范围操作 |
| **无重复** | 插入时自动去重 |

## 七、快速列表（QuickList）

### 7.1 QuickList 的引入

Redis 3.2 引入了 **QuickList** 作为 List 类型的新底层实现，它结合了**压缩列表（ZipList）的空间效率**和**双向链表（LinkedList）的灵活性**。

### 7.2 为什么需要 QuickList

#### 原有方案的问题

| 方案 | 优点 | 缺点 |
|------|------|------|
| **ZipList** | 内存紧凑 | 大元素性能差，连锁更新 |
| **LinkedList** | 灵活高效 | 内存开销大，指针多 |

#### QuickList 的解决方案

QuickList 将链表按段切分，每段使用 ZipList 存储，兼顾内存效率和操作灵活性。

### 7.3 QuickList 结构

```c
typedef struct quicklist {
    quicklistNode *head;    // 头节点
    quicklistNode *tail;    // 尾节点
    unsigned long count;    // 元素总数
    unsigned long len;      // 段（节点）数量
    int fill : QL_FILL_BITS;        // 填充因子
    unsigned int compress : QL_COMP_BITS;  // 压缩深度
    unsigned int bookmarks_small : 1;  // 小书签标记
} quicklist;
```

#### QuickList 节点结构

```c
typedef struct quicklistNode {
    struct quicklistNode *prev;  // 前一个节点
    struct quicklistNode *next;  // 后一个节点
    unsigned char *zl;           // 压缩列表（ZipList）
    unsigned int sz;             // 压缩列表占用的字节数
    unsigned int count : 16;     // 该段的元素数量
    unsigned int encoding : 2;   // 编码方式：RAW=1, LZF=2
    unsigned int container : 2;  // 容器类型：ZLIST=1
    unsigned int recompress : 1;  // 是否需要重新压缩
    unsigned int attempted_compress : 1;  // 已尝试压缩
    unsigned int extra : 10;     // 预留字段
} quicklistNode;
```

### 7.4 QuickList 结构示意图

```
QuickList 整体结构:

  ┌─────────────────────────────────────────────────────────────┐
  │                    quicklist                                │
  ├─────────────────────────────────────────────────────────────┤
  │ head │ tail │ count │ len │ fill │ compress                 │
  └──────┴──────┴───────┴─────┴─────┴───────────┬───────────┘
```

### 7.7 QuickList 的操作

#### 头部插入

```
头部插入元素 "X":

1. 检查 head 节点的 ZipList 是否有空间
   - 如果有空间: 直接在 head 的 ZipList 中插入
   - 如果已满: 创建新节点作为新的 head

2. 更新相关指针和计数
```

#### 尾部插入

```
尾部插入元素 "Y":

1. 检查 tail 节点的 ZipList 是否有空间
   - 如果有空间: 直接在 tail 的 ZipList 中插入
   - 如果已满: 创建新节点作为新的 tail

2. 更新相关指针和计数
```

#### 中间插入

```
在位置 10 插入元素 "Z":

1. 遍历找到目标段和段内位置
2. 在段内的 ZipList 中插入
3. 如果插入后段溢出:
   - 分裂为两个段
   - 插入到链表中间

4. 更新相关指针和计数
```

### 7.8 QuickList 的时间复杂度

| 操作 | 时间复杂度 | 说明 |
|------|-----------|------|
| 头部插入/删除 | O(1) | 直接操作 head 段 |
| 尾部插入/删除 | O(1) | 直接操作 tail 段 |
| 随机位置访问 | O(n/s) | n 个元素，s 为每段大小 |
| 中间插入/删除 | O(n/s) | 需要定位到目标段 |

### 7.9 QuickList 与其他结构的对比

| 特性 | ZipList | LinkedList | QuickList |
|------|---------|------------|-----------|
| **内存效率** | 高 | 低 | 高 |
| **头部操作** | O(n) | O(1) | O(1) |
| **尾部操作** | O(1) | O(1) | O(1) |
| **随机访问** | O(n) | O(n) | O(n/s) |
| **连锁更新** | 可能触发 | 不触发 | 有限触发 |
| **实现复杂度** | 低 | 低 | 中 |
| **压缩支持** | 不支持 | 不支持 | 支持 |

## 八、对象系统

### 8.1 Redis 对象系统概述

Redis 的对象系统是其类型系统的核心，它为所有数据类型提供了统一的表示方式。每个 Redis 对象都包含类型信息、编码方式和实际数据。

### 8.2 RedisObject 结构

```c
typedef struct redisObject {
    unsigned int type:4;        // 对象类型
    unsigned int encoding:4;     // 对象编码方式
    unsigned int lru:24;        // LRU 信息（用于过期淘汰）
    int refcount;               // 引用计数
    void *ptr;                  // 指向实际数据的指针
} robj;
```

#### RedisObject 结构示意图

```
redisObject 结构 (共 16 字节):

  ┌────────────────────────────────────────────────────────────────────────┐
  │ type (4bit) │ encoding (4bit) │ lru (24bit) │ refcount (32bit) │ ptr (64bit) │
  └────────────────────────────────────────────────────────────────────────┘
       │              │              │              │                 │
       │              │              │              │                 └──► 实际数据
       │              │              │              │                    (SDS/dict/zskiplist等)
       │              │              │              │
       │              │              │              └── 引用计数
       │              │              │                  用于内存管理
       │              │              │
       │              │              └── LRU 信息
       │              │                  用于过期键淘汰
       │              │
       │              └── 编码方式
       │                  0: INT (整数)
       │                  1: EMBSTR (嵌入式字符串)
       │                  2: RAW (原始字符串)
       │                  ...
       │
       └── 对象类型
           0: STRING
           1: LIST
           2: HASH
           3: SET
           4: ZSET
```

### 8.3 对象类型（type 字段）

Redis 支持五种基本数据类型：

| 类型 | 类型常量 | 说明 |
|------|---------|------|
| `REDIS_STRING` | 0 | 字符串 |
| `REDIS_LIST` | 1 | 列表 |
| `REDIS_HASH` | 2 | 哈希 |
| `REDIS_SET` | 3 | 集合 |
| `REDIS_ZSET` | 4 | 有序集合 |
| `REDIS_STREAM` | 5 | 流 (5.0+) |

### 8.4 对象编码（encoding 字段）

不同对象类型可以有多种编码方式，Redis 会根据数据特点选择最优编码：

#### String 类型的编码

| 编码 | 说明 | 适用场景 |
|------|------|---------|
| `REDIS_ENCODING_INT` | 整数 | 可以用整数表示的字符串 |
| `REDIS_ENCODING_EMBSTR` | 嵌入式字符串 | 长度 ≤ 44 字节的字符串 |
| `REDIS_ENCODING_RAW` | 原始字符串 | 长度 > 44 字节的字符串 |

```
String 编码示例:

INT 编码:
  obj->type = REDIS_STRING
  obj->encoding = REDIS_ENCODING_INT
  obj->ptr = (void*)123456  // 直接存储整数值
  
  节省内存，无需分配额外空间

EMBSTR 编码:
  obj->type = REDIS_STRING
  obj->encoding = REDIS_ENCODING_EMBSTR
  obj->ptr = 指向连续内存块
  
  内存布局: [redisObject][SDS 数据]
  一次内存分配，效率更高

RAW 编码:
  obj->type = REDIS_STRING
  obj->encoding = REDIS_ENCODING_RAW
  obj->ptr = 指向 SDS
  
  内存布局: [redisObject] → [SDS 数据]
  两次内存分配，支持更长字符串
```

#### List 类型的编码

| 编码 | 说明 | 适用场景 |
|------|------|---------|
| `REDIS_ENCODING_QUICKLIST` | 快速列表 | 所有 List (3.2+) |

#### Hash 类型的编码

| 编码 | 说明 | 适用场景 |
|------|------|---------|
| `REDIS_ENCODING_ZIPLIST` | 压缩列表 | 字段少、值小 |
| `REDIS_ENCODING_HT` | 哈希表 | 字段多或值大 |

```
Hash 编码转换:

ZipList (字段 ≤ 128 且值 ≤ 64 字节):
  obj->encoding = REDIS_ENCODING_ZIPLIST
  obj->ptr → ZipList 结构

  插入 "key3": "very_long_value..." (> 64 字节)
  或字段数量超过 128

  ↓ 转换为 ↓

HashTable:
  obj->encoding = REDIS_ENCODING_HT
  obj->ptr → dict 结构
```

#### Set 类型的编码

| 编码 | 说明 | 适用场景 |
|------|------|---------|
| `REDIS_ENCODING_INTSET` | 整数集合 | 全是整数且数量少 |
| `REDIS_ENCODING_HT` | 哈希表 | 非整数或数量多 |

#### ZSet 类型的编码

| 编码 | 说明 | 适用场景 |
|------|------|---------|
| `REDIS_ENCODING_ZIPLIST` | 压缩列表 | 元素少、值小 |
| `REDIS_ENCODING_SKIPLIST` | 跳表+哈希表 | 元素多或值大 |

```
ZSet 的 SkipList 编码:
  obj->encoding = REDIS_ENCODING_SKIPLIST
  obj->ptr → zset 结构
  
  zset 结构:
  ┌─────────────────────────────────────────────────────┐
  │  zskiplist  │  dict  (哈希表用于 O(1) 查找)          │
  │  (跳表用于   │  key → score 映射                     │
  │   范围查询)  │                                       │
  └─────────────────────────────────────────────────────┘
```

### 8.6 类型转换时机

#### String 类型转换

```c
// String 类型的转换逻辑
void shareValue(robj *o) {
    if (o->encoding == REDIS_ENCODING_INT) {
        // INT → EMBSTR: 当整数转换为字符串时
        o->encoding = REDIS_ENCODING_EMBSTR;
        o->ptr = createEmbeddedStringObject(...);
    } else if (sdslen(o->ptr) > 44) {
        // EMBSTR → RAW: 当字符串长度超过 44 字节时
        o->encoding = REDIS_ENCODING_RAW;
        o->ptr = createRawStringObject(...);
    }
}
```

#### Hash 类型转换

```c
// Hash 编码转换条件
if (hash->used > REDIS_HASH_ZIPLIST_MAX_FIELDS ||  // > 128 个字段
    hashValueTooLarge(hash)) {                       // 任意值 > 64 字节
    // ZIPLIST → HT
    hashConvert(hash, REDIS_ENCODING_HT);
}
```

#### Set 类型转换

```c
// Set 编码转换条件
if (set->used > REDIS_SET_INTSET_MAX_SIZE ||  // > 512 个元素
    !isAllIntegers(set)) {                     // 存在非整数值
    // INTSET → HT
    setConvert(set, REDIS_ENCODING_HT);
}
```

#### ZSet 类型转换

```c
// ZSet 编码转换条件
if (zset->used > REDIS_ZSET_ZIPLIST_MAX_ENTRIES ||  // > 128 个元素
    zsetValueTooLarge(zset)) {                        // 任意值 > 64 字节
    // ZIPLIST → SKIPLIST
    zsetConvert(zset, REDIS_ENCODING_SKIPLIST);
}
```

### 8.7 引用计数与内存管理

Redis 使用**引用计数**来管理对象的内存生命周期：

```c
// 增加引用
void incrRefCount(robj *o) {
    o->refcount++;
}

// 减少引用
void decrRefCount(robj *o) {
    if (o->refcount == 1) {
        // 引用计数为 0，释放内存
        freeObject(o);
    } else {
        o->refcount--;
    }
}
```

#### 引用计数的应用场景

| 场景 | 说明 |
|------|------|
| **数据库键引用** | 每个数据库键引用一个值对象 |
| **共享对象** | 多个地方引用同一个对象（如共享的小整数） |
| **函数参数传递** | 避免不必要的对象复制 |
| **Lua 脚本** | 脚本执行期间持有对象引用 |

### 8.8 对象系统的优势

| 优势 | 说明 |
|------|------|
| **统一接口** | 所有类型使用相同的 API 操作 |
| **自适应编码** | 根据数据特点自动选择最优编码 |
| **节省内存** | 整数共享、嵌入式字符串等优化 |
| **高效转换** | 编码方式可在运行时转换 |
| **易于扩展** | 新增类型只需实现对象接口 |

## 十、性能分析与最佳实践

### 10.1 各数据结构的时间复杂度汇总

| 数据结构 | 查找 | 插入 | 删除 | 范围查询 |
|---------|------|------|------|---------|
| **SDS** | O(n) | O(n) | O(n) | - |
| **Hash Table** | O(1) | O(1) | O(1) | - |
| **Skip List** | O(log n) | O(log n) | O(log n) | O(log n + m) |
| **ZipList** | O(n) | O(n) | O(n) | O(n) |
| **IntSet** | O(log n) | O(n) | O(n) | O(n) |
| **QuickList** | O(n/s) | O(1)~O(n/s) | O(1)~O(n/s) | O(n/s) |

### 10.2 空间复杂度对比

| 数据结构 | 空间复杂度 | 内存特点 |
|---------|-----------|---------|
| **SDS** | O(n) | 有空间预分配，减少 realloc |
| **Hash Table** | O(n) | 负载因子 1，有空闲空间 |
| **Skip List** | O(n) | 多层指针，约 2 倍链表空间 |
| **ZipList** | O(n) | 紧凑存储，无指针开销 |
| **IntSet** | O(n) | 最紧凑的整数存储 |
| **QuickList** | O(n) | 链表 + ZipList 的折中方案 |

### 10.3 Redis 数据结构设计哲学

Redis 的数据结构设计体现了以下哲学思想：

#### 1. 按需优化

Redis 不会对所有场景使用最优结构，而是**根据实际数据动态选择**：
- 小数据量使用紧凑结构（ZipList、IntSet）
- 大数据量使用高效结构（Hash Table、Skip List）

#### 2. 渐进式升级

Redis 的编码升级是**单向的、不可逆的**：
- ZipList → Hash Table（不会反向）
- IntSet → Hash Table（不会反向）
- 小规模 → 大规模（不会降级）

#### 3. 时间与空间的平衡

Redis 在时间和空间之间做出了明智的权衡：
- ZipList：空间换时间（节省内存，但操作慢）
- Hash Table：时间换空间（操作快，但内存占用高）
- QuickList：折中方案（兼顾两者）

#### 4. 简单即美

Redis 的数据结构设计保持了简单性：
- 跳表替代红黑树：实现更简单
- ZipList 替代双向链表：内存更紧凑
- 对象系统统一管理：接口更简洁

### 10.4 实际应用场景

#### 场景一：用户 Session 存储

```redis
    username "Tom"
```

## 十一、常见面试题

### Q1：Redis 为什么使用 SDS 而不是 C 字符串？

**答：** 主要有四个原因：
1. **O(1) 获取长度**：SDS 直接存储 `len` 字段，而 C 字符串需要遍历
2. **避免缓冲区溢出**：SDS 会自动扩展空间，而 C 字符串需要手动管理
3. **二进制安全**：SDS 以显式长度为准，支持存储 `\0` 等二进制数据
4. **兼容 C 字符串**：SDS 仍然以 `\0` 结尾，可以直接使用 C 字符串函数

### Q2：Redis 哈希表的渐进式 rehash 是如何实现的？

**答：** 渐进式 rehash 的实现包括：
1. 使用两个哈希表 `table[0]` 和 `table[1]`
2. rehash 期间，每次操作（查找、插入、删除）都会顺便迁移一个索引位置
3. 通过 `rehashidx` 记录 rehash 进度
4. 查找时先查 `table[0]`，再查 `table[1]`
5. 当所有元素迁移完成后，`table[1]` 成为新的 `table[0]`

### Q3：跳表为什么比红黑树更适合 Redis？

**答：** 主要有三个原因：
1. **实现简单**：跳表的代码量约为红黑树的 1/3，更容易维护
2. **范围查询高效**：跳表利用 `span` 字段可以快速计算排名
3. **常数因子小**：跳表的插入和删除操作的常数因子比红黑树小

### Q4：压缩列表的连锁更新是什么？

**答：** 连锁更新是指当 ZipList 中某个 entry 的 `prevrawlen` 字段变化时，导致后续所有 entry 的位置变化，进而需要更新它们的 `prevrawlen`。虽然最坏时间复杂度为 O(n²)，但实际中触发条件苛刻，平均性能良好。

### Q5：QuickList 是如何结合 ZipList 和 LinkedList 的优点的？

**答：** QuickList 的设计思路是：
1. 将链表按段切分，每段使用 ZipList 存储
2. 保持链表的结构，支持 O(1) 的头部和尾部操作
3. 利用 ZipList 的紧凑性，节约内存
4. 支持段级压缩，进一步节省空间

### Q6：Redis 对象系统的类型转换时机是什么？

**答：** 类型转换是为了在数据规模变化时自动选择最优编码：
- **STRING**：INT → EMBSTR（整数转字符串）→ RAW（字符串超过 44 字节）
- **HASH**：ZIPLIST → HT（字段超过 128 个或值超过 64 字节）
- **SET**：INTSET → HT（元素超过 512 个或存在非整数值）
- **ZSET**：ZIPLIST → SKIPLIST（元素超过 128 个或值超过 64 字节）
