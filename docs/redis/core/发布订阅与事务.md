# Redis 发布订阅、事务与 Lua 脚本：从消息传递到原子操作的全面剖析

## 一、发布订阅（Pub/Sub）

### 1.1 基本概念

发布订阅（Publish/Subscribe，简称 Pub/Sub）是一种**消息传递模式**，它将消息的发送方和接收方解耦，实现了一对多、多对多的消息广播机制。

在 Redis 的发布订阅模型中，有三个核心角色：

| 角色 | 说明 | 示例 |
|------|------|------|
| **发布者（Publisher）** | 负责向频道发送消息的客户端 | 新闻系统中的新闻发布服务 |
| **订阅者（Subscriber）** | 订阅一个或多个频道，接收消息的客户端 | 客户端 App、邮件通知服务 |
| **频道（Channel）** | 消息的广播通道，发布者向频道发消息，订阅者从频道收消息 | `news:technology`、`order:created` |

#### 发布订阅的工作流程

```
┌──────────────┐     PUBLISH      ┌──────────────┐    推送消息    ┌──────────────┐
│  发布者 A    │ ──────────────► │              │ ─────────────► │  订阅者 X    │
│  (Publisher) │  "Redis 7.2 发布" │              │               │  (Subscriber)│
└──────────────┘                  │              │               └──────────────┘
                                  │              │
┌──────────────┐     PUBLISH      │   频道       │    推送消息    ┌──────────────┐
│  发布者 B    │ ──────────────► │  (Channel)   │ ─────────────► │  订阅者 Y    │
│  (Publisher) │  "新版本特性"    │              │               │  (Subscriber)│
└──────────────┘                  │              │               └──────────────┘
                                  │              │
                                  └──────────────┘               ┌──────────────┐
                                                                 │  订阅者 Z    │
                                                                 │  (Subscriber)│
                                                                 └──────────────┘
```

发布订阅的核心思想是：**发布者不需要知道消息被谁接收，订阅者不需要知道消息由谁发送**，二者通过频道实现解耦。

### 1.2 常用命令

Redis 提供了完整的发布订阅命令集，支持精确频道订阅和模式匹配订阅两种方式。

#### PUBLISH：发布消息

```redis
PUBLISH news:technology "Redis 7.2 正式发布，带来多项性能提升"
```

PUBLISH 命令将消息发送到指定频道，返回值为**接收到消息的订阅者数量**。

#### SUBSCRIBE：订阅频道

```redis
SUBSCRIBE news:technology news:finance
```

SUBSCRIBE 命令订阅一个或多个频道，支持同时订阅多个频道。订阅者会进入**阻塞状态**，等待接收消息。

**订阅者接收到的消息格式：**

```
1) "message"           -- 消息类型
2) "news:technology"   -- 来源频道
3) "Redis 7.2 正式发布" -- 消息内容
```

#### UNSUBSCRIBE：取消订阅

```redis
UNSUBSCRIBE news:technology
UNSUBSCRIBE            -- 取消所有频道订阅
```

#### PSUBSCRIBE：模式订阅

```redis
PSUBSCRIBE news:*         -- 订阅所有以 "news:" 开头的频道
PSUBSCRIBE user:*:login   -- 订阅所有用户登录事件
```

PSUBSCRIBE 使用 glob 模式匹配频道名，支持 `*`（匹配任意字符）、`?`（匹配单个字符）、`[...]`（匹配指定字符集）。

**模式订阅者接收到的消息格式：**

```
1) "pmessage"          -- 消息类型（模式消息）
2) "news:*"            -- 匹配的模式
3) "news:technology"   -- 实际匹配的频道
4) "Redis 7.2 发布"     -- 消息内容
```

#### PUNSUBSCRIBE：取消模式订阅

```redis
PUNSUBSCRIBE news:*
PUNSUBSCRIBE           -- 取消所有模式订阅
```

#### PUBSUB：查看订阅状态

```redis
PUBSUB CHANNELS                              -- 查看所有活跃频道
PUBSUB CHANNELS news:*                       -- 按模式筛选活跃频道
PUBSUB NUMSUB news:technology news:finance   -- 查看频道的订阅者数量
PUBSUB NUMPAT                                -- 查看模式订阅数量
```

#### 命令汇总表

| 命令 | 作用 | 返回值 |
|------|------|--------|
| `PUBLISH channel msg` | 向频道发布消息 | 接收消息的订阅者数量 |
| `SUBSCRIBE [channel ...]` | 订阅频道 | 持续接收消息 |
| `UNSUBSCRIBE [channel ...]` | 取消订阅 | 确认取消 |
| `PSUBSCRIBE [pattern ...]` | 按模式订阅 | 持续接收匹配消息 |
| `PUNSUBSCRIBE [pattern ...]` | 取消模式订阅 | 确认取消 |
| `PUBSUB CHANNELS [pattern]` | 查看活跃频道 | 频道列表 |
| `PUBSUB NUMSUB [channel ...]` | 查看订阅者数量 | 频道-数量映射 |
| `PUBSUB NUMPAT` | 查看模式订阅数 | 模式订阅数量 |

### 1.3 底层实现

Redis 的发布订阅系统基于**字典（Dict）**和**链表**实现，核心数据结构定义在 `server.h` 中。

#### 订阅字典（pubsub_channels）

```c
typedef struct redisServer {
    // ...
    dict *pubsub_channels;  // 频道订阅字典
    dict *pubsub_patterns;  // 模式订阅链表
    // ...
} redisServer;
```

`pubsub_channels` 是一个字典结构，键为频道名，值为订阅该频道的客户端链表。

#### 频道订阅结构示意图

```
pubsub_channels 字典:

┌─────────────────────────────────────────────────────────────┐
│  Hash Table                                                  │
├──────────┬──────────┬──────────┬──────────┬──────────┬─────┤
│ news:tech │ news:fin │ order:cr │ user:log │ event:pay │ ... │
└────┬─────┴────┬─────┴────┬─────┴────┬─────┴────┬─────┴─────┘
     │          │          │          │          │
     ▼          ▼          ▼          ▼          ▼
  ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
  │Client│   │Client│   │Client│   │Client│   │Client│
  │  X   │   │  A   │   │  M   │   │  P   │   │  J   │
  └──┬───┘   └──┬───┘   └──┬───┘   └──┬───┘   └──┬───┘
     │          │          │          │          │
     ▼          ▼          ▼          ▼          ▼
  ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
  │Client│   │Client│   │Client│   │Client│   │Client│
  │  Y   │   │  B   │   │  N   │   │  Q   │   │  K   │
  └──────┘   └──────┘   └──────┘   └──────┘   └──────┘
```

#### 模式订阅结构

模式订阅使用**链表**结构存储，每个节点包含模式字符串和订阅客户端。

```c
typedef struct pubsubPattern {
    client *client;              // 订阅客户端
    char *pattern;               // 订阅模式（如 "news:*"）
    struct pubsubPattern *next;  // 链表下一个节点
} pubsubPattern;
```

#### 消息发布流程

当客户端执行 `PUBLISH channel message` 命令时，Redis 内部执行以下流程：

```
PUBLISH news:technology "Redis 7.2 发布"

步骤 1: 查找订阅该频道的客户端
  → 在 pubsub_channels 字典中查找 "news:technology"
  → 获取订阅客户端链表

步骤 2: 遍历链表，向每个订阅者推送消息
  → 对每个订阅客户端调用 addReplyPubsubMessage()
  → 将消息推入客户端的输出缓冲区

步骤 3: 查找模式订阅
  → 遍历 pubsub_patterns 链表
  → 检查每个模式是否匹配 "news:technology"
  → 对匹配的模式订阅者推送 pmessage

步骤 4: 返回接收者数量
  → 返回成功推送的客户端总数
```

#### 关键实现细节

**订阅操作：**

```c
void subscribeCommand(client *c) {
    // 遍历所有指定频道
    for (j = 0; j < argc; j++) {
        // 将客户端添加到频道的订阅链表中
        if (dictAdd(c->pubsub_channels, argv[j], NULL) == DICT_OK) {
            // 同时在频道字典中添加客户端
            pubsubSubscribeChannel(c, argv[j]);
        }
    }
    // 回复订阅确认
    addReplyPubsubSubscribe(c, argv[j]);
}
```

**发布操作：**

```c
void publishCommand(client *c) {
    // 从参数中提取频道名和消息
    channel = c->argv[1];
    message = c->argv[2];

    // 查找频道订阅者
    de = dictFind(server.pubsub_channels, channel);
    if (de) {
        // 遍历订阅链表，发送消息
        list *clients = dictGetVal(de);
        len = listLength(clients);
        // ... 向每个客户端发送消息
    }

    // 检查模式订阅
    p = server.pubsub_patterns;
    while (p) {
        if (stringmatchlen(p->pattern, ...)) {
            // 向模式订阅者发送 pmessage
        }
        p = p->next;
    }

    // 返回接收者数量
    addReplyLongLong(c, receivers);
}
```

### 1.4 发布订阅的优缺点

#### 优点

| 优点 | 说明 |
|------|------|
| **解耦性强** | 发布者和订阅者无需互相知晓，独立开发和部署 |
| **实时性高** | 消息即时推送给订阅者，延迟极低（通常 <1ms） |
| **扩展性好** | 动态添加/移除订阅者，无需修改发布者代码 |
| **实现简单** | 仅需几条命令即可实现消息广播 |
| **支持模式匹配** | 通过 PSUBSCRIBE 灵活订阅多个频道 |

#### 缺点

| 缺点 | 说明 |
|------|------|
| **消息不持久化** | Redis 重启后订阅关系丢失，发布的消息如果没有订阅者则直接丢弃 |
| **无消息确认** | 发布者不知道订阅者是否真正收到了消息 |
| **无法回溯** | 新订阅者无法收到之前发布的历史消息 |
| **内存占用** | 大量订阅者和频道会消耗较多内存 |
| **不支持消费组** | 每条消息推送给所有订阅者，无法实现负载均衡消费 |
| **可靠性依赖客户端** | 订阅者断线重连后，期间的消息会丢失 |

### 1.5 与消息队列对比

| 对比维度 | Redis Pub/Sub | Redis Stream | 专业消息队列（Kafka/RabbitMQ） |
|---------|---------------|-------------|-------------------------------|
| **消息持久化** | ❌ 不支持 | ✅ 支持 | ✅ 支持 |
| **消费回溯** | ❌ 不支持 | ✅ 支持 | ✅ 支持 |
| **消费组** | ❌ 不支持 | ✅ 支持 | ✅ 支持 |
| **消息确认** | ❌ 不支持 | ✅ 支持 | ✅ 支持 |
| **实时性** | ✅ 极高（<1ms） | ✅ 高（~1ms） | ⚠️ 较高（~ms级） |
| **吞吐量** | 中等 | 高 | 极高（百万级 QPS） |
| **功能丰富度** | 简单 | 中等 | 丰富（路由、重试、死信等） |
| **运维复杂度** | 极低 | 低 | 高 |
| **适用场景** | 实时通知、广播 | 中等规模消息 | 大规模消息系统 |

**选型建议：**
- 简单的实时通知场景 → Redis Pub/Sub
- 需要消息持久化和消费组 → Redis Stream
- 大规模、高可靠消息系统 → Kafka/RabbitMQ

## 二、Redis 事务

### 2.1 事务概述

Redis 事务是一组命令的集合，这些命令在 Redis 中被**顺序执行**，但与传统关系型数据库的事务不同，Redis 事务**不保证原子性**。

Redis 事务的核心命令：

| 命令 | 说明 |
|------|------|
| `MULTI` | 开启事务 |
| `EXEC` | 执行事务中的所有命令 |
| `DISCARD` | 取消事务，放弃执行 |
| `WATCH [key ...]` | 监听键的变化，实现乐观锁 |
| `UNWATCH` | 取消所有键的监听 |

### 2.2 事务执行流程

Redis 事务的执行分为三个阶段：

```
阶段 1: 开启事务（MULTI）
  → 客户端发送 MULTI 命令
  → Redis 返回 OK，表示进入事务模式

阶段 2: 命令入队
  → 客户端发送普通命令（SET、GET、INCR 等）
  → Redis 不立即执行命令，而是将命令放入队列
  → Redis 返回 QUEUED，表示命令已入队

阶段 3: 执行事务（EXEC）
  → 客户端发送 EXEC 命令
  → Redis 按顺序执行队列中的所有命令
  → 返回每条命令的执行结果
```

#### 事务示例

```redis
MULTI
SET counter 0
INCR counter
INCR counter
INCR counter
EXEC
```

**执行过程：**

```
客户端 1:                            Redis 服务端:
  MULTI ──────────────────────────►  (开启事务，状态设为 MULTI_OK)
  ◄──────────────────────────────  OK
  SET counter 0 ─────────────────►  (命令入队)
  ◄──────────────────────────────  QUEUED
  INCR counter ─────────────────►  (命令入队)
  ◄──────────────────────────────  QUEUED
  INCR counter ─────────────────►  (命令入队)
  ◄──────────────────────────────  QUEUED
  INCR counter ─────────────────►  (命令入队)
  ◄──────────────────────────────  QUEUED
  EXEC ─────────────────────────►  (执行所有命令)
  ◄──────────────────────────────  1) OK
                                    2) (integer) 1
                                    3) (integer) 2
                                    4) (integer) 3
```

### 2.3 事务的原子性：一个被误解的概念

#### Redis 事务不保证原子性

这是 Redis 事务与传统数据库事务的**最大区别**。在传统数据库（如 MySQL InnoDB）中，事务中的命令要么全部成功要么全部失败（原子性）。但 Redis 事务中，如果某条命令执行失败，**后续命令仍然会继续执行**。

```redis
MULTI
SET counter 100
INCR counter          -- 对字符串 "100" 执行 INCR，成功
SET counter "hello"   -- 将 counter 改为字符串
INCR counter          -- 对字符串 "hello" 执行 INCR，失败！
SET status "done"     -- 后续命令仍然执行！
EXEC
```

**执行结果：**

```
1) OK
2) (integer) 101
3) OK
4) (error) ERR value is not an integer or out of range
5) OK
```

可以看到，第 4 条命令（INCR counter）虽然失败了，但第 5 条命令（SET status "done"）仍然成功执行。

#### 为什么 Redis 不保证原子性

Redis 不保证原子性的原因在于其**设计哲学**：

1. **性能优先**：如果要实现原子性，Redis 需要在执行前检查所有命令的正确性，这会增加额外开销
2. **简单性**：单条 Redis 命令本身就是原子的，复杂操作推荐使用 Lua 脚本
3. **灵活性**：允许事务中部分命令成功，部分失败，由客户端决定如何处理

#### 如果需要原子性怎么办

如果业务场景确实需要原子性保证，有以下方案：

| 方案 | 说明 |
|------|------|
| **Lua 脚本** | Redis 中 Lua 脚本是原子执行的，推荐方案 |
| **单条原子命令** | Redis 单条命令本身就是原子的 |
| **客户端锁** | 使用 SET NX 等命令实现分布式锁 |
| **错误检查** | 在事务外先验证数据合法性，再开启事务 |

### 2.4 事务的隔离性

由于 Redis 使用**单线程模型**执行命令，事务在执行期间不会被其他命令打断，因此天然具有隔离性。

```
时间线:
  T1: 客户端 A 发送 MULTI (入队 3 条命令)
  T2: 客户端 B 发送 SET key value (处于等待状态)
  T3: 客户端 A 发送 EXEC
  T4: Redis 开始执行事务中的 3 条命令
      → 期间客户端 B 的命令无法执行
  T5: 事务执行完毕
  T6: Redis 开始执行客户端 B 的命令
```

Redis 事务的隔离性特点：
- **命令入队期间不阻塞**：客户端在 MULTI 之后、EXEC 之前的命令入队不会阻塞其他客户端
- **执行期间完全串行**：EXEC 执行期间，所有其他客户端的命令都被阻塞
- **隔离性是强制的**：无法通过任何配置改变这一行为

### 2.5 WATCH 命令与 CAS 机制

WATCH 命令为 Redis 事务提供了**乐观锁**机制，用于解决并发场景下的数据一致性问题。

#### CAS（Compare-And-Swap）原理

WATCH 命令实现的是 CAS（比较并交换）思想：

```
1. 客户端读取 key 的值（如 balance = 100）
2. 客户端开启事务，WATCH 该 key
3. 其他客户端修改了 key 的值（balance → 200）
4. 客户端执行事务，EXEC 时检查 key 是否被修改
5. 发现 key 已被修改，事务执行失败，返回错误
6. 客户端重新读取最新值，重试操作
```

#### WATCH 使用示例

```redis
-- 客户端 A 和 B 同时操作同一个账户

-- 初始状态: balance = 100

-- 客户端 A:
WATCH balance        -- 监听 balance 键
MULTI
SET balance 200      -- 将 balance 改为 200
EXEC
-- 如果 balance 在此期间被其他客户端修改，EXEC 返回 nil
-- (error) ERR EXEC aborted due to WATCH

-- 客户端 B（并发修改）:
SET balance 150      -- 在 A 执行 EXEC 之前修改了 balance
```

#### WATCH 的实现原理

```c
// 客户端结构体中的 watched_keys 字段
typedef struct client {
    // ...
    dict *watched_keys;  // 该客户端监听的所有键
    // ...
} client;

// 数据库结构体中的 watched_keys 字段
typedef struct redisDb {
    // ...
    dict *watched_keys;  // 正在监听该数据库中键的客户端
    // ...
} redisDb;
```

当 Redis 执行修改命令（SET、INCR、DEL 等）时，会触发以下检查：

```
修改 key 时:
  1. 查找 db->watched_keys 中是否有该 key 的监听记录
  2. 如果有，遍历所有监听该 key 的客户端
  3. 将这些客户端标记为 CLIENT_DIRTY_CAS 状态
  4. 当这些客户端执行 EXEC 时，检查 CLIENT_DIRTY_CAS 标记
  5. 如果标记为脏，拒绝执行事务，返回错误
```

#### UNWATCH 命令

```redis
WATCH key1 key2
-- 取消所有监听
UNWATCH
MULTI
SET key1 value1
EXEC  -- 即使 key1 被其他客户端修改，也能成功执行
```

### 2.6 事务的局限性

| 局限性 | 说明 |
|--------|------|
| **不保证原子性** | 单条命令失败不会阻止后续命令执行 |
| **不支持回滚** | 事务执行失败后无法回滚到之前的状态 |
| **不支持嵌套** | Redis 事务不支持嵌套，MULTI 后再发 MULTI 会报错 |
| **命令无法获取中间结果** | 事务中的命令在 EXEC 前不会执行，无法获取中间结果做条件判断 |
| **WATCH 存在竞态** | 在极端情况下，WATCH 可能因网络延迟等原因失效 |
| **执行期间阻塞** | EXEC 执行期间阻塞所有其他命令，事务中的命令越多阻塞时间越长 |

#### 事务嵌套示例

```redis
MULTI
SET key1 value1
MULTI          -- 尝试嵌套
-- (error) ERR MULTI calls can not be nested
EXEC           -- 第一个 MULTI 的 EXEC 仍然可以执行
```

#### 事务中的条件判断问题

```redis
-- 错误写法：无法在事务中根据中间结果做判断
MULTI
SET counter (GET counter) + 1   -- 不支持！GET 命令不会立即执行
EXEC

-- 正确写法：先在客户端计算好值，再放入事务
new_value = GET counter + 1     -- 客户端计算
MULTI
SET counter new_value            -- 使用计算后的值
EXEC
```

### 2.7 事务 vs 管道

很多人会混淆 Redis 事务和管道，它们是完全不同的两个概念：

| 对比维度 | 事务（MULTI/EXEC） | 管道（Pipeline） |
|---------|-------------------|-----------------|
| **目的** | 将多条命令作为一个整体执行 | 减少网络往返开销 |
| **执行方式** | 服务端顺序执行，EXEC 前不执行 | 客户端批量发送，服务端批量响应 |
| **原子性** | 保证命令连续执行，不被打断 | 不保证原子性，其他命令可能插入 |
| **实现位置** | 服务端 | 客户端 |
| **命令数量** | 无硬性限制，但影响性能 | 建议适量，过多会阻塞网络 |
| **返回结果** | EXEC 时统一返回 | 每条命令独立返回 |
| **使用场景** | 需要原子性的操作 | 批量操作优化 |

#### 管道示例

```bash
# 不使用管道：3 次网络往返
redis-cli SET key1 val1    # 往返 1
redis-cli SET key2 val2    # 往返 2
redis-cli SET key3 val3    # 往返 3

# 使用管道：1 次网络往返
redis-cli <<EOF
SET key1 val1
SET key2 val2
SET key3 val3
EOF
```

## 三、Lua 脚本

### 3.1 Lua 脚本基础

Redis 从 2.6 版本开始支持 Lua 脚本，允许在 Redis 服务端执行自定义逻辑。Lua 脚本在 Redis 中是**原子执行**的，并且可以通过 `redis.call()` 和 `redis.pcall()` 调用 Redis 命令。

#### 核心命令

| 命令 | 说明 |
|------|------|
| `EVAL script numkeys key ... arg ...` | 执行 Lua 脚本 |
| `EVALSHA sha1 numkeys key ... arg ...` | 根据 SHA1 摘要执行缓存的脚本 |
| `SCRIPT LOAD script` | 将脚本缓存到服务端，返回 SHA1 摘要 |
| `SCRIPT EXISTS sha1 ...` | 检查脚本是否已缓存 |
| `SCRIPT FLUSH` | 清除所有脚本缓存 |
| `SCRIPT KILL` | 终止正在执行的慢脚本 |
| `SCRIPT DEBUG YES/SYNC/NO` | 开启/关闭脚本调试模式 |

#### EVAL 基本用法

```redis
-- 简单脚本：返回一个字符串
EVAL "return 'Hello, Redis!'" 0

-- 输出: "Hello, Redis!"
```

```redis
-- 带参数的脚本
EVAL "return redis.call('GET', KEYS[1])" 1 user:1001

-- 执行过程:
-- KEYS[1] = "user:1001"
-- 调用 GET user:1001
-- 返回结果
```

```redis
-- 带多个参数的脚本
EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 mykey myvalue

-- KEYS[1] = "mykey"
-- ARGV[1] = "myvalue"
-- 执行 SET mykey myvalue
```

#### EVALSHA 脚本缓存

```redis
-- 第一步：加载脚本，获取 SHA1 摘要
SCRIPT LOAD "return redis.call('GET', KEYS[1])"
-- 返回: "a44809bcf984b2e1c3e8b3e6b9e4f5a7c8d9e0f1"

-- 第二步：通过 SHA1 执行脚本
EVALSHA a44809bcf984b2e1c3e8b3e6b9e4f5a7c8d9e0f1 1 user:1001
-- 返回: "张三"

-- 检查脚本是否存在
SCRIPT EXISTS a44809bcf984b2e1c3e8b3e6b9e4f5a7c8d9e0f1
-- 返回: 1

-- 清除所有缓存（慎用！会导致所有 EVALSHA 失败）
SCRIPT FLUSH
```

#### EVAL vs EVALSHA 对比

| 对比维度 | EVAL | EVALSHA |
|---------|------|---------|
| **脚本传输** | 每次传输完整脚本 | 仅传输 SHA1 摘要 |
| **网络开销** | 较大 | 较小 |
| **缓存依赖** | 无 | 依赖服务端缓存 |
| **适用场景** | 脚本较短或首次执行 | 频繁执行的长脚本 |
| **容错性** | 始终可用 | 缓存被清除后需要回退到 EVAL |

### 3.2 Lua 脚本的原子性

**Lua 脚本在 Redis 中是原子执行的**——这是 Lua 脚本最重要的特性，也是它能解决事务局限性的关键。

#### 原子性保证

Lua 脚本执行期间，Redis 保证：
1. **脚本中的命令要么全部执行，要么都不执行**
2. **脚本执行期间不会被其他客户端命令打断**
3. **脚本中不能执行 `BGSAVE`、`BGREWRITEAOF`、`CONFIG`、`SHUTDOWN` 等破坏性命令**

```lua
-- Lua 脚本实现原子性的银行转账
local balance_a = redis.call('GET', KEYS[1])
local balance_b = redis.call('GET', KEYS[2])
local amount = tonumber(ARGV[1])

if tonumber(balance_a) < amount then
    return redis.error_reply('余额不足')
end

redis.call('SET', KEYS[1], balance_a - amount)
redis.call('SET', KEYS[2], balance_b + amount)

return redis.status_reply('转账成功')
```

**执行过程分析：**

```
步骤 1: 客户端发送 EVAL 命令
步骤 2: Redis 开始执行 Lua 脚本
  → 读取 A 的余额
  → 读取 B 的余额
  → 检查余额是否充足
  → 扣减 A 的余额
  → 增加 B 的余额
步骤 3: 返回执行结果

原子性保证:
  → 以上所有步骤作为一个整体执行
  → 执行过程中不会被其他命令打断
  → 即使脚本执行错误，也不会影响其他 key 的状态
```

#### Lua 脚本与事务的原子性对比

| 对比维度 | Lua 脚本 | Redis 事务 |
|---------|---------|-----------|
| **原子性** | ✅ 完全保证 | ❌ 不保证 |
| **执行方式** | 服务端一次性执行 | 服务端顺序执行队列 |
| **错误处理** | 脚本错误则整体回滚 | 单条错误不影响后续 |
| **回滚支持** | ✅ 自动回滚 | ❌ 不支持回滚 |

### 3.3 Redis 与 Lua 的交互

Redis 为 Lua 脚本提供了两个内置函数来调用 Redis 命令。

#### redis.call()

`redis.call()` 用于调用 Redis 命令，如果命令执行失败，**脚本会立即终止并返回错误**。

```lua
-- redis.call() 的使用
local result = redis.call('SET', 'mykey', 'myvalue')
-- 如果 SET 成功，result = 'OK'

-- 如果命令执行错误
redis.call('GET', 'nonexistent_key')
-- 返回 (nil)，不会中断脚本
-- 因为 GET 对不存在的 key 返回 nil 是正常行为
```

```lua
-- redis.call() 在错误命令上的行为
redis.call('INCR', 'mykey')  -- 如果 mykey 是字符串
-- 返回错误: ERR value is not an integer or out of range
-- 脚本立即终止，返回错误给客户端
```

#### redis.pcall()

`redis.pcall()` 用于调用 Redis 命令，与 `redis.call()` 的区别在于：**命令执行错误不会终止脚本，而是返回错误对象**。

```lua
-- redis.pcall() 的使用
local result = redis.pcall('INCR', 'mykey')

if type(result) == 'table' and result.err then
    -- 命令执行错误，但脚本继续执行
    redis.call('SET', 'mykey', '0')
    result = redis.pcall('INCR', 'mykey')
end

return result
```

#### redis.call() vs redis.pcall()

| 对比维度 | redis.call() | redis.pcall() |
|---------|-------------|--------------|
| **错误处理** | 错误立即终止脚本 | 错误返回错误对象，脚本继续 |
| **适用场景** | 关键命令，失败则整体失败 | 需要容错处理的场景 |
| **返回值** | 命令正常返回值 | 命令返回值或错误对象 |
| **推荐程度** | 推荐大多数场景 | 特殊容错场景 |

#### Lua 数据类型与 Redis 数据类型的转换

Redis 在调用 Lua 脚本时，会自动进行数据类型转换：

| Redis 类型 | Lua 类型 | 示例 |
|-----------|---------|------|
| 整数 | number | `1` → `1` |
| 浮点数 | number | `1.5` → `1.5` |
| 字符串 | string | `"hello"` → `"hello"` |
| 批量字符串 | string | `"hello"` → `"hello"` |
| 数组 | table | `[1, 2, 3]` → `{1, 2, 3}` |
| nil | false | `(nil)` → `false` |
| 错误 | table (带 err 字段) | `ERR ...` → `{err="..."}` |

```lua
-- 数据类型转换示例
local str = redis.call('GET', 'mykey')       -- 返回 string
local num = redis.call('INCR', 'counter')     -- 返回 number
local list = redis.call('LRANGE', 'mylist', 0, -1)  -- 返回 table
local exists = redis.call('EXISTS', 'mykey')  -- 返回 number (0 或 1)
```

### 3.4 脚本缓存与执行

#### 脚本缓存机制

Redis 通过 SHA1 摘要对 Lua 脚本进行缓存，缓存的特点：

1. **缓存键**：脚本内容的 SHA1 哈希值
2. **缓存值**：编译后的 Lua 脚本字节码
3. **缓存位置**：Redis 服务端内存
4. **缓存有效期**：永不过期（除非主动清除）

```
脚本缓存流程:

客户端 A:                          Redis 服务端:
  SCRIPT LOAD "return redis.call(  │
    'GET', KEYS[1])"               │
                                   │ 1. 计算脚本 SHA1 = "abc123"
                                   │ 2. 编译脚本为字节码
                                   │ 3. 存储到脚本缓存
  ◄──────────────────────────────  │ 4. 返回 SHA1
  "abc123"                         │
                                   │
  EVALSHA abc123 1 mykey           │
                                   │ 5. 从缓存查找脚本
                                   │ 6. 执行脚本
  ◄──────────────────────────────  │ 7. 返回结果
  "myvalue"                        │
```

#### 脚本缓存的维护

```redis
-- 检查脚本是否存在
SCRIPT EXISTS sha1 sha2 sha3
-- 返回: 1) (integer) 1    2) (integer) 1    3) (integer) 0

-- 清除所有脚本缓存
SCRIPT FLUSH

-- 在集群模式下，SCRIPT FLUSH 只清除当前节点的缓存
-- 需要在所有节点上执行 SCRIPT FLUSH
```

#### 脚本执行的限制

为了保证 Redis 的稳定性和脚本的原子性，Redis 对 Lua 脚本做了以下限制：

**不能执行的命令：**

| 类别 | 命令 | 原因 |
|------|------|------|
| 持久化相关 | `BGSAVE`、`BGREWRITEAOF`、`SAVE` | 可能阻塞其他客户端 |
| 复制相关 | `REPLICAOF`、`SLAVEOF` | 破坏复制结构 |
| 配置相关 | `CONFIG SET`、`CONFIG RESETSTAT` | 动态配置可能影响脚本行为 |
| 数据库相关 | `SELECT`、`FLUSHDB`、`FLUSHALL` | 破坏数据库隔离 |
| 调试相关 | `DEBUG`、`OBJECT` | 增加额外开销 |
| 管理相关 | `SHUTDOWN`、`CLIENT KILL` | 破坏性操作 |
| 随机相关 | `RANDOMKEY` | 不确定性，破坏原子性 |

**执行时间限制：**
- 脚本默认执行时间上限为 **5 秒**（通过 `lua-time-limit` 配置）
- 超时后 Redis 会记录警告日志
- 可以通过 `SCRIPT KILL` 终止超时脚本

```conf
# redis.conf 中的脚本执行时间配置
lua-time-limit 5000    # 5 秒（单位：毫秒）
```

#### Lua 脚本调试

Redis 3.2+ 内置了 Lua 脚本调试器：

```redis
-- 开启调试模式（同步模式，客户端被阻塞）
SCRIPT DEBUG YES

-- 开启调试模式（异步模式，客户端不阻塞）
SCRIPT DEBUG SYNC

-- 执行脚本触发调试
EVAL "return redis.call('GET', KEYS[1])" 1 mykey

-- 在 redis-cli 中使用调试器
redis-cli --ldb --eval myscript.lua key1 arg1
```

### 3.5 实战示例

#### 示例一：分布式锁

基于 Lua 脚本实现安全的分布式锁，确保**检查-设置-删除**的原子性。

```lua
-- 加锁脚本 (lock.lua)
local key = KEYS[1]           -- 锁的 key
local value = ARGV[1]         -- 唯一标识符（如 UUID）
local ttl = tonumber(ARGV[2]) -- 过期时间（毫秒）

-- SET 命令的 NX + PX 选项实现原子加锁
local result = redis.call('SET', key, value, 'NX', 'PX', ttl)

if result then
    return 1  -- 加锁成功
else
    return 0  -- 加锁失败
end
```

```lua
-- 解锁脚本 (unlock.lua)
local key = KEYS[1]           -- 锁的 key
local value = ARGV[1]         -- 唯一标识符

-- 检查值是否匹配，防止误删
local current_value = redis.call('GET', key)

if current_value == value then
    redis.call('DEL', key)
    return 1  -- 解锁成功
else
    return 0  -- 不是自己的锁，不删除
end
```

```redis
-- 使用示例
-- 加锁
EVALSHA <lock_sha1> 1 lock:order:1001 uuid-xxx-xxx 30000
-- 解锁
EVALSHA <unlock_sha1> 1 lock:order:1001 uuid-xxx-xxx
```

#### 示例二：限流

基于 Lua 脚本实现**滑动窗口限流**算法，比简单的计数器更精准。

```lua
-- 滑动窗口限流脚本 (ratelimit.lua)
local key = KEYS[1]
local limit = tonumber(ARGV[1])    -- 时间窗口内允许的最大请求数
local window = tonumber(ARGV[2])  -- 窗口大小（毫秒）
local now = tonumber(ARGV[3])      -- 当前时间戳

-- 添加当前请求的时间戳
redis.call('ZADD', key, now, now .. '-' .. math.random())

-- 删除窗口外的旧数据
local min_score = now - window
redis.call('ZREMRANGEBYSCORE', key, '-inf', min_score)

-- 统计当前窗口内的请求数
local current = redis.call('ZCARD', key)

-- 设置过期时间
redis.call('PEXPIRE', key, window)

if current > limit then
    return 0  -- 超过限流
else
    return 1  -- 允许请求
end
```

```redis
-- 使用示例：限流每用户每秒最多 100 次请求
EVALSHA <ratelimit_sha1> 1 ratelimit:user:1001 100 1000 1720000000000
```

#### 示例三：复杂原子操作

在电商场景中，原子性地完成库存扣减、订单创建和积分累积。

```lua
-- 电商下单原子操作 (create_order.lua)
local stock_key = KEYS[1]         -- 库存 key
local order_key = KEYS[2]        -- 订单 key
local points_key = KEYS[3]       -- 积分 key

local product_id = ARGV[1]
local user_id = ARGV[2]
local quantity = tonumber(ARGV[3])
local order_id = ARGV[4]

-- 检查库存
local stock = tonumber(redis.call('GET', stock_key))
if stock < quantity then
    return redis.error_reply('库存不足')
end

-- 扣减库存
redis.call('DECRBY', stock_key, quantity)

-- 创建订单
local order_info = cjson.encode({
    order_id = order_id,
    user_id = user_id,
    product_id = product_id,
    quantity = quantity,
    status = 'paid',
    created_at = redis.call('TIME')[1]
})
redis.call('SET', order_key, order_info)

-- 累积积分（假设每消费 1 元积 1 分）
redis.call('HINCRBY', points_key, 'total', quantity * 100)

return redis.status_reply('订单创建成功')
```

```redis
-- 使用示例
EVALSHA <order_sha1> 3 \
  stock:product:1001 \
  order:user:1001:order:abc123 \
  points:user:1001 \
  "product:1001" "user:1001" 2 "order-abc123"
```

#### 示例四：排行榜更新

原子性地更新多个排行榜（日榜、周榜、月榜）。

```lua
-- 多排行榜更新脚本 (update_rankings.lua)
local user_id = ARGV[1]
local score = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 计算时间周期的 key
local day_key = 'ranking:day:' .. math.floor(now / 86400)
local week_key = 'ranking:week:' .. math.floor(now / 604800)
local month_key = 'ranking:month:' .. math.floor(now / 2592000)

-- 使用 ZIncrBy 原子性地更新每个排行榜
redis.call('ZINCRBY', day_key, score, user_id)
redis.call('ZINCRBY', week_key, score, user_id)
redis.call('ZINCRBY', month_key, score, user_id)

-- 设置过期时间
redis.call('EXPIRE', day_key, 86400 * 2)       -- 日榜保留 2 天
redis.call('EXPIRE', week_key, 86400 * 14)     -- 周榜保留 2 周
redis.call('EXPIRE', month_key, 86400 * 60)    -- 月榜保留 60 天

return redis.status_reply('更新成功')
```

## 四、三者对比与选择

### 4.1 核心特性对比

| 对比维度 | 发布订阅 | 事务 | Lua 脚本 |
|---------|---------|------|---------|
| **核心目的** | 消息广播 | 命令批量执行 | 复杂逻辑原子执行 |
| **原子性** | 不涉及 | ❌ 不保证 | ✅ 保证 |
| **隔离性** | 共享频道 | ✅ 天然隔离 | ✅ 天然隔离 |
| **持久化** | ❌ 消息不持久 | ❌ 不持久 | ❌ 不持久 |
| **执行方式** | 即时推送 | 延迟执行 | 即时执行 |
| **可编程性** | 无 | 有限 | 强（完整 Lua 语言） |
| **错误处理** | 无 | 不中断 | 可中断/不中断 |
| **网络开销** | 低 | 低 | 低（配合缓存极低） |
| **复杂度** | 简单 | 简单 | 中等 |

### 4.2 适用场景选择

#### 发布订阅适用场景

```
✅ 实时通知系统：新消息推送、系统公告
✅ 实时数据同步：缓存更新、数据失效通知
✅ 日志收集：日志广播到多个处理节点
✅ 系统监控：健康检查、告警通知
✅ 社交应用：实时消息、在线状态
```

#### 事务适用场景

```
✅ 批量命令执行：减少网络往返
✅ 简单的原子操作：INCR + EXPIRE 组合
✅ 需要 WATCH 的乐观锁：CAS 更新
✅ 条件性更新：先检查再更新
```

#### Lua 脚本适用场景

```
✅ 分布式锁：原子性加锁/解锁
✅ 限流算法：滑动窗口、令牌桶
✅ 复杂业务逻辑：多表联动操作
✅ 自定义数据结构：高效数据处理
✅ 事务增强：保证命令原子性
✅ 性能优化：减少网络往返
```

### 4.3 组合使用的最佳实践

在实际项目中，三者往往是组合使用的：

```lua
-- 组合示例：分布式锁 + Lua 脚本 + 发布订阅

-- 1. 使用 Lua 脚本实现原子性的分布式锁
local lock_key = KEYS[1]
local lock_value = ARGV[1]
local lock_ttl = ARGV[2]

if redis.call('SET', lock_key, lock_value, 'NX', 'PX', lock_ttl) then
    -- 2. 在 Lua 脚本中完成复杂业务逻辑
    redis.call('HSET', 'user:' .. ARGV[3], 'status', 'locked')
    
    -- 3. 通过发布订阅通知其他节点
    redis.call('PUBLISH', 'lock:acquired', lock_key)
    
    return 1
else
    return 0
end
```

### 4.4 选型决策流程

```
需要消息广播吗？
  │
  ├── 是 → 需要持久化吗？
  │         │
  │         ├── 否 → 使用发布订阅
  │         │
  │         └── 是 → 需要消费组吗？
  │                   │
  │                   ├── 是 → Redis Stream 或 Kafka
  │                   │
  │                   └── 否 → Redis Stream
  │
  └── 否 → 需要多条命令原子执行吗？
            │
            ├── 是 → 需要复杂逻辑吗？
            │         │
            │         ├── 是 → 使用 Lua 脚本
            │         │
            │         └── 否 → 使用事务（MULTI/EXEC）
            │
            └── 否 → 使用单条命令或管道
```

## 五、常见面试题

### 5.1 发布订阅相关

#### Q1：Redis 发布订阅有哪些缺点？如何解决？

**答：**

Redis 发布订阅的主要缺点包括：

1. **消息不持久化**：如果订阅者不在线，消息直接丢失
   - 解决方案：使用 Redis Stream 或配合数据库持久化

2. **无消息确认机制**：发布者无法确认消息是否送达
   - 解决方案：使用 Redis Stream 的消费确认机制

3. **不支持消费组**：每条消息推送给所有订阅者
   - 解决方案：使用 Redis Stream 的消费组功能

4. **订阅关系不持久**：Redis 重启后订阅关系丢失
   - 解决方案：客户端断线重连后自动重新订阅

#### Q2：如何实现可靠的消息发布订阅？

**答：**

```
方案一：Redis Stream
  → 使用 XADD 添加消息到流
  → 使用 XREADGROUP 创建消费组
  → 使用 XACK 确认消息
  → 使用 XCLAIM 重新处理未确认的消息

方案二：发布订阅 + 持久化
  → 发布者先将消息写入 Redis List 或数据库
  → 再通过 PUBLISH 通知订阅者
  → 订阅者收到通知后从 List 或数据库拉取消息

方案三：专业消息队列
  → 使用 Kafka/RabbitMQ 等专业 MQ
  → 提供完整的消息可靠性保证
```

#### Q3：Redis 发布订阅的消息是推模式还是拉模式？

**答：**

Redis 发布订阅采用**推模式**（Push）：
- 发布者发布消息后，Redis 立即将消息推送给所有订阅者
- 订阅者被动接收消息，无需主动拉取

相比之下，Redis Stream 同时支持推模式和拉模式：
- XREAD/XREADGROUP 是拉模式
- 但 Redis 内部也是先推送，客户端再确认

### 5.2 事务相关

#### Q4：Redis 事务保证原子性吗？为什么？

**答：**

**Redis 事务不保证原子性**，原因如下：

1. **设计哲学不同**：Redis 追求的是性能和简单性，而非传统意义上的事务一致性
2. **实现机制不同**：Redis 事务只是将命令排队，EXEC 时按顺序执行，不做回滚
3. **错误处理不同**：单条命令失败不会阻止后续命令的执行
4. **如何实现原子性**：需要使用 Lua 脚本或单条原子命令

#### Q5：WATCH 命令的实现原理是什么？

**答：**

WATCH 的实现基于**双向引用**机制：

```
1. 客户端 A 执行 WATCH key1
   → 在客户端 A 的 watched_keys 字典中添加 key1
   → 在 key1 所在数据库的 watched_keys 字典中添加客户端 A

2. 其他客户端 B 修改了 key1
   → Redis 检查 key1 的 watched_keys
   → 找到监听的客户端 A
   → 将客户端 A 标记为 CLIENT_DIRTY_CAS

3. 客户端 A 执行 EXEC
   → 检查 CLIENT_DIRTY_CAS 标记
   → 如果标记为脏，拒绝执行，返回错误
```

#### Q6：事务中能否使用 Lua 脚本？

**答：**

```redis
-- 事务中不能直接使用 Lua 脚本
MULTI
EVAL "return redis.call('GET', KEYS[1])" 1 mykey
-- (error) ERR Can't use EVAL inside a MULTI/EXEC context

-- 但 Lua 脚本中可以使用事务命令
EVAL "
  redis.call('MULTI')
  redis.call('SET', KEYS[1], ARGV[1])
  return redis.call('EXEC')
" 1 mykey myvalue
```

**注意**：在 Lua 脚本中使用事务命令没有实际意义，因为 Lua 脚本本身就是原子执行的。

### 5.3 Lua 脚本相关

#### Q7：为什么 Lua 脚本是原子的？

**答：**

Lua 脚本的原子性是由 Redis 的**单线程执行模型**保证的：

1. **单线程执行**：Redis 的命令执行是单线程的，Lua 脚本作为一个整体在单线程中执行
2. **不允许中断**：Lua 脚本执行期间，其他客户端的命令必须等待
3. **全有或全无**：脚本要么执行完成，要么完全不执行

```
时间线:
  T1: 客户端 A 发送 EVAL 命令
  T2: Redis 开始执行 Lua 脚本
      → 执行第 1 条命令
      → 执行第 2 条命令
      → 执行第 3 条命令
      → 脚本执行完毕
  T3: Redis 处理其他客户端的命令
```

#### Q8：如何防止 Lua 脚本执行超时？

**答：**

```
方法一：合理控制脚本复杂度
  → 避免在脚本中执行过多命令
  → 避免在脚本中执行耗时操作
  → 将复杂逻辑拆分为多个脚本

方法二：设置合理的超时时间
  → lua-time-limit 5000 (默认 5 秒)
  → 根据业务需求调整

方法三：使用 SCRIPT KILL 终止超时脚本
  → SCRIPT KILL
  → 注意：SCRIPT KILL 只能终止没有修改数据的脚本

方法四：使用 redis.pcall() 处理错误
  → 避免脚本因意外错误中断
  → 提高脚本的健壮性
```

#### Q9：EVAL 和 EVALSHA 如何选择？

**答：**

```
选择 EVAL 的场景：
  - 脚本较短（< 100 字节）
  - 执行频率较低
  - 临时的一次性操作
  - 网络带宽充足

选择 EVALSHA 的场景：
  - 脚本较长
  - 执行频率高（热点脚本）
  - 对网络延迟敏感
  - 需要优化网络传输

最佳实践：
  1. 首次执行使用 SCRIPT LOAD 加载脚本
  2. 后续执行使用 EVALSHA
  3. 当 EVALSHA 返回 NOSCRIPT 错误时，回退到 EVAL
```

```python
# Python 客户端示例
def execute_script(redis_client, script, *args):
    # 先尝试使用缓存的 SHA1
    sha1 = hashlib.sha1(script.encode()).hexdigest()
    try:
        return redis_client.evalsha(sha1, len(args), *args)
    except redis.exceptions.NoScriptError:
        # 缓存不存在，先加载再执行
        redis_client.script_load(script)
        return redis_client.evalsha(sha1, len(args), *args)
```

#### Q10：如何在 Redis 集群中使用 Lua 脚本？

**答：**

在 Redis 集群中使用 Lua 脚本需要注意以下几点：

1. **所有 KEY 必须在同一个 Hash Slot 中**
   - 可以使用 Hash Tag 强制将 key 分配到同一 slot
   - 示例：`{user}:name` 和 `{user}:age` 在同一 slot

2. **所有 KEY 必须在命令中明确指定**
   - Redis 集群需要知道所有涉及的 key，以便路由到正确的节点

3. **SCRIPT LOAD 和 EVALSHA 不保证跨节点**
   - 脚本缓存仅在当前节点有效
   - 每个节点都需要执行 SCRIPT LOAD

```redis
-- 在集群中使用 Lua 脚本
-- 使用 Hash Tag 确保 key 在同一 slot
EVAL "
  local name = redis.call('GET', '{user}:name')
  local age = redis.call('GET', '{user}:age')
  return name .. ' (' .. age .. ')'
" 2 {user}:name {user}:age
```

### 5.4 综合对比类

#### Q11：发布订阅、事务、Lua 脚本的区别与联系？

**答：**

| 维度 | 发布订阅 | 事务 | Lua 脚本 |
|------|---------|------|---------|
| **运行模式** | 推送模式 | 批处理模式 | 编程模式 |
| **原子性** | 不涉及 | ❌ 不保证 | ✅ 保证 |
| **适用场景** | 消息传递 | 简单批处理 | 复杂原子操作 |
| **技术复杂度** | 低 | 低 | 中 |
| **扩展性** | 高 | 低 | 高 |

**联系：**
- 三者都可以使用 Redis 命令
- Lua 脚本中可以调用发布订阅和事务命令
- 事务中不能使用 Lua 脚本
- 发布订阅中的消息可以触发事务或 Lua 脚本的执行

#### Q12：什么场景下应该使用 Lua 脚本而不是事务？

**答：**

```
场景 1：需要保证原子性
  → 事务不保证原子性，Lua 脚本保证原子性

场景 2：需要复杂的条件判断
  → 事务无法在执行过程中根据中间结果做判断
  → Lua 脚本可以在执行过程中使用 if/else 做条件判断

场景 3：需要减少网络往返
  → 事务需要 MULTI + N 条命令 + EXEC，共 N+2 次往返
  → Lua 脚本只需 1 次往返

场景 4：需要复用逻辑
  → Lua 脚本可以通过 SCRIPT LOAD 缓存
  → 事务逻辑无法复用

场景 5：需要实现自定义数据结构
  → Lua 脚本可以实现 ZSet 范围查询等复杂逻辑
  → 事务只能执行已有的 Redis 命令
```
