# Redis 主从复制、哨兵与集群模式

> 本文档系统性地讲解 Redis 高可用架构，涵盖主从复制（Replication）、哨兵模式（Sentinel）和集群模式（Cluster）三种核心架构的原理、配置、实战与选型建议，并深入剖析 PSYNC 协议、Raft 领导者选举、Gossip 通信、哈希槽分片等关键机制。

---

## 一、高可用概述

### 1.1 为什么需要高可用

Redis 作为内存数据库，以极高的性能著称，但单点部署存在严重的安全隐患：

- **数据丢失风险**：Redis 将数据存储在内存中，进程重启或服务器宕机后数据会丢失（即使开启了 AOF/RDB 持久化，也可能丢失最后一段时间的数据）
- **服务中断**：单台 Redis 服务器故障会导致整个业务系统不可用
- **容量瓶颈**：单台 Redis 的内存容量受限于物理机器，无法无限扩展
- **性能瓶颈**：单节点的 QPS 有上限，无法支撑海量并发访问

**高可用（High Availability，HA）** 旨在通过架构设计消除单点故障，确保 Redis 服务在各种异常情况下仍能稳定运行。

### 1.2 Redis 高可用演进路线

Redis 的高可用方案经历了从简单到复杂的演进过程，每一步都在解决前一阶段的痛点：

```

│                        Redis HA 演进路线                             │

│                                                                     │

│  └──────────────────────────────────┘                               │
│         │                                                           │
│         │ 痛点：单点故障、无数据冗余                                 │
│         ▼                                                           │

│  ┌──────────┐         ┌──────────┐                                 │

│  │  (Sentinel)  │   但数据仍在单节点、无横向扩展                     │
│  └──────────────┘                                                   │
│         │                                                           │
│         │ 痛点：单主架构、无法横向扩容                               │

│  ┌──────────┐  ┌──────────┐  ┌──────────┐                         │

```

### 1.3 三种架构对比一览

| 维度 | 主从复制 | 哨兵模式 | 集群模式 |
|------|---------|---------|---------|
| **数据分布** | 全量复制到所有从节点 | 全量复制到所有从节点 | 分片存储（16384 slot） |
| **读写能力** | 主节点写，从节点读 | 主节点写，从节点读 | 多主写入，可横向扩展 |
| **故障转移** | 手动 | 自动（Raft 选举） | 自动（Gossip 协议） |
| **存储扩展** | 不支持 | 不支持 | 支持（添加节点） |
| **典型场景** | 读多写少、小规模 | 中等规模、高可用要求 | 大规模、海量数据 |

## 二、主从复制（Replication）

### 2.1 主从复制架构

Redis 主从复制是实现高可用的基础。通过主从复制，一个 Redis 实例（主节点）的数据会自动同步到其他实例（从节点），从而实现数据冗余和读写分离。

```
                    ┌─────────────────────┐
                    │    客户端 (Client)   │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
                    │   主节点 (Master)    │
                    │  - 处理写请求        │
                    │  - 接收读请求       │
                    │  - 维护 Replication│
                    │    Backlog          │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              │   全量/增量复制   │                │
              ▼                ▼                ▼
       ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
       │  从节点1      │ │  从节点2      │ │  从节点3      │
       │  (Slave)     │ │  (Slave)     │ │  (Slave)     │
       │  - 只读服务  │ │  - 只读服务  │ │  - 数据备份  │
       │  - 重写主节点│ │  - 重写主节点│ │  - 重写主节点│
       │    的写命令  │ │    的写命令  │ │    的写命令  │
       └──────────────┘ └──────────────┘ └──────────────┘
```

**主从复制的核心特性**：
- **数据冗余**：从节点是主节点的实时数据副本
- **读写分离**：写操作在主节点，读操作可以分发到从节点
- **故障恢复**：主节点故障时，可以将从节点提升为主节点

### 2.2 主从复制原理

#### 2.2.1 复制 ID（Replication ID）与 Offset

为了实现精确的数据同步，Redis 使用 **复制 ID** 和 **复制偏移量（Offset）** 来追踪数据同步状态：

- **replication id（replid）**：每个 Redis 实例在启动时会生成一个随机的 40 位十六进制字符串作为自己的 `replid`。当一个从节点连接到主节点时，主节点会将自己的 `replid` 传递给从节点。从节点只接收这个 `replid` 对应的数据流。
- **replication offset**：一个单调递增的计数器，表示当前复制进度。主节点在向所有从节点传播写命令时，会递增这个 offset。

```
主节点 (replid: "abc123...")
│
│  写入: SET key1 value1     → offset: 100
│  写入: SET key2 value2     → offset: 120
│  写入: DEL key1            → offset: 135
│
│  复制 backlog (环形缓冲区):
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
│  │...│100│120│135│...│...│...│...│...│...│
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
│
└─────────────────────────────────────► 从节点
  replid: "abc123..."
  offset: 100 → 已同步到位置 100
```

#### 2.2.2 全量复制流程

当从节点首次连接主节点，或者从节点的复制 offset 在主节点的 replication backlog 中找不到时，会触发全量复制（Full Synchronization）。

```
从节点 (Slave)                              主节点 (Master)
    │                                          │
    │  1. PSYNC ? -1  ──────────────────────►  │
    │     (首次同步，replid 和 offset 未知)      │
    │                                          │
    │                              2. 执行 BGSAVE 生成 RDB
    │                              ┌────────────────────┐
    │                              │   BGSAVE (fork子进程) │
    │                              │   生成 RDB 快照文件  │
    │                              └────────────────────┘
    │                                          │
    │                     3. +FULLRESYNC replid offset ──►
    │                        发送 FULLRESYNC 响应
    │                        携带主节点的 replid 和当前 offset
    │                                          │
    │                     4. 发送 RDB 文件流 ────────────►
    │                        (以二进制流形式发送 RDB 内容)
    │                                          │
    │  5. 接收 RDB 并加载                       │
    │     - 清空旧数据                          │
    │     - 加载 RDB 文件到内存                 │
    │                                          │
    │                     6. 发送 RDB 之后的写命令 ───────►
    │                        (从 backlog 中获取)  │
    │                                          │
    │  7. 更新 replid 和 offset                 │
    │     复制完成，进入增量同步状态            │
    │                                          │
```

**全量复制的详细步骤**：

| 步骤 | 发起方 | 说明 |
|------|--------|------|
| 1 | 从节点 | 向主节点发送 `PSYNC ? -1` 命令，表示首次同步 |
| 2 | 主节点 | 检测到无法进行增量同步，执行 `BGSAVE` 生成 RDB 快照 |
| 3 | 主节点 | 向从节点发送 `+FULLRESYNC <replid> <offset>` 响应 |
| 4 | 主节点 | 将 RDB 文件以二进制流方式发送给从节点 |
| 5 | 从节点 | 接收 RDB 文件，清空自身数据，加载 RDB 到内存 |
| 6 | 主节点 | 发送 RDB 文件过程中产生的增量写命令（从 backlog 获取） |
| 7 | 从节点 | 更新自身的 `replid` 和 `offset`，进入增量同步模式 |

#### 2.2.3 增量复制流程

当从节点与主节点断开连接后重新连接，如果断连时间不长（offset 仍在 backlog 范围内），则可以使用增量复制（Partial Resynchronization），避免重新加载全量数据。

```
从节点 (Slave)                              主节点 (Master)
    │                                          │
    │  1. PSYNC replid offset ─────────────►   │
    │     带上自己的 replid 和 offset           │
    │     (上次同步到的位置)                    │
    │                                          │
    │                              2. 检查 backlog
    │                              offset 是否在 backlog 中？
    │                              ┌────────────────────┐
    │                              │ backlog 环形缓冲区 │
    │                              │ [90...100...110...] │
    │                              └────────────────────┘
    │                                          │
    │                              ┌───YES─────┴────NO───┐
    │                              ▼                      ▼
    │               3a. +CONTINUE             3b. +FULLRESYNC
    │                  (增量同步)                 (全量同步)
    │                              │              │
    │               4a. 发送缺失的写命令       4b. 走全量复制流程
    │                  (从 backlog 中读取)
    │                              │
    │               5a. 更新 offset             │
    │                  同步完成                 │
    │                                          │
```

**增量复制的关键条件**：
- 从节点的 `replid` 与主节点的 `replid` 一致
- 从节点的 `offset` 在主节点的 `replication backlog` 范围内

#### 2.2.4 PSYNC 命令与断点续传

PSYNC（Partial Sync）是 Redis 2.8 引入的同步命令，替代了旧版的 `SYNC` 命令。`PSYNC` 支持断点续传，是实现高效主从同步的核心。

```redis
# 从节点向主节点发送同步请求
PSYNC <replid> <offset>

# 首次同步（不知道 replid 和 offset）
PSYNC ? -1

# 增量同步（已知 replid 和 offset）
PSYNC abc123def456... 12345
```

**PSYNC 返回值**：

| 响应 | 含义 | 后续操作 |
|------|------|---------|
| `+FULLRESYNC <replid> <offset>` | 需要全量同步 | 接收 RDB 文件 + 增量命令 |
| `+CONTINUE` | 增量同步成功 | 直接接收增量写命令 |
| `-ERR` | 协议错误 | 从节点重新发起同步 |

**replication backlog（复制积压缓冲区）**：

replication backlog 是一个固定大小的环形缓冲区，用于缓存最近的写命令，供从节点进行增量同步。

```
┌─────────────────────────────────────────────────────────┐
│              Replication Backlog (环形缓冲区)            │
│  大小由 repl-backlog-size 参数控制（默认 1MB）           │
├─────────────────────────────────────────────────────────┤
│  ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐    │
│  │...│cmd│cmd│cmd│cmd│cmd│cmd│cmd│cmd│cmd│cmd│...│    │
│  └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘    │
│     ↑ 写入指针 (主节点写命令时移动)          ↑ 读取指针   │
│     (覆盖最旧的数据)                         (从节点同步) │
└─────────────────────────────────────────────────────────┘
```

**backlog 大小计算建议**：

```
backlog 大小 = 主从断连最大时间 × 主节点每秒写命令数

示例：
  主从最大断连时间：60 秒
  主节点每秒写命令数：1000 条
  每条命令平均大小：100 字节
  → backlog-size = 60 × 1000 × 100 = 6MB

redis.conf 配置：
  repl-backlog-size 67108864   # 64MB
```

### 2.3 主从配置

#### 2.3.1 主节点配置

```redis
# redis.conf - 主节点配置

# 绑定地址
bind 0.0.0.0

# 端口
port 6379

# 开启持久化（推荐使用 RDB + AOF 混合）
save 900 1
save 300 10
save 60 10000

# 主节点密码（可选，用于从节点连接认证）
requirepass "master_password"

# 主节点用于复制的密码（与 requirepass 相同或独立设置）
masterauth "master_password"

# 复制 backlog 大小
repl-backlog-size 67108864

# 当主节点的从节点数量少于此值时，停止接受写请求
# 用于保证数据安全，防止主节点在无从节点时继续接受写入
min-replicas-to-write 1
min-replicas-max-lag 10

# 主从心跳间隔
repl-ping-replica-period 10
```

#### 2.3.2 从节点配置

```redis
# redis.conf - 从节点配置

# 绑定地址
bind 0.0.0.0

# 端口（每个节点使用不同端口）
port 6380

# 设置当前节点为从节点，指向主节点
# 方式一：配置文件中设置
replicaof 192.168.1.100 6379

# 方式二：运行时命令（Redis 5.0+，替代 slaveof）
# replicaof 192.168.1.100 6379

# 主节点的认证密码
masterauth "master_password"

# 从节点设置为只读模式（默认开启，防止误写）
replica-read-only yes

# 从节点的密码（供客户端连接从节点时使用）
requirepass "slave_password"

# 复制 backlog 大小（从节点断连重连时也需要）
repl-backlog-size 67108864

# 是否允许从节点在主节点宕机时继续服务
replica-serve-stale-data yes

# 当从节点与主节点断开时，是否让从节点保持只读
replica-read-only yes

# 从节点优先级（用于哨兵选举新主节点，数值越小优先级越高）
# 哨兵选择新主节点时会优先选择较小优先级的从节点
replica-priority 100
```

#### 2.3.3 主从配置命令

```redis
# 在从节点上动态设置主节点
replicaof 192.168.1.100 6379

# 取消复制（使从节点变为独立节点）
replicaof no one

# 动态修改主节点密码
config set masterauth "new_password"

# 查看复制信息
info replication

# 在主节点上查看从节点连接状态
info replication
# 输出示例：
# role:master
# connected_slaves:2
# slave0:ip=192.168.1.101,port=6379,state=online,offset=2341,lag=0
# slave1:ip=192.168.1.102,port=6379,state=online,offset=2341,lag=1

# 在从节点上查看同步状态
info replication
# 输出示例：
# role:slave
# master_host:192.168.1.100
# master_port:6379
# master_link_status:up
# master_last_io_seconds_ago:1
# master_sync_in_progress:0
# master_repl_offset:2341
```

### 2.4 主从延迟分析

主从延迟是指从节点的数据与主节点之间的时间差。

#### 2.4.1 延迟产生的原因

| 原因 | 说明 | 解决方案 |
|------|------|---------|
| **主节点写入压力大** | 主节点有大量写入，命令产生速度超过从节点消费速度 | 优化写入模式、使用 Pipeline |
| **从节点硬件差异** | 从节点 CPU/内存/磁盘性能较弱 | 使用与主节点相同等级的硬件 |
| **从节点负载过高** | 从节点上有大量查询或计算任务 | 读写分离、限制从节点负载 |
| **网络带宽/延迟** | 主从之间网络不稳定或带宽不足 | 优化网络、使用内网直连 |
| **大命令阻塞** | 单个命令涉及大量数据（如 `KEYS *`、大 `SETEX`） | 避免大命令、使用增量操作 |
| **RDB 保存阻塞** | 主节点 fork 子进程保存 RDB 时阻塞 | 使用 `BGSAVE`、开启 AOF |

#### 2.4.2 监控主从延迟

```redis
# 方法一：通过 INFO replication 查看
info replication
# 关注字段：
# master_link_status        连接状态（up/down）
# master_last_io_seconds_ago  距离上次收到主节点数据的秒数
# master_sync_in_progress  是否正在进行全量同步

# 方法二：通过 repl-monitor 命令（需要从节点开启 repl-backlog）
# Redis 没有直接的延迟监控命令，但可以通过以下方式计算：
# 1. 监控从节点的 master_repl_offset
# 2. 监控主节点的 offset
# 3. 计算差值

# 方法三：使用 redis-cli --stat 实时监控
redis-cli --stat -h <master_ip> -p 6379

# 方法四：编写监控脚本
# 主节点获取当前 replication offset
redis-cli -h master_ip -p 6379 info replication | grep offset
# 从节点获取当前同步到的 offset
redis-cli -h slave_ip -p 6379 info replication | grep offset
```

#### 2.4.3 延迟优化策略

1. **硬件对等**：从节点硬件配置不低于主节点
2. **网络优化**：主从部署在同一机房/可用区，使用低延迟网络
3. **避免大命令**：将大操作拆分为小操作，使用 `HSCAN`、`SSCAN` 等迭代命令
4. **读写分离**：将读请求分发到多个从节点，降低单个从节点负载
5. **关闭不必要的持久化**：从节点可以关闭 RDB，使用 AOF（或关闭持久化）
6. **调整复制参数**：适当增大 `repl-backlog-size`，减少全量同步频率

### 2.5 主从复制的应用

#### 2.5.1 读写分离

```
         ┌──────────────┐
         │   客户端      │
         └──────┬───────┘
                │
         ┌──────▼───────┐
         │  读写分离    │
         │  中间件/SDK  │
         └──┬───────┬───┘
            │       │
  写请求 ←──┘       └──→ 读请求
            │       │
            ▼       ▼
      ┌──────────┐  ┌──────────┐
      │  主节点   │  │  从节点   │
      │ (Master) │  │ (Slave)  │
      └──────────┘  └──────────┘
                           │
                           ▼
                     ┌──────────┐
                     │  从节点2  │
                     └──────────┘
```

**读写分离实现方式**：

1. **应用层实现**：在代码中根据操作类型选择主节点或从节点
2. **中间件实现**：使用 Twemproxy、Redis Cluster Proxy 等
3. **客户端 SDK 实现**：部分 Redis 客户端支持读写分离

# 备份 RDB 文件

## 三、哨兵模式（Sentinel）

### 3.1 哨兵角色

哨兵（Sentinel）是 Redis 的高可用管理组件，它本身也是一个特殊的 Redis 进程，专门用于监控主从集群并实现自动故障转移。

```
┌─────────────────────────────────────────────────────────────────────┐
│                        哨兵模式架构                                  │
│                                                                     │
│  ┌──────────┐     ┌──────────┐     ┌──────────┐                    │
│  │ 主节点    │────►│ 从节点    │────►│ 从节点    │                    │
│  │ (Master) │     │ (Slave1) │     │ (Slave2) │                    │
│  └────┬─────┘     └────┬─────┘     └────┬─────┘                    │
│       │                │                │                           │
│       │   监控（每10秒 PING）          监控                        │
│       │                │                │                           │
│       ▼                ▼                ▼                           │
│  ┌─────────────────────────────────────────────────────┐           │
│  │                  哨兵集群 (Sentinel)                  │           │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐          │           │
│  │  │  哨兵1    │  │  哨兵2    │  │  哨兵3    │          │           │
│  │  │(监控+投票)│  │(监控+投票)│  │(监控+投票)│          │           │
│  │  └──────────┘  └──────────┘  └──────────┘          │           │
│  │                                                     │           │
│  │  四大功能:                                           │           │
│  │  1. 监控 (Monitoring)                                │           │
│  │  2. 提醒 (Notification)                              │           │
│  │  3. 自动故障转移 (Failover)                          │           │
│  │  4. 配置提供者 (Configuration Provider)              │           │
│  └─────────────────────────────────────────────────────┘           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 3.1.1 监控（Monitoring）

哨兵以固定频率（默认 10 秒）向所有主从节点发送 `PING` 命令，检测节点是否存活。

```
哨兵 ──PING──► 主节点    →  PONG (在线)
哨兵 ──PING──► 从节点1   →  PONG (在线)
哨兵 ──PING──► 从节点2   →  超时无响应 → 主观下线
```

#### 3.1.2 提醒（Notification）

当节点出现问题时，哨兵可以通过以下方式发送通知：

- 调用用户自定义的脚本（`sentinel notification-script`）
- 向管理员发送邮件、短信等
- 发送 Webhook 通知

```redis
# sentinel.conf - 配置通知脚本
sentinel notification-script mymaster /path/to/notify.sh
```

```bash
#!/bin/bash
# /path/to/notify.sh
# 脚本参数: <事件类型> <角色> <节点名> <节点地址> <节点端口>
EVENT=$1
ROLE=$2
NAME=$3
ADDR=$4
PORT=$5

# 发送邮件通知
echo "Redis Sentinel Alert: $EVENT $ROLE $NAME $ADDR:$PORT" | mail -s "Redis Alert" admin@example.com
```

#### 3.1.3 自动故障转移（Failover）

当主节点发生故障时，哨兵自动执行故障转移流程：
1. 检测主节点故障（主观下线 → 客观下线）
2. 在从节点中选举新的主节点
3. 将其他从节点指向新的主节点
4. 通知所有客户端新的主节点地址

#### 3.1.4 配置提供者（Configuration Provider）

哨兵作为配置提供者，为客户端提供当前主节点的地址信息。客户端可以通过哨兵来发现主节点，实现透明故障转移。

```
客户端 → 查询主节点地址 → 哨兵集群
                           │
                           ▼
                     返回当前主节点 IP:Port
                           │
                           ▼
                     客户端连接新的主节点
```

### 3.2 哨兵配置

#### 3.2.1 哨兵配置文件（sentinel.conf）

```redis
# sentinel.conf - 哨兵节点配置

# 监听端口
port 26379

# 绑定地址
bind 0.0.0.0

# 后台运行
daemonize yes

# 工作目录
dir /var/log/redis-sentinel

# 日志文件
logfile /var/log/redis-sentinel/sentinel.log

# 哨兵进程 ID 文件
pidfile /var/run/redis-sentinel.pid

# ========== 核心配置 ==========

# 定义主从集群的名称（mymaster 是集群别名）
# 参数: <集群名> <主节点IP> <主节点端口> <法定人数>
# 法定人数: 判定主节点下线所需的最少哨兵数量
sentinel monitor mymaster 127.0.0.1 6379 2

# 判定主观下线的超时时间（毫秒）
# 如果哨兵在此时间内没有收到节点的有效回复，判定为主观下线
sentinel down-after-milliseconds mymaster 5000

# 故障转移时，允许同时从新主节点同步的从节点数量
# 设置为 1 可以确保只有一个从节点同步，避免主节点压力过大
sentinel parallel-syncs mymaster 1

# 故障转移超时时间（毫秒）
# 从开始故障转移到完成的最大时间
sentinel failover-timeout mymaster 60000

# 主节点的认证密码（如果主节点配置了 requirepass）
sentinel auth-pass mymaster master_password

# ========== 高级配置 ==========

# 哨兵之间通信的密码（集群中所有哨兵需相同）
# requirepass "sentinel_password"

# 哨兵运行 ID（自动生成，无需手动配置）
# sentinel run-id <auto-generated>

# 开启 TILT 模式保护
# 当哨兵检测到自身环境异常时，进入 TILT 模式，暂停故障转移
sentinel deny-scripts-reconfig yes

# TILT 模式触发条件：
# 1. 系统时钟发生跳变
# 2. 哨兵进程被长时间阻塞（超过 2 秒）
```

#### 3.2.2 关键参数详解

| 参数 | 说明 | 默认值 | 调优建议 |
|------|------|--------|---------|
| `sentinel monitor` | 监控的主从集群及法定人数 | - | 法定人数设为 `哨兵数/2 + 1` |
| `down-after-milliseconds` | 主观下线超时时间 | 30000ms | 网络稳定时设 5000，不稳定时设 10000 |
| `parallel-syncs` | 故障转移时并行同步的从节点数 | 1 | 保持 1，避免新主压力过大 |
| `failover-timeout` | 故障转移最大耗时 | 60000ms | 根据网络和节点性能调整 |
| `auth-pass` | 主节点认证密码 | - | 与主节点 requirepass 一致 |

### 3.3 故障转移流程

#### 3.3.1 主观下线（Subjectively Down）

当一个哨兵在 `down-after-milliseconds` 时间内无法收到节点的有效回复（PING 命令的 PONG 响应）时，该哨兵判定此节点为**主观下线（SDOWN）**。

```
时间线:
t=0s    哨兵 ──PING──► 主节点
t=5s    哨兵 ──PING──► 主节点     (无响应)
t=10s   哨兵 ──PING──► 主节点    (无响应)
...
t=Ns    哨兵判定主节点为 SDOWN（主观下线）
        但此时还不能触发故障转移！
```

**主观下线的特点**：
- 是单个哨兵的本地判断
- 可能因为网络分区导致误判
- 需要其他哨兵的确认才能升级为客观下线

#### 3.3.2 客观下线（Objectively Down）

当有超过 `quorum`（法定人数）个哨兵都判定主节点为 SDOWN 时，主节点被判定为**客观下线（ODOWN）**。

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│  哨兵1    │     │  哨兵2    │     │  哨兵3    │
│ 监控主节点 │     │ 监控主节点 │     │ 监控主节点 │
└────┬─────┘     └────┬─────┘     └────┬─────┘
     │                │                │
     │ 判定 SDOWN     │ 判定 SDOWN     │ 正常
     │                │                │
     └────────────────┼────────────────┘
                      │
                      │ 法定人数 = 2
                      │ 已有 2 个哨兵判定 SDOWN
                      ▼
               ┌──────────────┐
               │ 主节点 ODOWN  │  ← 客观下线
               └──────────────┘
```

**客观下线的特点**：
- 需要法定数量的哨兵达成共识
- 是全局判断，所有哨兵都知晓
- 可以触发故障转移流程

#### 3.3.3 选举新主节点

故障转移的核心是在多个从节点中选举一个最优的新主节点。这个过程涉及 Raft 协议的领导者选举机制。

```
客观下线主节点后:
┌──────────┐     ┌──────────┐     ┌──────────┐
│  哨兵1    │     │  哨兵2    │     │  哨兵3    │
│ (Leader) │     │  (Follower)│    │  (Follower)│
└────┬─────┘     └──────────┘     └──────────┘
     │
     │ 选举 Leader 哨兵
     │ 选择一个哨兵作为故障转移的领导者
     │
     ▼
┌──────────┐     ┌──────────┐     ┌──────────┐
│  从节点1  │     │  从节点2  │     │  从节点3  │
│ priority │     │ priority │     │ priority │
│   100    │     │   200    │     │   300    │
└────┬─────┘     └────┬─────┘     └────┬─────┘
     │                │                │
     │  筛选候选从节点:
     │  1. 排除已经下线或断线的
     │  2. 排除处于全量同步中的
     │  3. 排除优先级为 0 的（不可作为主节点）
     │
     │  排序规则:
     │  1. 优先级越小越优先
     │  2. 复制 offset 越大越优先（数据最新）
     │  3. run_id 越小越优先
     │
     ▼
┌──────────┐
│ 新主节点  │ ← 选举出的最优从节点
└──────────┘
```

**选举算法详解**：

```
排序步骤:
1. 过滤:
   - 移除已断开的从节点
   - 移除正在进行全量同步的从节点
   - 移除 replica-priority = 0 的从节点
   - 移除与主节点断连的从节点

2. 排序（依次比较）:
   a. replica-priority 越小越优先
   b. replication offset 越大越优先（数据最新）
   c. 运行 ID 越小越优先

示例:
   从节点A: priority=100, offset=50000
   从节点B: priority=100, offset=49000
   从节点C: priority=200, offset=50000

   排序结果: A > B > C
   (A 与 B 优先级相同，A 的 offset 更大)
```

#### 3.3.4 通知从节点并完成故障转移

```
Leader 哨兵完成选举后:
1. 将新主节点升级为 Master
   - 执行 SLAVEOF NO ONE（或 REPLICAOF NO ONE）
   - 取消只读模式

2. 将其他从节点指向新主节点
   - 执行 SLAVEOF <new_master_ip> <new_master_port>

3. 通知所有哨兵更新主节点信息
   - 哨兵集群更新自身的主节点记录

4. 故障转移完成
```

### 3.4 Raft 协议与领导者选举

Redis 哨兵集群使用 Raft 协议的变种来实现领导者选举。

#### 3.4.1 Raft 协议基础

Raft 是一种为了理解而设计的分布式一致性协议，它将分布式问题分解为三个子问题：

1. **领导者选举（Leader Election）**：集群中选出唯一的领导者
2. **日志复制（Log Replication）**：领导者接收客户端请求并复制到其他节点
3. **安全性（Safety）**：确保只有获得多数投票的节点才能成为领导者

#### 3.4.2 哨兵中的 Raft 选举

```
哨兵集群选举 Leader 过程:

┌──────────┐  超时  ┌──────────┐
│  哨兵1    │───────►│  哨兵1    │
│ (Follower)│        │ (Candidate)│
└────┬─────┘        └────┬─────┘
     │                    │
     │ 发起投票请求        │ 发送 RequestVote
     │ 自增 term          │ 请求其他哨兵投票
     │                    │
     ▼                    ▼
┌──────────┐           ┌──────────┐
│  哨兵2    │──同意────│  哨兵2    │
│ (Follower)│          │ (Follower)│
└──────────┘           └──────────┘

     哨兵1 获得多数票 → 成为 Leader
     开始执行故障转移流程
```

**关键规则**：
- 任何时刻只有一个 Leader
- Leader 必须获得多数节点（`N/2 + 1`）的投票
- 每次选举都有超时机制，避免无限等待
- 网络分区时，只有包含多数节点的分区才能选出 Leader

### 3.5 哨兵集群部署

#### 3.5.1 部署奇数个哨兵

哨兵集群应该部署**奇数个节点**（3、5、7），原因：

- **脑裂防护**：需要获得多数节点同意才能执行故障转移
- **容错能力**：3 节点允许 1 个节点故障，5 节点允许 2 个节点故障
- **避免平票**：偶数个节点可能出现票数相同的情况

```
┌──────────────────────────────────────────────────────────┐
│  3 哨兵集群 (容忍 1 个节点故障)                            │
│  ┌──────────┐                                              │
│  │  哨兵1    │ ─┐                                          │
│  └──────────┘   │ 多数派 = 2                               │
│  ┌──────────┐   ├─► 可以执行故障转移                       │
│  │  哨兵2    │ ─┤                                          │
│  └──────────┘   │                                          │
│  ┌──────────┘   │                                          │
│  │  哨兵3    │ ─┘                                          │
│  └──────────┘                                              │
└──────────────────────────────────────────────────────────┘
```

#### 3.5.2 三哨兵架构搭建实战

```bash
# ========== 环境准备 ==========
# 假设 3 台服务器:
# 192.168.1.100 - 主节点 (Master) + 哨兵1
# 192.168.1.101 - 从节点 (Slave1) + 哨兵2
# 192.168.1.102 - 从节点 (Slave2) + 哨兵3

# ========== 步骤一：部署主从集群 ==========

# 在 192.168.1.100 上配置主节点
cat > /etc/redis/redis-master.conf << 'EOF'
bind 0.0.0.0
port 6379
requirepass "master_password"
masterauth "master_password"
repl-backlog-size 67108864
min-replicas-to-write 1
min-replicas-max-lag 10
save 900 1
save 300 10
save 60 10000
dir /var/lib/redis
dbfilename dump-master.rdb
EOF

# 启动主节点
redis-server /etc/redis/redis-master.conf

# 在 192.168.1.101 上配置从节点1
cat > /etc/redis/redis-slave1.conf << 'EOF'
bind 0.0.0.0
port 6379
replicaof 192.168.1.100 6379
masterauth "master_password"
replica-read-only yes
requirepass "slave_password"
replica-priority 100
repl-backlog-size 67108864
dir /var/lib/redis
dbfilename dump-slave1.rdb
EOF

# 启动从节点1
redis-server /etc/redis/redis-slave1.conf

# 在 192.168.1.102 上配置从节点2
cat > /etc/redis/redis-slave2.conf << 'EOF'
bind 0.0.0.0
port 6379
replicaof 192.168.1.100 6379
masterauth "master_password"
replica-read-only yes
requirepass "slave_password"
replica-priority 200
repl-backlog-size 67108864
dir /var/lib/redis
dbfilename dump-slave2.rdb
EOF

# 启动从节点2
redis-server /etc/redis/redis-slave2.conf

# ========== 步骤二：部署哨兵集群 ==========

# 在 192.168.1.100 上配置哨兵1
cat > /etc/redis/sentinel.conf << 'EOF'
port 26379
bind 0.0.0.0
daemonize yes
dir /var/log/redis-sentinel
logfile /var/log/redis-sentinel/sentinel.log
pidfile /var/run/redis-sentinel.pid

sentinel monitor mymaster 192.168.1.100 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
sentinel auth-pass mymaster master_password
EOF

# 启动哨兵1
redis-server /etc/redis/sentinel.conf --sentinel

# 在 192.168.1.101 上配置哨兵2（配置相同）
# ... (同上，只需放在不同服务器)

# 在 192.168.1.102 上配置哨兵3（配置相同）
# ... (同上，只需放在不同服务器)

# ========== 步骤三：验证集群 ==========

# 查看主从信息
redis-cli -h 192.168.1.100 -p 6379 -a master_password info replication

# 查看哨兵状态
redis-cli -h 192.168.1.100 -p 26379 sentinel master mymaster
redis-cli -h 192.168.1.100 -p 26379 sentinel slaves mymaster
redis-cli -h 192.168.1.100 -p 26379 sentinel sentinels mymaster

# 模拟主节点故障
redis-cli -h 192.168.1.100 -p 6379 -a master_password SHUTDOWN

# 等待故障转移完成（约 10-30 秒）
redis-cli -h 192.168.1.101 -p 26379 sentinel get-master-addr-by-name mymaster
# 返回新主节点的 IP:Port

# ========== 步骤四：客户端集成 ==========

# 客户端连接哨兵查询主节点地址
redis-cli -h 192.168.1.100 -p 26379 sentinel get-master-addr-by-name mymaster
# 输出:
# 1) "192.168.1.101"
# 2) "6379"

# Java 客户端示例 (Jedis)
JedisSentinelPool pool = new JedisSentinelPool(
    "mymaster",                        // 主从集群名称
    new HashSet<>(Arrays.asList(        // 哨兵地址集合
        "192.168.1.100:26379",
        "192.168.1.101:26379",
        "192.168.1.102:26379"
    )),
    new JedisPoolConfig(),
    "master_password"                   // 主节点密码
);

Jedis jedis = pool.getResource();
jedis.set("key", "value");
```

### 3.6 哨兵常用命令

```redis
# 集群信息查询
sentinel master <master_name>         # 查看主节点信息
sentinel slaves <master_name>         # 查看所有从节点信息
sentinel sentinels <master_name>       # 查看所有哨兵信息
sentinel get-master-addr-by-name <name>  # 获取主节点地址

# 故障转移管理
sentinel failover <master_name>       # 手动触发故障转移
sentinel ckquorum <master_name>       # 检查当前哨兵集群是否可以执行故障转移
sentinel flushconfig                  # 强制刷新配置文件

# 动态配置
sentinel set <master_name> <option> <value>  # 动态修改哨兵配置

# 强制重新加载主节点配置
sentinel reset <pattern>              # 重置匹配的主节点
```

## 四、集群模式（Cluster）

### 4.1 集群架构

Redis 集群模式是 Redis 官方提供的分布式集群方案，它通过**哈希槽（Hash Slot）**将数据分布到多个主节点上，实现了横向扩展和高可用。

```
┌─────────────────────────────────────────────────────────────────────┐
│                        Redis Cluster 架构                            │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ┌──────────┐  Gossip  ┌──────────┐  Gossip  ┌──────────┐          │
│  │  主节点1  │◄────────►│  主节点2  │◄────────►│  主节点3  │          │
│  │ (Master) │          │ (Master) │          │ (Master) │          │
│  │          │          │          │          │          │          │
│  │ Slot:   │          │ Slot:   │          │ Slot:   │          │
│  │ 0-5460  │          │ 5461-10922│         │ 10923-16383│         │
│  └────┬─────┘          └────┬─────┘          └────┬─────┘          │
│       │                     │                     │                │
│       │ 复制                │ 复制                │ 复制            │
│       ▼                     ▼                     ▼                │
│  ┌──────────┐          ┌──────────┐          ┌──────────┐          │
│  │  从节点1  │          │  从节点2  │          │  从节点3  │          │
│  │ (Slave)  │          │ (Slave)  │          │ (Slave)  │          │
│  └──────────┘          └──────────┘          └──────────┘          │
│                                                                     │
│  客户端：需连接任意节点，通过 MOVED/ASK 重定向定位正确的主节点       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 哈希槽（Hash Slot）原理

#### 4.2.1 16384 个哈希槽

Redis Cluster 将整个键空间划分为 **16384 个哈希槽（Slot）**，每个主节点负责一部分槽。

```
哈希槽分布:
┌─────────────────────────────────────────────────────────────┐
│  Slot 0 ───────────────────────────────────── Slot 16383    │
│  │                                                           │
│  ├─ 主节点1 (Slot 0-5460)                                    │
│  ├─ 主节点2 (Slot 5461-10922)                               │
│  └─ 主节点3 (Slot 10923-16383)                              │
└─────────────────────────────────────────────────────────────┘

计算键的哈希槽:
  slot = CRC16(key) % 16384

示例:
  key = "user:1001"
  CRC16("user:1001") = 12345
  slot = 12345 % 16384 = 12345
  → 该 key 属于主节点3 (Slot 10923-16383)
```

#### 4.2.2 CRC16 算法

Redis 使用 CRC16 校验和算法来计算键的哈希槽。CRC16 是一种 16 位的循环冗余校验算法。

```
CRC16 多项式: x^16 + x^12 + x^5 + 1 (0x11021)

Redis CRC16 实现（C 语言）:
unsigned int CRC16(const unsigned char *data, int len) {
    unsigned int crc = 0;
    while (len--) {
        crc = (crc << 8) ^ crc16tab[(crc >> 8) ^ *data++];
    }
    return crc;
}

// 预计算的 CRC16 查找表（256 项）
static const unsigned int crc16tab[256] = {
    0x0000, 0x1021, 0x2042, 0x3063, 0x4084, 0x50a5, ...
};
```

#### 4.2.3 哈希标签（Hash Tag）

为了支持将多个键分组到同一个槽（例如实现多键事务），Redis 引入了**哈希标签**机制。

```
规则:
  如果 key 中包含 "{" 和 "}"，并且 "{" 后面紧跟着 "}"，
  则只计算 "{" 和 "}" 之间的部分作为哈希值

示例:
  {user}:1001 → 只对 "user" 计算 CRC16
  {user}:1002 → 只对 "user" 计算 CRC16
  → 两个 key 在同一个槽中！

  user:1001    → 对整个 "user:1001" 计算 CRC16
  user:1002    → 对整个 "user:1002" 计算 CRC16
  → 两个 key 可能不在同一个槽中！
```

**哈希标签的应用场景**：

- **多键操作**：`MGET`、`MSET`、`SUNION` 等多键命令要求所有键在同一槽
- **分布式事务**：`MULTI/EXEC`、`WATCH` 等事务操作要求所有键在同一槽
- **Lua 脚本**：`EVAL`、`EVALSHA` 要求所有键在同一槽
- **Hash 结构分片**：将一个大 Hash 的多个字段分布到不同槽

### 4.3 Gossip 协议（集群节点通信）

Redis Cluster 节点之间通过 **Gossip 协议**进行通信，每个节点周期性地与其他节点交换集群状态信息。

#### 4.3.1 Gossip 基本原理

Gossip 协议是一种去中心化的通信协议，信息以类似"谣言传播"的方式在节点间扩散。

```
Gossip 传播过程:
时间 t=0:
┌──────────┐
│  节点A    │  知道事件 X
└────┬─────┘
     │ 随机选择节点 B 交换信息
     ▼
时间 t=1:
┌──────────┐     ┌──────────┐
│  节点A    │     │  节点B    │  也知道事件 X
└────┬─────┘     └────┬─────┘
     │                │
     │ 随机选择节点   │ 随机选择节点
     ▼                ▼
时间 t=2:
┌──────────┐  ┌──────────┐  ┌──────────┐
│  节点A    │  │  节点B    │  │  节点C    │  也知道事件 X
└──────────┘  └────┬─────┘  └──────────┘
                   │
                   │
                   ▼
时间 t=3:
            ┌──────────┐
            │  节点D    │  也知道事件 X
            └──────────┘

信息以 O(log N) 的速度在 N 个节点中传播
```

#### 4.3.2 Redis Gossip 的实现

Redis Cluster 使用 `CLUSTER MEET` 命令和 `Gossip` 消息来构建集群。

```
1. 节点 A 通过 CLUSTER MEET 加入节点 B:
   节点A ──CLUSTER MEET──► 节点B
   节点B 添加节点A 到 peers 列表

2. Gossip 消息交换:
   节点A ──PING/PONG──► 节点B
   （包含自身的集群信息和已知的其他节点信息）
   节点A ──PING/PONG──► 节点C
   ...

3. 集群信息扩散:
   每个节点维护一个完整的集群状态视图
   通过 Gossip 逐渐同步所有节点的状态
```

#### 4.3.3 Gossip 消息类型

| 消息类型 | 说明 |
|---------|------|
| `MEET` | 邀请新节点加入集群 |
| `PING` | 检测节点是否存活（包含集群状态摘要） |
| `PONG` | 对 PING 或 MEET 的响应 |
| `FAIL` | 广播某节点已下线 |

### 4.4 MOVED 与 ASK 重定向

当客户端发送命令到错误的节点（即键的哈希槽不在该节点上）时，Redis 会返回 `MOVED` 或 `ASK` 重定向指令。

#### 4.4.1 MOVED 重定向

```
客户端 ──SET key value──► 节点A (Slot 5000)
                         ↓
                    key = "user:1001"
                    slot = CRC16("user:1001") % 16384 = 12345
                    → 属于节点C (Slot 10923-16383)
                         ↓
                    节点A 返回:
                    -MOVED 12345 nodeC_ip:nodeC_port
                         ↓
                    客户端直接连接节点C，重新发送命令
```

**MOVED 的含义**：此槽已经完成迁移（或从未在此节点），客户端应该永久重定向到新节点。

#### 4.4.2 ASK 重定向

```
ASCK 与 MOVED 的区别:
┌─────────────────────────────────────────────────────────────┐
│  MOVED:                                                      │
│  此槽已经正式归属于其他节点，客户端应该永久更新路由表         │
│                                                             │
│  ASK:                                                       │
│  此槽正在迁移过程中，客户端应该临时转向另一个节点             │
│  迁移完成后会收到 MOVED 指令                                  │
└─────────────────────────────────────────────────────────────┘

客户端处理逻辑:
  收到 MOVED → 更新本地路由缓存，后续请求直接发送到新节点
  收到 ASK → 临时转向目标节点，但不更新路由缓存
```

#### 4.4.3 客户端处理流程

```
┌──────────────┐
│  客户端       │
└──────┬───────┘
       │
       │ 1. 发送命令到已知的任意节点
       ▼
┌──────────────┐     ┌──────────────┐
│   节点X       │────►│   节点X       │
└──────┬───────┘     └──────┬───────┘
       │                    │
  键在此节点？          键不在此节点
       │                    │
       ▼                    ▼
  执行命令            返回 MOVED/ASK
       │                    │
       │                    │
       ▼                    ▼
  返回结果            客户端解析响应
                            │
                     ┌──────┴──────┐
                     │             │
                     ▼             ▼
                  MOVED          ASK
                     │             │
                     ▼             ▼
              更新路由缓存    临时转发
                     │             │
                     ▼             ▼
              重发到正确节点  重发到目标节点
```

### 4.6 集群搭建

#### 4.6.1 创建集群

```bash

# 6 台服务器（3 主 3 从）:
# 192.168.1.100:6379 - 主节点1
# 192.168.1.101:6379 - 主节点2
# 192.168.1.102:6379 - 主节点3
# 192.168.1.103:6379 - 从节点1 (主节点1的从)
# 192.168.1.104:6379 - 从节点2 (主节点2的从)
# 192.168.1.105:6379 - 从节点3 (主节点3的从)

done

# 启动所有节点
redis-server /etc/redis/redis-100.conf

redis-server /etc/redis/redis-102.conf
redis-server /etc/redis/redis-103.conf
redis-server /etc/redis/redis-104.conf
redis-server /etc/redis/redis-105.conf

# ========== 步骤二：使用 redis-cli 创建集群 ==========

# Redis 5.0+ 推荐使用 redis-cli 创建集群
# create 命令自动分配哈希槽和主从关系
redis-cli --cluster create \
    192.168.1.100:6379 \
    192.168.1.101:6379 \
    192.168.1.102:6379 \
    192.168.1.103:6379 \
    192.168.1.104:6379 \
    192.168.1.105:6379 \

# 参数说明:
# --cluster-replicas 1  → 每个主节点分配 1 个从节点
# -a cluster_password    → 集群密码

# 输出示例:
# >>> Performing hash slot alignment...
# >>> Adding node 192.168.1.101:6379 to cluster
# >>> Adding node 192.168.1.102:6379 to cluster
# >>> Adding replica 192.168.1.103:6379 to 192.168.1.100:6379
# >>> Adding replica 192.168.1.104:6379 to 192.168.1.101:6379
# >>> Adding replica 192.168.1.105:6379 to 192.168.1.102:6379

# 查看哈希槽分配

# 测试数据操作

# ========== 步骤四：添加新节点 ==========

#### 4.6.2 哈希槽迁移

```
哈希槽迁移流程:
┌──────────┐     迁移槽     ┌──────────┐
│  源主节点  │──────────────►│  目标主节点 │
│ (Source)  │   数据同步     │  (Target) │
└──────────┘               └──────────┘

详细步骤:
1. 目标节点导入源节点:
   CLUSTER SET-CONFIG-EPOCH <epoch>
   CLUSTER SETSLOT <slot> NODE <target_node_id>

2. 源节点准备迁移:
   CLUSTER SETSLOT <slot> MIGRATING <target_node_id>

3. 目标节点准备接收:
   CLUSTER SETSLOT <slot> IMPORTING <source_node_id>

4. 迁移数据:
   在源节点上执行 CLUSTER GETKEYSINSLOT <slot> <count>
   然后使用 MIGRATE 命令迁移每个 key

5. 完成迁移:
   在源节点上: CLUSTER SETSLOT <slot> NODE <target_node_id>
   在目标节点上: CLUSTER SETSLOT <slot> NODE <target_node_id>

6. 所有节点更新配置:
   Gossip 协议传播新的槽分配信息
```

### 4.7 集群读写规则

#### 4.7.1 支持的命令

Redis Cluster 支持大部分 Redis 命令，但有一些限制：

```
支持的命令:
  单键命令: SET, GET, DEL, HSET, HGET, LPUSH, RPUSH, SADD, ZADD 等
  多键命令（同槽）: MGET, MSET, SUNION, SDIFF, ZUNION 等
  事务命令（同槽）: MULTI, EXEC, WATCH 等
  Lua 脚本（同槽）: EVAL, EVALSHA 等
  数据库命令: SELECT 不支持，只能使用 0 号数据库

不支持的命令:
  RANDOMKEY, KEYS, SCAN (部分支持)
  涉及多个槽的多键命令
  FLUSHALL, FLUSHDB
```

#### 4.7.2 多键命令的限制

```
规则: 所有多键命令的键必须在同一个哈希槽中

示例:
  MSET user:1001 "Alice" user:1002 "Bob"
  → 如果两个 key 在不同槽中，会报错:
    CROSSSLOT Keys in request don't hash to the same slot

  解决方案: 使用哈希标签
  MSET {user}:1001 "Alice" {user}:1002 "Bob"
  → 两个 key 都对 "user" 计算哈希，在同一槽中
```

### 4.8 集群 vs 哨兵对比

| 维度 | 哨兵模式 | 集群模式 |
|------|---------|---------|
| **数据分布** | 全量复制，所有节点数据相同 | 分片存储，16384 槽分散到多个主节点 |
| **写入能力** | 单个主节点写入 | 多个主节点并行写入 |
| **存储扩展** | 不支持，受单节点内存限制 | 支持，添加主节点扩展内存 |
| **故障转移** | 哨兵集群自动选举新主 | 各主节点通过 Gossip 自动故障转移 |
| **客户端** | 通过哨兵查询主节点地址 | 连接任意节点，通过 MOVED 重定向 |
| **多键操作** | 无限制 | 同槽限制（使用哈希标签解决） |
| **复杂度** | 较低 | 较高 |
| **典型场景** | 中小规模，单主架构 | 大规模，需要横向扩展 |

## 五、三种模式对比与选型建议

### 5.1 功能对比

| 维度 | 主从复制 | 哨兵模式 | 集群模式 |
|------|---------|---------|---------|
| **数据冗余** | ✅ 从节点备份 | ✅ 从节点备份 | ✅ 每个主节点有从节点 |
| **读写分离** | ✅ 手动实现 | ✅ 哨兵提供地址 | ✅ 自动路由 |
| **故障转移** | ❌ 手动 | ✅ 自动（Raft） | ✅ 自动（Gossip） |
| **横向扩展** | ❌ | ❌ | ✅ 分片存储 |
| **数据一致性** | 最终一致 | 最终一致 | 最终一致 |
| **脑裂防护** | ❌ | ✅ Raft 多数派 | ✅ Gossip 协议 |
| **运维复杂度** | 低 | 中 | 高 |

### 5.2 性能对比

| 维度 | 主从复制 | 哨兵模式 | 集群模式 |
|------|---------|---------|---------|
| **写入性能** | 单主节点瓶颈 | 单主节点瓶颈 | 多主节点并行，线性扩展 |
| **读取性能** | 可通过从节点扩展 | 可通过从节点扩展 | 每个主节点的从节点都可读取 |
| **数据容量** | 单节点内存上限 | 单节点内存上限 | 所有主节点内存之和 |
| **网络开销** | 主从复制流量 | 哨兵通信 + 主从复制 | Gossip 通信 + 主从复制 + 重定向 |

### 5.3 选型建议

#### 小型项目（QPS < 5000，数据 < 4GB）

```
推荐方案: 主从复制
架构: 1 主 + 2 从
优点: 简单、易维护、成本低
缺点: 无自动故障转移
```

#### 中型项目（QPS 5000-50000，数据 < 16GB）

```
推荐方案: 哨兵模式
架构: 1 主 + 2 从 + 3 哨兵
优点: 自动故障转移、读写分离
缺点: 单主瓶颈、无法横向扩展
```

#### 大型项目（QPS > 50000，数据 > 16GB）

```

## 七、常见面试题

### 7.1 主从复制相关

**Q1: Redis 主从复制的原理是什么？**

Redis 主从复制基于 `PSYNC` 命令实现：
1. 从节点连接主节点，发送 `PSYNC <replid> <offset>` 请求
2. 如果是首次同步，主节点执行 `BGSAVE` 生成 RDB，发送给从节点（全量同步）
3. 从节点接收 RDB 并加载到内存
4. 主节点发送 RDB 生成期间的增量写命令
5. 如果是重连且 offset 在 backlog 中，直接发送增量命令（增量同步）
6. 主节点持续将写命令传播给所有从节点

**Q2: 什么是 replication backlog？它的作用是什么？**

replication backlog 是主节点上的一个固定大小的环形缓冲区，用于缓存最近的写命令。它的作用是：
- 支持从节点的增量同步（断点续传）
- 从节点断开重连时，若 offset 仍在 backlog 范围内，可以直接同步增量命令，无需全量同步
- 避免频繁的全量同步对主节点性能的影响

**Q3: Redis 主从复制如何保证数据一致性？**

Redis 使用以下机制保证数据一致性：
1. **replication id + offset**：精确追踪每个从节点的同步进度
2. **PSYNC 协议**：支持断点续传，确保数据完整
3. **主从心跳**：定期检测主从连接状态
4. **半同步复制**（Redis 6.0+）：主节点等待从节点确认后再返回
5. **min-replicas-to-write**：当从节点数量不足时暂停写入

### 7.2 哨兵模式相关

**Q4: 哨兵如何判定主节点下线？**

哨兵将主节点下线分为两个阶段：
1. **主观下线（SDOWN）**：单个哨兵在 `down-after-milliseconds` 时间内未收到主节点的有效响应
2. **客观下线（ODOWN）**：超过法定数量（quorum）的哨兵都判定主节点为 SDOWN

只有达到客观下线，哨兵才能触发故障转移流程。

**Q5: 哨兵如何选举新的主节点？**

哨兵选举新主节点的规则：
1. 过滤已下线、全量同步中、优先级为 0 的从节点
2. 按照以下规则排序：
   - `replica-priority` 越小越优先
   - replication offset 越大越优先（数据最新）
   - 运行 ID 越小越优先
3. 选择排序最靠前的从节点作为新主节点

**Q6: 哨兵如何避免脑裂？**

哨兵通过 Raft 协议的多数派原则避免脑裂：
- 法定人数（quorum）= 哨兵数量 / 2 + 1
- 只有获得法定数量哨兵同意才能执行故障转移
- 网络分区时，只有包含多数派的分区才能选出新主节点
- 建议部署奇数个哨兵（3、5、7）

### 7.3 集群模式相关

**Q7: Redis Cluster 为什么使用 16384 个哈希槽？**

选择 16384（2^14）个哈希槽是在以下因素之间的权衡：
- **槽数量**：槽越多，数据分布越均匀，但每个槽的管理开销越大
- **网络通信**：Gossip 协议传播的信息与槽数量相关
- **迁移效率**：槽数量适中，单个槽迁移的数据量不会太大
- **实际考量**：16384 足以支撑大规模集群（数百个主节点）

**Q8: MOVED 和 ASK 重定向有什么区别？**

| 维度 | MOVED | ASK |
|------|-------|-----|
| **含义** | 槽已永久迁移到其他节点 | 槽正在迁移过程中 |
| **客户端行为** | 永久更新路由缓存 | 临时转发，不更新缓存 |
| **触发时机** | 槽迁移完成后 | 槽迁移进行中 |
| **后续请求** | 直接发送到新节点 | 仍然发送到原节点，原节点返回 ASK |

**Q9: 如何解决 Redis Cluster 的跨槽问题？**

有以下解决方案：
1. **哈希标签（Hash Tag）**：使用 `{tag}` 包裹需要在同一槽的 key
2. **合理设计 key**：在设计阶段就考虑 key 的分布
3. **使用 Lua 脚本**：在同一个 Lua 脚本中处理多个 key（同槽）
4. **客户端路由**：在客户端层面实现分库分表逻辑

**Q10: Redis Cluster 的故障转移是如何实现的？**

Redis Cluster 的故障转移基于 Gossip 协议：
1. 节点通过 Gossip 消息检测其他节点的状态
2. 当主节点失联超过 `cluster-node-timeout`，被标记为 PFAIL（可能下线）
3. 当超过半数主节点标记某节点为 PFAIL，该节点被标记为 FAIL（确定下线）
4. 从节点检测到主节点 FAIL 后，发起故障转移选举
5. 从节点通过 config epoch 竞争，获得投票的从节点升级为新主节点
6. 新主节点接管哈希槽，通知其他节点更新配置

### 7.4 综合对比

**Q11: 哨兵和集群模式如何选择？**

- 选择哨兵模式：
  - 数据量在单节点内存范围内
  - 主要痛点是高可用，而非扩展性
  - 业务对多键操作需求多（无跨槽限制）
  - 团队规模小，希望架构简单

- 选择集群模式：
  - 数据量超出单节点内存
  - 需要处理高并发写入
  - 需要横向扩展能力
  - 能够接受架构复杂度

**Q12: Redis 高可用方案有哪些常见坑？**

1. **主从复制延迟**：高负载下延迟可能很大，需要监控和优化
2. **哨兵法定人数设置**：过小可能导致误判，过大可能导致无法故障转移
3. **集群跨槽问题**：多键命令需要合理使用哈希标签
4. **持久化配置**：高可用架构中每个节点都要合理配置持久化
5. **网络分区**：需要设计合理的网络架构，减少分区风险
6. **从节点数量**：哨兵模式下从节点太多会影响主节点性能
7. **内存限制**：每个主节点的内存要合理规划

## 总结

Redis 高可用架构是构建稳定可靠的 Redis 服务的核心。从主从复制到哨兵模式，再到集群模式，每一步演进都在解决前一阶段的瓶颈：

1. **主从复制** 解决了数据冗余问题，但主节点仍是单点
2. **哨兵模式** 实现了自动故障转移，但无法横向扩展
3. **集群模式** 实现了横向扩展和高可用，但架构更复杂

在实际工作中，需要根据业务规模、数据量、团队能力等因素选择合适的方案。同时，需要关注以下要点：

- **监控告警**：建立完善的监控体系，及时发现和处理问题
- **定期演练**：定期进行故障转移演练，确保方案在真实故障中有效
- **容量规划**：根据业务增长规划集群容量，预留扩展空间
- **数据安全**：合理配置持久化和复制策略，确保数据不丢失

通过合理的架构设计和持续的运维优化，可以构建稳定、高效、可扩展的 Redis 高可用体系，为业务提供可靠的内存数据服务。
