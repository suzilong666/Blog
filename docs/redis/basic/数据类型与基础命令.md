# 数据类型与基础命令

## 一、Redis 数据类型总览

### 1.1 Redis 核心数据类型

Redis 提供了丰富的数据类型，每种类型都有其独特的底层实现和适用场景。熟练掌握这些数据类型是高效使用 Redis 的基础。

| 类型 | 英文名称 | 底层实现 | 说明 |
|------|---------|---------|------|
| String | 字符串 | SDS（简单动态字符串） | 最基础的类型，可存储字符串、整数、浮点数、二进制数据 |
| Hash | 哈希 | ziplist / hashtable | 键值对集合，适合存储对象 |
| List | 列表 | ziplist / linkedlist | 有序字符串列表，支持从两端推入和弹出 |
| Set | 集合 | intset / hashtable | 无序不重复字符串集合，支持集合运算 |
| ZSet | 有序集合 | ziplist / skiplist+hashtable | 每个元素关联一个分数，按分数排序 |
| HyperLogLog | 超日志 | 概率数据结构 | 用于基数统计，精度约 0.81% |
| Bitmap | 位图 | 位数组 | 按位操作，节省空间 |
| Geo | 地理坐标 | Sorted Set | 存储地理位置并进行距离计算 |
| Stream | 流 | 类 Kafka 日志 | 消息队列，支持消费者组 |

### 1.2 各类型使用场景概览

| 类型 | 典型应用场景 |
|------|-------------|
| String | 缓存、计数器、分布式锁、共享 Session |
| Hash | 用户信息、商品属性、配置缓存 |
| List | 消息队列、最新消息排行、时间线 |
| Set | 标签系统、共同好友、去重 |
| ZSet | 排行榜、评分系统、延迟队列 |
| HyperLogLog | UV 统计、独立访客计数 |
| Bitmap | 签到打卡、在线状态、用户活跃标记 |
| Geo | 附近的人、地理位置搜索 |
| Stream | 消息队列、事件溯源、实时数据流 |

### 1.3 Redis 键的命名规范

在学习各种数据类型之前，先了解 Redis 键的命名规范：

```redis
// 推荐使用 "业务:对象:唯一标识" 的格式
SET user:1001:name "张三"
SET product:2001:price 99.9
SET order:3001:status "paid"

// 使用冒号分隔符（也可用其他分隔符，如 "."、"-"）
SET user:1001:profile '{"name":"张三","age":25}'

// 键名大小写敏感
SET User:1001 "value1"
SET user:1001 "value2"
GET User:1001  // "value1"
GET user:1001   // "value2"
```

**键的命名建议**：
- 具有可读性：`user:1001:name` 比 `u1001n` 更好
- 控制长度：过长的键名会消耗内存
- 保持一致性：在整个项目中使用统一的命名格式
- 避免特殊字符：尽量使用字母、数字和分隔符

## 二、String 类型

### 2.1 底层实现（SDS 字符串）

Redis 的 String 类型底层使用 **SDS（Simple Dynamic String）** 实现，而非 C 语言原生字符串。

**C 字符串的问题**：
- 获取字符串长度需要遍历，时间复杂度为 O(N)
- 二进制不安全，遇到 `\0` 会被截断
- 缓冲区溢出风险，修改字符串前需要手动分配内存

**SDS 的结构**：

```
┌──────────────┬──────────────┬──────────────┬──────────────┬─────────────────────┐
│  free (len)   │  len (len)   │  flags (1)   │  buf[]       │  '\0' 终止符        │
└──────────────┴──────────────┴──────────────┴──────────────┴─────────────────────┘
```

- `free`：已分配但未使用的字节数
- `len`：字符串实际长度
- `flags`：SDS 类型标识（SDS_TYPE_5、SDS_TYPE_8、SDS_TYPE_16、SDS_TYPE_32、SDS_TYPE_64）
- `buf[]`：存储实际数据的字节数组

**SDS 的优势**：
- **常数复杂度获取长度**：直接读取 `len` 字段，O(1)
- **二进制安全**：通过 `len` 判断字符串结束，而非 `\0`
- **减少内存分配次数**：预分配策略，修改字符串时减少 realloc 次数
- **兼容 C 字符串**：仍以 `\0` 结尾，可以直接使用 C 字符串函数

### 2.2 常用命令

#### SET / GET：设置与获取值

```redis
// 基本设置
SET name "张三"
GET name  // "张三"

// 设置并指定过期时间（秒）
SET token "abc123" EX 3600
SET token "abc123" PX 3600000  // 毫秒

// 仅当键不存在时设置
SETNX counter 0  // 键不存在时设置，返回 1；已存在时返回 0

// 同时设置多个键
MSET user:1:name "张三" user:1:age 25 user:1:city "北京"
MGET user:1:name user:1:age user:1:city  // 返回所有值
```

#### SET 系列命令对比

| 命令 | 说明 | 时间复杂度 |
|------|------|-----------|
| `SET key value` | 设置值，覆盖已存在的键 | O(1) |
| `SETNX key value` | 键不存在时才设置 | O(1) |
| `SETEX key seconds value` | 设置值并指定过期时间（秒） | O(1) |
| `PSETEX key milliseconds value` | 设置值并指定过期时间（毫秒） | O(1) |
| `SETRANGE key offset value` | 从指定偏移量开始覆盖字符串 | O(M)，M 为新值长度 |
| `GETRANGE key start end` | 获取指定范围的子字符串 | O(N)，N 为范围长度 |
| `GETSET key value` | 设置新值并返回旧值 | O(1) |

#### 自增自减命令

```redis
// 整数自增
SET page_view 100
INCR page_view       // 101
INCR page_view       // 102
INCRBY page_view 10  // 112

// 自减
DECR page_view       // 111
DECRBY page_view 5   // 106

// 浮点数自增（Redis 2.6+）
SET balance 100.50
INCRBYFLOAT balance 10.25  // 110.75
INCRBYFLOAT balance -5.50  // 105.25
```

**INCR 命令的原子性**：
INCR 命令是原子操作，即使在多客户端并发访问的情况下也能保证数据正确性。这是 Redis 作为计数器的基础。

```redis
// 应用场景：统计页面访问量
// 多个客户端同时执行 INCR page_view，不会出现竞态条件
```

#### 字符串操作命令

```redis
// 追加内容
SET greeting "Hello"
APPEND greeting " World"  // "Hello World"

// 获取字符串长度
STRLEN greeting  // 11

// 获取子字符串
GETRANGE greeting 0 4     // "Hello"
GETRANGE greeting 6 10    // "World"
GETRANGE greeting 0 -1    // "Hello World"（-1 表示最后一个字符）

// 设置子字符串
SETRANGE greeting 6 "Redis"  // "Hello Redis"

// 位操作
SETBIT bitmap 0 1   // 在偏移量 0 设置位为 1
SETBIT bitmap 1 0   // 在偏移量 1 设置位为 0
GETBIT bitmap 0     // 获取偏移量 0 的位值
BITCOUNT bitmap     // 统计位图中值为 1 的位数量
```

#### 字符串其他常用命令

```redis
// 字符串长度
STRLEN key

// 追加内容
APPEND key value

// 设置并返回旧值
GETSET key new_value

// 键的过期时间设置
EXPIRE key seconds      // 秒级过期
PEXPIRE key milliseconds  // 毫秒级过期
EXPIREAT key timestamp  // 指定时间戳过期

// 查看剩余存活时间
TTL key    // 秒级，-1 表示永不过期，-2 表示键不存在
PTTL key   // 毫秒级

// 移除过期时间
PERSIST key
```

### 2.3 应用场景

#### 场景一：缓存

将数据库查询结果缓存到 Redis 中，减轻数据库压力。

```redis
// 缓存用户信息
SET user:1001:info '{"name":"张三","email":"zhangsan@example.com","role":"admin"}' EX 3600

// 读取缓存
GET user:1001:info

// 缓存商品详情
SET product:2001:detail '{"name":"MacBook Pro","price":19999,"stock":50}' EX 600
```

#### 场景二：计数器

利用 INCR 命令的原子性实现各种计数器。

```redis
// 文章阅读量统计
INCR article:1001:view_count

// 用户在线人数统计
SET online_users 0
INCR online_users   // 用户上线
DECR online_users   // 用户下线

// 限流器（基于计数器）
// 实现接口访问频率限制：1 秒内最多访问 100 次
SET rate_limit:user:1001 100 EX 1
DECR rate_limit:user:1001  // 每次请求递减
```

#### 场景三：分布式锁

```redis
// 获取锁（SETNX 保证原子性）
SETNX lock:order:3001 1
// 获取成功返回 1，失败返回 0

// 释放锁
DEL lock:order:3001

// 更安全的方式：使用唯一值 + 过期时间
SET lock:order:3001 unique_value NX EX 30
// 释放时验证值
// if redis.get("lock:order:3001") == unique_value:
//     redis.del("lock:order:3001")
```

#### 场景四：共享信息

```redis
// 存储 Session 信息
SET session:token:abc123 '{"userId":1001,"role":"admin","loginTime":"2024-01-15T10:30:00"}' EX 7200

// 存储配置信息
SET config:site:title "我的博客"
SET config:site:description "一个技术博客"
SET config:site:keywords "Redis,MySQL,Java"
```

## 三、Hash 类型

### 3.1 底层实现

Hash 类型根据元素数量和元素大小动态选择两种底层实现：

#### ziplist（压缩列表）

当满足以下条件时，Hash 使用 ziplist 编码：
- 元素数量小于 `hash-max-ziplist-entries`（默认 512 个）
- 所有元素的键和值长度都小于 `hash-max-ziplist-value`（默认 64 字节）

```
┌───────────────────────────────────────────────────────┐
│  zlentry 1: [key1][value1]                            │
│  zlentry 2: [key2][value2]                            │
│  ...                                                   │
│  zlentry N: [keyN][valueN]                            │
└───────────────────────────────────────────────────────┘
```

**ziplist 的优势**：
- 内存紧凑，无需指针，节省内存
- 元素有序排列，可利用局部性原理提升缓存效率
- 适合小哈希场景

**ziplist 的劣势**：
- 插入和删除需要内存移动，时间复杂度 O(N)
- 元素过多时性能下降

#### hashtable（哈希表）

当不满足 ziplist 条件时，Hash 自动转换为 hashtable 编码。

```
┌───────────────────────────────────────────────────────┐
│  table[0] → [entry1] → [entry2] → NULL               │
│  table[1] → [entry3] → NULL                           │
│  table[2] → NULL                                      │
│  ...                                                   │
│  table[N] → [entry4] → [entry5] → NULL               │
└───────────────────────────────────────────────────────┘
```

**hashtable 的优势**：
- 平均 O(1) 的查找和插入性能
- 支持快速定位任意元素

**hashtable 的劣势**：
- 内存占用比 ziplist 大
- 存在哈希冲突

#### 编码转换规则

```
ziplist → hashtable（自动转换）
  当元素数量 > 512，或任一元素长度 > 64 字节时

hashtable → ziplist（自动转换）
  当元素数量 <= 512，且所有元素长度 <= 64 字节时
```

### 3.2 常用命令

#### HSET / HGET：设置与获取字段

```redis
// 设置单个字段
HSET user:1001:profile name "张三"
HSET user:1001:profile age 25
HSET user:1001:profile city "北京"

// 获取单个字段
HGET user:1001:profile name    // "张三"
HGET user:1001:profile age     // "25"

// 批量设置和获取
HMSET user:1001:profile email "zhangsan@example.com" phone "13800138000"
HMGET user:1001:profile name age email phone
// 返回 ["张三", "25", "zhangsan@example.com", "13800138000"]

// 当字段不存在时才设置
HSETNX user:1001:profile name "李四"  // 已存在，返回 0
```

#### 获取所有字段

```redis
// 获取所有键
HKEYS user:1001:profile
// 返回 ["name", "age", "city", "email", "phone"]

// 获取所有值
HVALS user:1001:profile
// 返回 ["张三", "25", "北京", "zhangsan@example.com", "13800138000"]

// 获取所有键值对
HGETALL user:1001:profile
// 返回 ["name", "张三", "age", "25", "city", "北京", ...]
```

#### 字段操作

```redis
// 判断字段是否存在
HEXISTS user:1001:profile name   // 1
HEXISTS user:1001:profile gender  // 0

// 删除字段
HDEL user:1001:profile city
HDEL user:1001:profile email phone  // 支持批量删除

// 获取 Hash 中字段数量
HLEN user:1001:profile  // 3 (name, age, phone)

// 获取字段值的长度
HSTRLEN user:1001:profile name  // 6 ("张三" 的 UTF-8 编码长度)
```

#### 自增自减命令

```redis
// 整数字段自增
HSET product:2001 stock 50
HINCRBY product:2001 stock -5   // 45（库存减少 5）
HINCRBY product:2001 stock 10   // 55（库存增加 10）

// 浮点数字段自增
HSET product:2001 rating 4.5
HINCRBYFLOAT product:2001 rating 0.3  // 4.8
HINCRBYFLOAT product:2001 rating -0.1  // 4.7
```

#### 遍历 Hash 字段

```redis
// 使用 HSCAN 遍历（适合大数据量）
HSCAN user:1001:profile 0 COUNT 100
// 返回 [cursor, [key1, value1, key2, value2, ...]]

// 从指定 cursor 继续遍历
HSCAN user:1001:profile 1 COUNT 100

// HSCAN 的优势：
// 1. 基于游标的迭代，不会阻塞 Redis
// 2. 支持 COUNT 参数控制每次返回数量
// 3. 遍历结果可能重复，需要应用层处理
```

#### Hash 常用命令汇总

| 命令 | 说明 | 时间复杂度 |
|------|------|-----------|
| `HSET key field value` | 设置字段值 | O(1) |
| `HSETNX key field value` | 字段不存在时设置 | O(1) |
| `HMSET key f1 v1 f2 v2 ...` | 批量设置字段 | O(N)，N 为字段数 |
| `HGET key field` | 获取字段值 | O(1) |
| `HMGET key f1 f2 ...` | 批量获取字段 | O(N) |
| `HGETALL key` | 获取所有字段和值 | O(N) |
| `HKEYS key` | 获取所有字段名 | O(N) |
| `HVALS key` | 获取所有字段值 | O(N) |
| `HEXISTS key field` | 判断字段是否存在 | O(1) |
| `HDEL key f1 f2 ...` | 删除字段 | O(N) |
| `HLEN key` | 获取字段数量 | O(1) |
| `HSTRLEN key field` | 获取字段值长度 | O(1) |
| `HINCRBY key field increment` | 字段值自增（整数） | O(1) |
| `HINCRBYFLOAT key field incr` | 字段值自增（浮点数） | O(1) |
| `HSCAN key cursor` | 游标遍历 Hash | O(N) |

### 3.3 应用场景

#### 场景一：用户信息存储

使用 Hash 存储用户信息，比使用 JSON 字符串更便于单独更新某个字段。

## 四、List 类型

### 4.1 底层实现

#### ziplist（压缩列表）

与 Hash 类型类似，当 List 满足以下条件时使用 ziplist：
- 元素数量小于 `list-max-ziplist-entries`（默认 512 个）
- 每个元素长度小于 `list-max-ziplist-value`（默认 64 字节）

```
┌───────────────────────────────────────────────────────────┐
│  zlentry 1: [element1]                                    │
│  zlentry 2: [element2]                                    │
│  ...                                                       │
│  zlentry N: [elementN]                                    │
│  [zlend] 结束标记                                         │
└───────────────────────────────────────────────────────────┘
```

**ziplist 的特点**：
- 内存连续，无额外指针开销
- 支持双向遍历
- 适合小型列表

#### linkedlist（双向链表）

当不满足 ziplist 条件时，List 转换为双向链表实现。

```
┌─────────┐    ┌─────────┐    ┌─────────┐
│  node1  │───▶│  node2  │───▶│  node3  │───▶ NULL
└─────────┘    └─────────┘    └─────────┘
    │              │              │
    ▼              ▼              ▼
  element1      element2      element3
    │              │              │
    └──────────prev────────────prev──┘
```

**linkedlist 的特点**：
- 每个节点包含前驱和后继指针
- 插入和删除只需修改指针，O(1)
- 随机访问需要遍历，O(N)

#### quicklist（Redis 3.2+）

Redis 3.2 引入了 quicklist，作为 ziplist 和 linkedlist 的折中方案。quicklist 是一个双向链表，每个节点是一个 ziplist。

```
┌─────────┐    ┌─────────┐    ┌─────────┐
│  ziplist1│───▶│  ziplist2│───▶│  ziplist3│───▶ NULL
│[e1][e2] │    │[e3][e4] │    │[e5][e6] │
└─────────┘    └─────────┘    └─────────┘
```

**quicklist 的优势**：
- 减少链表指针的内存开销
- 保持 ziplist 的内存紧凑性
- 插入和删除只需操作对应的 ziplist 节点

### 4.2 常用命令

#### 推入和弹出命令

```redis
// 从左端推入
LPUSH tasks "任务1"
LPUSH tasks "任务2" "任务3"  // 批量推入，顺序为 "任务3"、"任务2"、"任务1"

// 从右端推入
RPUSH tasks "任务4"
RPUSH tasks "任务5" "任务6"  // 批量推入，顺序为 "任务5"、"任务6"

// 从左端弹出
LPOP tasks  // "任务3"（先进先出）

// 从右端弹出
RPOP tasks  // "任务6"（后进先出）
```

**LPUSH + RPOP = 栈（Stack）**：

```redis
// 实现栈：后进先出
LPUSH stack "元素1"
LPUSH stack "元素2"
LPUSH stack "元素3"
RPOP stack  // "元素3"
RPOP stack  // "元素2"
RPOP stack  // "元素1"
```

**LPUSH + LPOP = 队列（Queue）**：

```redis
// 实现队列：先进先出
LPUSH queue "消息1"
LPUSH queue "消息2"
LPUSH queue "消息3"
LPOP queue  // "消息1"
LPOP queue  // "消息2"
LPOP queue  // "消息3"
```

#### 访问命令

```redis
// 获取列表长度
LLEN tasks

// 通过索引获取元素（索引从 0 开始）
LINDEX tasks 0     // 第一个元素
LINDEX tasks -1    // 最后一个元素
LINDEX tasks 2     // 第三个元素

// 获取指定范围的元素（闭区间）
LRANGE tasks 0 -1      // 获取所有元素
LRANGE tasks 0 2       // 获取前三个元素
LRANGE tasks -3 -1     // 获取最后三个元素
LRANGE tasks 1 3       // 获取第 2 到第 4 个元素
```

#### 插入和修改

```redis
// 在指定元素前或后插入
LINSERT tasks BEFORE "任务3" "新任务"
LINSERT tasks AFTER "任务3" "另一个任务"

// 通过索引设置元素值
LSET tasks 0 "修改后的任务"

// 修剪列表（只保留指定范围内的元素）
LTRIM tasks 0 4   // 只保留前 5 个元素
LTRIM tasks -10 -1  // 只保留最后 10 个元素
```

#### 阻塞弹出

```redis
// 阻塞弹出：当列表为空时等待，直到有新元素或超时
BRPOP tasks 30           // 等待 tasks 列表，超时 30 秒
BLPOP tasks queue 30     // 同时等待多个列表
BRPOPLPUSH tasks completed 30  // 安全队列：弹出并推到另一个列表

// 返回值：[key, value] 或 nil（超时）
// 当有元素时立即返回，否则等待
```

#### List 常用命令汇总

| 命令 | 说明 | 时间复杂度 |
|------|------|-----------|
| `LPUSH key v1 v2 ...` | 左端推入 | O(N)，N 为推入数量 |
| `RPUSH key v1 v2 ...` | 右端推入 | O(N) |
| `LPOP key` | 左端弹出 | O(1) |
| `RPOP key` | 右端弹出 | O(1) |
| `BLPOP k1 k2 ... timeout` | 阻塞左端弹出 | O(1) |
| `BRPOP k1 k2 ... timeout` | 阻塞右端弹出 | O(1) |
| `LRANGE key start stop` | 获取范围元素 | O(N) |
| `LINDEX key index` | 获取指定索引元素 | O(N)，小列表 O(1) |
| `LSET key index value` | 设置指定索引元素 | O(N) |
| `LINSERT key BEFORE/AFTER pivot value` | 在指定元素前后插入 | O(N) |
| `LTRIM key start stop` | 修剪列表 | O(N) |
| `LLEN key` | 获取列表长度 | O(1) |
| `RPOPLPUSH source destination` | 安全队列（原子操作） | O(1) |

### 4.3 应用场景

#### 场景一：消息队列

使用 List 实现简单的消息队列。

```redis
// 生产者推入消息
LPUSH queue:order
    '{"orderId":"3001","userId":1001,"productId":2001}'

// 消费者弹出消息
BRPOP queue:order 30
// 返回 ["queue:order", '{"orderId":"3001",...}']

// 更安全的做法：使用 RPOPLPUSH 实现可靠队列
RPOPLPUSH queue:order queue:order:processing
// 处理完成后从处理队列中移除
LPOP queue:order:processing
```

**可靠消息队列流程**：
1. 生产者通过 `LPUSH` 推入消息
2. 消费者通过 `BRPOPLPUSH` 原子地弹出并推到处理队列
3. 消费者处理完成后通过 `LPOP` 从处理队列中移除
4. 如果消费者崩溃，消息仍保留在处理队列中，可恢复

#### 场景二：最新消息排行

```redis
// 社交媒体的最新动态
LPUSH user:1001:timeline
    '{"type":"post","content":"今天天气不错","time":"2024-01-15T10:30:00"}'

// 只保留最新的 100 条
LTRIM user:1001:timeline 0 99

// 获取最新动态
LRANGE user:1001:timeline 0 9   // 获取最新的 10 条
```

#### 场景三：最新评论列表

```redis
// 文章评论
LPUSH article:1001:comments
    '{"userId":1001,"content":"写得很好","time":"2024-01-15T10:30:00"}'
LPUSH article:1001:comments
    '{"userId":1002,"content":"赞同观点","time":"2024-01-15T10:35:00"}'

// 只保留最新 50 条
LTRIM article:1001:comments 0 49

// 分页获取评论
LRANGE article:1001:comments 0 9     // 第 1 页
LRANGE article:1001:comments 10 19   // 第 2 页
```

## 五、Set 类型

### 5.1 底层实现

#### intset（整数集合）

当 Set 中的所有元素都是整数且元素数量小于 `set-max-intset-entries`（默认 512）时，使用 intset 编码。

```
┌───────────────────────────────────────────────────────┐
│  encoding: INTSET_ENC_INT16 / INT32 / INT64          │
│  length: 元素数量                                     │
│  contents: [1001, 1002, 1003, ...]  (有序、无重复)   │
└───────────────────────────────────────────────────────┘
```

**intset 的特点**：
- 内存紧凑，元素按升序排列
- 使用二分查找，查找效率为 O(log N)
- 不支持除整数外的其他类型
- 当整数范围溢出时自动升级编码

#### hashtable（哈希表）

当不满足 intset 条件时，Set 使用 hashtable 编码，与 Hash 类型的 hashtable 实现类似。

```
┌───────────────────────────────────────────────────────┐
│  table[0] → [element1] → [element2] → NULL           │
│  table[1] → [element3] → NULL                        │
│  ...                                                   │
│  table[N] → [element4] → NULL                        │
└───────────────────────────────────────────────────────┘
```

**Set 的 hashtable 特点**：
- 只存储键，不存储值（值为 NULL）
- 平均 O(1) 的查找和插入性能
- 支持任意字符串元素

#### 编码转换规则

```
intset → hashtable（自动转换）
  当元素数量 > 512，或插入非整数值时

hashtable 不会自动转回 intset（即使删除元素后满足条件）
```

### 5.2 常用命令

#### SADD / SREM：添加和删除元素

```redis
// 添加元素
SADD tags "Redis"
SADD tags "MySQL" "Java" "Python"

// 删除元素
SREM tags "Python"
SREM tags "Java" "MySQL"  // 支持批量删除

// 获取集合中的元素数量
SCARD tags  // 3 (Redis, MySQL, Java)
```

#### 查询元素

```redis
// 判断元素是否属于集合
SISMEMBER tags "Redis"   // 1
SISMEMBER tags "Python"  // 0

// 获取集合中所有元素
SMEMBERS tags
// 返回 ["Redis", "MySQL", "Java"]

// 随机获取一个元素（不删除）
SRANDMEMBER tags         // 随机返回一个元素
SRANDMEMBER tags 3       // 随机返回 3 个不同元素

// 随机弹出元素
SPOP tags                // 随机弹出并返回一个元素
SPOP tags 2              // 随机弹出 2 个元素
```

#### 集合运算

```redis
// 创建两个集合
SADD set1 "a" "b" "c" "d"
SADD set2 "c" "d" "e" "f"

// 交集
SINTER set1 set2
// 返回 ["c", "d"]

// 并集
SUNION set1 set2
// 返回 ["a", "b", "c", "d", "e", "f"]

// 差集（set1 中有但 set2 中没有的）
SDIFF set1 set2
// 返回 ["a", "b"]

// 对称差集（两个集合的并集减去交集）
// 注意：Redis 没有直接的对称差集命令，可用 SDIFF + SUNION 组合
SUNION SDIFF set1 set2, SDIFF set2 set1
// 返回 ["a", "b", "e", "f"]
```

#### 集合运算存储

```redis
// 将交集存储到新集合
SINTERSET set1 set2 result
SMEMBERS result  // ["c", "d"]

// 将并集存储到新集合
SUNIONSET set1 set2 result
SMEMBERS result  // ["a", "b", "c", "d", "e", "f"]

// 将差集存储到新集合
SDIFFSET set1 set2 result
SMEMBERS result  // ["a", "b"]
```

#### 遍历集合

```redis
// 使用 SSCAN 遍历（适合大数据量）
SSCAN tags 0 COUNT 100
// 返回 [cursor, [element1, element2, ...]]

// SSCAN 的优势：
// 1. 基于游标的迭代
// 2. 不会阻塞 Redis
// 3. 遍历结果可能重复，需要应用层处理
```

#### Set 常用命令汇总

| 命令 | 说明 | 时间复杂度 |
|------|------|-----------|
| `SADD key m1 m2 ...` | 添加元素 | O(N)，N 为添加数量 |
| `SREM key m1 m2 ...` | 删除元素 | O(N) |
| `SMEMBERS key` | 获取所有元素 | O(N) |
| `SISMEMBER key member` | 判断元素是否存在 | O(1) |
| `SCARD key` | 获取集合大小 | O(1) |
| `SMISMEMBER key m1 m2 ...` | 批量判断元素是否存在 | O(N) |
| `SRANDMEMBER key [count]` | 随机获取元素 | O(N) |
| `SPOP key [count]` | 随机弹出元素 | O(N) |
| `SDIFF key1 key2 ...` | 差集运算 | O(N) |
| `SDIFFSET dest key1 key2 ...` | 差集运算并存储 | O(N) |
| `SINTER key1 key2 ...` | 交集运算 | O(N) |
| `SINTERSET dest key1 key2 ...` | 交集运算并存储 | O(N) |
| `SUNION key1 key2 ...` | 并集运算 | O(N) |
| `SUNIONSET dest key1 key2 ...` | 并集运算并存储 | O(N) |
| `SSCAN key cursor` | 游标遍历集合 | O(N) |

### 5.3 应用场景

#### 场景一：标签系统

```redis
// 为文章添加标签
SADD article:1001:tags "Redis" "数据库" "后端" "缓存"
SADD article:1002:tags "MySQL" "数据库" "SQL"

// 获取文章的所有标签
SMEMBERS article:1001:tags

// 查找包含 "数据库" 标签的所有文章
// 需要在应用层维护反向索引或使用其他数据结构
SISMEMBER article:1001:tags "数据库"  // 1
SISMEMBER article:1002:tags "数据库"  // 1

// 查找同时包含 "Redis" 和 "后端" 标签的文章
SINTER article:1001:tags article:1002:tags
// 返回 ["数据库"]（两篇文章共有的标签）
```

#### 场景二：共同好友

```redis
// 用户 A 的好友
SADD user:A:friends "B" "C" "D" "E"

// 用户 B 的好友
SADD user:B:friends "A" "C" "D" "F"

// A 和 B 的共同好友
SINTER user:A:friends user:B:friends
// 返回 ["C", "D"]

// A 的独有关注（不是 B 的好友）
SDIFF user:A:friends user:B:friends
// 返回 ["E"]

// 可能认识的人（共同好友的好友）
SISMEMBER user:C:friends "F"  // 判断 C 是否和 F 为好友
```

#### 场景三：去重

```redis
// 文章访问者去重
SADD article:1001:visitors "user:1001"
SADD article:1001:visitors "user:1002"
SADD article:1001:visitors "user:1001"  // 重复，自动忽略

// 获取独立访客数
SCARD article:1001:visitors  // 2

// 全局在线用户
SADD online:users "user:1001" "user:1002" "user:1003"
SREM online:users "user:1002"  // 用户下线

// 获取在线人数
SCARD online:users  // 2
```

## 六、ZSet 类型

### 6.1 底层实现

#### ziplist（压缩列表）

当满足以下条件时，ZSet 使用 ziplist 编码：
- 元素数量小于 `zset-max-ziplist-entries`（默认 128 个）
- 每个元素长度小于 `zset-max-ziplist-value`（默认 64 字节）

```
┌───────────────────────────────────────────────────────────────────┐
│  zlentry 1: [member1][score1]                                    │
│  zlentry 2: [member2][score2]                                    │
│  ...                                                               │
│  zlentry N: [memberN][scoreN]                                    │
└───────────────────────────────────────────────────────────────────┘
```

**ziplist 的特点**：
- 紧凑存储，节省内存
- 按 score 排序存储
- 适合小型有序集合

#### skiplist + hashtable（跳表 + 哈希表）

当不满足 ziplist 条件时，ZSet 使用跳表和哈希表的组合实现。

**跳表（skiplist）结构**：

```
Level 3:  [  1  ] ──────────────────────────► [  5  ] ─────────────────► NULL
Level 2:  [  1  ] ─────────────► [  3  ] ──► [  5  ] ─────► [  7  ] ──► NULL
Level 1:  [  1  ] ──► [  2  ] ──► [  3  ] ──► [  4  ] ──► [  5  ] ──► [  6  ] ──► [  7  ] ──► NULL
Level 0:  [  1  ] ──► [  2  ] ──► [  3  ] ──► [  4  ] ──► [  5  ] ──► [  6  ] ──► [  7  ] ──► NULL
           score=1     score=2     score=3     score=4     score=5     score=6     score=7
```

**跳表的特点**：
- 多层链表结构，查询效率接近平衡二叉树，平均 O(log N)
- 支持范围查询，按 score 排序遍历
- 实现简单，比红黑树更易维护

**哈希表的作用**：
- 存储 member → score 的映射
- 支持 O(1) 的成员查找
- 弥补跳表在精确查找方面的不足

**双结构的优势**：
- 跳表：支持按 score 范围查询和排序
- 哈希表：支持 O(1) 的成员精确查找
- 两者结合，兼顾查询和范围操作的性能

### 6.2 常用命令

#### ZADD / ZREM：添加和删除元素

```redis
// 添加元素（member + score）
ZADD rank 100 "Alice"
ZADD rank 200 "Bob"
ZADD rank 150 "Charlie"

// 批量添加
ZADD rank 180 "David" 220 "Eve" 90 "Frank"

// 删除元素
ZREM rank "Frank"
ZREM rank "Alice" "Bob"  // 支持批量删除
```

#### 查询排名和分数

```redis
// 获取成员排名（从 0 开始，升序）
ZRANK rank "Charlie"  // 2 (第三)

// 获取成员排名（降序）
ZREVRANK rank "Charlie"  // 1 (第二)

// 获取成员分数
ZSCORE rank "Charlie"  // "150"
ZSCORE rank "Alice"    // nil（已删除）
```

#### 范围查询

```redis
// 获取指定排名范围的成员（升序）
ZRANGE rank 0 2       // 排名前 3 的成员
ZRANGE rank -3 -1     // 排名后 3 的成员

// 获取指定排名范围的成员（降序）
ZREVRANGE rank 0 2    // 排名前 3 的成员（从高到低）

// 获取指定分数范围的成员
ZRANGEBYSCORE rank 100 200
// 返回分数在 [100, 200] 之间的成员

// 带 LIMIT 分页的范围查询
ZRANGEBYSCORE rank 100 200 LIMIT 0 10
// 分数在 [100, 200] 之间的前 10 个成员

// 带 WITHSCORES 返回分数
ZRANGE rank 0 2 WITHSCORES
// 返回 ["David", "180", "Eve", "220", "Charlie", "150"]
```

#### 分数操作

```redis
// 分数自增
ZADD rank 100 "Alice"
ZINCRBY rank 50 "Alice"   // Alice 的分数变为 150
ZINCRBY rank -30 "Alice"  // Alice 的分数变为 120

// 批量获取分数
ZSCORE rank "Alice" "Bob" "Charlie"
// 返回 ["120", nil, "150"]
```

#### 集合操作

```redis
// 并集
ZUNIONSTORE rank:total 2 rank:week rank:month
// 将每周和每月的分数合并（相同 member 的分数相加）

// 并集并指定聚合方式
ZUNIONSTORE rank:total 2 rank:week rank:month AGGREGATE MAX
// 相同 member 取最大分数

// 交集
ZINTERSTORE rank:common 2 rank:week rank:month
// 两个榜单的共同成员，分数相加
```

#### 其他操作

```redis
// 获取 ZSet 元素数量
ZCARD rank  // 5

// 统计指定分数范围的成员数量
ZCOUNT rank 100 200

// 删除指定排名范围的成员
ZREMRANGEBYRANK rank 0 2

// 删除指定分数范围的成员
ZREMRANGEBYSCORE rank 100 200

// 遍历 ZSet
ZSCAN rank 0 COUNT 100
```

#### ZSet 常用命令汇总

| 命令 | 说明 | 时间复杂度 |
|------|------|-----------|
| `ZADD key score member` | 添加元素 | O(log N) |
| `ZREM key m1 m2 ...` | 删除元素 | O(M log N) |
| `ZRANK key member` | 获取排名（升序） | O(log N) |
| `ZREVRANK key member` | 获取排名（降序） | O(log N) |
| `ZSCORE key member` | 获取分数 | O(1) |
| `ZRANGE key start stop` | 获取排名范围元素 | O(log N + M) |
| `ZREVRANGE key start stop` | 获取排名范围元素（降序） | O(log N + M) |
| `ZRANGEBYSCORE key min max` | 获取分数范围元素 | O(log N + M) |
| `ZREVRANGEBYSCORE key max min` | 获取分数范围元素（降序） | O(log N + M) |
| `ZINCRBY key increment member` | 分数自增 | O(log N) |
| `ZCARD key` | 获取元素数量 | O(1) |
| `ZCOUNT key min max` | 分数范围内的元素数量 | O(log N) |
| `ZREMRANGEBYRANK key start stop` | 删除排名范围元素 | O(log N + M) |
| `ZREMRANGEBYSCORE key min max` | 删除分数范围元素 | O(log N + M) |
| `ZUNIONSTORE dest num k1 k2` | 并集运算并存储 | O(N) |
| `ZINTERSTORE dest num k1 k2` | 交集运算并存储 | O(N) |
| `ZSCAN key cursor` | 游标遍历 | O(N) |

## 七、其他数据类型简介

### 7.1 HyperLogLog

HyperLogLog 是一种**概率数据结构**，用于估算集合的基数（元素数量），而非存储实际元素。

**特点**：
- 固定内存占用：约 12KB
- 标准误差：约 0.81%
- 最多可存储 2^64 个元素

```redis
// 添加元素
PFADD uv:article:1001 "user:1001"
PFADD uv:article:1001 "user:1002" "user:1003"
PFADD uv:article:1001 "user:1001"  // 自动去重

// 估算基数
PFCOUNT uv:article:1001  // 3（近似值）

// 合并多个 HyperLogLog
PFMERGE uv:total uv:article:1001 uv:article:1002
PFCOUNT uv:total  // 估算总 UV
```

**应用场景**：
- 文章 UV（独立访客）统计
- 实时在线人数估算
- 大规模数据去重统计

**注意事项**：
- 只能获取近似值，无法获取精确值
- 无法获取实际存储的元素
- 适合对精度要求不高的统计场景

### 7.2 Bitmap（位图）

Bitmap 是基于字符串的位操作数据结构，通过设置每一位来表示某种状态。

```redis
// 场景：用户签到打卡
// 每个用户一个 Bitmap，每一位代表一天

// 用户 1001 在第 1 天签到
SETBIT sign:1001 1 1
// 用户 1001 在第 3 天签到
SETBIT sign:1001 3 1
// 用户 1001 在第 7 天签到
SETBIT sign:1001 7 1

// 查询某一天是否签到
GETBIT sign:1001 1   // 1 (已签到)
GETBIT sign:1001 2   // 0 (未签到)

// 统计签到天数
BITCOUNT sign:1001  // 3

// 统计指定范围的签到天数
BITCOUNT sign:1001 0 30  // 第 0-30 天的签到天数

// 位运算
SETBIT online:users:day1 1001 1  // 用户 1001 在线
SETBIT online:users:day1 1002 1  // 用户 1002 在线
SETBIT online:users:day2 1001 1
SETBIT online:users:day2 1003 1

// 计算两天都在线的用户（AND 运算）
BITOP AND online:both online:users:day1 online:users:day2
BITCOUNT online:both  // 1 (只有用户 1001 两天都在线)

// 计算两天中至少一天在线的用户（OR 运算）
BITOP OR online:either online:users:day1 online:users:day2
BITCOUNT online:either  // 3
```

**应用场景**：
- 签到打卡系统
- 在线状态标记
- 用户活跃天数统计
- 数据去重

### 7.3 Geo（地理坐标）

Geo 类型用于存储地理位置信息，并支持计算两点之间的距离或查找附近的地点。

```redis
// 添加地理位置（经度、纬度、名称）
GEOADD places
    116.397428 39.90923 "天安门"
    116.405285 39.904989 "故宫"
    116.397428 39.90923 "北京"
    121.473701 31.230416 "上海"
    113.264434 23.129162 "广州"

// 获取地理位置坐标
GEOPOS places "天安门" "故宫"
// 返回 [[116.397428, 39.90923], [116.405285, 39.904989]]

// 计算两点之间的距离（默认米）
GEODIST places "天安门" "故宫"
// 返回 "518.6923"（约 518 米）

// 指定单位计算距离
GEODIST places "北京" "上海" km
// 返回 "1068.1358"（约 1068 公里）

// 查找附近的地点
GEOSEARCH places FROMLONLAT 116.397428 39.90923
    BYRADIUS 1 km WITHDIST
// 返回距离天安门 1 公里内的地点及距离

// 查找附近的地点（按成员）
GEOSEARCH places FROMMEMBER "天安门"
    BYRADIUS 2 km WITHDIST
```

**GEO 的底层实现**：
- 基于 ZSet 实现
- 使用 Geohash 编码将二维坐标转换为一维字符串
- 支持高效的范围查询

**应用场景**：
- 附近的人/地点搜索
- 配送范围管理
- 地理围栏

### 7.4 Stream（流）

Stream 是 Redis 5.0+ 引入的消息队列数据类型，功能类似于 Kafka。

```redis
// 添加消息
XADD mystream
    *  // 自动生成 ID
    type "order"
    userId "1001"
    productId "2001"
    count "2"
    totalPrice "39998"

// 指定消息 ID
XADD mystream 1001 type "order" userId "1001"

// 读取消息
XREAD COUNT 10 STREAMS mystream 0  // 从 ID 0 开始读取

// 阻塞读取新消息
XREAD BLOCK 5000 STREAMS mystream $  // 等待新消息，超时 5 秒

// 创建消费者组
XGROUP CREATE mystream group1

// 消费者组读取
XREADGROUP GROUP group1 consumer1
    COUNT 10 STREAMS mystream >

// 确认消息已处理
XACK mystream group1 1001

// 获取流信息
XINFO STREAM mystream

// 获取消费者组信息
XINFO GROUPS mystream
```

**Stream 的特点**：
- 支持持久化，消息不会丢失
- 支持消费者组，实现负载均衡
- 支持消息确认机制
- 支持消息回放
- 支持裁剪流长度

**应用场景**：
- 高吞吐消息队列
- 事件溯源
- 实时数据处理
- 日志收集

## 八、数据类型选择策略

### 8.1 核心类型选择矩阵

| 需求场景 | 推荐类型 | 原因 |
|---------|---------|------|
| 简单 KV 存储 | String | 简单高效，支持过期时间 |
| 对象存储 | Hash | 部分读写优于 JSON 序列化 |
| 队列/栈 | List | 原生支持两端操作，O(1) 时间复杂度 |
| 标签/去重 | Set | 自动去重，支持集合运算 |
| 排行榜 | ZSet | 有序、支持分数更新和范围查询 |
| 大规模计数 | HyperLogLog | 固定内存，支持 UV 统计 |
| 状态标记 | Bitmap | 极省空间，支持位运算 |
| 地理位置 | Geo | 原生支持距离计算和范围查询 |
| 消息队列 | Stream | 支持消费者组和消息确认 |

### 8.2 常见数据结构对比

| 对比项 | String | Hash | List | Set | ZSet |
|--------|--------|------|------|-----|------|
| 数据模型 | 单值 | 键值对 | 有序列表 | 无序集合 | 有序集合 |
| 内存效率 | 高 | 中 | 中 | 中 | 中 |
| 随机访问 | O(1) | O(1) | O(N) | O(1) | O(log N) |
| 范围查询 | 不支持 | 不支持 | 支持 | 支持 | 支持 |
| 去重 | 不支持 | 不支持 | 不支持 | 自动 | 自动 |
| 典型场景 | 缓存、计数器 | 用户信息、配置 | 消息队列、时间线 | 标签、好友 | 排行榜、评分 |

### 8.3 选择建议

1. **优先选择简单类型**：能用 String 解决的问题不用 Hash，能用 Hash 解决的问题不用 List
2. **考虑数据规模**：小数据量可选用 ziplist 编码的类型，大数据量考虑性能
3. **评估读写模式**：读多写少（如缓存）和写多读少（如计数器）的选择不同
4. **关注内存使用**：HyperLogLog 和 Bitmap 在大规模数据下有显著优势
5. **利用组合**：多个数据类型可以组合使用，如 ZSet + Hash 实现复杂业务

## 本章小结

本章详细讲解了 Redis 的九大核心数据类型及其底层实现、常用命令和应用场景：

1. **String 类型**：基于 SDS 实现，支持缓存、计数器、分布式锁等场景
2. **Hash 类型**：基于 ziplist/hashtable 动态编码，适合存储对象结构
3. **List 类型**：基于 ziplist/quicklist 实现，适合消息队列和时间线
4. **Set 类型**：基于 intset/hashtable 实现，支持集合运算和去重
5. **ZSet 类型**：基于 ziplist/skiplist+hashtable 实现，适合排行榜和评分系统
6. **HyperLogLog**：概率数据结构，适合大规模基数统计
7. **Bitmap**：位操作数据结构，适合状态标记和签到系统
8. **Geo**：地理坐标类型，适合位置服务
9. **Stream**：消息队列类型，适合实时数据流处理

每种数据类型都有其独特的设计哲学和适用场景，掌握它们的底层实现原理有助于在实际工作中做出最优选择。
