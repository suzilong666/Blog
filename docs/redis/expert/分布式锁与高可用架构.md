## 一、分布式锁概述

### 1.1 什么是分布式锁

在单机应用中，我们可以使用 `synchronized` 关键字或 `ReentrantLock` 来实现多线程的互斥访问。但在分布式系统中，多个服务实例部署在不同的服务器上，JVM 级别的锁机制已无法满足需求。

**分布式锁（Distributed Lock）** 是一种跨进程、跨节点的互斥控制机制，用于保证在分布式环境中，同一时刻只有一个节点可以执行某段关键代码或访问某个共享资源。

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  服务实例 A   │     │  服务实例 B   │     │  服务实例 C   │
│  (节点1)     │     │  (节点2)     │     │  (节点3)     │
└──────┬───────┘     └──────┬───────┘     └──────┬───────┘
       │                    │                    │
       │    竞争共享资源     │    竞争共享资源     │
       │                    │                    │
       └────────────────────┼────────────────────┘
                            │
                            ▼
                    ┌──────────────┐
                    │  共享资源     │
                    │  (如订单库存) │
                    └──────────────┘
                    
        需要分布式锁保证：同一时刻只有一个实例能访问共享资源
```

### 1.2 分布式锁需要满足的特性

一个健壮的分布式锁方案应当具备以下核心特性：

| 特性 | 说明 | 重要性 |
|------|------|--------|
| **互斥性（Mutual Exclusion）** | 同一时刻只能有一个客户端获取锁 | 最基本要求 |
| **不可死锁（No Deadlock）** | 即使持有锁的客户端崩溃，锁也能被其他客户端获取 | 核心保障 |
| **可重入性（Reentrancy）** | 同一个客户端可以多次获取同一把锁而不被阻塞 | 提升易用性 |
| **高性能（High Performance）** | 加锁和解锁操作的延迟低、吞吐量高 | 工程关键 |
| **自动过期（Auto Expiration）** | 锁有超时时间，防止因异常导致锁无法释放 | 死锁防护 |
| **原子性（Atomicity）** | 加锁、解锁操作必须是原子的，不可分割 | 正确性保证 |
| **可续约（Lease Renewal）** | 支持在持有锁期间自动续期，防止业务执行时间超过锁超时 | 增强可靠性 |

#### 各特性详解

**互斥性**是分布式锁的根本目的，确保在高并发场景下，对共享资源的操作严格串行化。

**不可死锁**要求锁具备自动释放机制。如果获取锁的客户端因为网络分区、进程崩溃等异常无法正常释放锁，锁也能在超时后自动释放，避免系统永久卡死。

**可重入性**对于复杂业务场景非常重要。例如在一个业务方法中调用另一个需要同一把锁的方法时，如果锁不支持可重入，就会导致死锁。

```java
// 可重入锁示例
public void methodA() {
    lock.lock();        // 第一次获取锁
    try {
        // 执行业务逻辑
        methodB();      // methodB 内部也获取同一把锁
    } finally {
        lock.unlock();  // 第一次释放锁
    }
}

public void methodB() {
    lock.lock();        // 第二次获取锁（可重入，不会阻塞）
    try {
        // 业务逻辑
    } finally {
        lock.unlock();  // 第二次释放锁
    }
}
```

### 1.3 常见实现方案对比

#### 基于 MySQL 的实现

```sql
CREATE TABLE distributed_lock (
    lock_name VARCHAR(64) PRIMARY KEY COMMENT '锁名称',
    lock_value VARCHAR(128) NOT NULL COMMENT '锁标识（持有者ID）',
    expire_time BIGINT NOT NULL COMMENT '过期时间戳',
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 获取锁（利用唯一索引实现互斥）
INSERT INTO distributed_lock (lock_name, lock_value, expire_time)
VALUES ('order_lock_1001', 'node-A-001', UNIX_TIMESTAMP() + 30);

-- 释放锁
DELETE FROM distributed_lock 
WHERE lock_name = 'order_lock_1001' AND lock_value = 'node-A-001';
```

**优点**：实现简单、使用方便、基于关系数据库易于理解。
**缺点**：性能较差（磁盘 I/O 瓶颈）、需要数据库资源、无法自动续约、可重入实现复杂。

#### 基于 ZooKeeper 的实现

## 二、Redis 实现分布式锁

### 2.1 基础实现（SETNX + EXPIRE 的问题）

#### SETNX 命令介绍

```redis
# SETNX = SET if Not eXists
# 仅当 key 不存在时设置值
SETNX lock_key 1
# 返回 1 表示设置成功（获取锁）
# 返回 0 表示设置失败（锁已被他人持有）
```

#### 存在的问题：非原子操作

```java
// ❌ 错误实现：SETNX 和 EXPIRE 是两个独立命令
public boolean tryLock(String lockKey, String requestId, long expireTime) {
    // 步骤1: SETNX - 设置键
    Long result = jedis.setnx(lockKey, requestId);
    
    // 步骤2: EXPIRE - 设置过期时间
    // 如果在步骤1和步骤2之间，Redis 宕机或客户端崩溃
    // 则锁永远不会过期，造成死锁！
    if (result == 1L) {
        jedis.expire(lockKey, expireTime);
        return true;
    }
    return false;
}
```

```
问题场景示意:
┌──────────┐                    ┌──────────┐
│ 客户端 A  │                    │  Redis    │
└────┬─────┘                    └────┬─────┘
     │ SETNX lock_key value          │
     │──────────────────────────────►│
     │                                │ 设置成功 ✓
     │                                │
     │ [此时 Redis 宕机！]            │
     │                                │ EXPIRE 命令未执行 ✗
     │                                │
     │                       ┌────────┴────────┐
     │                       │ key 永远不会过期  │
     │                       │ → 死锁！         │
     │                       └─────────────────┘
```

**核心问题**：`SETNX` 和 `EXPIRE` 是两个独立的 Redis 命令，它们的执行不是原子的。如果在两个命令之间发生异常，就会导致锁无法过期，形成死锁。

### 2.2 SET 命令正确实现（SET key value NX PX milliseconds）

#### SET 命令完整语法

```redis
SET key value [EX seconds] [PX milliseconds] [NX|XX]

# 参数说明:
# - EX seconds: 设置过期时间（秒）
# - PX milliseconds: 设置过期时间（毫秒）
# - NX: 仅当 key 不存在时设置（Not eXists）
# - XX: 仅当 key 已存在时设置（eXists）
```

#### 原子加锁实现

```java
public boolean tryLock(String lockKey, String requestId, long expireMillis) {
    // ✅ 正确实现: SET 命令原子地完成"设置值 + 设置过期时间"
    // NX: 保证互斥性
    // PX: 保证自动过期
    String result = jedis.set(
        lockKey,           // 锁的 key
        requestId,         // 请求标识（唯一值）
        "NX",              // 仅当 key 不存在时设置
        "PX",              // 使用毫秒级过期
        expireMillis       // 过期时间（毫秒）
    );
    // 返回 "OK" 表示设置成功，返回 null 表示 key 已存在
    return "OK".equals(result);
}
```

#### 加锁流程示意

```
客户端 A 加锁流程:

  ┌──────────┐                    ┌──────────┐
  │ 客户端 A  │                    │  Redis    │
  └────┬─────┘                    └────┬─────┘
       │ SET lock_key requestId NX PX 30000
       │──────────────────────────────►│
       │                                │
       │                                │ 检查 lock_key 是否存在
       │                                │
       │                                │ ┌─────────────────┐
       │                                │ │ key 不存在?      │
       │                                │ └────────┬────────┘
       │                                │       │
       │                                │   是 │      │ 否
       │                                │       ▼      ▼
       │                                │   设置值   返回 null
       │                                │   + 过期   (获取失败)
       │                                │   时间
       │                                │       │
       │   "OK" (获取成功)               │       │
       │◄──────────────────────────────│       │
       │                                │       │
       │   锁已获取！                    │   客户端 B 也在尝试:
       │   执行核心业务逻辑              │   SET lock_key requestId-B NX PX 30000
       │                                │   → 返回 null（获取失败）
```

#### 为什么需要唯一的 requestId？

```java
// ❌ 错误做法: 使用固定值
jedis.set(lockKey, "1", "NX", "PX", 30000);
// 问题: 任何客户端都能解锁，无法验证锁的持有者身份

// ✅ 正确做法: 使用唯一标识
String requestId = UUID.randomUUID().toString();
jedis.set(lockKey, requestId, "NX", "PX", 30000);
// 解锁时验证 requestId，只有持有者本人才能释放锁
```

`requestId` 的作用是**标识锁的持有者**，防止误删他人持有的锁。每个客户端在获取锁时生成一个唯一 ID，并在释放锁时验证该 ID。

### 2.3 释放锁的原子性（Lua 脚本实现）

#### 错误的释放锁方式

```java
// ❌ 错误实现：GET 和 DEL 不是原子操作
public boolean unlock(String lockKey, String requestId) {
    // 步骤1: 获取当前锁的值
    String currentValue = jedis.get(lockKey);
    
    // 步骤2: 验证是否为自己的锁
    if (requestId.equals(currentValue)) {
        // 步骤3: 删除锁
        jedis.del(lockKey);
        return true;
    }
    return false;
}
```

```
问题场景:

│ 客户端 A  │                    │  Redis    │
└────┬─────┘                    └────┬─────┘
     │ GET lock_key                   │
     │──────────────────────────────►│
     │                                │ 返回 requestId-A
     │                                │
     │ [锁超时自动过期！]              │
     │                                │
     │                                │ 客户端 B 获取了锁
```

#### Lua 脚本实现原子解锁

```lua
-- unlock.lua
-- 原子释放锁脚本
-- KEYS[1]: 锁的 key
-- ARGV[1]: 锁持有者的唯一标识 (requestId)

if redis.call('get', KEYS[1]) == ARGV[1] then
    -- 确认是自己的锁，删除并返回1（成功）
    return redis.call('del', KEYS[1])
else
    -- 不是自己的锁或锁已不存在，返回0（失败）
    return 0
end
```

```java
// ✅ 正确实现：Lua 脚本保证原子性
public boolean unlock(String lockKey, String requestId) {
    // Lua 脚本在 Redis 中是原子执行的，不会被其他命令打断
    String luaScript = 
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "    return redis.call('del', KEYS[1]) " +
        "else " +
        "    return 0 " +
        "end";
    
    Long result = jedis.eval(
        luaScript,      // Lua 脚本内容
        1,              // KEYS 参数数量
        lockKey,        // KEYS[1]
        requestId       // ARGV[1]
    );
    return result == 1L;
}
```

```
3. 整个脚本作为一个原子操作执行
```

### 2.4 锁超时问题

#### 超时时间的选择

锁的超时时间是一个关键的设计参数，需要平衡以下因素：

```
超时时间过短的风险:
- 业务执行时间超过超时时间
- 锁提前释放，其他客户端获取锁
- 导致并发执行，破坏互斥性

超时时间过长的风险:
- 客户端崩溃后，锁长时间不释放
- 影响系统可用性
- 资源被长时间占用
```

**经验值**：超时时间一般设置为业务最大执行时间的 **3 倍**，既要保证业务能在超时内完成，又要给异常情况留出缓冲。

```java
public boolean tryLock(String lockKey, String requestId) {
    // 根据业务执行时间动态设置超时
    // 假设订单创建业务通常在 500ms 内完成，最长不超过 2s
    // 设置超时为 6s (2s × 3)
    long expireMillis = 6000L; 
    
    return jedis.set(lockKey, requestId, "NX", "PX", expireMillis) != null;
}
```

#### 锁超时导致的问题

```
场景: 业务执行时间超过锁超时时间

时间线:
  T0: 客户端 A 获取锁，超时时间 6s
  T1: 客户端 A 开始执行业务
  T2: 业务执行缓慢，已耗时 6s
  T3: 锁自动过期！Redis 删除了锁
  T4: 客户端 B 获取锁成功
  T5: 客户端 A 仍在执行业务（持有"已过期"的锁）
  T6: 客户端 A 和 B 同时执行业务 → 并发问题！

  ┌─────────────────────────────────────────────────────┐
  │ 时间轴                                               │
  │ T0    T1    T2    T3    T4    T5    T6               │
  │ |     |     |     |     |     |     |               │
  │ A:  [获取锁][执行业务...]  [锁过期]  [继续执行...]    │
  │ B:                    [获取锁][执行业务...]          │

```

### 2.5 锁续期机制（看门狗、Redisson 续期）

#### 看门狗（Watchdog）续期机制

**看门狗**是一种自动续期机制，在客户端获取锁后，启动一个后台线程定期检查并延长锁的过期时间。

```
┌─────────────────────────────────────────────────────────┐
│                   看门狗续期机制                          │
│                                                          │
│  ┌──────────────┐     ┌──────────────┐                  │
│  │  业务线程      │     │  看门狗线程    │                  │
│  └──────┬───────┘     └──────┬───────┘                  │
│         │                    │                           │
│         │ 获取锁              │                           │
│         │                    │ 启动                       │
│         │                    │                           │
│         │ 执行业务            │ 定期检查                  │
│         │                    │ (每 1/3 超时时间)          │
│         │                    │                           │
│         │                    │ 延长锁过期时间             │
│         │                    │ PERSIST key new_expire     │
│         │                    │                           │
│         │                    │ 继续检查...                │
│         │                    │                           │
│         │ 业务完成            │ 检测到业务完成            │
│         │ 释放锁              │ 停止续期                  │
│         │                    │                           │
│         │                    │ 退出                      │
│                                                          │

```

```java
public class DistributedLockWithWatchdog {
    
    private static final long LOCK_EXPIRE_MILLIS = 30000L;
    private static final long WATCHDOG_INTERVAL_MILLIS = LOCK_EXPIRE_MILLIS / 3;
    
    private final JedisPool jedisPool;
    private String lockKey;
    private String requestId;
    private volatile boolean locked = false;
    private Thread watchdogThread;
    
    public boolean tryLock() {
        Jedis jedis = jedisPool.getResource();
        try {
            requestId = UUID.randomUUID().toString();
            String result = jedis.set(lockKey, requestId, "NX", "PX", LOCK_EXPIRE_MILLIS);
            
            if ("OK".equals(result)) {
                locked = true;
                startWatchdog();
                return true;
            }
            return false;
        } finally {
            jedis.close();
        }
    }
    
    private void startWatchdog() {
        watchdogThread = new Thread(() -> {
            while (locked) {
                try {
                    Thread.sleep(WATCHDOG_INTERVAL_MILLIS);
                    
                    // 检查自己是否仍然持有锁
                    Jedis jedis = jedisPool.getResource();
                    try {
                        String currentValue = jedis.get(lockKey);
                        if (requestId.equals(currentValue)) {
                            // 延长过期时间
                            jedis.pexpire(lockKey, LOCK_EXPIRE_MILLIS);
                        } else {
                            // 锁已丢失，停止续期
                            locked = false;
                            break;
                        }
                    } finally {
                        jedis.close();
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
        }, "lock-watchdog-" + lockKey);
        watchdogThread.setDaemon(true);
        watchdogThread.start();
    }
    
    public void unlock() {
        locked = false;
        if (watchdogThread != null) {
            watchdogThread.interrupt();
        }
        
        Jedis jedis = jedisPool.getResource();
        try {
            // Lua 脚本原子释放
            String luaScript = 
                "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                "    return redis.call('del', KEYS[1]) " +
                "else return 0 end";
            jedis.eval(luaScript, 1, lockKey, requestId);
        } finally {
            jedis.close();
        }
    }
}
```

#### Redisson 续期机制

Redisson 是目前最流行的 Redis 客户端框架之一，它内置了完善的分布式锁实现和续期机制。

### 3.2 可重入锁实现原理

#### RLock 核心方法

```java
// Redisson 可重入锁使用示例
RedissonClient redisson = Redisson.create();
RLock lock = redisson.getLock("myLock");

// 阻塞式加锁
lock.lock();

// 带超时的加锁（支持自动续期）

// 尝试获取锁

```

#### 可重入锁的 Redis 数据结构

```
Redisson 可重入锁使用 Hash 数据结构存储:

Type: Hash
Fields:
  - "uuid:threadId": 重入次数 (Long)
  
示例:

    "client-uuid-1234:thread-5678" 3

- 持有者: client-uuid-1234 的 thread-5678
```

#### Lua 脚本实现可重入加锁

```lua
-- tryLock.lua
-- KEYS[1]: 锁的 key
-- ARGV[1]: 持有者标识 (clientId:threadId)
-- ARGV[2]: 锁的超时时间 (毫秒)
-- ARGV[3]: 获取锁的等待时间 (毫秒)

if redis.call('exists', KEYS[1]) == 0 then
    -- 锁不存在，设置新锁
    redis.call('hset', KEYS[1], ARGV[1], 1)
    redis.call('pexpire', KEYS[1], ARGV[2])
    return nil
end

if redis.call('hexists', KEYS[1], ARGV[1]) == 1 then
    -- 锁已存在且是自己持有，可重入
    redis.call('hincrby', KEYS[1], ARGV[1], 1)
    redis.call('pexpire', KEYS[1], ARGV[2])
    return nil
end

-- 锁被他人持有，返回过期时间
return redis.call('pttl', KEYS[1])
```

#### 解锁 Lua 脚本

```lua
-- unlock.lua
-- KEYS[1]: 锁的 key
-- ARGV[1]: 持有者标识 (clientId:threadId)

if redis.call('hexists', KEYS[1], ARGV[1]) == 0 then
    -- 不是锁的持有者，返回 nil
    return nil
end

local counter = redis.call('hincrby', KEYS[1], ARGV[1], -1)

if counter > 0 then
    -- 重入次数减1，但还未完全释放
    redis.call('pexpire', KEYS[1], redis.call('pttl', KEYS[1]))
    return 0
else
    -- 最后一次释放，删除 key 并发布通知
    redis.call('del', KEYS[1])
    redis.call('publish', KEYS[1] .. ':unlock', ARGV[1])
    return 1
end
```


### 3.3 读写锁、公平锁

#### 读写锁（RReadWriteLock）

读写锁允许多个客户端同时读取，但写入时独占。适用于读多写少的场景。

```java
RReadWriteLock rwLock = redisson.getReadWriteLock("rwLock");

// 读锁（共享锁）- 多个读者可同时持有
RLock readLock = rwLock.readLock();
readLock.lock();
try {
    // 读取操作
    String data = getData();
} finally {
    readLock.unlock();
}

// 写锁（排他锁）- 独占
RLock writeLock = rwLock.writeLock();
writeLock.lock();
try {
    // 写入操作
    updateData();
} finally {
    writeLock.unlock();
}
```

```
读写锁互斥规则:
┌──────────┬──────────┬──────────┐
│          │ 读锁      │ 写锁      │
├──────────┼──────────┼──────────┤
│ 读锁      │ 兼容      │ 冲突      │
│ 写锁      │ 冲突      │ 冲突      │
└──────────┴──────────┴──────────┘

场景:
- 多个客户端可以同时读取数据（读锁共享）
- 当一个客户端要写入时，必须等待所有读者释放
- 当有写入时，新的读操作也必须等待
```

#### 公平锁（Fair Lock）

公平锁按照请求顺序分配锁，先来的客户端先获得锁。

```java
// 普通锁（非公平）- 可能被后来者抢先获取
RLock unfairLock = redisson.getLock("lock");

// 公平锁 - 严格按照等待顺序获取
RLock fairLock = redisson.getFairLock("fairLock");
```

```
公平锁 vs 非公平锁:

非公平锁:
  客户端 A: [获取锁] → [执行] → [释放]
  客户端 B:          [等待...] → [获取锁] → [执行]
  客户端 C:                   [尝试...] → [获取锁!] ← C 抢先了 B

公平锁:
  客户端 A: [获取锁] → [执行] → [释放]
  客户端 B:          [等待...] → [获取锁] → [执行] ← B 先到，先获得
  客户端 C:                   [等待...] → [获取锁] → [执行]
```

#### 信号量（RSemaphore）与倒计时器（RCountDownLatch）

```java
// 信号量 - 限制并发数量
RSemaphore semaphore = redisson.getSemaphore("mySemaphore");
semaphore.trySetPermits(5);  // 最多5个并发

// 获取许可
semaphore.acquire();
try {
    // 并发执行
} finally {
    semaphore.release();
}

// 倒计时器 - 等待多个操作完成
RCountDownLatch latch = redisson.getCountDownLatch("myLatch");
latch.trySetCount(3);  // 等待3个完成

// 等待所有完成
latch.await();

// 某个任务完成时倒计时
latch.countDown();
```

### 3.4 RedLock 算法（多 Redis 实例）

#### RedLock 问题背景

当 Redis 主从切换时，可能导致锁丢失。

```
主从切换导致锁丢失场景:
┌──────────┐     复制     ┌──────────┐
│  主库      │──────────►│  从库     │
│  Master   │            │  Slave   │
└────┬─────┘            └──────────┘
     │
     │ 客户端 A 获取锁
     │ SET lock_key value NX PX 30000
     │
     │ [主库宕机！]
     │
     │            从库提升为新主库
     │            但锁的 key 还未同步过来！
     │
     │ 客户端 B 从新主库获取锁
     │ SET lock_key value-B NX PX 30000
     │ → 成功！（因为 key 还没同步）
     │
     │ 结果: A 和 B 同时持有锁 → 严重错误！
```

#### RedLock 算法原理

RedLock 是 Redis 作者 antirez 提出的一种在**多个独立 Redis 实例**上分布式加锁的算法。

```
RedLock 算法流程:
┌─────────────────────────────────────────────────────────┐
│                                                          │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│   │ Redis #1  │  │ Redis #2  │  │ Redis #3  │              │
│   └──────────┘  └──────────┘  └──────────┘              │
│        ↑              ↑              ↑                    │
│        │              │              │                    │
│   客户端同时向所有实例尝试加锁:                             │
│                                                          │
│   步骤:                                                  │
│   1. 获取当前时间 T1                                      │
│   2. 依次向 N 个 Redis 实例尝试加锁（带超时）              │
│   3. 统计成功加锁的实例数 M（M > N/2）                    │
│   4. 计算加锁耗时 T2 - T1                                │
│   5. 如果 M > N/2 且耗时 < 锁超时时间                     │
│      → 加锁成功，有效时间 = 超时 - 耗时                   │
│   6. 否则 → 加锁失败，向所有实例解锁                      │
│                                                          │
│   示例: 5 个 Redis 实例                                   │
│   - 至少需要 3 个成功（多数派）                            │
│   - 即使 1-2 个实例故障，仍能正常工作                      │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

#### RedLock 实现代码

```java
public class RedLock {
    
    private final RedissonClient[] redissonClients;
    
    public RedLock(RedissonClient... redissonClients) {
        this.redissonClients = redissonClients;
    }
    
    public boolean tryLock(long waitTime, long leaseTime, TimeUnit unit) {
        long start = System.currentTimeMillis();
        int successCount = 0;
        String requestId = UUID.randomUUID().toString();
        
        // 向所有实例尝试加锁
        for (RedissonClient client : redissonClients) {
            RLock lock = client.getLock("myLock");
            try {
                if (lock.tryLock(waitTime, leaseTime, unit)) {
                    successCount++;
                }
            } catch (Exception e) {
                // 单个实例失败不影响整体
            }
        }
        
        long elapsed = System.currentTimeMillis() - start;
        int quorum = redissonClients.length / 2 + 1;
        
        // 多数派成功且耗时小于租约时间
        if (successCount >= quorum && elapsed < leaseTime) {
            return true;
        }
        
        // 加锁失败，向所有实例解锁
        for (RedissonClient client : redissonClients) {
            RLock lock = client.getLock("myLock");
            try {
                lock.unlock();
            } catch (Exception e) {
                // 忽略
            }
        }
        return false;
    }
    
    public void unlock() {
        for (RedissonClient client : redissonClients) {
            RLock lock = client.getLock("myLock");
            try {
                lock.unlock();
            } catch (Exception e) {
                // 忽略
            }
        }
    }
}
```

#### RedLock 的争议与评价

| 观点 | 说明 |
|------|------|
| **支持** | 在多 Redis 实例场景下提供了更强的一致性保证，即使部分实例故障也能正常工作 |
| **反对** | Martin Kleppmann 认为 RedLock 存在时钟依赖问题，不是真正的分布式锁 |
| **中立** | 在大多数业务场景下，单实例 + 合理的故障转移机制已经足够 |

**RedLock 的适用场景**：
- 对锁的可靠性要求极高（如金融交易、分布式事务）
- 可以接受更复杂的部署和实现
- 有多个独立 Redis 实例的基础设施

### 4.2 双写模式 vs 读写分离

#### 读写分离模式

```
┌──────────┐
│  应用实例  │
└────┬─────┘
     │
     ▼
┌─────────────────────────────────────┐
│           读写分离中间件              │
│  (如 ShardingSphere, ProxySQL)       │
└────┬────────────────────────────┬────┘
     │                            │
  写请求                       读请求
     │                            │
     ▼                            ▼
┌──────────┐              ┌──────────┐
│  Redis    │              │  Redis    │
│  主库     │              │  从库     │
└──────────┘              └──────────┘

适用场景:
- 读多写少
- 可以容忍短暂的数据不一致
- 如：排行榜、缓存、配置信息
```

#### 双写模式

```
┌──────────┐
│  应用实例  │
└────┬─────┘
     │
     ├──► 先写主库 Redis
     │         │
     │         └──► 成功后，再写从库 Redis
     │
     ▼
┌─────────────────────────────────────┐
│  双写逻辑                             │
│  1. 写主库                            │
│  2. 写从库（同步或异步）               │
│  3. 两个都成功才返回                   │
└─────────────────────────────────────┘

适用场景:
- 对数据一致性要求高
- 写操作重要（如锁操作）
- 可以接受一定的性能损失
```

#### 两种模式对比

| 对比维度 | 读写分离 | 双写模式 |
|---------|---------|---------|
| **数据一致性** | 可能有延迟 | 强一致 |
| **性能** | 高（读负载分散） | 较低（双写开销） |
| **实现复杂度** | 低 | 高 |
| **适用场景** | 读多写少 | 强一致性要求 |
| **锁操作推荐** | ❌ 不推荐 | ✅ 推荐 |

**锁操作的最佳实践**：锁操作应使用**双写模式**或**主库单写**，避免在从库上执行加锁/解锁操作。

### 4.4 Redis 与数据库一致性

#### 缓存与数据库一致性策略

```
方案一：先更新数据库，再删除缓存（Cache-Aside Pattern）

  写请求:
  1. 更新数据库
  2. 删除缓存
  3. 返回成功

  读请求:
  1. 读缓存
  2. 缓存未命中 → 读数据库
  3. 写入缓存
  4. 返回数据

  问题: 并发场景下可能有短暂不一致
```

```java
// 先更新数据库，再删除缓存
public void updateUser(Long userId, UserInfo info) {
    // 1. 更新数据库
    userMapper.updateById(userId, info);
    
    // 2. 删除缓存
    redisCache.del("user:" + userId);
}
```

#### 分布式锁与数据库的一致性

```
使用分布式锁保证缓存与数据库的一致性:

  1. 获取分布式锁（基于数据 ID）
  2. 读取当前数据（可能在缓存中）
  3. 更新数据库
  4. 更新缓存（或删除缓存）
  5. 释放分布式锁

  优势:
  - 锁保证同一时刻只有一个写操作
  - 避免并发更新导致的一致性问题
  - 适合关键数据的更新场景
```

```java
public void updateStock(Long productId, int quantity) {
    RLock lock = redissonClient.getLock("stock:" + productId);
    
    try {
        lock.lock();
        
        // 1. 读取当前库存
        Stock stock = stockMapper.selectById(productId);
        
        // 2. 计算新库存
        int newStock = stock.getQuantity() - quantity;
        if (newStock < 0) {
            throw new BusinessException("库存不足");
        }
        
        // 3. 更新数据库
        stockMapper.update(productId, newStock);
        
        // 4. 更新缓存
        redisCache.set("stock:" + productId, newStock);
        
    } finally {
        lock.unlock();
    }
}
```

### 4.5 高可用架构选型

#### 根据业务规模选型

```
┌────────────┬─────────────────────────────────────┬──────────────────────┐
│ 业务规模     │ 推荐架构                             │ 特点                 │
├────────────┼─────────────────────────────────────┼──────────────────────┤
│ 小型应用     │ 单机 Redis + 定时备份                │ 简单、成本低          │
│ (< 1万 QPS) │                                     │                      │
├────────────┼─────────────────────────────────────┼──────────────────────┤
│ 中型应用     │ 主从 + Sentinel                      │ 自动故障转移          │
│ (1-10万QPS) │ + 从节点备份                         │ 读写分离             │
├────────────┼─────────────────────────────────────┼──────────────────────┤
│ 大型应用     │ Redis Cluster + 跨机房部署           │ 自动分片             │
│ (10万+QPS)  │ + 双活/灾备                          │ 高可用               │
├────────────┼─────────────────────────────────────┼──────────────────────┤
│ 核心业务     │ 多独立集群 + RedLock               │ 最强一致性            │
│ (金融/支付) │ + 异地灾备 + 数据校验                │ 多活容灾             │
└────────────┴─────────────────────────────────────┴──────────────────────┘
```

#### 关键决策因素

```
1. 数据一致性要求
   - 强一致 → 双写 / RedLock
   - 最终一致 → 读写分离 / 主从复制

2. 性能要求
   - 高并发 → Cluster 分片
   - 一般 → 主从或单机

3. 可用性要求
   - 99.9% → 主从复制
   - 99.99% → Sentinel / Cluster
   - 99.999% → 多活 / 异地灾备

4. 成本预算
   - 低 → 单机 + 定时备份
   - 中 → 主从 + Sentinel
   - 高 → Cluster + 跨机房

5. 运维能力
   - 弱 → 云服务（阿里云 Redis、AWS ElastiCache）
   - 强 → 自建集群
```

### 5.2 核心流程：扣减库存

#### 方案一：Redis Lua 脚本原子扣减

```lua
-- deduct_stock.lua
-- 原子扣减库存脚本

local stock_key = KEYS[1]        -- 库存 key
local order_key = KEYS[2]        -- 订单集合 key
local user_id = ARGV[1]          -- 用户 ID
local order_id = ARGV[2]         -- 订单 ID
local deduct_count = tonumber(ARGV[3])  -- 扣减数量

-- 检查库存
local stock = tonumber(redis.call('get', stock_key))
if stock == nil or stock < deduct_count then
    return -1  -- 库存不足
end

-- 检查是否重复下单
if redis.call('sismember', order_key, user_id) == 1 then
    return -2  -- 重复下单
end

-- 扣减库存
redis.call('decrby', stock_key, deduct_count)

-- 记录订单
redis.call('sadd', order_key, user_id)
redis.call('hset', 'order:' .. order_id, 
    'user_id', user_id,
    'status', 'pending',
    'create_time', redis.call('time')[1]
)

-- 设置过期时间（防止订单无限增长）
redis.call('expire', order_key, 86400)

return 1  -- 成功
```

```java
@Service
public class SeckillService {
    
    @Autowired
    private RedissonClient redissonClient;
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private RocketMQTemplate mqTemplate;
    
    /**
     * 秒杀核心方法
     */
    public SeckillResult seckill(SeckillRequest request) {
        String stockKey = "seckill:stock:" + request.getActivityId();
        String orderKey = "seckill:orders:" + request.getActivityId();
        
        // 1. Lua 脚本原子扣减库存
        String luaScript = new String(
            Files.readAllBytes(Paths.get("deduct_stock.lua")),
            StandardCharsets.UTF_8
        );
        
        String orderId = "ORDER_" + UUID.randomUUID().toString().replace("-", "");
        
        Long result = redisTemplate.execute(
            RedisScript.of(luaScript, Long.class),
            stockKey,
            orderKey,
            request.getUserId(),
            orderId,
            String.valueOf(request.getQuantity())
        );
        
        if (result == -1L) {
            throw new BusinessException("活动已结束或库存不足");
        }
        if (result == -2L) {
            throw new BusinessException("您已参与过本次活动");
        }
        
        // 2. 发送消息到消息队列，异步创建正式订单
        SeckillOrderMessage message = new SeckillOrderMessage();
        message.setOrderId(orderId);
        message.setUserId(request.getUserId());
        message.setActivityId(request.getActivityId());
        message.setQuantity(request.getQuantity());
        
        mqTemplate.syncSend("seckill-order-topic", message);
        
        // 3. 返回秒杀成功
        return SeckillResult.success(orderId);
    }
    
    /**
     * 消费消息，创建正式订单
     */
    @RabbitListener(queues = "seckill-order-queue")
    public void createSeckillOrder(SeckillOrderMessage message) {
        RLock lock = redissonClient.getLock(
            "order:create:" + message.getOrderId()
        );
        
        try {
            if (!lock.tryLock(5, 60, TimeUnit.SECONDS)) {
                retryMessage(message);
                return;
            }
            
            Map<Object, Object> orderInfo = redisTemplate.ops()
                .forHash().entries("order:" + message.getOrderId());
            
            if (orderInfo.isEmpty()) {
                log.warn("订单信息不存在: {}", message.getOrderId());
                return;
            }
            
            Order order = new Order();
            order.setOrderId(message.getOrderId());
            order.setUserId(message.getUserId());
            order.setStatus(OrderStatus.PAID);
            order.setCreateTime(new Date());
            
            orderMapper.insert(order);
            
            redisTemplate.opsForHash().put(
                "order:" + message.getOrderId(), 
                "status", "created"
            );
            
        } catch (Exception e) {
            log.error("创建订单失败", e);
            restoreStock(message);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

## 六、常见问题与陷阱

### 6.1 缓存与数据库一致性

#### 问题描述

在使用 Redis 作为数据库缓存时，如何保证缓存与数据库的数据一致性？

#### 常见方案对比

| 方案 | 流程 | 优点 | 缺点 |
|------|------|------|------|
| **Cache-Aside** | 先更新DB，再删缓存 | 简单、常用 | 并发下可能短暂不一致 |
| **Read/Write Through** | 应用不直接操作DB | 逻辑内聚 | 实现复杂 |
| **Write Behind** | 先写缓存，异步写DB | 性能好 | 可能丢数据 |
| **两阶段提交** | 分布式事务保证强一致 | 强一致 | 性能差、复杂 |

#### 最佳实践

```
1. 使用 Cache-Aside 模式（最常用）
2. 删除缓存而非更新缓存
3. 缓存设置合理的过期时间
4. 使用分布式锁保护关键数据的更新
5. 定期进行缓存与数据库的对账

关键数据更新流程:
  1. 获取分布式锁
  2. 更新数据库
  3. 删除缓存
  4. 释放锁
```

### 6.2 锁粒度问题

#### 什么是锁粒度

锁粒度是指锁的保护范围。粗粒度锁保护范围大但并发度低，细粒度锁保护范围小但并发度高。

```
粗粒度锁:
  lock("order") → 所有订单操作串行化
  简单但性能差

细粒度锁:
  lock("order:12345") → 只有订单12345的操作串行化
  复杂但性能好
```

#### 锁粒度选择原则

```
1. 尽可能细粒度：只保护必要的资源
2. 避免锁内操作耗时：锁内只做核心操作
3. 锁的生命周期尽可能短：获取后尽快释放
4. 锁的命名规范：清晰标识锁的范围

示例:
  // 好的锁粒度
  lock("stock:" + productId)  // 按商品加锁
  
  // 差的锁粒度
  lock("stock")  // 所有商品共用一把锁
```

### 6.3 锁超时与续期

#### 超时设置原则

```
1. 超时时间 = 业务最大执行时间 × 3
   - 给异常情况留出缓冲
   - 避免业务执行超时导致锁提前释放

2. 使用看门狗自动续期
   - Redisson 默认支持
   - 自定义实现时需注意
```

#### 常见超时问题

```
问题1: 业务执行超时，锁提前释放
  解决方案: 
  - 增加超时时间
  - 使用看门狗续期
  - 优化业务逻辑，减少执行时间

问题2: 看门狗续期失败
  解决方案:
  - 检查 Redis 连接状态
  - 设置续期失败告警
  - 实现续期重试机制

问题3: 锁在业务完成前丢失
  解决方案:
  - 检查锁的持有者标识是否正确
  - 使用 Lua 脚本保证原子性
```

### 6.4 锁重入与降级

#### 可重入锁的正确使用

```java
// 正确：可重入，不会死锁
public void methodA() {
    lock.lock();
    try {
        methodB();  // methodB 也使用同一把锁
    } finally {
        lock.unlock();
    }
}

public void methodB() {
    lock.lock();  // 可重入，计数+1
    try {
        // 业务逻辑
    } finally {
        lock.unlock();  // 计数-1
    }
}

// 错误：不可重入时会死锁
public void methodA() {
    lock.lock();
    try {
        methodB();  // 如果锁不支持重入，这里会死锁
    } finally {
        lock.unlock();
    }
}
```

#### 降级策略

当分布式锁服务不可用时，需要有降级方案：

```java
public class LockServiceWithFallback {
    
    public <T> T executeWithLock(String lockKey, 
                                  long timeout,
                                  Callable<T> task) {
        RLock lock = redissonClient.getLock(lockKey);
        
        try {
            if (lock.tryLock(timeout, TimeUnit.SECONDS)) {
                return task.call();
            }
        } catch (Exception e) {
            log.warn("获取分布式锁失败，尝试降级", e);
        }
        
        // 降级方案：使用本地锁
        return executeWithLocalLock(lockKey, task);
    }
    
    private <T> T executeWithLocalLock(String lockKey, Callable<T> task) {
        // 使用 ConcurrentHashMap 存储本地锁
        ReentrantLock localLock = localLocks.computeIfAbsent(
            lockKey, k -> new ReentrantLock()
        );
        
        localLock.lock();
        try {
            return task.call();
        } finally {
            localLock.unlock();
        }
    }
}
```

## 七、常见面试题

### 7.1 基础概念

**Q1: 什么是分布式锁？它解决了什么问题？**

分布式锁是一种跨进程、跨节点的互斥控制机制。在单机应用中，我们使用 `synchronized` 或 `ReentrantLock` 来实现线程间的互斥；但在分布式系统中，多个服务实例部署在不同服务器上，JVM 级别的锁无法跨 JVM 生效。分布式锁就是为了解决分布式环境下的并发控制问题，确保同一时刻只有一个节点能访问共享资源。

**Q2: 分布式锁应该满足哪些特性？**

一个完善的分布式锁需要满足：
1. **互斥性**：同一时刻只能有一个客户端持有锁
2. **不可死锁**：锁有超时机制，即使持有者崩溃也能自动释放
3. **可重入性**：同一个客户端可以多次获取同一把锁
4. **原子性**：加锁、解锁操作必须原子执行
5. **高性能**：加锁解锁延迟低、吞吐量高
6. **可续期**：支持业务执行期间自动延长锁的过期时间

**Q3: 为什么 SETNX + EXPIRE 不是正确的实现？**

`SETNX` 和 `EXPIRE` 是两个独立的 Redis 命令，它们的执行不是原子的。如果在 `SETNX` 执行成功后、`EXPIRE` 执行前，Redis 宕机或客户端崩溃，锁就不会设置过期时间，导致死锁。正确做法是使用 `SET key value NX PX milliseconds` 命令，它原子地完成了设置值和设置过期时间两个操作。

### 7.2 实现原理

**Q4: Redis 分布式锁如何保证解锁的原子性？**

通过 Lua 脚本实现。Redis 执行 Lua 脚本时是原子的，不会被其他命令打断。解锁脚本先验证当前锁的持有者标识是否与请求者一致，只有一致时才执行删除操作。这样避免了"锁过期后被他人持有，但原持有者误删"的问题。

**Q5: Redisson 的看门狗续期机制是怎样的？**

Redisson 在获取锁后会启动一个看门狗任务，默认每 10 秒（30 秒超时的 1/3）检查并续期一次。续期时使用 Lua 脚本验证持有者身份，只有持有者仍然存活且持有锁时才会续期。当业务完成主动解锁，或客户端关闭时，看门狗自动停止。

**Q6: RedLock 算法解决了什么问题？它有什么局限性？**

RedLock 试图解决主从切换导致的锁丢失问题。它向多个独立的 Redis 实例尝试加锁，只有获得多数派（>N/2）的锁才算成功。局限性包括：
1. 实现复杂，需要多个独立 Redis 实例
2. 性能较低，需要多次网络通信
3. Martin Kleppmann 指出其存在时钟依赖问题
4. 在大多数业务场景下过于复杂

### 7.3 高可用

**Q7: Redis 集群模式下如何实现分布式锁？**

Redis Cluster 使用 Hash Slot 机制将 16384 个槽位分配到不同的主节点上。分布式锁的 key 会根据哈希算法定位到特定槽位，由对应的主节点处理。Redisson 客户端会自动处理集群路由，将锁操作发送到正确的节点。集群模式天然支持故障转移，当某个主节点故障时，其从节点会自动提升为新主节点。

**Q8: 主从切换时如何保证锁的一致性？**

有三种策略：
1. **双写模式**：同时写主库和从库，两边都成功才返回
2. **RedLock 算法**：向多个独立实例加锁，多数派成功即可
3. **合理的超时设置**：即使发生主从切换，锁的超时机制可以保证最终释放

实际生产中通常结合使用：集群模式 + 合理超时 + 主从延迟监控。

**Q9: 如何防止分布式锁的误删？**

1. 使用唯一的 requestId 标识每个锁的持有者
2. 解锁时先验证持有者身份，再删除
3. 使用 Lua 脚本原子执行"验证 + 删除"操作
4. 不要使用 `DEL` 命令直接删除锁

### 7.4 工程实践

**Q10: 如何选择锁的超时时间？**

超时时间应根据业务执行时间来确定：
1. 统计业务的平均执行时间和最大执行时间
2. 设置超时时间 = 最大执行时间 × 3
3. 使用看门狗自动续期，避免业务超时导致锁提前释放
4. 监控锁的持有时间，及时发现异常

**Q11: 获取锁失败后应该如何处理？**

1. **重试等待**：等待一段时间后重试（推荐）
2. **立即失败**：适用于实时性要求高的场景
3. **降级处理**：使用本地锁或直接执行（适用于非关键场景）
4. **排队等待**：使用消息队列排队处理

```java
// 推荐的重试策略
public boolean tryLockWithRetry(String lockKey, int maxRetry, long intervalMs) {
    for (int i = 0; i < maxRetry; i++) {
        if (lock.tryLock(intervalMs, TimeUnit.MILLISECONDS)) {
            return true;
        }
        // 指数退避
        sleep(intervalMs * (1L << i));
    }
    return false;
}
```

**Q12: 如何设计高可用的分布式锁服务？**

1. **部署层面**：Redis 主从 + Sentinel 自动故障转移，或 Redis Cluster 集群模式
2. **数据层面**：双写保证主从一致性，监控主从延迟
3. **应用层面**：Redisson 客户端自动重连、优雅降级方案
4. **监控层面**：监控锁的获取率、持有时间、超时次数
5. **容灾层面**：跨机房部署、异地灾备、锁服务独立部署
