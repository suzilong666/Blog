一、Redis 数据结构概述 ​

1.1 Redis 为什么要自研数据结构 ​

Redis 是一款高性能的内存数据库，其核心竞争力在于极致的执行效率。为了实现这一目标，Redis 没有直接使用 C 语言标准库或现有的数据结构库，而是自行实现了一套高效的数据结构。

这些自定义数据结构的设计目标包括：

设计目标说明
高效的内存使用动态调整内存大小，避免浪费
快速的查询速度实现 O(1) 或 O(log n) 的操作
灵活的编码方式根据数据规模自动选择最优编码
二进制安全支持存储任意二进制数据
兼容性设计在效率和兼容性之间取得平衡

二、SDS（Simple Dynamic String） ​

2.1 为什么不使用 C 字符串 ​

C 语言中的字符串是以 \0 结尾的字符数组，这种设计存在以下问题：

问题C 字符串SDS 解决方案
获取长度需要遍历字符串，O(n)直接存储长度，O(1)
缓冲区溢出不确定空间大小，易溢出动态分配空间，自动扩展
二进制安全遇到 \0 截断以显式长度为准，支持二进制
重复分配每次修改都需重新分配空间预分配，减少 realloc

C 字符串的问题示例：

c
// C 字符串获取长度需要遍历
char* str = "Hello, Redis!";
size_t len = strlen(str);  // O(n) 遍历字符串

// 二进制数据无法存储
char* binary_data = "data\0binary";  // 存储到 \0 处就结束了
printf("%s", binary_data);  // 只输出 "data"

// 缓冲区溢出风险
char buffer[10];
strcpy(buffer, "This string is too long!");  // 缓冲区溢出！

2.2 SDS 结构定义 ​

SDS 的底层实现位于 Redis 源码的 sds.h 文件中，其结构定义如下：

c
typedef struct sdshdr {
    int len;      // 已使用的字符串长度
    int free;     // 剩余可用空间长度
    char buf[];   // 实际存储数据的字符数组
} sdshdr;

SDS 与 C 字符串的兼容性：

SDS 的 buf 字段仍然以 \0 结尾，这使得 SDS 可以直接使用 C 字符串的函数（如 printf），实现了向后兼容。

2.3 SDS 的核心优势 ​

常数时间获取字符串长度 ​

c
// SDS 获取长度，O(1)
sds mystr = sdsnew("Hello, Redis!");
size_t len = sdslen(mystr);  // 直接读取 len 字段

// C 字符串获取长度，O(n)
char* str = "Hello, Redis!";
size_t len = strlen(str);  // 遍历整个字符串

避免缓冲区溢出 ​

c
// SDS 自动扩展空间
sds s = sdsnew("Hello");
// 内部: len=5, free=?, buf=["Hello\0"]

s = sdscat(s, ", Redis!");  // 自动分配足够的空间
// 内部: len=13, free=? 
// 不会发生缓冲区溢出

二进制安全 ​

c
// SDS 可以存储任意二进制数据
char binary_data[] = {'d', 'a', 't', 'a', '\0', 'b', 'i', 'n', 'a', 'r', 'y'};
sds s = sdsnewlen(binary_data, 11);  // 显式指定长度

// SDS 内部以 len 为准，\0 只是结束符，不是分隔符
sdslen(s);  // 返回 11，而不是 4

兼容 C 字符串 ​

c
// SDS 可以直接作为 C 字符串使用
sds s = sdsnew("Hello, Redis!");
printf("%s", s);  // 直接传递，不需要转换

// 获取 C 字符串指针
const char* c_str = sdscstr(s);  // 但不需要这样做，SDS 本身就是 char* 类型

2.4 SDS 空间预分配策略 ​

为了减少内存重分配的次数，SDS 采用了空间预分配策略：

扩展时的分配规则 ​

当 SDS 需要扩展时，会根据以下规则预分配额外空间：

c
// sdsMakeRoomFor 函数的预分配逻辑
sds sdsMakeRoomFor(sds s, size_t addlen) {
    // ... 
    size_t newlen = sdslen(s) + addlen;
    
    if (newlen < SDS_MAX_PREALLOC) {
        // 如果新长度小于 SDS_MAX_PREALLOC (1024*1024 = 1MB)
        // 分配 2 倍的新长度
        newlen *= 2;
    } else {
        // 如果新长度超过 1MB
        // 分配新长度 + 1MB
        newlen += SDS_MAX_PREALLOC;
    }
    // ...
}

预分配示意图 ​

扩展前:
  ┌─────┬─────┬──────────────────────┐
  │ len │free │         buf[]         │
  ├─────┼─────┼──────────────────────┤
  │  10 │   5 │ [data][...][\0]      │
  └─────┴─────┴──────────────────────┘

需要追加 20 字节:
  新长度 = 10 + 20 = 30
  30 < SDS_MAX_PREALLOC (1MB)
  预分配 = 30 * 2 = 60

扩展后:
  ┌─────┬─────┬──────────────────────────────────────────────────┐
  │ len │free │                    buf[]                           │
  ├─────┼─────┼──────────────────────────────────────────────────┤
  │  30 │  30 │ [新data][...][\0]  ...  ...  ...  ...  ...  ...  │
  └─────┴─────┴──────────────────────────────────────────────────┘

2.6 SDS 对 Redis 性能的贡献 ​

SDS 的设计对 Redis 的高性能至关重要：

  1. O(1) 的长度获取：STRLEN 命令直接读取 len 字段，无需遍历
  2. 减少内存重分配：预分配策略使 APPEND 操作的平均时间复杂度为 O(1)
  3. 二进制安全：支持存储图片、序列化数据等二进制内容
  4. 避免缓冲区溢出：减少安全漏洞的风险

三、哈希表（Hash Table） ​

3.1 哈希表在 Redis 中的应用 ​

哈希表是 Redis 最重要的数据结构之一，被广泛用于：

  • 数据库核心结构：Redis 的每个数据库都是一个哈希表
  • Hash 类型的底层实现：当 Hash 对象字段较多时使用哈希表
  • 字典实现：Redis 的 dict 结构就是一个哈希表

3.2 Redis 字典（dict）结构 ​

Redis 使用 dict 结构作为其核心哈希表实现，定义在 dict.h 中：

c
typedef struct dict {
    dictType *type;      // 字典类型，包含一组操作函数
    void *privdata;      // 私有数据，传给类型特定的函数
    dictht table[2];     // 两个哈希表，用于渐进式 rehash
    int rehashidx;       // rehash 进度标记，-1 表示未在 rehash
    int iterators;       // 正在使用的迭代器数量
} dict;

哈希表结构（dictht） ​

c
typedef struct dictht {
    dictEntry **table;   // 哈希表数组
    unsigned long size;  // 哈希表大小（必须是 2 的幂）
    unsigned long sizemask;  // size - 1，用于快速取模
    unsigned long used;  // 已使用的节点数量
} dictht;

哈希表节点（dictEntry） ​

c
typedef struct dictEntry {
    void *key;           // 键
    union {
        void *val;       // 指针值
        uint64_t u64;   // 无符号 64 位整数
        int64_t s64;    // 有符号 64 位整数
        double d;       // 浮点数
    } v;
    struct dictEntry *next;  // 冲突链表的下一个节点
} dictEntry;

  • 非加密：不需要安全保证，追求速度

Redis 使用链地址法解决哈希冲突。当多个键映射到同一位置时，通过链表串联：

查询过程:
  1. 计算 hash(key) & sizemask 得到位置
  2. 遍历该位置的链表
  3. 逐个比较 key 是否匹配
  4. 找到则返回，否则继续或返回 NULL

3.6 渐进式 Rehash 机制 ​

为什么需要渐进式 Rehash ​

当哈希表的负载因子（used / size）过高或过低时，需要进行扩容或收缩。但如果一次性完成 rehash，对于大型哈希表会造成阻塞问题。

Redis 采用渐进式 rehash 来解决这个问题，将 rehash 分散到多次操作中完成。

渐进式 Rehash 过程 ​

Rehash 开始前:
  table[0]: size=4, used=4, rehashidx=-1
  ┌────┬────┬────┬────┐
  │ A  │ B  │ C  │ D  │
  └────┴────┴────┴────┘

第一步: 创建 table[1]
  table[0]: size=4, used=4
  ┌────┬────┬────┬────┐
  │ A  │ B  │ C  │ D  │
  └────┴────┴────┴────┘
  
  table[1]: size=8, used=0
  ┌────┬────┬────┬────┬────┬────┬────┬────┐
  │NULL│NULL│NULL│NULL│NULL│NULL│NULL│NULL│
  └────┴────┴────┴────┴────┴────┴────┴────┘

渐进式 Rehash（每次 rehash 一个索引位置）:
  rehashidx=0: 迁移 table[0][0] → table[1]
  rehashidx=1: 迁移 table[0][1] → table[1]
  rehashidx=2: 迁移 table[0][2] → table[1]
  rehashidx=3: 迁移 table[0][3] → table[1]
  
  每次 rehash 完成后，rehashidx++
  
  当 rehashidx == table[0].size 时，rehash 完成
  释放 table[0]，table[1] 成为新的 table[0]

Rehash 期间的读写操作 ​

在渐进式 rehash 期间，Redis 的读写操作会同时操作两个哈希表：

c
// 查找操作：先查 table[0]，没找到再查 table[1]
dictEntry *dictFind(dict *d, const void *key) {
    // 先在 table[0] 中查找
    entry = dictFindInHashTable(d->table[0], key);
    if (entry) return entry;
    
    // 如果在 rehash，还要查 table[1]
    if (d->rehashidx != -1) {
        entry = dictFindInHashTable(d->table[1], key);
        if (entry) return entry;
    }
    return NULL;
}

// 插入操作：直接插入 table[1]
// 删除操作：同时从两个表中删除

触发 Rehash 的条件 ​

扩容条件：

  • 当负载因子 used / size >= 1 时，且未在执行 BGSAVE 或 BGWRITEAOF
  • 当负载因子 used / size >= 5 时，无论是否在执行子进程任务

收缩条件：

  • 当负载因子 used / size < 0.1 时
c
// 扩容时机判断

    // 当负载因子过大时触发扩容

        !(d->iterator & DICT_HT_REHASH_AVOID)) {
        // 执行 rehash

四、跳表（Skip List） ​

4.1 跳表的引入 ​

跳表是一种基于有序链表的数据结构，通过在链表上建立多级索引，实现了类似二分查找的效率。

Redis 使用跳表作为有序集合（Sorted Set）的底层实现之一，相比红黑树，跳表的实现更简单，范围查询更高效。

4.2 跳表的结构 ​

跳表节点结构 ​

c
typedef struct zskiplistNode {
    sds ele;                        // 成员对象
    double score;                   // 分值，用于排序
    struct zskiplistNode *backward; // 后退指针
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // 前进指针
        unsigned long span;            // 跨度
    } level[];                          // 层数组
} zskiplistNode;

跳表整体结构 ​

typedef struct zskiplist {
    struct zskiplistNode *header, *tail;  // 头尾节点
    unsigned long length;                  // 跳表长度
    int level;                             // 最大层数
} zskiplist;

Level 2:
  header ─────────────► node C ──────────────────► tail
  |                     |                         ^
  | 25 > C.score(30)? 不，25 < 30，在 C 前面

Level 1:
  header ───► node A ──► node C ──────────────────► tail
  |            |          |                       ^
  | 25 > A.score(10)? 是
  | 25 > C.score(30)? 不，25 < 30，在 C 前面

Level 0 (找到精确位置):
  header ──► node A ──► node B ──► node C ──► node D ──► tail
                         |
                         | 25 > B.score(20)? 是
                         | 25 < C.score(30)? 是 → 找到了！
                         ↓
                      node B (score=20)
                      node C (score=30) → 目标位置在 B 和 C 之间

4.5 跳表的插入过程 ​

插入位置的确定 ​

插入节点前需要先找到合适的位置，同时记录每一层的前驱节点：

c
// 插入前的查找过程
zskiplistNode *update[ZSKIPLIST_MAXLEVEL];  // 记录每一层的前驱
unsigned long rank[ZSKIPLIST_MAXLEVEL];     // 记录排名

// 从最高层开始向下查找
for (int i = z->level - 1; i >= 0; i--) {
    // 记录当前排名
    rank[i] = (i == z->level - 1) ? 0 : rank[i + 1];
    
    // 在当前层向前遍历，直到找到合适位置
    while (x->level[i].forward && 
           (x->level[i].forward->score < score ||
            (x->level[i].forward->score == score && 
             compare(x->level[i].forward->ele, ele) <= 0))) {
        rank[i] += x->level[i].span;
        x = x->level[i].forward;
    }
    
    // 记录前驱节点
    update[i] = x;
}

随机层数生成 ​

跳表通过随机算法决定新节点的层数，层数越高的节点越稀疏：

c
// 随机生成层数
int zslRandomLevel(void) {
    int level = 1;
    // 有 1/4 概率继续增加层数
    while ((random() & 0xFFFF) < (ZSKIPLIST_P * 0xFFFF))  // ZSKIPLIST_P = 0.25
        level += 1;
    return (level < ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;
}

层数分布概率：

  • 1 层：100%（所有节点）
  • 2 层：25%（1/4 概率）
  • 3 层：6.25%（1/16 概率）
  • 4 层：1.56%（1/64 概率）
  • ...
  • 32 层：几乎不可能

插入操作示意图 ​

插入 score=25, ele="e" 的节点:

1. 查找插入位置，获取 update 数组:
  update[0] = node B (Level 0 的前驱)
  update[1] = node A (Level 1 的前驱)
  update[2] = header (Level 2 的前驱)
  update[3] = header (Level 3 的前驱)

2. 随机生成层数: level = 2

3. 创建新节点:
  new_node: score=25, ele="e", level[0], level[1]

4. 更新各层的指针:
  Level 0: new_node→forward = update[0]→forward
           update[0]→forward = new_node
           
  Level 1: new_node→level[1].forward = update[1]→level[1].forward
           update[1]→level[1].forward = new_node

5. 更新 span 和 backward 指针

4.6 跳表的删除过程 ​

删除 score=25 的节点:

1. 查找待删除节点和其前驱:
  update[0] = node B
  update[1] = node A
  ...

2. 逐层删除:
  for i = 0 to level-1:
    update[i]->level[i].forward = node->level[i].forward

3. 更新 span 值

4. 更新 backward 指针

5. 如果最高层变空，减少跳表的 level

五、压缩列表（ZipList） ​

5.1 压缩列表概述 ​

压缩列表（ZipList）是 Redis 为节约内存而设计的一种特殊编码结构，用于存储小数据量的 List、Hash 和 Sorted Set。

5.2 压缩列表的设计目标 ​

目标说明
极致的内存节省连续内存，无指针开销
快速的随机访问通过偏移量快速定位
支持多种编码整数和字符串的灵活编码
兼容性可快速转换为其他结构

5.3 压缩列表结构 ​

c
typedef struct zlentry {
    unsigned int prevrawlen;  // 前一个节点的长度（用于反向遍历）
    unsigned int len;         // 当前节点数据长度
    unsigned char encoding;   // 编码方式
    unsigned char* data;      // 实际数据
} zlentry;

压缩列表整体结构 ​

压缩列表整体布局:

┌──────────┬──────────┬──────────┬──────────┬──────────┬─────┐
│ zlbytes  │ zltail   │ zllen    │ entry 1  │ entry 2  │ ... │
│ (4字节)  │ (4字节)  │ (2字节)  │          │          │     │
└──────────┴──────────┴──────────┴──────────┴──────────┴─────┘
                                                                   ┌─────┐
                                                                   │zlend│
                                                                   │(1字节)│
                                                                   └─────┘

字段说明:
- zlbytes: 压缩列表占用的总字节数
- zltail: 最后一个节点的起始偏移（用于快速访问尾部）
- zllen: 压缩列表包含的节点数量
- entry: 各个数据节点
- zlend: 结束标记，值为 0xFF

entry 内部结构:
  ┌─────────────┬──────────┬──────────────┬──────────────────────┐
  │ prevrawlen  │ len      │ encoding     │ data                 │
  │ (1-5字节)   │ (1-5字节) │ (1字节)      │ (变长)               │
  └─────────────┴──────────┴──────────────┴──────────────────────┘
  
  prevrawlen: 前一个节点的总长度（用于反向遍历）
  len: 当前节点数据部分的长度
  encoding: 数据编码方式
  data: 实际存储的数据

5.4 编码方式详解 ​

压缩列表支持两种编码方式：整数编码和字符串编码。

整数编码 ​

为不同范围的整数选择合适的字节数：

编码类型字节数取值范围
INT8 (11000000)1-128 ~ 127
INT16 (11010000)2-32768 ~ 32767
INT24 (11110000)3-8388608 ~ 8388607
INT32 (11020000)4-2^31 ~ 2^31-1
INT64 (11030000)8-2^63 ~ 2^63-1
ENCINT (11111111)变长0~12 用 1 字节，13~255 用 2 字节

字符串编码 ​

字符串编码 (0xxxxxx):
  最高位为 0，低 7 位表示字符串长度
  最大支持 127 字节的字符串

长字符串编码 (10xxxxxx):
  最高位为 10，后 6 位 + 后续字节表示长度
  支持更长的字符串

5.5 压缩列表操作 ​

查找操作 ​

查找过程:
  1. 从第一个 entry 开始，逐个遍历
  2. 解码 entry 的数据
  3. 比较是否匹配
  4. 如果不匹配，根据 prevrawlen 跳转到下一个 entry
  5. 直到找到目标或到达 zlend

插入操作 ​

插入新 entry:
  1. 确定插入位置
  2. 计算新 entry 的 prevrawlen、len 等字段
  3. 为新 entry 分配空间
  4. 更新相关 entry 的 prevrawlen（连锁更新！）
  5. 更新 zlbytes、zltail、zllen

删除操作 ​

删除 entry:
  1. 定位待删除的 entry
  2. 移除该 entry
  3. 更新后续 entry 的 prevrawlen
  4. 更新 zlbytes、zllen

5.6 连锁更新问题 ​

压缩列表插入或删除时可能触发连锁更新（Cascade Update）。

连锁更新原因 ​

当 entry 的 prevrawlen 字段需要变化时（从 1 字节变为 5 字节），会导致后续所有 entry 的起始位置变化，进而需要更新它们的 prevrawlen。

连锁更新示例:

初始状态 (所有 prevrawlen 都是 1 字节):
  ┌─────┬─────┬─────┬─────┐
  │  A  │  B  │  C  │  D  │
  └─────┴─────┴─────┴─────┘
  prevrawlen: 1 字节

在 A 前插入新节点 X，X 的长度超过 253 字节:
  prevrawlen_B 需要从 1 字节变为 5 字节
  → B 的总长度增加 4 字节
  → C 的 prevrawlen 需要更新
  → D 的 prevrawlen 需要更新
  → 连锁更新开始！

连锁更新的时间复杂度 ​

连锁更新的最坏时间复杂度为 O(n²)，但实际中：

  • 只有当 entry 长度跨越特定阈值时才会触发
  • 大多数情况下，连锁更新在几步内就会终止
  • 平均时间复杂度仍然是 O(n)

5.7 压缩列表升级为双向链表 ​

当压缩列表不再节省内存时（连锁更新过于频繁或元素过大），Redis 会将其升级为双向链表。

升级条件 ​

对于 List 类型：

  • 元素数量超过 128 个
  • 任意元素长度超过 64 字节
c
// 升级判断
if (list->length > 128 || 
    element->len > 64) {
    // 升级为双向链表
    list->encoding = OBJ_ENCODING_LINKEDLIST;
    // 遍历压缩列表，逐个转换为链表节点
    listConvertZiplistToList(list);
}

升级过程 ​

压缩列表:
  ┌─────┬─────┬─────┬─────┐
  │  A  │  B  │  C  │  D  │
  └─────┴─────┴─────┴─────┘

升级为双向链表:

  │  node A  │◄►│  node B  │◄►│  node C  │◄►│  node D  │
  └──────────┘  └──────────┘  └──────────┘  └──────────┘

5.8 压缩列表的优缺点 ​

优点缺点

六、整数集合（IntSet） ​

6.1 整数集合概述 ​

整数集合（IntSet）是 Redis 为存储整数集合而设计的专用数据结构，当 Set 类型只包含整数且元素数量较少时，Redis 会使用 IntSet 而非哈希表。

6.2 整数集合结构 ​

c

    uint32_t encoding;  // 编码方式
    uint32_t length;    // 元素数量
    int8_t contents[];  // 存储元素的数组（按升序排列）
} intset;

整数集合结构示意图 ​

intset 结构:
  ┌────────────┬──────────┬──────────────────────────────────────────┐
  │ encoding   │ length   │            contents[]                     │
  ├────────────┼──────────┼──────────────────────────────────────────┤
  │ INT16      │    5     │ [10][20][30][40][50]                       │
  │ (2字节)    │          │  每个元素占 2 字节                          │

不同编码方式下的存储:
  INT16: 每个元素 2 字节，范围 -32768 ~ 32767
  INT32: 每个元素 4 字节，范围 -2^31 ~ 2^31-1
  INT64: 每个元素 8 字节，范围 -2^63 ~ 2^63-1

6.3 编码方式与升级机制 ​

编码方式 ​

整数集合支持三种编码方式，按存储范围从小到大排列：

编码类型每个元素字节数取值范围
INTSET_ENC_INT162-32768 ~ 32767
INTSET_ENC_INT324-2^31 ~ 2^31-1
INTSET_ENC_INT648-2^63 ~ 2^63-1

升级机制 ​

当插入的整数超出当前编码的范围时，会触发升级操作，转换为更大的编码：

升级过程 (INT16 → INT32):

升级前:
  encoding: INT16 (2 字节/元素)
  contents: [10][20][30]  (每个占 2 字节)

插入 value = 40000 (超出 INT16 范围):
  1. 判断需要升级到 INT32
  2. 重新分配内存: 元素数 * 4 字节
  3. 将现有元素转换为 INT32 格式
  4. 插入新元素

升级后:
  encoding: INT32 (4 字节/元素)
  contents: [10][20][30][40000]  (每个占 4 字节)

升级的时间复杂度 ​

升级操作需要重新分配内存并复制所有元素，时间复杂度为 O(n)。但由于升级是单向的（不会降级），且触发条件特殊，实际性能影响较小。

6.4 整数集合的查找操作 ​

整数集合内部元素按升序排列，可以使用二分查找提高效率：

c
// 二分查找
static uint8_t intsetSearch(intset *is, int64_t value, uint32_t *pos) {
    int min = 0, max = intlen(is) - 1, mid;
    
    while (min <= max) {
        mid = (min + max) / 2;
        int64_t cur = intsetGet(is, mid);
        
        if (value > cur) min = mid + 1;
        else if (value < cur) max = mid - 1;
        else return 1;  // 找到
    }
    
    *pos = min;  // 插入位置
    return 0;     // 未找到
}

查找示意图 ​

二分查找 value=30:

  contents: [10][20][30][40][50]
  
  min=0, max=4
  mid=2: contents[2]=30 == value → 找到！

查找 value=25:
  
  min=0, max=4
  mid=2: contents[2]=30 > 25 → max=1
  mid=0: contents[0]=10 < 25 → min=1
  mid=1: contents[1]=20 < 25 → min=2
  min > max → 未找到，pos=2

6.5 整数集合的插入操作 ​

c
// 插入元素
intset *intsetAdd(intset *is, int64_t value, uint8_t *success) {
    uint32_t pos;
    uint8_t enc = intsetEncodingOfValue(value);
    
    // 检查是否需要升级编码
    if (enc > intsetEncoding(is)) {
        is = intsetUpgradeAndAdd(is, value);
    } else {
        // 查找插入位置
        if (intsetSearch(is, value, &pos)) {
            *success = 0;  // 已存在
        } else {
            // 扩展数组空间
            is = intsetResize(is, intlen(is) + 1);
            // 移动后续元素，腾出位置
            intsetMoveTail(is, pos, pos + 1);
            // 插入新元素
            intsetSet(is, pos, value);
            is->length++;
            *success = 1;
        }
    }
    return is;
}

七、快速列表（QuickList） ​

7.1 QuickList 的引入 ​

Redis 3.2 引入了 QuickList 作为 List 类型的新底层实现，它结合了压缩列表（ZipList）的空间效率和双向链表（LinkedList）的灵活性。

7.2 为什么需要 QuickList ​

原有方案的问题 ​

10.3 Redis 数据结构设计哲学 ​

Redis 的数据结构设计体现了以下哲学思想：

1. 按需优化 ​

Redis 不会对所有场景使用最优结构，而是根据实际数据动态选择：

  • 小数据量使用紧凑结构（ZipList、IntSet）
  • 大数据量使用高效结构（Hash Table、Skip List）

2. 渐进式升级 ​

Redis 的编码升级是单向的、不可逆的：

  • ZipList → Hash Table（不会反向）
  • IntSet → Hash Table（不会反向）
  • 小规模 → 大规模（不会降级）

3. 时间与空间的平衡 ​

Redis 在时间和空间之间做出了明智的权衡：

  • ZipList：空间换时间（节省内存，但操作慢）
  • Hash Table：时间换空间（操作快，但内存占用高）
  • QuickList：折中方案（兼顾两者）

4. 简单即美 ​

Redis 的数据结构设计保持了简单性：

  • 跳表替代红黑树：实现更简单
  • ZipList 替代双向链表：内存更紧凑
  • 对象系统统一管理：接口更简洁

十一、常见面试题 ​

Q1：Redis 为什么使用 SDS 而不是 C 字符串？ ​

答： 主要有四个原因：

  1. O(1) 获取长度：SDS 直接存储 len 字段，而 C 字符串需要遍历
  2. 避免缓冲区溢出：SDS 会自动扩展空间，而 C 字符串需要手动管理
  3. 二进制安全：SDS 以显式长度为准，支持存储 \0 等二进制数据
  4. 兼容 C 字符串：SDS 仍然以 \0 结尾，可以直接使用 C 字符串函数

Q2：Redis 哈希表的渐进式 rehash 是如何实现的？ ​

答： 渐进式 rehash 的实现包括：

  1. 使用两个哈希表 table[0] 和 table[1]
  2. rehash 期间，每次操作（查找、插入、删除）都会顺便迁移一个索引位置
  3. 通过 rehashidx 记录 rehash 进度
  4. 查找时先查 table[0]，再查 table[1]
  5. 当所有元素迁移完成后，table[1] 成为新的 table[0]

Q3：跳表为什么比红黑树更适合 Redis？ ​

答： 主要有三个原因：

  1. 实现简单：跳表的代码量约为红黑树的 1/3，更容易维护
  2. 范围查询高效：跳表利用 span 字段可以快速计算排名
  3. 常数因子小：跳表的插入和删除操作的常数因子比红黑树小

Q4：压缩列表的连锁更新是什么？ ​

答： 连锁更新是指当 ZipList 中某个 entry 的 prevrawlen 字段变化时，导致后续所有 entry 的位置变化，进而需要更新它们的 prevrawlen。虽然最坏时间复杂度为 O(n²)，但实际中触发条件苛刻，平均性能良好。

Q5：QuickList 是如何结合 ZipList 和 LinkedList 的优点的？ ​

答： QuickList 的设计思路是：

  1. 将链表按段切分，每段使用 ZipList 存储
  2. 保持链表的结构，支持 O(1) 的头部和尾部操作
  3. 利用 ZipList 的紧凑性，节约内存
  4. 支持段级压缩，进一步节省空间

Q6：Redis 对象系统的类型转换时机是什么？ ​

答： 类型转换是为了在数据规模变化时自动选择最优编码：

  • STRING：INT → EMBSTR（整数转字符串）→ RAW（字符串超过 44 字节）
  • HASH：ZIPLIST → HT（字段超过 128 个或值超过 64 字节）
  • SET：INTSET → HT（元素超过 512 个或存在非整数值）
  • ZSET：ZIPLIST → SKIPLIST（元素超过 128 个或值超过 64 字节）
