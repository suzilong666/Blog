Redis 持久化机制：从 RDB 到 AOF 的深度剖析 ​

一、持久化概述 ​

1.1 为什么需要持久化 ​

Redis 是一款基于内存的键值对存储系统，所有数据都驻留在内存中。这意味着一旦 Redis 进程退出或服务器断电，内存中的数据将全部丢失。

然而，在实际生产环境中，Redis 往往承担着缓存、会话存储、计数器、排行榜等核心业务角色。数据丢失意味着：

  • 业务中断：缓存穿透导致数据库瞬间承受巨大压力
  • 用户体验下降：会话丢失导致用户需要重新登录
  • 数据不一致：计数器、排行榜等数据需要重新计算

因此，Redis 提供了将内存数据持久化到磁盘的机制，确保数据在重启后能够恢复。

1.2 Redis 持久化的设计哲学 ​

Redis 的持久化机制遵循其极简、高效、灵活的设计哲学：

设计原则说明
选择性持久化用户可以根据业务需求选择合适的持久化方式
高性能优先在持久化过程中尽量减少对主线程的影响
简单可靠文件格式简单，易于理解和调试
灵活组合支持多种持久化方式的组合使用

二、RDB（Redis DataBase） ​

2.1 RDB 概述 ​

RDB 是 Redis 最经典的持久化方式，它会在特定的时间点将当前内存中的数据快照以二进制格式写入磁盘文件。

RDB 的核心思想可以概括为一句话：在某个时间点拍一张照片，保存下来，出问题了就从照片恢复。

2.3 触发方式 ​

RDB 的触发方式主要分为四类：

save 命令触发 ​

redis
# 同步保存（阻塞主线程）
SAVE
# Redis 会阻塞，直到 RDB 文件保存完成
# 不推荐在生产环境使用

SAVE 命令会阻塞 Redis 主线程，直到 RDB 文件创建完成。在数据量较大时，可能导致 Redis 长时间无法响应请求。

bgsave 命令触发 ​

redis
# 异步保存（非阻塞，推荐使用）
BGSAVE
# Redis 会 fork 一个子进程来完成 RDB 保存
# 主线程继续处理客户端请求

BGSAVE 是 RDB 持久化的推荐方式。Redis 主进程通过 fork() 系统调用创建一个子进程，由子进程完成 RDB 文件的写入工作，主进程继续服务。

BGSAVE 执行流程:

  主进程                           子进程
  ┌───────────┐                 ┌───────────┐
  │ 接收 BGSAVE │                 │           │
  │  命令       │                 │           │
  └──────┬──────┘                 │           │
         │                        │           │
         │ fork()                 │           │
         ├──────────────────────►│           │
         │                        │ 开始写入  │
  继续处理              复制内存数据到 RDB 文件
  客户端请求              │
  │                        │           │
  │                        │ 写入完成  │
  │◄───────────────────────┤           │
  │ 日志记录完成信息        │ 退出      │
  └───────────┘                 └───────────┘

自动触发 ​

通过 redis.conf 中的 save 规则配置自动触发：

conf
# save 规则格式: save <seconds> <changes>
# 表示在 seconds 秒内，至少有 changes 次写操作，则自动触发 BGSAVE

# Redis 默认配置:
save 3600 1      # 3600 秒（1小时）内至少 1 次写操作
save 300 10      # 300 秒（5分钟）内至少 10 次写操作
save 60 10000    # 60 秒（1分钟）内至少 10000 次写操作

# 满足任一条件即触发 BGSAVE
# 如果同时满足多个条件，只触发一次

flushall / flushdb 触发 ​

redis
# FLUSHALL 和 FLUSHDB 命令执行后
# Redis 会自动触发一次 BGSAVE
FLUSHALL
# 清空所有数据库后自动保存

这是因为 FLUSHALL 会清除所有数据，Redis 会自动触发 BGSAVE 来保存一个空的 RDB 文件，防止误操作导致数据完全丢失。

2.4 save vs bgsave 对比 ​

对比维度SAVEBGSAVE
执行方式同步，阻塞主线程异步，fork 子进程
对客户端影响所有请求被阻塞无影响，继续服务
内存开销无额外开销fork 产生的内存拷贝
执行速度较快（无 fork 开销）略慢（需要 fork）
适用场景数据量小时可临时使用生产环境首选
推荐程度❌ 不推荐✅ 推荐使用

2.5 自动保存配置详解 ​

save 规则配置 ​

conf
# 查看当前 save 规则
redis-cli CONFIG GET save
# 输出: "3600 1 300 10 60 10000"

# 动态修改 save 规则（立即生效，无需重启）
redis-cli CONFIG SET save "60 1000"
# 表示 60 秒内至少 1000 次写操作就保存

# 取消所有 save 规则
redis-cli CONFIG SET save ""
# 设置为空字符串表示禁用 RDB 自动保存

stop-writes-on-bgsave-error 配置 ​

conf
# 当 BGSAVE 出错时，是否停止写入
# 默认值: yes（推荐保持默认）
stop-writes-on-bgsave-error yes

# 设置为 yes 时:
# 如果 BGSAVE 失败（如磁盘空间不足），Redis 会拒绝所有写操作
# 这样可以防止数据丢失

# 设置为 no 时:
# 即使 BGSAVE 失败，Redis 仍然继续接受写操作
# 可能导致数据在内存中丢失

2.6 RDB 文件压缩与校验 ​

RDB 文件压缩 ​

conf
# 是否对 RDB 文件进行压缩
# 默认值: yes
rdbcompression yes

# 使用 LZF 压缩算法
# 压缩率通常在 50%~70% 之间
# 压缩 CPU 开销较小，但可以节省大量磁盘空间

# 关闭压缩:
rdbcompression no
# 文件更大，但节省 CPU 资源
# 适用于磁盘空间充足且 CPU 紧张的场景

RDB 文件校验 ​

conf
# 是否对 RDB 文件进行校验
# 默认值: yes
rdbchecksum yes

# 开启校验:
# 在 RDB 文件末尾添加 CRC64 校验和
# 加载时会校验文件是否损坏
# 开销很小，推荐保持开启

# 关闭校验:
rdbchecksum no
# 文件末尾不添加校验和
# 加载时跳过校验，加载速度略快
# 不推荐关闭，除非对加载速度有极致要求

RDB 文件命名与路径 ​

conf
# RDB 文件名
dbfilename dump.rdb

# 可以使用动态文件名
# dbfilename dump_${port}.rdb
# dbfilename dump_${date}.rdb

# RDB 文件保存目录
dir /var/lib/redis

# 查看当前 RDB 文件路径
redis-cli CONFIG GET dir
redis-cli CONFIG GET dbfilename

2.7 RDB 的优缺点 ​

RDB 的优点 ​

优点说明
文件紧凑RDB 文件是压缩的二进制格式，体积小，适合备份和传输
恢复速度快直接从二进制格式加载，恢复速度比 AOF 快数倍
性能影响小BGSAVE 通过 fork 子进程实现，对主线程影响极小
数据可用性高RDB 文件包含某个时间点的完整数据快照，即使 Redis 损坏也可恢复
适合冷备份可以定时将 RDB 文件备份到远程服务器，实现冷备份

RDB 的缺点 ​

缺点说明
数据丢失风险两次 BGSAVE 之间的数据可能丢失，最多丢失 15 分钟的数据
fork 开销fork 子进程需要拷贝父进程的内存空间，大数据量时开销大
内存峰值BGSAVE 期间，子进程与父进程共享内存，写入操作会触发 Copy-On-Write，导致内存峰值约为平时的 2 倍
只能恢复到某个时间点无法恢复到精确的某个操作点

RDB 数据丢失场景分析 ​

时间线:
  T0: BGSAVE 完成，生成 RDB 文件
  T1: 写入 key1, key2, key3
  T2: 写入 key4, key5
  T3: Redis 崩溃！
  
结果: key1~key5 全部丢失，因为它们都在最后一次 BGSAVE 之后

最坏情况下丢失的数据量:
  = save 规则的最大间隔时间内的写操作
  = max(3600秒/1次, 300秒/10次, 60秒/10000次)
  = 3600 秒（1小时）

三、AOF（Append Only File） ​

3.1 AOF 概述 ​

AOF 是 Redis 的另一种持久化方式，它不保存数据本身，而是将每一个写命令以 Redis 协议的格式追加到一个日志文件中。当 Redis 重启时，会重新执行 AOF 文件中的所有命令，恢复到崩溃前的状态。

AOF 的核心思想可以概括为一句话：把所有写操作都记下来，出问题了就从头重做一遍。

3.2 AOF 刷写策略 ​

AOF 的刷写策略决定了写命令何时从缓冲区写入磁盘文件，是 AOF 性能与数据安全平衡的关键。

三种刷写策略 ​

conf
# AOF 刷写策略
# 可选值: always / everysec / no
appendfsync everysec
策略说明数据安全性性能
always每次写操作都同步到磁盘最高（不丢数据）最低（每次都 fsync）
everysec每秒同步一次到磁盘较高（最多丢 1 秒数据）较高（每秒一次 fsync）
no由操作系统决定同步时机最低（丢数据不可控）最高（完全异步）

三种策略的详细分析 ​

always 策略：

写请求流程:
  1. 客户端发送写命令
  2. Redis 执行命令，写入 AOF 缓冲区
  3. 立即调用 fsync() 将缓冲区数据刷入磁盘
  4. 返回成功给客户端

特点:
  - 最安全，每次写操作都持久化
  - 最慢，每次写操作都触发磁盘 I/O
  - 适用于对数据安全要求极高的场景

everysec 策略（推荐）：

写请求流程:
  1. 客户端发送写命令
  2. Redis 执行命令，写入 AOF 缓冲区
  3. 返回成功给客户端（不等 fsync 完成）
  4. 后台线程每秒将缓冲区数据 fsync 到磁盘

特点:
  - 安全性较高，最多丢失 1 秒数据
  - 性能较好，每秒一次 fsync
  - Redis 默认推荐的策略
  - 实际生产中使用最广泛

no 策略：

写请求流程:
  1. 客户端发送写命令
  2. Redis 执行命令，写入 AOF 缓冲区
  3. 返回成功给客户端
  4. 操作系统决定何时将缓冲区数据刷入磁盘

特点:
  - 性能最高，完全由操作系统控制
  - 安全性最低，丢失数据的时机不可控
  - 一般不推荐使用

三种策略的性能对比 ​

性能对比（概念演示，非基准测试数据）:

always:   | 写 | fsync | 写 | fsync | 写 | fsync |
          └──1ms──┘└──5ms──┘└──1ms──┘└──5ms──┘
          每次写需要等待 fsync，性能最低

everysec: | 写 | 写 | 写 | 写 |  fsync  | 写 | 写 |
          └──1ms──┘└──1ms──┘└──1ms──┘└──1ms──┘└──5ms──┘
          写操作不等待 fsync，每秒同步一次

no:       | 写 | 写 | 写 | 写 | 写 | 写 |
          └──1ms──┘└──1ms──┘└──1ms──┘└──1ms──┘
          完全不等待 fsync，性能最高

3.3 AOF 文件结构 ​

AOF 文件采用 Redis 协议（RESP） 格式存储写命令，具有良好的可读性。

RESP 协议格式 ​

RESP（Redis Serialization Protocol）是 Redis 的通信协议，具有简单、高效、易解析的特点。

RESP 数据类型:
  - 简单字符串: +OK\r\n
  - 错误消息: -ERR message\r\n
  - 整数: :1000\r\n
  - 批量字符串: $5\r\nhello\r\n
  - 数组: *2\r\n$4\r\nSET\r\n$7\r\nmykey\r\n

  特殊标记:
  - \r\n 作为分隔符
  - 批量字符串以 $ 开头，后跟长度
  - 数组以 * 开头，后跟元素数量

AOF 文件内容示例 ​

# AOF 文件实际内容（十六进制视图）
*3\r\n$3\r\nSET\r\n$6\r\nmykey\r\n$5\r\nhello\r\n
*3\r\n$3\r\nSET\r\n$7\r\nmyvalue\r\n$5\r\nworld\r\n
*3\r\n$3\r\nINCR\r\n$7\r\ncounter\r\n
*3\r\n$3\r\nDEL\r\n$7\r\nmykey\r\n

# 解析后的等价命令:
SET mykey hello
SET myvalue world
INCR counter
DEL mykey

3.4 AOF 重写机制 ​

为什么需要 AOF 重写 ​

AOF 通过追加写命令的方式持久化，随着时间推移，AOF 文件会变得越来越大。其中包含大量冗余的历史命令。

示例：一个 key 的多次操作

AOF 文件中的命令序列:
  SET counter 1          # 设置初始值
  SET counter 2          # 覆盖
  SET counter 3          # 覆盖
  INCR counter           # 4
  INCR counter           # 5
  INCR counter           # 6
  DECR counter           # 5
  SET counter 10         # 最终值

实际只需要:
  SET counter 10         # 一条命令即可

AOF 重写就是将当前内存中的数据重新序列化为更精简的命令序列，用新的 AOF 文件替换旧的 AOF 文件。

重写触发方式 ​

触发方式命令/配置说明
手动触发BGREWRITEAOF命令行主动触发
自动触发auto-aof-rewrite-percentageAOF 文件增长比例阈值
自动触发auto-aof-rewrite-min-sizeAOF 文件最小尺寸阈值
redis
# 手动触发 AOF 重写
BGREWRITEAOF
# 该命令会 fork 子进程来完成重写
# 不阻塞主线程
conf
# 自动重写配置
auto-aof-rewrite-percentage 100
# 当 AOF 文件体积相比上次重写时增长了 100%，触发重写

auto-aof-rewrite-min-size 64mb
# AOF 文件最小 64MB 时才考虑重写
# 避免小文件频繁重写

重写流程详解 ​

AOF 重写执行流程:

  主进程                            子进程（重写进程）
  ┌───────────┐                 ┌───────────┐
  │ 接收重写请求│                 │           │
  └──────┬──────┘                 │           │
         │                        │           │
         │ fork()                 │           │
         ├──────────────────────►│           │
         │                        │           │
         │                        │ 读取内存数据│
         │                        │ 生成新命令  │
         │                        │ 写入新 AOF │
         │                        │ 文件       │
         │                        │           │
  主进程继续                       │ 新 AOF 文件│
  处理客户端                       │ 写入完成   │
  请求                             │           │
  │                                │           │
  │                                │ 发送完成信号│
  │◄──────────────────────────────┤           │
  │                                │ 退出      │
  │ 用新 AOF 文件替换旧文件          └───────────┘
  │                               
  │ 处理在重写期间收到的写命令:    
  │ → 追加到新 AOF 文件中          
  └───────────┘

重写期间的写命令处理：

在 AOF 重写期间，主进程仍然会接收到新的写命令。为了保证数据一致性，Redis 会将重写期间的写命令同时写入：

  1. 旧的 AOF 文件（保证持久化）
  2. 新的 AOF 缓冲区（用于合并到新文件）

重写完成后，新的 AOF 文件会包含：重写开始时的数据快照 + 重写期间的增量写命令。

重写期间的内存开销 ​

重写期间的内存状态:

  内存数据（共享）
  ┌──────────────────────────────────────────┐
  │  key1: value1                             │
  │  key2: value2                             │
  │  key3: value3                             │
  └──────────────────────────────────────────┘
         │ fork()
         ▼
  子进程拷贝（Copy-On-Write）
  ┌──────────────────────────────────────────┐
  │  key1: value1  ← 只读，共享物理页         │
  │  key2: value2  ← 只读，共享物理页         │
  │  key3: value3  ← 只读，共享物理页         │
  └──────────────────────────────────────────┘
  
  如果主进程修改了 key2:
  → key2 的物理页被复制
  → 子进程看到的还是旧的 key2 值
  → 主进程看到的是新的 key2 值

3.5 AOF 重写的两个小问题 ​

重写期间阻塞问题 ​

虽然 BGREWRITEAOF 是非阻塞的，但 fork() 操作本身会短暂阻塞主线程。阻塞时间与内存大小正相关。

conf
# 解决方法: 合理设置重写触发阈值
auto-aof-rewrite-percentage 100  # 增长 100% 时触发
auto-aof-rewrite-min-size 64mb   # 最小 64MB 才触发

# 避免频繁重写导致的 fork 开销

重写期间的写命令积压 ​

在 AOF 重写期间，如果写请求非常频繁，AOF 重写缓冲区可能会积压大量命令。Redis 会通过以下机制处理：

conf
# aof-rewrite-incremental-fsync 配置
# 是否在重写期间采用增量 fsync
# 默认值: yes
aof-rewrite-incremental-fsync yes

# 开启后:
# 重写期间每写入 32MB 数据就执行一次 fsync
# 避免重写结束时大量数据一次性 fsync 造成 I/O 尖峰

3.6 AOF 的优缺点 ​

AOF 的优点 ​

优点说明
数据安全性高最多丢失 1 秒数据（everysec 策略），安全性远高于 RDB
文件可读性强AOF 文件是 Redis 协议格式的文本，可以直接阅读和编辑
支持灵活恢复可以通过修改 AOF 文件来恢复到特定状态
对主线程影响小写命令追加到缓冲区，刷盘异步进行
适合数据加密可以对 AOF 文件进行加密传输和存储

AOF 的缺点 ​

缺点说明
文件体积大AOF 文件比 RDB 文件大 2-3 倍
恢复速度慢需要逐条执行命令恢复，速度比 RDB 慢
持续 I/O 开销每次写操作都需要追加到 AOF 文件
重写开销需要定期执行 AOF 重写，产生 fork 开销

四、混合持久化（4.0+ 引入） ​

4.1 混合持久化概述 ​

Redis 4.0 引入了混合持久化机制，它将 RDB 和 AOF 的优点结合起来：

  • 使用 RDB 格式存储大部分数据：文件紧凑，恢复速度快
  • 使用 AOF 格式存储增量命令：数据安全性高，丢失窗口小

混合持久化是目前 Redis 最推荐的持久化方式，兼顾了性能和数据安全。

混合持久化的 AOF 文件由两部分组成：

4.3 混合持久化的工作流程 ​

开启混合持久化 ​

conf
# 开启 AOF 持久化
appendonly yes

# 开启混合持久化（Redis 4.0+）
aof-use-rdb-preamble yes

工作流程 ​

混合持久化工作流程:

1. Redis 正常运行:
   写操作 → 追加到 AOF 缓冲区 → 刷入 AOF 文件（AOF 格式）

2. 触发 AOF 重写:
   主进程 fork 子进程
   子进程执行:
     a. 将当前内存数据以 RDB 格式写入新文件（前半部分）
     b. 重写期间的增量写命令以 AOF 格式追加到新文件（后半部分）
     c. 写入完成，通知主进程

3. 重写完成后:
   新的 AOF 文件 = RDB 前缀 + AOF 增量
   用新文件替换旧文件

4. Redis 重启时:
   a. 检测到文件以 "REDIS" 开头（RDB 格式）
   b. 先加载 RDB 部分（快速恢复数据快照）
   c. 再加载 AOF 部分（重放增量命令）
   d. 完成恢复

5.5 双保险策略 ​

对于关键业务数据，可以同时开启 RDB 和 AOF 作为双保险：

conf
# 同时开启 RDB 和 AOF

save 300 10
save 60 10000

appendfsync everysec
aof-use-rdb-preamble no  # 使用纯 AOF 作为补充

Redis 会优先使用 AOF 文件恢复（因为 AOF 数据更完整），如果 AOF 文件损坏，再尝试使用 RDB 文件恢复。

七、常见面试题 ​

7.1 RDB 相关 ​

Q1: RDB 文件的保存时机是怎样的？

Redis 通过 save 规则触发 RDB 保存。每条 save 规则指定了"时间 + 写操作次数"两个条件，当满足任一规则时就会触发 BGSAVE。例如 save 60 10000 表示 60 秒内至少 10000 次写操作就保存。多条规则之间是"或"的关系，同时满足也只触发一次。

Q2: BGSAVE 时 fork 子进程，此时内存占用情况如何？

fork 之后，子进程会获得父进程内存空间的拷贝。但由于操作系统的 Copy-On-Write（COW） 机制，fork 后并不会立即复制所有内存页，而是共享物理页。只有当父进程或子进程修改某个页时，才会复制该页。因此 BGSAVE 期间的内存峰值取决于修改的数据量，通常约为正常内存的 1.2~2 倍。

Q3: RDB 文件中保存了过期时间吗？过期键在恢复时如何处理？

RDB 文件中保存了每个键的过期时间。Redis 加载 RDB 文件时，会根据当前时间判断过期键：

  • 如果键的过期时间已过，跳过该键
  • 如果键的过期时间未到，加载该键并设置过期时间

这意味着即使是通过 RDB 恢复数据，过期机制也是有效的。

7.2 AOF 相关 ​

Q4: AOF 重写和 RDB 快照有什么区别？

两者在结果上类似——都是将当前内存数据写入新文件。但本质不同：

  • RDB 是将数据序列化为二进制格式，文件紧凑，恢复快
  • AOF 重写是将数据转换为写命令序列，文件较大，恢复慢
  • AOF 重写的触发频率通常比 RDB 高，因为 AOF 文件持续增长

Q5: AOF 重写期间新写的命令会丢失吗？

不会。AOF 重写通过以下机制保证数据不丢失：

  1. 主进程在重写期间继续接收写命令
  2. 写命令同时写入旧 AOF 文件（保证持久化）和新 AOF 缓冲区
  3. 重写完成后，新 AOF 文件包含：重写时的快照 + 重写期间的增量

Q6: AOF 的 always、everysec、no 三种刷写策略在性能上的差异？

性能从高到低：no > everysec > always

  • no：完全异步，性能最高，但丢数据风险不可控
  • everysec：每秒一次 fsync，性能约为 no 的 80-90%
  • always：每次写都 fsync，性能约为 everysec 的 50-60%

实际生产中 everysec 是最常用的，它在性能和安全之间取得了良好的平衡。

7.3 混合持久化相关 ​

Q7: 混合持久化的加载流程是怎样的？

Redis 启动时加载混合持久化文件的流程：

  1. 读取文件开头，检测到 "REDIS" 标识
  2. 按照 RDB 格式解析前半部分，快速恢复数据快照
  3. 按照 AOF 格式解析后半部分，重放增量写命令
  4. 完成数据恢复

这种方式结合了 RDB 的加载速度和 AOF 的数据完整性。

Q8: 混合持久化文件和纯 RDB 文件如何区分？

  • 纯 RDB 文件以 REDIS 开头，后面全是二进制数据
  • 纯 AOF 文件以 RESP 协议的命令开头（如 *3\r\n$3\r\nSET）
  • 混合持久化文件以 REDIS 开头，但后面既有二进制数据又有 RESP 命令

Redis 通过检测文件开头的 REDIS 标识来判断是否为 RDB 格式（包括混合格式）。

7.4 综合问题 ​

Q9: 如何选择 RDB 和 AOF？

选择的核心依据是数据安全要求和性能要求的权衡：

  • 数据可丢失（缓存场景）→ RDB
  • 数据不能丢失（订单、支付）→ AOF 或混合持久化
  • 追求恢复速度 → RDB
  • 追求最小数据丢失 → AOF（everysec）
  • 生产环境推荐 → 混合持久化

Q10: Redis 重启后，RDB 和 AOF 文件的加载顺序是什么？

Redis 重启时的加载优先级：

  1. 如果开启了 AOF（appendonly yes），优先加载 AOF 文件
  2. 如果 AOF 文件不存在，加载 RDB 文件
  3. 如果两者都不存在，Redis 以空数据库启动

AOF 优先的原因是 AOF 数据比 RDB 更完整（丢失窗口更小）。

Q11: 如何手动编辑 AOF 文件恢复数据？

AOF 文件是 Redis 协议格式的文本，可以手动编辑：

  1. 停止 Redis
  2. 备份 AOF 文件
  3. 打开 AOF 文件，删除不需要的命令或添加需要的命令
  4. 启动 Redis，会按照修改后的 AOF 文件恢复
bash
# 示例：手动删除某个 key 的所有操作
# 1. 找到相关命令并删除
# 2. 或直接用 AOF 重写生成干净的文件

# 重新加载 AOF 文件
redis-cli BGREWRITEAOF
# 重写后的 AOF 文件只包含当前数据的最小命令集

Q12: 为什么生产环境不推荐使用 SAVE 命令？

SAVE 命令会阻塞 Redis 主线程，在 RDB 保存完成之前，Redis 无法响应任何客户端请求。数据量越大，阻塞时间越长。而 BGSAVE 通过 fork 子进程实现，主线程可以继续服务。因此生产环境应使用 BGSAVE 或自动触发机制。

Q13: AOF 文件损坏了怎么办？

如果 AOF 文件损坏，Redis 启动时会检测到错误并拒绝加载。可以通过以下方式恢复：

bash
# 1. 备份损坏的 AOF 文件
cp appendonly.aof appendonly.aof.corrupt

# 2. 使用 redis-check-aof 工具修复
redis-check-aof --fix appendonly.aof
# 该工具会跳过损坏的部分，保留有效数据
# 输出会显示修复的部分和跳过的字节数

# 3. 如果 AOF 完全损坏，尝试从 RDB 恢复
# Redis 会自动检测到 AOF 不可用，回退到 RDB 文件

Q14: 持久化对 Redis 性能的影响有多大？

  • RDB（BGSAVE）：fork 开销 + 子进程写入，对主线程影响极小（<5%）
  • AOF（everysec）：每次写操作追加到缓冲区，每秒一次 fsync，影响约 5-10%
  • AOF（always）：每次写操作都 fsync，影响约 30-50%

生产环境中使用混合持久化（everysec），性能影响通常在 5% 以内。

本章小结 ​

本章我们深入探讨了 Redis 的三种持久化机制，总结如下：

  1. RDB：通过数据快照实现持久化，文件紧凑、恢复快速，但存在数据丢失风险。适合数据可丢失、追求恢复速度的场景。

  2. AOF：通过记录写命令实现持久化，数据安全性高（everysec 策略最多丢 1 秒数据），但文件体积大、恢复慢。适合数据安全要求高的场景。

  3. 混合持久化：结合 RDB 和 AOF 的优点，前半部分使用 RDB 格式存储数据快照，后半部分使用 AOF 格式存储增量命令。兼顾了恢复速度和数据安全，是目前生产环境的最佳选择。

  4. 选择建议：

    • 缓存场景 → RDB
    • 关键业务数据 → 混合持久化
    • 对数据安全有极致要求 → AOF（always）
    • 一般生产环境 → 混合持久化（everysec）

  5. 最佳实践：合理配置刷写策略和重写规则，定期验证持久化恢复流程，确保在故障发生时能够快速恢复数据。
