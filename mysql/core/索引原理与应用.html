MySQL 索引原理与应用：从底层数据结构到最佳实践 ​

一、索引的本质与作用 ​

1.1 什么是索引 ​

索引是数据库中用于加速查询操作的数据结构。它类似于书籍的目录——通过目录可以快速定位到所需内容的页码，而无需逐页翻阅。在数据库中，索引存储了表中数据的关键字段值及其对应的物理存储位置，使得查询操作可以通过索引直接定位到目标数据，而不必扫描整张表。

从本质上讲，索引是一种空间换时间的策略：它通过额外的存储空间来维护一份有序的数据引用副本，从而在查询时避免全表扫描（Full Table Scan），将时间复杂度从 O(n) 降低到 O(log n) 甚至 O(1)。

1.2 索引的核心作用 ​

索引的作用远不止加速查询，它还承担着多种重要职责：

作用说明
加速查询这是索引最核心的作用，通过索引可以避免全表扫描
保证数据唯一性唯一索引和主键索引通过唯一性约束保证数据完整性
加速排序与分组索引的有序性可以直接用于 ORDER BY 和 GROUP BY 操作
加速表连接连接字段上的索引可以显著提升 JOIN 操作的性能
减少磁盘 I/O索引使数据库能够通过更少的磁盘读操作获取所需数据

1.3 为什么使用索引：查询性能对比 ​

通过一个实际案例来对比有无索引的性能差异。假设有一张包含 100 万行数据的 users 表：

sql
-- 创建测试表
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    age INT,
    created_at DATETIME
);

-- 插入 100 万行数据（此处省略存储过程）

-- 不带索引的查询
SELECT * FROM users WHERE username = 'user_500000';

无索引场景（全表扫描）：

+----+-------------+-------+------+---------------+------+---------+------+--------+-------------+
| id | select_type | table | type | possible_keys | key  | key_len | ref  | rows   | Extra       |
+----+-------------+-------+------+---------------+------+---------+------+--------+-------------+
|  1 | SIMPLE      | users | ALL  | NULL          | NULL | NULL    | NULL | 1000000 | Using where |
+----+-------------+-------+------+---------------+------+---------+------+--------+-------------+
  • type = ALL：全表扫描，需要扫描 100 万行
  • 耗时：约 3.5-5 秒

创建索引后的查询：

sql
CREATE INDEX idx_username ON users(username);

SELECT * FROM users WHERE username = 'user_500000';
+----+-------------+-------+------+---------------+-------------+---------+-------+------+-------+
| id | select_type | table | type | possible_keys | key         | key_len | ref   | rows | Extra |
+----+-------------+-------+------+---------------+-------------+---------+-------+------+-------+
|  1 | SIMPLE      | users | ref  | idx_username  | idx_username | 152     | const |    1 | NULL  |
+----+-------------+-------+------+---------------+-------------+---------+-------+------+-------+
  • type = ref：通过索引引用查找，仅扫描 1 行
  • 耗时：约 0.001-0.005 秒

性能提升约 1000 倍以上！

二、索引的物理存储结构：B+ 树详解 ​

2.1 为什么选择 B+ 树 ​

数据库索引需要满足以下需求：

  • 支持等值查询和范围查询
  • 保持数据有序
  • 尽可能减少磁盘 I/O 次数
  • 支持高效的插入和删除操作

常见的数据结构对比：

数据结构时间复杂度磁盘友好性范围查询备注
哈希表O(1) 查找差❌ 不支持仅支持等值查询
二叉搜索树O(log n)差✅ 支持树太深，I/O 次数多
红黑树O(log n)差✅ 支持节点太多，不利于磁盘
B 树O(log n)好✅ 支持非叶子节点存储数据
B+ 树O(log n)极好✅ 支持最适合磁盘存储

2.2 B+ 树的结构原理 ​

B+ 树是一种多路平衡查找树，它的核心特点包括：

  1. 所有数据都存储在叶子节点上：非叶子节点仅存储索引键值，不存储实际数据
  2. 叶子节点通过链表连接：支持高效的范围查询
  3. 所有叶子节点位于同一层：树的高度平衡，查询效率稳定
  4. 非叶子节点的子节点数 = 键值数 + 1：每个中间节点可以存储更多的索引项

B+ 树结构示意图 ​

                          [30, 60]
                         /        \
                    [10, 20]    [40, 50]   [70, 80]
                   /    |    \   /    |    \   /    |    \
                  5    15   25  35   45   55  65   75   85
                  ↓    ↓    ↓   ↓    ↓    ↓   ↓    ↓    ↓
                 [5]  [15] [25] [35] [45] [55] [65] [75] [85]
                 (数据页)  ← 所有数据存储在叶子节点
                    ←→ 链表连接，支持范围查询 →→

B+ 树的磁盘 I/O 优化 ​

InnoDB 的页（Page）大小默认为 16KB，一个 B+ 树节点对应一个页。假设：

  • 一个索引键值 + 指针约占 12 字节
  • 一个非叶子节点（页）可存储约 1365 个索引项（16KB / 12B）
  • 3 层 B+ 树可索引：1365 × 1365 × 1365 ≈ 25 亿行数据

这意味着查询 25 亿行数据中的任意一行，仅需 3 次磁盘 I/O！

2.3 B+ 树的插入与分裂 ​

当向 B+ 树插入数据时，可能触发节点分裂：

插入前: [10, 20, 30, 40, 50]  （一个叶子节点，已达最大容量）

插入 25 后，触发分裂:
        [25]             ← 分裂出的中间节点（向上冒泡）
       /     \
  [10, 20]  [25, 30, 40, 50]

分裂规则：

  • 当叶子节点已满，从中间分裂
  • 中间键值向上冒泡到父节点
  • 如果父节点也满了，继续递归分裂
  • 根节点分裂时，树的高度 +1

三、聚簇索引与非聚簇索引 ​

3.1 聚簇索引（Clustered Index） ​

聚簇索引的叶子节点直接存储完整的行数据。在 InnoDB 中，主键索引就是聚簇索引。

聚簇索引结构示意图 ​

                    [30]
                   /    \
              [10, 20]  [40, 50]
              /    |     /    \
           (行1) (行2) (行3) (行4)
           ↓      ↓     ↓      ↓
        id=10  id=20  id=40  id=50
        name=张三 name=李四 name=王五 name=赵六
        age=25  age=30  age=28  age=35

聚簇索引的特点：

  • 数据物理上按主键顺序存储
  • 每个表只能有一个聚簇索引
  • 主键索引的查询效率最高，因为直接定位到数据行
  • 插入新数据时可能触发页分裂，影响插入性能

3.2 非聚簇索引（Secondary Index / 二级索引） ​

非聚簇索引的叶子节点存储主键值，而非完整数据。查询时需要通过主键值再回到聚簇索引中查找完整数据，这个过程称为回表。

非聚簇索引结构示意图 ​

         [30]
        /    \
    [10, 20]  [40, 50]
    /    |     /    \
  (10)  (20)  (40)  (50)    ← 叶子节点存储的是主键值
    ↓     ↓     ↓     ↓
  回表查询 → 聚簇索引 → 获取完整行数据

3.3 回表查询 ​

回表查询是指通过二级索引找到主键值，然后再回聚簇索引查找完整行数据的过程。

sql
-- 假设在 users 表上有索引 idx_username(username)
-- 查询时触发回表
SELECT * FROM users WHERE username = '张三';

执行过程：

  1. 在二级索引 idx_username 中查找 username = '张三'，找到主键值 id = 10
  2. 回到聚簇索引（主键索引）中查找 id = 10，获取完整的行数据
  3. 这个"先查二级索引，再查聚簇索引"的过程就是回表

回表的性能开销：

  • 增加了一次 B+ 树的查找
  • 如果二级索引匹配多行，每行都要回表
  • 在大数据量下，回表的开销不可忽视

3.4 覆盖索引 ​

覆盖索引（Covering Index） 是一种特殊的优化：查询所需的所有列都在索引中，无需回表。

sql
-- 创建联合索引
CREATE INDEX idx_name_age ON users(username, age);

-- 这个查询可以被索引覆盖，无需回表
SELECT username, age FROM users WHERE username = '张三';

执行计划：

+----+-------------+-------+------+------------------+-------------+---------+-------+------+-------------+
| id | select_type | table | type | possible_keys    | key         | key_len | ref   | rows | Extra       |
+----+-------------+-------+------+------------------+-------------+---------+-------+------+-------------+
|  1 | SIMPLE      | users | ref  | idx_name_age     | idx_name_age | 152     | const |    1 | Using index |
+----+-------------+-------+------+------------------+-------------+---------+-------+------+-------------+

Extra = Using index 表示使用了覆盖索引，这是 InnoDB 性能优化的重要手段。

3.5 聚簇索引的优点与限制 ​

优点：

  • 查询速度快，直接定位数据，无需回表
  • 节省存储空间，不需要额外存储主键
  • 基于主键的范围查询效率极高

限制：

  • 插入数据需要按主键顺序排列，随机主键会导致大量页分裂
  • 二级索引的叶子节点存储主键，增大了二级索引的大小
  • 更新主键代价极高（需要重建所有二级索引）

四、联合索引与最左前缀原则 ​

4.1 联合索引的概念 ​

联合索引（复合索引）是基于多个列创建的索引，其本质是按照定义的列顺序构建一个有序的 B+ 树。

sql
-- 创建联合索引
CREATE INDEX idx_name_age_city ON users(username, age, city);

这个索引的 B+ 树结构相当于拼接了 (username, age, city) 作为排序键：

  • 先按 username 排序
  • 当 username 相同时，按 age 排序
  • 当 username 和 age 都相同时，按 city 排序

4.2 最左前缀原则 ​

最左前缀原则是指联合索引 (col1, col2, col3) 只能匹配以下查询条件：

查询条件能否使用索引说明
WHERE col1 = ?✅使用 col1
WHERE col1 = ? AND col2 = ?✅使用 col1, col2
WHERE col1 = ? AND col2 = ? AND col3 = ?✅使用全部三列
WHERE col2 = ?❌跳过了最左列 col1
WHERE col2 = ? AND col3 = ?❌跳过了最左列 col1
WHERE col1 = ? AND col3 = ?✅（仅用 col1）col3 无法使用索引

最左前缀原理 ​

由于 B+ 树是按联合索引的列顺序构建的，只有当查询条件包含索引的最左列时，才能利用索引的有序性进行查找。如果跳过了最左列，后续列的有序性就无法利用。

索引: (username, age, city)
B+ 树排序: username → age → city

可以利用的索引前缀:
  username
  username, age
  username, age, city

无法利用的:
  age, city        ← 缺少 username
  city             ← 缺少 username

4.3 联合索引的设计原则 ​

1. 最左前缀原则 ​

将最常用的查询条件列放在最前面。

sql
-- 如果常用查询是 WHERE username = ? AND age = ?
CREATE INDEX idx_user_age ON users(username, age);  -- ✅ 正确
-- 而不是
CREATE INDEX idx_age_user ON users(age, username);  -- ❌ 不推荐

2. 区分度优先 ​

将区分度高的列放在前面。区分度 = 列中不同值的数量 / 总行数。

sql
-- username 区分度高，age 区分度低
CREATE INDEX idx_name_age ON users(username, age);  -- ✅ 正确

3. 尽量减少回表 ​

创建联合索引时，尽可能把查询中涉及的所有列都包含进去，实现覆盖索引。

sql
-- 如果查询是 SELECT username, age FROM users WHERE username = ?
CREATE INDEX idx_covering ON users(username, age);  -- ✅ 覆盖索引，无需回表

五、唯一索引与普通索引 ​

5.1 基本区别 ​

特性普通索引唯一索引
重复值允许不允许（NULL 除外）
查询优化找到第一个匹配即停止找到第一个匹配即停止（更快）
约束作用无保证数据唯一性
创建语法CREATE INDEXCREATE UNIQUE INDEX

5.2 查询性能差异 ​

唯一索引在查询时，由于数据唯一，找到匹配项后立即停止搜索，性能略优于普通索引。

sql
-- 唯一索引查询
SELECT * FROM users WHERE username = '张三';
-- 使用唯一索引，找到第一个匹配即返回

-- 普通索引查询
SELECT * FROM users WHERE username = '张三';
-- 使用普通索引，找到第一个匹配后需要继续检查是否有重复值（InnoDB 优化后也会尽快停止）

5.3 唯一索引的约束检查 ​

唯一索引在插入数据时会检查唯一性约束，这带来额外的开销：

sql
-- 插入时需要检查 username 是否已存在
INSERT INTO users(username) VALUES ('张三');
-- InnoDB 会在 B+ 树中查找是否已存在 '张三'

六、全文索引 ​

6.1 全文索引概述 ​

全文索引（Fulltext Index）是 MySQL 提供的一种用于全文本搜索的索引类型，特别适用于长文本内容的模糊查询。

6.2 创建全文索引 ​

sql
-- 创建全文索引
CREATE FULLTEXT INDEX idx_content ON articles(content);

-- 使用全文索引进行搜索
SELECT * FROM articles WHERE MATCH(content) AGAINST('数据库优化');

6.3 全文索引的特点 ​

  • 基于倒排索引（Inverted Index）实现
  • 支持自然语言搜索和布尔模式搜索
  • 最小索引词长度由 ft_min_word_len 参数控制
  • InnoDB 和 MyISAM 都支持全文索引

6.4 全文索引 vs LIKE '%xxx%' ​

特性FULLTEXTLIKE '%xxx%'
性能高（索引查找）低（全表扫描）
分词支持✅❌
相关性排序✅❌
中文支持需要分词器简单匹配

七、哈希索引 ​

7.1 哈希索引概述 ​

哈希索引基于哈希表实现，仅支持等值查询，时间复杂度为 O(1)。

7.2 哈希索引的特点 ​

sql
-- Memory 引擎支持显式创建哈希索引
CREATE TABLE t_hash (
    id INT,
    name VARCHAR(50),
    INDEX idx_name USING HASH (name)
) ENGINE = MEMORY;

哈希索引的优势：

  • 查询速度极快，O(1) 时间复杂度
  • 适合等值查询场景

哈希索引的限制：

  • ❌ 不支持范围查询
  • ❌ 不支持排序
  • ❌ 不支持最左前缀匹配（联合索引的哈希）
  • ❌ 哈希冲突会影响性能

7.3 自适应哈希索引 ​

InnoDB 的自适应哈希索引（Adaptive Hash Index）是一个特殊功能：

  • 自动创建：InnoDB 会自动检测使用 B+ 树索引的高频查询
  • 自动优化：将高频访问的 B+ 树索引构建成哈希索引
  • 动态调整：根据访问模式自动创建和删除
  • 无需手动管理：由 InnoDB 引擎自动处理
sql
-- 查看自适应哈希索引状态
SHOW ENGINE INNODB STATUS\G
-- 关注 "Hash searches" 和 "non-Hash searches" 比例

自适应哈希索引的启用/禁用：

sql
-- 禁用（MySQL 8.0 中默认禁用）
SET GLOBAL innodb_adaptive_hash_index = OFF;

八、索引的创建与管理语法 ​

8.1 创建索引 ​

sql
-- 在创建表时指定索引
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100),
    INDEX idx_username (username),
    UNIQUE INDEX idx_email (email)
);

-- 在已有表上创建普通索引
CREATE INDEX idx_username ON users(username);

-- 创建唯一索引
CREATE UNIQUE INDEX idx_email ON users(email);

-- 创建联合索引
CREATE INDEX idx_name_age ON users(username, age);

-- 创建全文索引
CREATE FULLTEXT INDEX idx_content ON articles(content);

-- 重建索引
ALTER TABLE users REBUILD INDEX;

8.2 查看索引 ​

sql
-- 查看表的所有索引
SHOW INDEX FROM users;

-- 查看索引统计信息
SELECT * FROM mysql.innodb_index_stats WHERE database_name = 'your_db';

8.3 删除索引 ​

sql
-- 删除索引
DROP INDEX idx_username ON users;

-- 通过 ALTER TABLE 删除
ALTER TABLE users DROP INDEX idx_username;

九、EXPLAIN 执行计划详解 ​

9.1 EXPLAIN 基础用法 ​

EXPLAIN 是分析查询执行计划的核心工具：

sql
EXPLAIN SELECT * FROM users WHERE username = '张三';

9.2 核心字段解析 ​

type 字段（访问类型） ​

type 是衡量查询性能的核心指标，从差到好依次为：

type说明性能
ALL全表扫描❌ 最差
index全索引扫描❌ 较差
range索引范围扫描⚠️ 一般
ref索引引用查找✅ 良好
eq_ref唯一索引引用✅ 优秀
const常量查找（主键/唯一索引）✅ 最优
system表中仅有一行✅ 最优

key 字段 ​

  • 显示实际使用的索引
  • 如果为 NULL，表示没有使用索引

rows 字段 ​

  • 预估需要扫描的行数
  • 越少越好

Extra 字段 ​

Extra 值说明
Using where使用了 WHERE 过滤
Using index覆盖索引，无需回表
Using temporary使用了临时表（需优化）
Using filesort额外排序（需优化）
Using index condition索引下推优化

9.3 EXPLAIN 实战分析 ​

sql
-- 创建测试表和索引
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(10,2),
    created_at DATETIME,
    INDEX idx_user_status(user_id, status),
    INDEX idx_created(created_at)
);

-- 查询 1：全表扫描
EXPLAIN SELECT * FROM orders WHERE amount > 1000;
type: ALL  (无可用索引，全表扫描)
key: NULL
rows: 1000000
Extra: Using where
sql
-- 查询 2：使用联合索引
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 1;
type: ref
key: idx_user_status  (使用了联合索引)
rows: 50
Extra: Using where
sql
-- 查询 3：覆盖索引
EXPLAIN SELECT user_id, status FROM orders WHERE user_id = 100;
type: ref
key: idx_user_status
rows: 50
Extra: Using index  (覆盖索引，无需回表)
sql
-- 查询 4：索引下推
EXPLAIN SELECT * FROM orders WHERE user_id > 100 AND status = 1;
type: range
key: idx_user_status
rows: 5000
Extra: Using index condition  (索引下推优化)

十、索引失效的常见情况 ​

10.1 对索引列使用函数 ​

sql
-- ❌ 索引失效
SELECT * FROM users WHERE DATE(created_at) = '2024-01-01';

-- ✅ 改写为范围查询
SELECT * FROM users WHERE created_at >= '2024-01-01' 
                       AND created_at < '2024-01-02';

10.2 隐式类型转换 ​

sql
-- ❌ age 是 INT 类型，字符串转换导致索引失效
SELECT * FROM users WHERE age = '25';

-- ✅ 使用正确的类型
SELECT * FROM users WHERE age = 25;

10.3 LIKE 查询以通配符开头 ​

sql
-- ❌ 索引失效
SELECT * FROM users WHERE username LIKE '%张';

-- ✅ 通配符在后面可以使用索引
SELECT * FROM users WHERE username LIKE '张%';

10.4 OR 条件 ​

sql
-- ❌ 如果 email 没有索引，两个索引都失效
SELECT * FROM users WHERE username = '张三' OR email = 'test@test.com';

-- ✅ 优化方案 1：给 email 也加索引
CREATE INDEX idx_email ON users(email);

-- ✅ 优化方案 2：使用 UNION
SELECT * FROM users WHERE username = '张三'
UNION
SELECT * FROM users WHERE email = 'test@test.com';

10.5 违反最左前缀原则 ​

sql
-- ❌ 跳过了联合索引的最左列
SELECT * FROM users WHERE age = 25 AND city = '北京';
-- 联合索引 (username, age, city) 无法使用

10.6 负向查询 ​

sql
-- ❌ NOT IN、!=、<>、NOT LIKE 可能导致索引失效
SELECT * FROM users WHERE age != 25;
SELECT * FROM users WHERE age NOT IN (20, 30);

10.7 IS NOT NULL ​

sql
-- ⚠️ 某些情况下可能导致索引失效
SELECT * FROM users WHERE name IS NOT NULL;

十一、索引设计最佳实践 ​

11.1 高选择性优先 ​

选择区分度高的列作为索引列。

sql
-- ✅ username 区分度高，适合建索引
CREATE INDEX idx_username ON users(username);

-- ❌ gender 区分度低，不适合单独建索引
-- （但可作为联合索引的一部分）
CREATE INDEX idx_gender ON users(gender);

11.2 避免过多索引 ​

每个索引都会：

  • 占用存储空间
  • 降低 INSERT/UPDATE/DELETE 性能
  • 增加维护开销

建议：

  • 单表索引数不超过 5 个
  • 联合索引列数不超过 5 个
  • 定期审查并删除不用的索引

11.3 使用覆盖索引 ​

尽量使用覆盖索引，避免回表查询。

sql
-- 假设常用查询
SELECT username, email FROM users WHERE username = ?;

-- 创建覆盖索引
CREATE INDEX idx_name_email ON users(username, email);

11.4 合理利用联合索引 ​

通过联合索引同时优化多个查询。

sql
-- 如果有以下查询：
-- SELECT * FROM users WHERE username = ?;
-- SELECT * FROM users WHERE username = ? AND age = ?;
-- SELECT * FROM users WHERE username = ? AND age = ? AND city = ?;

-- 一个联合索引即可覆盖所有查询
CREATE INDEX idx_multi ON users(username, age, city);

11.5 定期分析与优化 ​

sql
-- 更新索引统计信息
ANALYZE TABLE users;

-- 检查索引使用情况
SELECT * FROM performance_schema.table_io_waits_summary_by_index_usage 
WHERE object_schema = 'your_db' 
  AND object_name = 'users'
  AND index_name IS NOT NULL
  AND count_fetch = 0;  -- 查找从未使用的索引

11.6 避免冗余索引 ​

sql
-- 如果已有索引 (a, b)，则索引 (a) 是冗余的
-- 因为 (a, b) 的最左前缀就是 (a)

-- 冗余索引示例：
CREATE INDEX idx_ab ON t(a, b);  -- 保留
CREATE INDEX idx_a ON t(a);      -- 冗余，可以删除

十二、索引下推优化 ​

12.1 什么是索引下推 ​

索引下推（Index Condition Pushdown，ICP）是 MySQL 5.6 引入的优化技术。在没有 ICP 时，存储引擎层通过索引找到匹配行后，将每行数据返回给 Server 层，再由 Server 层判断是否满足 WHERE 条件。

无 ICP 的执行过程：

存储引擎层:  索引查找 → 获取每行 → 返回 Server 层
Server 层:   逐行判断 WHERE 条件 → 过滤

有 ICP 的执行过程：

存储引擎层:  索引查找 → 同时判断 WHERE 条件 → 仅返回满足条件的行
Server 层:   直接使用过滤后的结果

12.2 ICP 示例 ​

sql
-- 假设联合索引 (zipcode, lastname, firstname)
-- 查询：SELECT * FROM persons WHERE zipcode='12345' AND lastname LIKE '%et' AND firstname='John';
  • 无 ICP：通过 zipcode='12345' 找到所有匹配行，返回给 Server 层，Server 层再判断 lastname 和 firstname 条件
  • 有 ICP：在存储引擎层同时判断 lastname LIKE '%et' 和 firstname='John'，仅返回满足所有条件的行

12.3 ICP 的启用与查看 ​

sql
-- 查看 ICP 是否启用
SHOW VARIABLES LIKE 'optimizer_switch';
-- 默认启用：index_condition_pushdown=on

-- 禁用 ICP
SET SESSION optimizer_switch = 'index_condition_pushdown=off';

-- 通过 EXPLAIN 验证
EXPLAIN SELECT * FROM persons WHERE zipcode='12345' AND lastname LIKE '%et';
-- Extra 列显示 "Using index condition" 表示使用了 ICP

12.4 ICP 的限制 ​

  • 只能用于 range、ref、eq_ref、system 访问类型
  • 适用于 InnoDB 和 MyISAM 引擎
  • 部分条件无法下推时，ICP 仍然有效（能推的先推）

13.2 黄金法则 ​

  1. 只为需要的列创建索引——不要过度索引
  2. 优先使用联合索引——一个索引服务多个查询
  3. 利用覆盖索引——避免回表开销
  4. 定期审查索引——删除未使用的索引
  5. 关注 EXPLAIN 结果——持续优化

13.3 常见面试题 ​

Q1：为什么 MySQL 使用 B+ 树而不是 B 树？

  • B+ 树非叶子节点不存储数据，单页可存储更多索引项，树更矮
  • B+ 树叶子节点链表连接，范围查询效率更高
  • B+ 树查询更稳定，每次查询都走到叶子节点

Q2：聚簇索引和非聚簇索引的区别？

  • 聚簇索引叶子节点存储完整数据，非聚簇索引叶子节点存储主键
  • 聚簇索引查询不需要回表，非聚簇索引需要回表
  • 每个表只能有一个聚簇索引

Q3：如何避免回表？

  • 使用覆盖索引，将查询涉及的所有列都包含在索引中
  • 使用 SELECT * 会导致回表，应明确指定需要的列

Q4：什么情况下索引会失效？

  • 对索引列使用函数
  • 隐式类型转换
  • LIKE 以通配符开头
  • 违反最左前缀原则
  • 负向条件查询
