MySQL 主从复制原理 ​

一、主从复制的架构概览 ​

1.1 什么是主从复制 ​

MySQL 主从复制（Replication）是指将一个 MySQL 数据库实例的数据变更实时同步到另一个或多个 MySQL 实例的过程。其中，产生数据变更的实例称为主库（Master），接收数据变更的实例称为从库（Slave）。

1.2 主从复制的核心用途 ​

  • 数据备份：从库作为主库的实时备份，主库故障时可以快速恢复
  • 读写分离：将读请求分发到从库，减轻主库压力
  • 高可用：主库故障时，从库可以提升为新的主库
  • 数据分析：在从库上执行耗时的查询和分析操作
  • 数据迁移：在不停机的情况下迁移数据

二、二进制日志（Binlog）详解 ​

2.1 Binlog 概述 ​

Binlog（Binary Log）是 MySQL 的二进制日志文件，记录了 MySQL 数据库中所有数据变更操作。Binlog 是主从复制的基础，也是数据恢复的重要手段。

Binlog 的特点 ​

  • 追加写入：Binlog 是追加写入的，不会修改已有内容
  • 二进制格式：以二进制格式存储，占用空间小
  • 事务安全：支持事务的原子性
  • 多格式支持：支持 Statement、Row、Mixed 三种格式

2.2 Binlog 记录格式 ​

MySQL 支持三种 Binlog 记录格式，各有优缺点：

Statement 格式（SBR） ​

Statement-Based Replication，基于 SQL 语句的复制。

sql
-- 记录的是 SQL 语句本身
-- Binlog 中记录：
INSERT INTO orders (user_id, total) VALUES (100, 200.00);
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

优点：

  • 日志体积小，只记录 SQL 语句
  • 减少网络传输量
  • 便于审计和理解

缺点：

  • 不确定性函数问题：如 NOW()、RAND()、SYSDATE() 在从库上执行结果可能不同
  • 自增 ID 不一致：主库和从库的自增 ID 步长可能不同
  • 无法精确复制：某些操作（如 UPDATE ... WHERE ... LIMIT）可能导致数据不一致
sql
-- 问题示例
INSERT INTO logs (create_time) VALUES (NOW());
-- 主库记录的时间和从库执行的时间不同

INSERT INTO users (name) VALUES (CONCAT('user_', RAND()));
-- 主库和从库的随机值不同

Row 格式（RBR） ​

Row-Based Replication，基于行的复制。

sql
-- 记录的是行的实际变更
-- Binlog 中记录的是变更前和变更后的行数据
-- 对于 INSERT：记录新行的完整数据
-- 对于 UPDATE：记录修改前行和修改后的行
-- 对于 DELETE：记录被删除行的完整数据

优点：

  • 数据一致性高：记录的是实际变更的数据，不依赖 SQL 执行
  • 支持所有类型的复制：包括不确定函数、自增 ID 等
  • 对主库压力小：主库只需记录变更，不需要执行

缺点：

  • 日志体积大：记录所有变更的行数据
  • 网络传输量大：特别是批量更新时
  • 不便于审计：无法直接查看执行了哪些 SQL
sql
-- Row 格式的 Binlog 示例
-- 对于 UPDATE orders SET status = 'paid' WHERE id = 1;
-- Binlog 记录：
-- TABLE_MAP_EVENT: orders 表的映射信息
-- WRITE_ROWS_EVENT: 包含 (id=1, status='pending') 和 (id=1, status='paid') 的行数据

Mixed 格式（MBR） ​

Mixed-Based Replication，混合格式复制。

Mixed 格式是 MySQL 推荐使用的格式，它会根据 SQL 语句的类型自动选择 Statement 或 Row 格式：

  • 对于安全的 SQL（如确定函数、不涉及自增 ID），使用 Statement 格式
  • 对于不安全的 SQL（如不确定函数、涉及自增 ID），自动切换为 Row 格式
sql
-- Mixed 格式的选择逻辑
INSERT INTO orders (user_id, total) VALUES (100, 200.00);
-- 安全，使用 Statement 格式

INSERT INTO logs (create_time) VALUES (NOW());
-- 不安全，自动切换为 Row 格式

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 安全，使用 Statement 格式

格式选择建议 ​

场景推荐格式原因
大多数业务场景MIXED兼顾性能和一致性
对数据一致性要求极高ROW保证数据绝对一致
需要节省存储空间STATEMENT日志体积最小
sql
-- 设置 Binlog 格式
SET GLOBAL binlog_format = 'ROW';
SET GLOBAL binlog_format = 'STATEMENT';
SET GLOBAL binlog_format = 'MIXED';

-- 查看当前格式
SHOW VARIABLES LIKE 'binlog_format';

2.3 Binlog 索引文件 ​

MySQL 维护一个索引文件（.index 文件），记录所有 Binlog 文件的路径列表。

sql
-- 查看 Binlog 文件列表
SHOW BINARY LOGS;

输出示例：

+------------------+-----------+
| Log_name         | File_size |
+------------------+-----------+
| mysql-bin.000001 | 154       |
| mysql-bin.000002 | 256       |
| mysql-bin.000003 | 1024      |
+------------------+-----------+

索引文件的作用：

  • 记录 Binlog 文件的生成顺序
  • 辅助 MySQL 查找指定的 Binlog 文件
  • 用于数据恢复和主从复制的定位

2.4 日志轮转 ​

什么是日志轮转 ​

当日志文件达到最大大小或满足某些条件时，MySQL 会创建新的日志文件继续写入，这个过程称为日志轮转（Log Rotation）。

触发轮转的条件 ​

条件配置参数说明
文件大小达到上限max_binlog_size默认 1GB
MySQL 重启-每次重启都会创建新日志
手动执行FLUSH BINARY LOGS强制创建新日志文件
sql
-- 手动触发日志轮转
FLUSH BINARY LOGS;

-- 配置日志轮转大小
SET GLOBAL max_binlog_size = 1073741824; -- 1GB

日志删除策略 ​

sql
-- 设置自动过期时间（秒）
SET GLOBAL expire_logs_days = 7;  -- 保留 7 天

-- 手动删除指定日志
PURGE BINARY LOGS BEFORE NOW() - INTERVAL 7 DAY;

-- 手动删除到指定文件
PURGE BINARY LOGS TO 'mysql-bin.000005';

注意：删除日志前必须确认从库已经消费完这些日志，否则会导致从库数据丢失。

3.2 详细步骤解析 ​

第一步：主库写入 Binlog ​

sql
-- 1. 客户端发送写请求
INSERT INTO orders (user_id, total) VALUES (100, 200.00);

-- 2. InnoDB 引擎执行事务
--    - 写入 Redo Log
--    - 更新 Buffer Pool
--    - 写入 Undo Log

-- 3. 事务提交时：
--    - 写入 Binlog Cache
--    - Binlog Cache 写入 Binlog 文件
--    - 调用 fsync 刷盘（如果 sync_binlog=1）

-- 4. 更新 Binlog 位置（file + position）
--    mysql-bin.000003: 154

第二步：从库拉取 Binlog ​

sql
-- 1. 从库的 I/O 线程连接主库
--    - 使用复制账号
--    - 报告当前已消费的 Binlog 位置

-- 2. 主库的 Binlog Dump 线程
--    - 读取请求位置之后的 Binlog 事件
--    - 发送给从库的 I/O 线程

-- 3. 从库的 I/O 线程
--    - 接收 Binlog 事件
--    - 写入 Relay Log 文件
--    - 更新 master_log_file 和 read_master_log_pos

第三步：从库重放 Binlog ​

sql
-- 1. SQL 线程（或 Worker 线程）读取 Relay Log

-- 2. 根据 Binlog 格式解析事件：
--    - Statement：直接执行 SQL 语句
--    - Row：根据行数据构造并执行 INSERT/UPDATE/DELETE

-- 3. 执行数据变更

-- 4. 更新 relay_log_file 和 exec_master_log_pos

-- 5. 记录到复制日志表（mysql.slave_master_info 等）

3.3 复制延迟的产生原因 ​

复制延迟是指从库的数据与主库之间存在的时间差。

产生延迟的主要原因 ​

原因说明
主库写入压力大主库有大量写入操作，生成 Binlog 速度超过从库消费速度
从库硬件差从库使用较差的硬件（如 HDD、小内存），处理能力不足
从库负载高从库上有大量查询或其他任务，抢占资源
单线程复制MySQL 5.6 之前是单线程复制，无法利用多核
大事务单次事务包含大量行变更，从库需要较长时间重放
网络延迟主从之间网络不稳定或带宽不足

查看复制延迟 ​

sql
-- 在从库上查看
SHOW SLAVE STATUS\G

-- 关键指标：
-- Seconds_Behind_Master: 落后主库的秒数
-- Relay_Master_Log_File: 正在读取的 Relay Log 文件
-- Exec_Master_Log_Pos: 已执行的位置
-- Read_Master_Log_Pos: 已读取的位置

复制延迟的优化 ​

  1. 硬件优化：从库使用与主库相同或更好的硬件
  2. 并行复制：开启多线程复制
  3. 读写分离：将读请求分发到多个从库
  4. 避免大事务：拆分大事务为多个小事务
  5. 网络优化：确保主从之间的网络带宽充足

四、主从复制的配置与搭建 ​

4.1 主库配置 ​

修改主库配置文件（my.cnf） ​

ini
[mysqld]
# 开启 Binlog
log-bin = mysql-bin
binlog_format = ROW
binlog_row_image = FULL

# 服务器 ID（必须唯一）
server-id = 1

# Binlog 文件大小
max_binlog_size = 100M

# Binlog 过期时间
expire_logs_days = 7

# 日志文件路径
log_bin_basename = /var/lib/mysql/binlog/mysql-bin
log_bin_index = /var/lib/mysql/binlog/mysql-bin.index

# GTID 模式（推荐）
gtid_mode = ON
enforce_gtid_consistency = ON

创建复制账号 ​

sql
-- 创建专门用于复制的账号
CREATE USER 'repl' @ '%' IDENTIFIED BY 'ReplPassword123!';
GRANT REPLICATION SLAVE ON *.* TO 'repl' @ '%';
FLUSH PRIVILEGES;

获取主库状态 ​

sql
SHOW MASTER STATUS;

输出：

+------------------+----------+--------------+------------------+
| File             | Position | Binlog_Do_DB | Binlog_Ignore_DB |
+------------------+----------+--------------+------------------+
| mysql-bin.000003 |    154   |              |                  |
+------------------+----------+--------------+------------------+

记录 File 和 Position 值，用于从库配置。

4.2 从库配置 ​

修改从库配置文件 ​

ini
[mysqld]
# 服务器 ID（必须与主库不同）
server-id = 2

# 开启 Relay Log
relay-log = mysql-relay-bin
relay-log-index = mysql-relay-bin.index

# 开启只读模式（防止误写）
read-only = ON
super-read-only = ON

# GTID 模式
gtid_mode = ON
enforce_gtid_consistency = ON

# 并行复制配置
slave_parallel_workers = 4
slave_parallel_type = LOGICAL_CLOCK

配置主库信息 ​

sql
-- 方式一：传统方式（指定 Binlog 文件和位置）
CHANGE MASTER TO
    MASTER_HOST = '192.168.1.100',
    MASTER_PORT = 3306,
    MASTER_USER = 'repl',
    MASTER_PASSWORD = 'ReplPassword123!',
    MASTER_LOG_FILE = 'mysql-bin.000003',
    MASTER_LOG_POS = 154;

-- 方式二：GTID 方式（推荐）
CHANGE MASTER TO
    MASTER_HOST = '192.168.1.100',
    MASTER_PORT = 3306,
    MASTER_USER = 'repl',
    MASTER_PASSWORD = 'ReplPassword123!',
    MASTER_AUTO_POSITION = 1;

启动复制 ​

sql
-- 启动从库复制
START SLAVE;

-- 查看复制状态
SHOW SLAVE STATUS\G

4.3 验证复制 ​

sql
-- 在主库上创建数据
CREATE DATABASE test_replication;
USE test_replication;
CREATE TABLE users (id INT PRIMARY KEY, name VARCHAR(50));
INSERT INTO users VALUES (1, 'Alice'), (2, 'Bob');

-- 在从库上验证
SELECT * FROM test_replication.users;
-- 应该看到相同的数据

4.4 GTID 模式详解 ​

GTID（Global Transaction Identifier）是 MySQL 5.6 引入的事务标识符，为每个事务分配全局唯一的 ID。

GTID 的组成 ​

GTID = source_id:transaction_id

示例：
gtid_set = 3E11FA47-71CA-11E1-9E33-C80AA9429562:1-5
  • source_id：MySQL 实例的 UUID（@@server_uuid）
  • transaction_id：事务序号，从 1 开始递增

GTID 的优势 ​

  1. 简化主从切换：无需手动指定 Binlog 文件和位置
  2. 自动去重：确保每个事务只执行一次
  3. 更精确的复制：基于事务而非文件位置
  4. 支持多源复制：方便实现更复杂的拓扑
  5. 故障恢复更简单：基于 GTID 而非 Binlog 位点

五、半同步复制（Semi-sync Replication） ​

5.1 同步复制 vs 异步复制 ​

异步复制（默认） ​

主库                              从库
┌──────────────┐                ┌──────────────┐
│ 执行事务     │                │              │
│ 写入Binlog   │                │              │
│              │   发送Binlog  │ 接收并执行   │
│ 立即返回成功 │ ◄────────────  │ 完成后确认   │
└──────────────┘                └──────────────┘

问题：主库返回成功时，从库可能还未收到 Binlog
      如果主库此时宕机，从库会丢失数据

全同步复制 ​

主库                              从库
┌──────────────┐                ┌──────────────┐
│ 执行事务     │                │              │
│ 写入Binlog   │                │              │
│              │   发送Binlog  │ 接收并执行   │
│ 等待所有从库 │ ◄────────────  │ 完成后确认   │
│ 确认后返回   │                │              │
└──────────────┘                └──────────────┘

问题：主库需要等待所有从库确认，性能影响大
      如果某个从库响应慢，主库也会被阻塞

5.2 半同步复制的实现 ​

半同步复制（Semi-synchronous Replication）是 MySQL 5.5 引入的折中方案：

  • 主库在提交事务后，等待至少一个从库确认收到 Binlog
  • 不需要等待从库执行完成，只需确认已经接收并写入 Relay Log
  • 兼顾了数据一致性和性能
主库                              从库
┌──────────────┐                ┌──────────────┐
│ 执行事务     │                │              │
│ 写入Binlog   │                │              │
│              │   发送Binlog  │ 接收并写入   │
│ 等待一个     │ ◄────────────  │ Relay Log    │
│ 从库确认     │   确认接收    │              │
│ 返回成功     │                │ 异步重放     │
└──────────────┘                └──────────────┘

5.3 半同步复制的配置 ​

主库配置 ​

ini
[mysqld]
# 加载半同步插件
plugin-load = "rpl_semi_sync_master=semisync_master.so"

# 开启半同步复制
rpl_semi_sync_master_enabled = ON

# 等待确认的超时时间（毫秒）
rpl_semi_sync_master_timeout = 10000

# 自动降级：超时后自动切换为异步
rpl_semi_sync_master_wait_no_slave = ON
rpl_semi_sync_master_wait_sessions = 0

从库配置 ​

ini
[mysqld]
# 加载半同步插件
plugin-load = "rpl_semi_sync_slave=semisync_slave.so"

# 开启半同步复制
rpl_semi_sync_slave_enabled = ON

运行时状态 ​

sql
-- 主库查看半同步状态
SHOW STATUS LIKE 'Rpl_semi_sync_master%';

-- 关键指标：
-- Rpl_semi_sync_master_status: 是否开启
-- Rpl_semi_sync_master_clients: 半同步从库数量
-- Rpl_semi_sync_master_net_avg_wait_time: 平均等待时间

5.4 半同步复制的降级机制 ​

当半同步复制出现问题时，MySQL 会自动降级为异步复制：

  • 超时降级：主库在 rpl_semi_sync_master_timeout 时间内未收到确认
  • 手动降级：管理员可以手动关闭半同步
半同步正常 → 超时/故障 → 自动降级为异步 → 故障恢复 → 自动恢复半同步

六、全同步复制 ​

6.1 全同步复制的原理 ​

全同步复制（Synchronous Replication）要求：

  • 主库提交事务前，必须等待所有从库完成事务执行
  • 任何一个从库不可用，主库都会被阻塞

6.2 全同步复制的实现方式 ​

MySQL 原生不支持全同步复制，通常通过以下方式实现：

方式一：应用层实现 ​

客户端 → 主库写 → 主库确认 → 从库1确认 → 从库2确认 → 返回成功

方式二：使用 Galera Cluster ​

Galera 是基于组复制的同步集群方案：

┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  节点1       │  │  节点2       │  │  节点3       │
│  (Primary)   │  │  (Secondary) │  │  (Secondary) │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                  │                  │
       └─────────┬────────┴──────────────────┘
                 │
          Galera Group Communication
          (基于 GTID 的同步复制)

方式三：MySQL Group Replication ​

MySQL 5.7 引入了组复制（Group Replication）插件：

  • 基于 Paxos 协议实现数据同步
  • 支持多主模式
  • 自动故障转移

七、主从切换策略 ​

7.1 主从切换的场景 ​

场景说明
主库故障主库宕机，需要提升从库为新主库
主库维护主库需要升级或维护，主动切换
性能优化主库性能不足，需要迁移到更强大的服务器

7.2 手动切换 ​

步骤一：确定新主库 ​

sql
-- 在所有从库上查看复制状态
SHOW SLAVE STATUS\G

-- 选择 Seconds_Behind_Master=0 的从库
-- 确保所有从库的 Relay Log 都已执行完

步骤二：提升从库为主库 ​

sql
-- 在新主库上执行
STOP SLAVE;
RESET SLAVE ALL;

-- 取消只读模式
SET GLOBAL read_only = OFF;
SET GLOBAL super_read_only = OFF;

-- 如果使用 GTID，注入空事务以跳过已执行的 GTID
SET GTID_PURGED = '已执行的 GTID 集合';

步骤三：更新其他从库 ​

sql
-- 指向新的主库
CHANGE MASTER TO
    MASTER_HOST = '新主库IP',
    MASTER_AUTO_POSITION = 1;

START SLAVE;

步骤四：更新应用配置 ​

将应用的数据库连接指向新的主库。

7.3 自动切换 ​

MHA（Master High Availability） ​

MHA 是最常用的 MySQL 高可用方案之一。

┌──────────────┐     ┌──────────────┐
│  MHA Manager │────►│  MHA Node    │
│  (管理节点)  │     │  (每个MySQL  │
│              │     │   实例上)    │
└──────┬───────┘     └──────┬───────┘
       │                    │
       │ 监控               │ 监控
       ▼                    ▼
┌──────────────┐     ┌──────────────┐
│  主库        │◄────│  从库        │
└──────────────┘     └──────────────┘

MHA 的特点：

  • 主库故障时，自动完成故障转移
  • 选择数据最新的从库作为新主库
  • 自动将其他从库指向新主库
  • 支持半同步复制

Orchestrator ​

Orchestrator 是另一个流行的 MySQL 高可用工具：

│  - 读写路由                                 │

ProxySQL ​

ProxySQL 是一个高性能的 MySQL 代理，可实现读写分离和故障转移：

客户端 → ProxySQL → 主库（写）
                 → 从库（读）

八、读写分离的实现 ​

8.1 读写分离架构 ​

                    ┌──────────────┐
                    │   客户端     │
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │  读写分离    │
                    │   中间件     │
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
       ┌──────▼──────┐ ┌──▼───────┐ ┌──▼───────┐
       │   主库      │ │  从库1   │ │  从库2   │
       │  (写操作)   │ │ (读操作) │ │ (读操作) │
       └─────────────┘ └──────────┘ └──────────┘

8.2 实现方式 ​

应用层实现 ​

在应用代码中根据操作类型选择数据库连接：

java
@Service
public class OrderService {
    
    @Autowired
    @Qualifier("masterDataSource")
    private DataSource masterDataSource;
    
    @Autowired
    @Qualifier("slaveDataSource")
    private DataSource slaveDataSource;
    
    public void createOrder(Order order) {
        // 写操作使用主库
        JdbcTemplate jdbc = new JdbcTemplate(masterDataSource);
        jdbc.update("INSERT INTO orders ...");
    }
    
    public Order getOrder(Long id) {
        // 读操作使用从库
        JdbcTemplate jdbc = new JdbcTemplate(slaveDataSource);
        return jdbc.queryForObject("SELECT * FROM orders WHERE id = ?", ...);
    }
}

使用动态数据源 ​

java
@Component
public class DynamicDataSource extends AbstractRoutingDataSource {
    
    @Override
    protected Object determineCurrentLookupKey() {
        return DataSourceHolder.getDataSourceType();
    }
}

public class DataSourceHolder {
    
    private static final ThreadLocal<String> holder = new ThreadLocal<>();
    
    public static void setMaster() {
        holder.set("master");
    }
    
    public static void setSlave() {
        holder.set("slave");
    }
    
    public static String getDataSourceType() {
        return holder.get();
    }
}

@Aspect
@Component
public class DataSourceAspect {
    
    @Before("@annotation(targetDataSource)")
    public void changeDataSource(JoinPoint point, TargetDataSource targetDataSource) {
        if ("master".equals(targetDataSource.value())) {
            DataSourceHolder.setMaster();
        } else {
            DataSourceHolder.setSlave();
        }
    }
}

中间件特点

MaxScaleMariaDB 官方代理，功能完善

8.3 读写分离的注意事项 ​

  1. 主从延迟问题：刚写入的数据可能无法在从库上立即读取
  2. 解决方案：
    • 关键读操作走主库
    • 使用缓存减少读压力
    • 监控主从延迟，延迟过大时走主库

九、主从复制中的数据一致性问题 ​

9.1 不一致的原因 ​

原因说明
主从延迟从库数据落后于主库
网络问题Binlog 传输过程中丢失
从库故障从库执行失败后停止
误操作在从库上执行了写操作
BugMySQL 自身的 Bug 导致复制异常

9.2 如何保证一致性 ​

1. 使用 Row 格式复制 ​

Row 格式记录的是行的实际变更，避免了 SQL 执行带来的不确定性。

2. GTID 模式 ​

GTID 确保每个事务全局唯一，从库可以自动跳过已执行的事务。

3. 校验和验证 ​

sql
-- 开启主从校验
SET GLOBAL server_id = 1;
SET GLOBAL binlog_checksum = CRC32;

-- 从库上校验
SET GLOBAL slave_checksum = CRC32;

4. 定期数据校验 ​

bash
# 使用 pt-table-checksum 工具
pt-table-checksum --host=主库IP --user=root --password=xxx

# 使用 pt-table-sync 同步差异
pt-table-sync --execute --host=主库IP --user=root --password=xxx

5. 避免在从库上写操作 ​

sql
-- 在从库上设置只读
SET GLOBAL read_only = ON;
SET GLOBAL super_read_only = ON;

十、多源复制 ​

10.1 多源复制概述 ​

多源复制（Multi-Source Replication）是指一个从库同时从多个主库接收数据。

┌──────────────┐     ┌──────────────┐
│  主库A       │     │  主库B       │
│  (业务A数据) │     │  (业务B数据) │
└──────┬───────┘     └──────┬───────┘
       │                    │
       │ 复制               │ 复制
       ▼                    ▼
┌──────────────────────────────────┐
│         从库（多源）              │
│  - 接收主库A的数据到数据库A      │
│  - 接收主库B的数据到数据库B      │
└──────────────────────────────────┘

10.2 多源复制的配置 ​

sql
-- 配置第一个主库
CHANGE MASTER TO
    MASTER_HOST = '主库A_IP',
    MASTER_PORT = 3306,
    MASTER_USER = 'repl',
    MASTER_PASSWORD = 'password',
    MASTER_LOG_FILE = 'mysql-bin.000001',
    MASTER_LOG_POS = 154
FOR CHANNEL 'channel_a';

-- 配置第二个主库
CHANGE MASTER TO
    MASTER_HOST = '主库B_IP',
    MASTER_PORT = 3306,
    MASTER_USER = 'repl',
    MASTER_PASSWORD = 'password',
    MASTER_LOG_FILE = 'mysql-bin.000002',
    MASTER_LOG_POS = 200
FOR CHANNEL 'channel_b';

-- 启动所有通道
START SLAVE;

-- 启动指定通道
START SLAVE FOR CHANNEL 'channel_a';

10.3 多源复制的应用场景 ​

  • 数据汇总：将多个业务系统的数据汇总到一个库
  • 数据备份：一个从库同时备份多个主库
  • 数据迁移：从多个源系统迁移数据

十一、并行复制 ​

11.1 并行复制的发展 ​

版本复制模式说明
MySQL 5.6 之前单线程SQL 线程单线程重放
MySQL 5.6按库并行多个 SQL 线程按数据库并行
MySQL 5.7+按逻辑时钟基于组提交的并行复制

11.2 MySQL 5.6 并行复制 ​

sql
-- 设置并行复制
slave_parallel_workers = 4

-- 设置并行模式
slave_parallel_type = DATABASE

问题：按库并行，如果只有一个库，无法并行。

11.3 MySQL 5.7+ 并行复制（基于逻辑时钟） ​

sql
-- 推荐配置
slave_parallel_workers = 4
slave_parallel_type = LOGICAL_CLOCK

-- 主库配置
binlog_group_commit_sync_delay = 100  -- 微秒
binlog_group_commit_sync_no_delay_count = 100

原理 ​

主库在提交事务时，将多个事务分为同一组（Group），赋予相同的逻辑时钟（logical_clock）。从库可以并行执行同一组内的事务。

主库：
  事务1 → logical_clock: 100
  事务2 → logical_clock: 100  (同一组)
  事务3 → logical_clock: 100  (同一组)
  事务4 → logical_clock: 101  (新组)

从库：
  Worker 1: 执行事务1
  Worker 2: 执行事务2  (并行)
  Worker 3: 执行事务3  (并行)

11.4 并行复制的监控 ​

sql
-- 查看复制状态
SHOW SLAVE STATUS\G

-- 查看并行复制状态
SELECT * FROM performance_schema.replication_applier_status_by_worker;
SELECT * FROM performance_schema.replication_applier_status_by_coordinator;

十二、故障转移与恢复 ​

12.1 故障转移流程 ​

1. 检测主库故障
   ↓
2. 选择新主库（从库中数据最新的）
   ↓
3. 提升新主库（取消只读，重置复制）
   ↓
4. 更新其他从库（指向新主库）
   ↓
5. 更新应用配置（指向新主库）
   ↓
6. 恢复服务

12.2 故障转移类型 ​

类型说明RTORPO
手动故障转移人工手动操作分钟级秒级
自动故障转移MHA/Orchestrator 自动秒级秒级
主从切换主库恢复后切回分钟级0

RTO（Recovery Time Objective）：故障恢复时间 RPO（Recovery Point Objective）：数据丢失容忍时间

12.3 数据恢复 ​

从备份恢复 ​

bash
# 使用 mysqldump 备份
mysqldump -u root -p --all-databases > backup.sql

# 恢复数据
mysql -u root -p < backup.sql

基于 Binlog 的时间点恢复 ​

bash
# 恢复到指定时间点
mysqlbinlog --stop-datetime="2024-01-15 10:00:00" \
            mysql-bin.000001 | mysql -u root -p

# 恢复指定位置的 Binlog
mysqlbinlog --start-position=154 --stop-position=308 \
            mysql-bin.000001 | mysql -u root -p

重建从库 ​

当从库数据与主库不一致时，需要重建从库：

sql
-- 方式一：使用 Xtrabackup 物理备份
-- 主库上执行
xtrabackup --backup --target-dir=/data/backup/

-- 恢复到从库
xtrabackup --prepare --target-dir=/data/backup/
xtrabackup --copy-back --target-dir=/data/backup/

-- 方式二：使用 mysqldump 逻辑备份
mysqldump --master-data=2 --single-transaction \
          -u root -p --all-databases > backup.sql

十三、总结 ​

MySQL 主从复制是构建高可用、高性能数据库系统的基础。核心要点包括：

  1. 理解 Binlog 机制：Binlog 是复制的基础，需要深入理解其格式和工作原理
  2. 掌握复制流程：主库写入 → 从库拉取 → 从库重放的完整流程
  3. 合理选择复制格式：根据业务需求选择 Statement、Row 或 Mixed 格式
  4. 使用 GTID：GTID 简化了复制管理，推荐在生产环境使用
  5. 优化复制性能：使用并行复制、半同步复制等特性
  6. 建立高可用架构：使用 MHA、Orchestrator 等工具实现自动故障转移
  7. 定期演练：定期进行故障转移和数据恢复演练，确保方案的可行性

通过合理配置和持续优化，MySQL 主从复制可以支撑从初创团队到大型企业的各种业务场景。
