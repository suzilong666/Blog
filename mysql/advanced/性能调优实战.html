MySQL 性能调优实战 ​

一、性能调优的方法论 ​

1.1 调优的核心思路 ​

性能调优是一个系统工程，需要遵循科学的方法：

┌─────────────────────────────────────────────────────────────┐
│                    性能调优方法论                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 发现问题    →  监控告警 / 用户反馈 / 性能测试            │
│       │                                                     │
│       ▼                                                     │
│  2. 定位瓶颈    →  剖析分析 / 指标度量 / 对比定位            │
│       │                                                     │
│       ▼                                                     │
│  3. 分析原因    →  深入代码 / 理解原理 / 找到根因            │
│       │                                                     │
│       ▼                                                     │
│  4. 实施优化    →  制定方案 / 实施变更 / 控制风险            │
│       │                                                     │
│       ▼                                                     │
│  5. 验证效果    →  对比数据 / 功能验证 / 回归测试            │
│       │                                                     │
│       ▼                                                     │
│  6. 持续监控    →  建立监控 / 长期跟踪 / 持续改进            │
│                                                             │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐

│  ┌─────────────────────────────────────────────────┐   │

│  │  │  ┌─────────────────────────────────┐   │   │   │
│  │  │  │  操作系统优化（内存、I/O、网络） │   │   │   │
│  │  │  │  ┌─────────────────────────┐   │   │   │   │

└─────────────────────────────────────────────────────────┘

原则：从上层到下层逐层优化，优先解决最容易见效的问题。

1.3 性能调优的常见误区 ​

误区说明正确做法
过度调优过早进行底层调优先优化 SQL 和索引
盲目调优不测量就调整参数先测量，再优化
忽略整体只优化某个指标关注整体性能
过度缓存缓存所有数据缓存热点数据
忽视监控调优后不跟踪建立长期监控

二、性能指标与监控 ​

2.1 核心性能指标 ​

QPS（Queries Per Second） ​

每秒查询数，衡量数据库的查询处理能力。

sql
-- 查看当前 QPS
SHOW GLOBAL STATUS LIKE 'Queries';
-- 每秒查询数 = (当前 Queries - 上次 Queries) / 时间间隔

TPS（Transactions Per Second） ​

每秒事务数，衡量数据库的事务处理能力。

sql
-- 查看 TPS
SHOW GLOBAL STATUS LIKE 'Com_commit';
SHOW GLOBAL STATUS LIKE 'Com_rollback';
-- TPS = (Com_commit + Com_rollback) / 时间间隔

响应时间 ​

响应时间是用户最直接感知的性能指标：

指标说明
平均响应时间所有请求的平均耗时
P95 响应时间95% 的请求耗时
P99 响应时间99% 的请求耗时
最大响应时间最慢的请求耗时

P99 响应时间比平均响应时间更重要，因为少量慢请求会严重影响用户体验。

并发数 ​

同时处理的请求数量，反映系统的并发处理能力。

sql
-- 查看当前连接数
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Threads_running';

-- 查看最大连接数
SHOW GLOBAL VARIABLES LIKE 'max_connections';

缓存命中率 ​

缓存命中率反映了 Buffer Pool 的使用效率。

sql
-- 查看 InnoDB Buffer Pool 命中率
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';

-- 计算命中率
-- Buffer Pool 命中率 = 
--   Innodb_buffer_pool_read_requests / 
--   (Innodb_buffer_pool_read_requests + Innodb_buffer_pool_reads) * 100%

理想值：> 99%，低于 99% 说明 Buffer Pool 大小不足或工作集设置不合理。

三、CPU 调优 ​

3.1 CPU 与 MySQL 的关系 ​

CPU 是 MySQL 性能的核心瓶颈之一。CPU 使用率过高通常意味着：

  • 查询需要大量计算（如复杂 JOIN、聚合）
  • 临时表操作过多
  • 锁竞争严重
  • 连接数过多，线程切换频繁

监控 CPU 使用 ​

bash
# 查看 CPU 使用率
top -bn1 | grep "Cpu(s)"

# 查看 MySQL 进程的 CPU 使用
top -b -n 1 -p $(pgrep -f mysql)

# 使用 vmstat 监控
vmstat 1 5

3.2 线程池配置 ​

线程池 vs 每连接一线程 ​

模式说明适用场景
每连接一线程每个连接创建一个线程连接数少，简单场景
线程池多个连接共享线程池高并发场景

MySQL 默认使用"每连接一线程"模式。当连接数过多时，会导致：

  • 线程切换开销大
  • 上下文切换浪费 CPU
  • 内存占用过高

线程池配置 ​

sql
-- MySQL 8.0+ 线程池
INSTALL PLUGIN thread_soname = 'thread_pool.so';

-- 配置线程池大小
SET GLOBAL thread_pool_size = 16;  -- 一般设置为 CPU 核数

-- 配置其他参数
SET GLOBAL thread_pool_oversubscribe = 3;
SET GLOBAL thread_pool_high_priority_connection = 20;

连接数配置 ​

sql
-- 最大连接数
SET GLOBAL max_connections = 500;

-- 等待队列大小
SET GLOBAL back_log = 256;

-- 连接超时
SET GLOBAL wait_timeout = 28800;
SET GLOBAL interactive_timeout = 28800;
SET GLOBAL connect_timeout = 10;

-- 跳过 DNS 解析
SET GLOBAL skip-name-resolve = ON;

线程缓存 ​

sql
-- 线程缓存大小
SET GLOBAL thread_cache_size = 100;

-- 监控线程缓存
SHOW GLOBAL STATUS LIKE 'Threads_created';
SHOW GLOBAL STATUS LIKE 'Threads_cached';

如果 Threads_created 持续增长，说明 thread_cache_size 设置过小，应该调大。

3.3 慢查询分析 ​

慢查询是 CPU 高使用率的常见原因。

sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.1;
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 查看慢查询统计
SELECT * FROM mysql.slow_log 
WHERE start_time > DATE_SUB(NOW(), INTERVAL 1 DAY)
ORDER BY query_time DESC
LIMIT 10;

-- 使用 performance_schema 分析
SELECT 
    DIGEST_TEXT,
    COUNT_STAR AS exec_count,
    AVG_TIMER_WAIT / 1000000000 AS avg_time_sec,
    SUM_TIMER_WAIT / 1000000000 AS total_time_sec
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

4.1 内存分配总览 ​

┌─────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────┤
│                                                             │

4.2 Buffer Pool 大小设置 ​

Buffer Pool 的作用 ​

InnoDB Buffer Pool 是缓存数据和索引的核心内存区域：

  • 缓存数据页和索引页
  • 减少磁盘 I/O
  • 提高查询性能
┌─────────────────────────────────────────────────────────────┐
│                    InnoDB Buffer Pool                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                   Free List                         │   │
│  │  空闲页链表                                          │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                   LRU List                          │   │
│  │  使用中的页链表（最近使用的在前端）                  │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                   Flush List                        │   │
│  │  脏页链表（需要刷盘的页）                            │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  Buffer Pool 命中率 = 命中次数 / 总访问次数               │
│  理想值 > 99%                                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘

推荐设置 ​

系统角色推荐设置
专用数据库服务器物理内存的 50-70%
混合部署（应用+数据库）物理内存的 30-40%
从库（只读）物理内存的 50-60%
sql
-- 设置 Buffer Pool 大小
SET GLOBAL innodb_buffer_pool_size = 8G;

-- 设置实例数（减少锁竞争）
SET GLOBAL innodb_buffer_pool_instances = 8;

-- 查看 Buffer Pool 使用情况
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool%';

Buffer Pool 命中率计算 ​

sql
-- 查看读写请求
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';

-- read_requests: 从 Buffer Pool 读取的次数（命中）
-- reads: 从磁盘读取的次数（未命中）
-- 命中率 = read_requests / (read_requests + reads) * 100%

Buffer Pool 脏页比例 ​

sql
-- 查看脏页比例
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_pages%';

-- Innodb_buffer_pool_pages_data: 已使用页数
-- Innodb_buffer_pool_pages_dirty: 脏页数
-- 脏页比例 = pages_dirty / pages_data * 100%

-- 脏页比例过高调整
SET GLOBAL innodb_max_dirty_pages_pct = 75;
SET GLOBAL innodb_max_dirty_pages_pct_lwm = 0;

4.3 连接内存配置 ​

每个数据库连接都会分配独立的内存，需要合理配置会话级内存参数。

主要会话级内存参数 ​

参数说明默认值建议值
sort_buffer_size排序缓冲区256KB256KB - 4MB
join_buffer_size关联缓冲区256KB256KB - 4MB
read_buffer_size读缓冲区128KB128KB - 4MB
read_rnd_buffer_size随机读缓冲区256KB256KB - 4MB
thread_stack线程栈大小256KB256KB
net_buffer_length连接缓冲区16KB16KB
max_allowed_packet最大包大小4MB64MB
sql
SET GLOBAL sort_buffer_size = 4 * 1024 * 1024;
SET GLOBAL join_buffer_size = 4 * 1024 * 1024;
SET GLOBAL read_buffer_size = 1 * 1024 * 1024;
SET GLOBAL read_rnd_buffer_size = 1 * 1024 * 1024;

内存估算公式 ​

总内存 = 
    innodb_buffer_pool_size
    + innodb_log_buffer_size
    + max_connections * (
        sort_buffer_size +
        join_buffer_size +
        read_buffer_size +
        read_rnd_buffer_size +
        thread_stack +
        net_buffer_length
    )
    + 其他内存（OS、其他进程）

注意：会话级内存参数是每连接独立分配的，max_connections 较大时需要调低单个会话的内存。

4.4 tmp_table_size 配置 ​

tmp_table_size 和 max_heap_table_size 共同决定了内存临时表的大小限制。

sql
-- 临时表超过 tmp_table_size 时会写入磁盘
SET GLOBAL tmp_table_size = 64M;
SET GLOBAL max_heap_table_size = 64M;

-- 监控临时表使用
SHOW GLOBAL STATUS LIKE 'Created_tmp%';
-- Created_tmp_disk_tables: 磁盘临时表数（应尽量为0）

建议：如果 Created_tmp_disk_tables 持续增长，需要增大 tmp_table_size 或优化 SQL。

五、I/O 调优 ​

5.1 磁盘选择（SSD vs HDD） ​

磁盘类型顺序读随机读IOPS价格
HDD200MB/s1MB/s~100低
SATA SSD550MB/s350MB/s~100K中
NVMe SSD3500MB/s2000MB/s~500K高

MySQL 对随机读写敏感，强烈推荐使用 SSD。

5.2 日志文件大小 ​

InnoDB Redo Log 大小 ​

sql
-- 查看当前设置

  • 写入密集型：512MB - 2GB

Binlog 文件大小 ​

sql

5.3 双清缓冲设置 ​

什么是双清（Doublewrite） ​

InnoDB 的双清机制是为了防止部分写（Partial Write）导致的数据损坏。

┌─────────────────────────────────────────────────────────────┐
│                    双清（Doublewrite）机制                   │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  写入路径一：Doublewrite Buffer（共享表空间）                │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  1. 先写入 Doublewrite Buffer（内存）               │   │
│  │  2. 从 Doublewrite Buffer 写入共享表空间             │   │
│  │  3. 再从 Doublewrite Buffer 写入表空间文件          │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  写入路径二：直接写入（独立表空间）                          │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  1. 直接从 Buffer Pool 写入表空间文件               │   │
│  │  2. 不经过 Doublewrite Buffer                       │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘

关闭双清 ​

sql
-- 查看双清状态
SHOW GLOBAL VARIABLES LIKE 'innodb_doublewrite';

-- 关闭双清（SSD 环境下可考虑）
SET GLOBAL innodb_doublewrite = OFF;

风险：关闭双清后，如果发生部分写，数据将损坏。只有在以下条件下才建议关闭：

  • 使用 SSD 存储
  • 有可靠的备份方案
  • 能接受极端情况下的数据丢失

InnoDB Page Cleaner ​

sql
-- Page Cleaner 线程数
SET GLOBAL innodb_page_cleaners = 4;

-- 脏页刷盘阈值
SET GLOBAL innodb_max_dirty_pages_pct = 75;
SET GLOBAL innodb_max_dirty_pages_pct_lwm = 0;

5.4 RAID 配置 ​

RAID 级别选择 ​

RAID 级别数据保护读写性能空间利用率适用场景
RAID 0无极高100%临时数据、缓存
RAID 1高高50%系统盘、关键数据
RAID 5中中67-94%通用场景
RAID 10高极高50%OLTP 数据库

MySQL 推荐 RAID 配置 ​

  • 系统盘：RAID 1
  • 数据盘：RAID 10
  • 日志盘：RAID 1
  • 备份盘：RAID 5 或更低

文件系统选择 ​

文件系统说明推荐场景
XFS高性能，支持大文件Linux 首选
ext4兼容性好，成熟稳定通用场景
ZFS支持快照和压缩备份存储
bash
# 挂载 XFS 文件系统
mkfs.xfs -f /dev/sdb
mount -o noatime,nodiratime /dev/sdb /data

关键挂载选项：

  • noatime：不更新文件访问时间（减少 I/O）
  • nodiratime：不更新目录访问时间

六、连接池配置 ​

6.1 max_connections ​

sql
-- 查看历史最大使用连接数
SHOW GLOBAL STATUS LIKE 'Max_used_connections';

-- OLTP 系统：500 - 2000
SET GLOBAL max_connections = 1000;

-- 配套参数
SET GLOBAL back_log = 128;
SET GLOBAL thread_cache_size = 200;

如果 Max_used_connections 接近 max_connections，需要增大或优化应用减少连接数。

6.2 超时设置 ​

sql
-- 连接建立超时

-- 非交互式连接空闲超时
SET GLOBAL wait_timeout = 28800;

-- 读写操作超时
SET GLOBAL net_read_timeout = 30;
SET GLOBAL net_write_timeout = 60;

-- 锁等待超时

connect_timeout10s连接建立超时
wait_timeout8h非交互连接空闲超时
innodb_lock_wait_timeout50s锁等待超时

HikariConfig config = new HikariConfig();

  2. 合理设置超时，避免长时间占用连接
  3. 使用连接复用，避免频繁创建和销毁

  5. 确保连接使用后正确关闭

七、参数调优 ​

7.1 innodb_buffer_pool_size ​

InnoDB Buffer Pool 的大小，用于缓存数据和索引。

场景推荐值
专用数据库（独占内存）物理内存的 50-70%
混合部署物理内存的 30-40%
从库物理内存的 50-60%
sql
-- MySQL 5.7+ 支持动态调整
SET GLOBAL innodb_buffer_pool_size = 8G;

7.2 innodb_log_file_size ​

Redo Log 文件大小，影响写入性能和恢复时间。

场景推荐值
OLTP（读多写少）256MB - 512MB
OLTP（写密集）512MB - 2GB
sql
SET GLOBAL innodb_log_file_size = 512M;

7.3 innodb_flush_log_at_trx_commit ​

控制 Redo Log 的刷盘策略。

值行为性能数据安全
0每秒刷一次盘最快最差（丢失1秒数据）
1每次事务提交刷盘最慢最好（不丢数据）
2提交写缓存，每秒刷盘中等较好
innodb_flush_log_at_trx_commit = 1（最安全）
事务提交 → 写入 Redo Log 文件 → 调用 fsync 刷盘 → 返回成功

innodb_flush_log_at_trx_commit = 2（性能与安全平衡）
事务提交 → 写入 Redo Log 文件 → 返回成功
（刷盘由后台线程每秒执行一次）

推荐值：

  • 金融、支付类：1
  • 一般业务：2
  • 日志、分析类：0

7.4 sync_binlog ​

控制 Binlog 的刷盘策略。

值行为性能数据安全
0OS 决定刷盘最快最差
1每次事务提交刷盘最慢最好
N每 N 个事务刷盘中等较好

与 innodb_flush_log_at_trx_commit 的组合 ​

组合安全性性能推荐场景
(1, 1)最高最低金融系统
(1, 2)高中一般业务
(2, 1)高中一般业务
(2, 2)较高较高非关键业务
(0, 0)最低最高日志系统
sql
-- 推荐配置
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
SET GLOBAL sync_binlog = 1;

7.5 query_cache_size（8.0 已移除） ​

MySQL 8.0 已移除查询缓存。在 MySQL 5.7 中：

sql
-- 查看查询缓存状态
SHOW GLOBAL STATUS LIKE 'Qcache%';

-- 如果命中率低于 50%，建议关闭
SET GLOBAL query_cache_size = 0;
SET GLOBAL query_cache_type = 0;

替代方案：使用应用层缓存（Redis、Memcached）。

7.6 其他重要参数 ​

innodb_file_per_table ​

sql

每个表使用独立的表空间文件，好处：

  • 表空间可以独立管理
  • 删除大表后空间可以回收
  • 便于数据导入导出

innodb_flush_method ​

sql

table_open_cache ​

sql

back_log ​

   ↓

十二、实战调优案例 ​

案例一：电商系统并发调优 ​

背景 ​

电商系统在大促期间性能瓶颈：QPS 从 3000 降到 500，CPU > 90%。

排查过程 ​

sql
-- 发现大量全表扫描
EXPLAIN SELECT * FROM orders 
WHERE user_id = 100 AND status = 'paid' 
ORDER BY create_time DESC 
LIMIT 20;
-- type: ALL

优化步骤 ​

  1. 创建联合索引：CREATE INDEX idx_user_status_create ON orders(user_id, status, create_time DESC);
  2. 优化 SQL，避免 SELECT *
  3. 调整 Buffer Pool 大小至 16G
  4. 启用读写分离

优化效果 ​

指标优化前优化后提升
QPS500800016x
平均响应时间500ms30ms16.7x
CPU 使用率90%40%-

案例二：日志系统写入优化 ​

优化步骤 ​

  1. 调整刷盘策略：innodb_flush_log_at_trx_commit=0, sync_binlog=0
  2. 增大 Redo Log：innodb_log_file_size=2G
  3. 使用批量写入
  4. 关闭双清（SSD 环境）
  5. 文件系统挂载添加 noatime

优化效果 ​

指标优化前优化后
写入 QPS500050000
平均写入延迟200ms10ms

案例三：报表查询优化 ​

优化步骤 ​

  1. 创建复合索引：CREATE INDEX idx_time_category ON orders(create_time, category_id, total);
  2. 使用覆盖索引
  3. 创建每日汇总表
  4. 应用层缓存

十三、总结 ​

MySQL 性能调优是一项系统工程，需要从多个层面入手。核心要点包括：

  1. 建立完善的监控体系：量化的性能指标是调优的基础
  2. 遵循科学的调优方法论：发现 → 定位 → 分析 → 实施 → 验证 → 监控
  3. 重视 SQL 和索引优化：大多数性能问题通过优化 SQL 就能解决
  4. 合理配置内存参数：Buffer Pool 是 InnoDB 性能的核心
  5. 优化 I/O 配置：使用 SSD、调整刷盘策略、RAID 配置
  6. 建立高可用架构：主从复制 + MHA/Orchestrator/Group Replication
  7. 定期性能测试：使用 sysbench、JMeter 等工具进行基准测试
  8. 持续监控与改进：性能调优没有终点，需要持续迭代

通过系统地应用这些调优策略，可以将 MySQL 的性能发挥到极致，支撑从单机到分布式集群的各种业务场景。
