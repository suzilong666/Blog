日志系统与恢复机制 ​

本文档从底层原理出发，系统性地剖析 MySQL 的日志体系，包括 Error Log、General Log、Slow Query Log、Binlog、Redo Log、Undo Log、Relay Log 等核心日志类型的内部结构与工作机制，并深入讲解事务日志流程与崩溃恢复原理。

一、MySQL 日志体系概览 ​

MySQL 提供了丰富的日志类型，每种日志服务于不同的目的，共同构成了 MySQL 的数据安全与性能监控体系。

日志分类：

  • 审计类日志：Error Log、General Log、Slow Query Log —— 用于诊断和性能分析
  • 数据安全类日志：Binlog、Redo Log、Undo Log、Relay Log —— 用于数据恢复和复制
  • 事务保障类日志：Redo Log（持久性）、Undo Log（原子性/一致性）

二、Error Log ​

2.1 配置与查看 ​

Error Log 记录 MySQL 服务启动、运行和关闭过程中的错误、警告和一般信息。

sql
-- 查看 Error Log 位置
SHOW VARIABLES LIKE 'log_error';

-- 动态设置
SET GLOBAL log_error = '/var/log/mysql/error.log';

-- 通过 my.cnf 配置
-- [mysqld]
-- log_error = /var/log/mysql/error.log
-- log_error_verbosity = 2  -- 1=Error, 2=Error+Warning, 3=Error+Warning+Info

2.2 日志级别 ​

MySQL Error Log 的消息分为三类：

  • Error：严重错误，必须处理
  • Warning：警告信息，建议关注
  • Note/Info：一般信息，可忽略
Error Log 格式:
2024-01-15T10:30:45.123456Z 0 [ERROR] [MY-012345] [Server] ... 错误信息
2024-01-15T10:30:45.123456Z 0 [Warning] [MY-012346] [InnoDB] ... 警告信息
2024-01-15T10:30:45.123456Z 0 [Note] [MY-012347] [Server] ... 一般信息

2.3 常见错误分析 ​

连接相关错误：

[ERROR] [HY000] [Connection] Aborted connection 12345 to db: 'mydb' 
user: 'myuser' host: '192.168.1.1' (Got an error reading communication packets)

→ 通常由客户端异常断开或网络问题导致

InnoDB 相关错误：

[ERROR] [InnoDB] [FATAL] The page index_page_no is corrupted in ...
[ERROR] [InnoDB] Database page corruption on disk or a failed OS call

→ 数据页损坏，需要恢复

复制相关错误：

[ERROR] [Repl] Slave I/O: error connecting to master 
[ERROR] [Repl] Slave SQL: Error 'Duplicate entry'

→ 主从复制中断，需要排查

三、General Log ​

3.1 通用查询日志 ​

General Log 记录 MySQL 服务器收到的每一条语句，无论是否执行成功。这对于调试应用程序和审计所有数据库访问非常有用。

sql
-- 查看配置
SHOW VARIABLES LIKE 'general_log%';

-- 开启 General Log
SET GLOBAL general_log = 'ON';

-- 设置日志输出目标
SET GLOBAL log_output = 'TABLE';       -- 输出到 mysql.general_log 表
SET GLOBAL log_output = 'FILE';        -- 输出到文件
SET GLOBAL general_log_file = '/var/log/mysql/general.log';

-- 动态开启/关闭（避免生产环境长期开启）
SET GLOBAL general_log = 'OFF';

3.2 General Log 表结构 ​

当输出到表时，日志存储在 mysql.general_log 表中：

sql
-- 查看 General Log 内容
SELECT event_time, user_host, thread_id, command_type, argument 
FROM mysql.general_log 
WHERE event_time > NOW() - INTERVAL 1 HOUR 
ORDER BY event_time DESC;
+----------------------------+---------------------+-----------+--------------+------------------------------------------+
| event_time                 | user_host           | thread_id | command_type | argument                                 |
+----------------------------+---------------------+-----------+--------------+------------------------------------------+
| 2024-01-15 10:30:45.123456 | root[root] @ localhost |      1234 | Query        | SELECT * FROM users WHERE id = 1         |
| 2024-01-15 10:30:45.234567 | root[root] @ localhost |      1234 | Query        | INSERT INTO orders SET ...               |
| 2024-01-15 10:30:45.345678 | root[root] @ localhost |      1234 | Quit         |                                          |
+----------------------------+---------------------+-----------+--------------+------------------------------------------+

3.3 General Log 的注意事项 ​

  1. 性能影响：开启 General Log 会显著影响性能（10%-20% 的性能下降）
  2. 日志量：日志量非常大，可能快速占满磁盘
  3. 敏感信息：日志中可能包含密码等敏感信息
  4. 适用场景：开发调试、审计需求、问题排查（短期使用）

四、Slow Query Log ​

4.1 慢查询阈值 ​

Slow Query Log 记录执行时间超过阈值的 SQL 语句，是性能优化的关键工具。

sql
-- 查看配置
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';

-- 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 2.0;  -- 阈值设为 2 秒
SET GLOBAL log_queries_not_using_indexes = 'ON';  -- 记录未使用索引的查询
SET GLOBAL min_examined_row_limit = 1000;  -- 最小检查行数

4.2 慢查询日志格式 ​

# Time: 2024-01-15T10:30:45.123456Z
# User@Host: root[root] @ localhost [127.0.0.1]  Id: 1234
# Query_time: 5.123456  Lock_time: 0.001234  
# Rows_sent: 100  Rows_examined: 50000
# SET timestamp=1705312245;
SELECT u.*, o.total 
FROM users u 
LEFT JOIN orders o ON u.id = o.user_id 
WHERE u.age > 20 
ORDER BY o.total DESC 
LIMIT 100;

关键字段：

  • Query_time：执行时间（秒）
  • Lock_time：等待锁的时间（秒）
  • Rows_sent：返回的行数
  • Rows_examined：检查的行数（这个值越大，性能问题可能越严重）
  • timestamp：执行的时间戳（可以用 SET timestamp= 来重放）

4.3 分析工具 ​

pt-query-digest ​

pt-query-digest 是 Percona Toolkit 中最常用的慢查询分析工具：

bash

# 分析最近1小时的慢查询
pt-query-digest /var/log/mysql/slow.log --since '1h ago'

# 输出 TOP 10 慢查询
pt-query-digest /var/log/mysql/slow.log --limit 10

# 将分析结果导出到表
pt-query-digest --output slowlog /var/log/mysql/slow.log | \
  mysql -e "SET @@session.sql_mode=''; SOURCE /dev/stdin"

# 实时分析（持续跟踪）
pt-query-digest /var/log/mysql/slow.log --watch

# 分析 binlog 格式的日志
pt-query-digest --type binlog /var/log/mysql/binlog.000001

五、Binlog（二进制日志） ​

5.1 Binlog 概述 ​

Binlog 是 MySQL 的逻辑日志，以事件（Event）形式记录所有修改数据的 SQL 语句。Binlog 的核心用途：

  1. 主从复制：从库通过 Binlog 同步数据
  2. 数据恢复：基于时间点的恢复（PITR）
  3. 审计追踪：记录所有数据变更

5.2 Binlog 格式 ​

MySQL 支持三种 Binlog 格式：

Statement 格式 ​

记录原始的 SQL 语句（不包含数据），体积小但可能导致主从不一致。

# 原始 SQL: INSERT INTO t VALUES (NOW(), @@hostname)
# 在主库执行时:  时间=10:30:45, 主机='master'
# 在从库执行时:  时间=10:30:48, 主机='slave'  ← 不一致！

问题场景：

  • 使用 NOW()、RAND()、SYSDATE() 等不确定性函数
  • 使用 LAST_INSERT_ID() 等会话相关函数
  • 使用 USER()、CURRENT_USER() 等用户相关函数
  • 非确定性 UPDATE 和 DELETE（无 ORDER BY 的 LIMIT）

Row 格式（推荐） ​

记录每行数据的实际变更，体积较大但保证一致性。

Row 格式事件示例:
┌─────────────────────────────────────────────────────┐
│  Table_map_event: 表映射事件                        │
│    - 表ID: 100                                       │
│    - 数据库: mydb                                    │
│    - 表名: users                                     │
│    - 列数: 3                                         │
│    - 列类型: (INT, VARCHAR(50), INT)                 │
├─────────────────────────────────────────────────────┤
│  Write_rows_event: 写入行事件                       │
│    - 行数: 2                                         │
│    - 行1: [1, 'Alice', 25]                           │
│    - 行2: [2, 'Bob', 30]                             │
├─────────────────────────────────────────────────────┤
│  Xid_event: 事务提交事件                             │
│    - XID: 12345                                      │
└─────────────────────────────────────────────────────┘

Mixed 格式 ​

混合格式，默认使用 Statement 格式，当语句可能导致不一致时自动切换为 Row 格式。

sql
-- 设置 Binlog 格式
SET GLOBAL binlog_format = 'ROW';       -- 推荐，保证一致性
SET GLOBAL binlog_format = 'STATEMENT';  -- 不推荐
SET GLOBAL binlog_format = 'MIXED';     -- 折中方案

格式对比：

特性StatementRowMixed
日志体积小大中
主从一致性有风险保证大部分保证
可读性高低中
不确定性函数有问题无问题自动处理
推荐场景无生产环境可选

5.3 MySQLbinlog 工具使用 ​

mysqlbinlog 工具用于解析和处理 Binlog 文件：

bash
# 解析 Binlog 文件
mysqlbinlog /var/log/mysql/binlog.000001

# 只解析特定数据库的事件
mysqlbinlog --database=mydb /var/log/mysql/binlog.000001

# 解析特定时间范围的事件
mysqlbinlog --start-datetime="2024-01-15 10:00:00" \
            --stop-datetime="2024-01-15 11:00:00" \
            /var/log/mysql/binlog.000001

# 解析特定位置范围的事件
mysqlbinlog --start-position=4 \
            --stop-position=1234 \
            /var/log/mysql/binlog.000001

# 解析 Row 格式 Binlog（需要 -v 参数查看行数据）
mysqlbinlog -v /var/log/mysql/binlog.000001
# -v: 显示列名
# -vv: 显示更多信息（如数据类型）
# -vvv: 显示完整的 SQL 语句

# 从远程服务器读取 Binlog
mysqlbinlog --read-from-remote-server \
            --host=master --port=3306 \
            --user=root --password \
            mysql-bin.000001

# 解析后直接执行（恢复数据）
mysqlbinlog /var/log/mysql/binlog.000001 | mysql -uroot -p

# 解析后过滤特定类型事件
mysqlbinlog --base64-output=decode-rows -v \
            /var/log/mysql/binlog.000001 | grep -A5 "UPDATE"

# 排除特定事件类型
mysqlbinlog --exclude-gtids='abc:def' \
            /var/log/mysql/binlog.000001

5.4 日志索引文件 ​

MySQL 维护两个索引文件用于追踪 Binlog 位置：

  • mysql-bin.index：记录当前所有 Binlog 文件列表
  • relay-log.index：从库的 Relay Log 索引文件
sql
-- 查看当前 Binlog 位置
SHOW MASTER STATUS;
-- File: mysql-bin.000003
-- Position: 154
-- Binlog_Do_DB:
-- Binlog_Ignore_DB:

-- 查看 Binlog 文件列表
SHOW BINARY LOGS;

5.5 日志清理与管理 ​

sql
-- 查看日志过期时间
SHOW VARIABLES LIKE 'expire_logs_days';

-- 设置过期时间
SET GLOBAL expire_logs_days = 7;  -- 7天后自动清理

-- 手动清理日志
PURGE BINARY LOGS BEFORE NOW() - INTERVAL 3 DAY;
PURGE BINARY LOGS TO 'mysql-bin.000005';

-- 刷新日志（生成新的 Binlog 文件）
FLUSH BINARY LOGS;

5.6 基于时间点恢复（PITR） ​

PITR（Point-In-Time Recovery）是 Binlog 最重要的应用场景：

恢复流程:
1. 恢复最近的全量备份
2. 通过 Binlog 回放到指定时间点
bash
# 完整恢复示例
# 1. 恢复全量备份
mysql < backup.sql

# 2. 回放到指定时间点（例如误删数据前）
mysqlbinlog --stop-datetime="2024-01-15 14:00:00" \
            /var/log/mysql/binlog.000001 \
            /var/log/mysql/binlog.000002 | mysql -uroot -p

# 3. 回放到指定位置
mysqlbinlog --stop-position=12345 \
            /var/log/mysql/binlog.000003 | mysql -uroot -p

PITR 注意事项：

  • 全量备份必须是在 Binlog 起始位置之前
  • 恢复时需要按时间顺序回放 Binlog 文件
  • Row 格式 Binlog 体积较大，恢复时间较长
  • GTID 模式下可以更精确地控制恢复范围

六、Redo Log ​

6.1 Redo Log 概述 ​

Redo Log 是 InnoDB 的物理日志，记录数据页的物理修改操作。它的核心职责是保证事务的持久性（Durability）——即使数据库崩溃，已提交的事务数据也能通过 Redo Log 恢复。

Redo Log 采用循环写模式，由固定大小的文件组成，其写入是顺序写（性能极高）。

6.2 物理日志特点 ​

与 Binlog（逻辑日志）对比：

特性Redo LogBinlog
日志类型物理日志逻辑日志
记录内容页的物理修改SQL 语句或行变更
写入方式顺序写，循环覆盖追加写，不覆盖
所属层级存储引擎层服务层
生命周期实例生命周期可独立配置
恢复粒度物理页逻辑行

6.3 日志结构 ​

Redo Log Block ​

Redo Log 以 Block 为单位组织，每个 Block 大小为 512 字节。

┌────────────────────────────────────────────────────────┐
│                  Redo Log Block (512 bytes)              │
├────────────────────────────────────────────────────────┤
│  ┌──────────────────────────────────────────────────┐  │
│  │  LOG_BLOCK_HEADER (12 bytes)                      │  │
│  │  ├── LOG_BLOCK_SPACE_ID (4B)    空间ID           │  │
│  │  ├── LOG_BLOCK_OFFSET (4B)     页号              │  │
│  │  └── LOG_BLOCK_TYPE (4B)       日志类型           │  │
│  │      (0=LOG_BLOCK, 1=CHECKPOINT, 2=FILE HEADER)  │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │  Redo Records (变长)                               │  │
│  │  ├── Record 1: [type|space|page|undo|data...]    │  │
│  │  ├── Record 2: [type|space|page|undo|data...]    │  │
│  │  └── ...                                          │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │  LOG_BLOCK_CHECKSUM (4 bytes)                     │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘

Redo Record 格式 ​

c
// Redo Record 头部
struct log_record_header {
    ulint type;          // 日志类型
    ulint space;         // 表空间ID
    ulint page_no;       // 页号
    ulint undo_no;       // Undo 号
    ulint info_bits;     // 信息位
};

// 日志类型枚举
enum log_type {
    MLOG_WRITE_STRING = 30,       // 写入字节串
    MLOG_SET_BIT = 31,            // 设置位
    MLOG_COMP_REC_INSERT = 32,    // 压缩插入记录
    MLOG_COMP_REC_DELETE = 33,    // 压缩删除记录
    MLOG_COMP_PAGE_CREATE = 34,   // 创建页
    MLOG_COMP_PAGE_FREE = 35,     // 释放页
    MLOG_NEXT_PAGE = 36,          // 下一页
    MLOG_COMP_PAGE_INIT = 37,     // 初始化页
    MLOG_FILE_NAME = 38,          // 文件名
    MLOG_FILE_DELETE = 39,        // 删除文件
    MLOG_COMP_REC_UPDATE_IN_PLACE = 40,  // 原地更新
};

6.4 LGWR 线程工作机制 ​

Redo Log 的写入由 Log Writer（LGWR）线程负责：

c
void* log_writer_thread(void* arg) {
    log_sys_t* log_sys = (log_sys_t*)arg;
    
    for (;;) {
        // 等待写入请求
        mutex_lock(log_sys->mutex);
        while (!log_sys->write_requested && !log_sys->shutdown) {
            cond_wait(log_sys->writer_cond, log_sys->mutex);
        }
        mutex_unlock(log_sys->mutex);
        
        if (log_sys->shutdown) break;
        
        // 1. 将 log_buffer 中的数据写入 Redo Log 文件
        log_write(log_sys->log_buffer, 
                  log_sys->write_pos, 
                  log_sys->buffer_size);
        
        // 2. 如果有刷盘请求，刷盘到物理磁盘
        if (log_sys->flush_requested) {
            log_buffer_sync();
        }
        
        // 3. 更新写入位置
        log_sys->last_write_pos = log_sys->write_pos;
        log_sys->write_requested = false;
    }
    
    return NULL;
}

LSN（Log Sequence Number）：LSN 是一个单调递增的 64 位整数，表示 Redo Log 中的位置。

c
// LSN 类型
typedef unsigned long long lsn_t;

// LSN 组成:
// 高 32 位: 日志文件编号
// 低 32 位: 文件内偏移
// lsn = (file_no << 32) | offset

6.5 写入与 Checkpoint ​

写入流程 ​

用户线程                    Redo Log Buffer              Redo Log 文件            物理磁盘
  │                           │                           │                      │
  │──修改数据页────────────→  │                           │                      │
  │                           │──先写 Redo Record          │                      │
  │                           │  (log_write())             │                      │
  │                           │                           │                      │
  │──提交事务──────────────→  │                           │                      │
  │                           │──log_buffer_sync()         │                      │
  │                           │  (根据 innodb_flush_log_   │                      │
  │                           │   at_trx_commit 配置)      │                      │
  │                           │                           │                      │
  │                           │                           │──写入 Redo Log 文件  │
  │                           │                           │──刷盘 (可选)        │
  │──返回成功─────────────────────────────────────────────→│                      │
sql
-- 控制 Redo Log 刷盘行为
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
-- 0: 每秒刷一次（最高性能，可能丢失1秒数据）
-- 1: 每次事务提交都刷盘（最安全，默认值）
-- 2: 每次事务提交写文件但不刷盘（折中方案）

Checkpoint 机制 ​

Redo Log 采用循环写模式，当写指针追上检查点位置时，必须推进检查点。

Redo Log 循环结构:
    ┌──────────────────────────────────────────────┐
    │  ib_logfile0                                  │
    │  [已刷盘] [待刷盘] [空闲空间]               │
    │   ↑                                        ↑
    │   last_checkpoint_lsn    write_lsn           │
    └──────────────────────────────────────────────┘
    
    当 write_lsn 追上 last_checkpoint_lsn 时:
    → 必须推进检查点
    → 刷脏页释放空间

Checkpoint 触发条件：

  1. Redo Log 空间不足：强制推进检查点
  2. Master Thread 定期检查：模糊检查点
  3. Buffer Pool 空间不足：淘汰脏页前先刷脏
  4. 数据库关闭：尖锐检查点
c
// 检查点推进逻辑
void log_checkpoint(log_sys_t* log_sys, ulint mode) {
    // 1. 确定需要刷到的 LSN
    lsn_t max_lsn = log_sys->write_lsn - log_sys->checkpoint_age;
    
    // 2. 从 Flush List 中找到需要刷的页
    buf_page_t* page = buf_flush_get_target(max_lsn);
    
    // 3. 异步刷脏
    buf_flush_async_page(page);
    
    // 4. 更新检查点位置
    log_sys->last_checkpoint_lsn = max_lsn;
}

6.6 崩溃恢复流程 ​

当 MySQL 实例异常关闭后，下次启动时会自动执行崩溃恢复：

崩溃恢复流程:
┌────────────┐
│  启动 InnoDB │
└──────┬─────┘
       │
       ▼
┌─────────────────────┐
│  读取上次检查点位置  │
│  (last_checkpoint_lsn)│
└──────┬──────────────┘
       │
       ▼
┌─────────────────────┐
│  前滚（Redo）       │
│  从检查点位置开始    │
│  重放所有 Redo 记录  │
└──────┬──────────────┘
       │
       ▼
┌─────────────────────┐
│  回滚（Undo）       │
│  回滚未提交的事务    │
└──────┬──────────────┘
       │
       ▼
┌─────────────────────┐
│  完成恢复            │
│  接受新连接          │
└─────────────────────┘
c
void innobase_start_or_first_init() {
    // 1. 读取检查点 LSN
    lsn_t checkpoint_lsn = log_sys->last_checkpoint_lsn;
    
    // 2. 前滚：重放 Redo Log 中从检查点之后的所有记录
    //    这会重建所有在崩溃时已修改但未落盘的数据页
    log_recover(checkpoint_lsn, log_sys->write_lsn);
    
    // 3. 回滚：通过 Undo Log 回滚未提交的事务
    //    这些事务在崩溃时还未提交或提交过程中崩溃
    trx_recover();
    
    // 4. 恢复完成
    log_sys->recovered = true;
}

七、Undo Log ​

7.1 Undo Log 概述 ​

Undo Log 是 InnoDB 的逻辑日志，记录数据变更前的逻辑信息。它承担两个核心职责：

  1. 事务回滚：ROLLBACK 时恢复数据到之前的状态
  2. MVCC：为其他事务提供历史版本数据

7.2 逻辑日志特点 ​

与 Redo Log（物理日志）对比：

Redo Log (物理日志):
  "将页 123 的偏移 50 处写入字符串 'hello'"
  → 精确的物理操作

Undo Log (逻辑日志):
  "将 id=1 的记录的 name 字段从 'Alice' 改为 NULL"
  → 逻辑描述的反向操作

7.3 回滚机制 ​

Insert 回滚 ​

sql
-- 事务开始
BEGIN;
INSERT INTO users (id, name) VALUES (1, 'Alice');
-- 生成 Insert Undo Log: 记录完整的行信息

-- 回滚
ROLLBACK;
-- InnoDB 将该记录标记为删除（设置 delete_mark 标志位）

Update 回滚 ​

sql
-- 初始数据: id=1, name='Alice', age=25
BEGIN;
UPDATE users SET name='Bob', age=30 WHERE id=1;
-- 生成 Update Undo Log: 记录修改前的完整行:
--   {id=1, name='Alice', age=25, roll_ptr → NULL}
-- 生成新的行版本:
--   {id=1, name='Bob', age=30, roll_ptr → 上面的Undo记录}

ROLLBACK;
-- InnoDB 将当前版本替换为 Undo Log 中记录的旧版本

Delete 回滚 ​

sql
BEGIN;
DELETE FROM users WHERE id=1;
-- 生成 Delete Undo Log: 记录被删除的完整行

ROLLBACK;
-- InnoDB 将记录的 delete_mark 标志位清除，恢复可见性

7.4 MVCC 实现基础 ​

Undo Log 是 MVCC 的基础——每个事务版本通过 DB_ROLL_PTR 指向前一个历史版本，形成版本链。

版本链:
  当前版本: {name='Bob', trx_id=105, roll_ptr → Undo#3}
       │
       ▼
  Undo#3:  {name='Alice', trx_id=102, roll_ptr → Undo#2}
       │
       ▼
  Undo#2:  {name='Charlie', trx_id=98, roll_ptr → Undo#1}
       │
       ▼
  Undo#1:  {name='Initial', trx_id=95, roll_ptr → NULL}

当事务 A（trx_id=110）读取该记录时：

  1. 读取当前版本：{name='Bob', trx_id=105}
  2. 如果 105 在事务 A 的 ReadView 中不可见
  3. 沿着 roll_ptr 找到 Undo#3：{name='Alice', trx_id=102}
  4. 如果 102 也不可见，继续查找
  5. 直到找到对事务 A 可见的版本

八、Relay Log ​

8.1 主从复制中的中继日志 ​

Relay Log 是从库上的中转日志，用于存储从主库接收到的 Binlog 事件。它在主从复制中扮演"缓冲区"的角色。

主库 (Master)                     从库 (Slave)
┌──────────┐                    ┌──────────┐
│ Binlog    │──IO Thread──→     │ Relay Log │
│ (二进制日志) │  拉取Binlog      │ (中继日志) │
└──────────┘                    └────┬─────┘
                                     │ SQL Thread
                                     ▼
                              ┌──────────┐
                              │ 执行事件  │
                              │ (SQL/Worker)│
                              └──────────┘

8.2 日志处理流程 ​

从库有两个关键线程：

  1. IO Thread：从主库拉取 Binlog 事件，写入本地 Relay Log
  2. SQL Thread（或 Worker Threads）：读取 Relay Log 事件并执行
c
// 从库 IO 线程
void* slave_io_thread(void* arg) {
    for (;;) {
        // 1. 从主库请求 Binlog 事件
        if (master_dump(slave->master_socket, 
                        slave->log_file, 
                        slave->log_pos)) {
            // 2. 接收到事件
            // 3. 写入 Relay Log
            relay_log_write(slave->relay_log, event);
        }
    }
}

// 从库 SQL 线程
void* slave_sql_thread(void* arg) {
    for (;;) {
        // 1. 从 Relay Log 读取事件
        if (relay_log_read(slave->relay_log, &event)) {
            // 2. 解析并执行事件
            exec_relay_event(&event);
            // 3. 更新执行位置
            slave->exec_pos = event->end_pos;
        }
    }
}

并行复制：MySQL 5.6+ 支持并行复制（slave_parallel_workers），多个 Worker Thread 同时执行 Relay Log 中的事件，提升复制效率。

sql
-- 配置并行复制
SET GLOBAL slave_parallel_workers = 4;
SET GLOBAL slave_parallel_type = 'LOGICAL_CLOCK';  -- MySQL 5.7+

九、事务日志流程 ​

9.1 Redo Log 写入顺序 ​

在事务提交过程中，Redo Log 的写入顺序为：

事务提交步骤:
1. 写 Undo Log（记录回滚信息）
2. 修改数据页（在 Buffer Pool 中）
3. 写 Redo Log（记录物理修改）
   → Redo Log 必须在数据页刷盘之前写入
4. 写 Binlog（在 Redo Log 之后写入）
5. 提交事务

9.2 Binlog 写入顺序 ​

Binlog 在 Redo Log 之后、事务提交之前写入：

c
void trx_commit_for_mysql(trx_t* trx) {
    // 1. 将 Redo Log 刷到磁盘（innodb_flush_log_at_trx_commit=1）
    log_buffer_sync();
    
    // 2. 写入 Binlog
    mysql_bin_log.write_binlog(trx->binlog_ctx);
    
    // 3. 将 Binlog 刷到磁盘（sync_binlog=1）
    mysql_binlog.sync();
    
    // 4. 提交事务
    trx->commit_internally(trx);
}

9.3 两阶段提交（2PC）完整流程 ​

两阶段提交保证了 Redo Log 和 Binlog 的一致性，是事务持久性的核心保障。

阶段一：准备阶段 (Prepare)
┌──────────┐     ┌──────────────┐     ┌──────────┐
│  应用层   │────→│   InnoDB     │────→│ Redo Log  │
│ (SQL执行) │     │  (prepare)   │     │ (prepare) │
└──────────┘     └──────────────┘     └──────────┘
                        │
                        │ Redo Log 已写入
                        │ 但还未提交
                        ▼
                 进入准备状态
                 (PREPARED)
                 可以接受崩溃恢复

阶段二：提交阶段 (Commit)
┌──────────┐     ┌──────────────┐     ┌──────────┐
│  应用层   │────→│   InnoDB     │────→│ Binlog    │
│ (提交确认) │     │  (commit)   │     │ (commit)  │
└──────────┘     └──────────────┘     └──────────┘
                        │
                        │ Binlog 已写入
                        │ 事务正式提交
                        ▼
                 进入已提交状态
                 (COMMITTED)
c
// 两阶段提交伪代码
void trx_commit_2pc(trx_t* trx) {
    // ===== 阶段一: Prepare =====
    // 1. 写 Redo Log（带 PREPARED 标记）
    log_write_prepared(trx);
    log_buffer_sync();  // 确保 Redo Log 已落盘
    
    // ===== 阶段二: Commit =====
    // 2. 写 Binlog
    mysql_binlog_write(trx->binlog_events);
    mysql_binlog_sync();  // 确保 Binlog 已落盘
    
    // 3. 写 Redo Log 的 COMMIT 标记
    log_write_commit(trx);
    log_buffer_sync();  // 确保 COMMIT 标记已落盘
    
    // 4. 清理 Undo Log（Insert Undo 可立即清理）
    trx_undo_set_state_at_prepare(trx, TRX_UNDO_COMMITTED);
}

两阶段提交的关键约束：

  1. Redo Log 在 Binlog 之前写入
  2. Redo Log 在数据页刷盘之前写入（WAL 协议）
  3. Binlog 作为事务提交的"见证者"
  4. 崩溃恢复时，通过 Binlog 判断事务是否已提交

十、崩溃恢复 ​

10.1 恢复触发条件 ​

崩溃恢复在以下情况下触发：

  • MySQL 进程异常终止（kill -9、系统崩溃、断电）
  • Redo Log 中存在未处理的 PREPARED 事务
  • 上次正常关闭时未完成的检查点
c
bool innobase_init_or_start() {
    // 检查是否需要崩溃恢复
    if (srv_was_crashed) {
        // 执行崩溃恢复
        crash_recovery();
    }
    // 正常启动
    return innobase_start();
}

10.2 Redo 前滚 ​

崩溃恢复的第一步是前滚（Redo）——将 Redo Log 中已提交但未刷盘的修改重做：

前滚过程:
1. 从检查点位置开始，顺序扫描 Redo Log
2. 对每条 Redo Record:
   a. 从 Buffer Pool 中查找数据页
   b. 如果不在 Buffer Pool，从磁盘读取
   c. 应用 Redo Record 中记录的物理修改
3. 继续直到 Redo Log 的最后位置
4. 前滚完成后，所有已提交的事务修改都已恢复
c
void log_recover(lsn_t start_lsn, lsn_t end_lsn) {
    lsn_t lsn = start_lsn;
    
    while (lsn < end_lsn) {
        // 1. 读取 Redo Record
        log_record_t* record = log_read_record(lsn);
        
        // 2. 获取或加载数据页
        buf_page_t* page = buf_page_get(record->space, 
                                         record->page_no);
        
        // 3. 应用物理修改
        switch (record->type) {
            case MLOG_WRITE_STRING:
                // 在指定位置写入字节串
                memcpy(page + record->offset, 
                       record->data, 
                       record->len);
                break;
            case MLOG_COMP_REC_INSERT:
                // 执行插入操作
                page_insert_record(page, record->data);
                break;
            case MLOG_COMP_REC_DELETE:
                // 执行删除操作
                page_delete_record(page, record->data);
                break;
            // ... 其他类型
        }
        
        // 4. 更新页的 LSN
        page->newest_modification = lsn;
        
        // 5. 移动到下一条记录
        lsn += log_record_size(record);
    }
}

10.3 Undo 回滚 ​

前滚完成后，需要通过 Undo Log 回滚未提交的事务：

回滚过程:
1. 扫描 Redo Log，找到所有处于 PREPARED 状态的事务
2. 对于每个 PREPARED 事务:
   a. 检查 Binlog 是否存在对应的 XID Event
   b. 如果 Binlog 中有 → 事务已提交，改为 COMMITTED
   c. 如果 Binlog 中没有 → 事务未提交，执行回滚
3. 对于已回滚的事务，清理其 Undo Log
c
void trx_recover_from_prepared() {
    // 1. 扫描所有 PREPARED 状态的事务
    for (trx_t* trx : prepared_trxs) {
        // 2. 检查 Binlog 中是否有该事务的 XID
        bool binlog_found = mysql_binlog_find_xid(trx->xid);
        
        if (binlog_found) {
            // 事务已提交，改为 COMMITTED
            trx->state = TRX_STATE_COMMITTED;
            // 写 Redo Log COMMIT 标记
            log_write_commit(trx);
        } else {
            // 事务未提交，执行回滚
            trx_roll_back(trx);
            trx->state = TRX_STATE_ROLLED_BACK;
        }
        
        // 3. 释放事务资源
        trx_free(trx);
    }
}

10.4 Binlog 一致性检查 ​

崩溃恢复完成后，还需要检查 Binlog 与 Redo Log 的一致性：

一致性检查:
1. Redo Log 中的 COMMIT 标记 ←→ Binlog 中的 XID Event
2. 对比 Redo Log 末尾位置 ←→ Binlog 末尾位置
3. 如果存在不一致，以 Binlog 为准（Binlog 是事务提交的最终见证）

十一、Binlog 与 Redo 一致性 ​

11.1 两阶段提交保证 ​

两阶段提交的核心目的是保证 Redo Log 和 Binlog 的一致性：

正常流程:
  用户事务 → Redo Log(PREPARED) → Binlog(COMMIT) → Redo Log(COMMIT)
                                           ↑
                                    事务的"生死线"
                                    只要 Binlog 写入成功，
                                    事务就一定是已提交的

11.2 崩溃点分析 ​

场景1：在 Redo Log PREPARED 之后、Binlog 之前崩溃

时间线:
  ✓ Redo Log PREPARED 已写入
  ✗ Binlog 未写入
  ✗ Redo Log COMMIT 未写入
  
恢复策略:
  → 扫描 Redo Log，找到 PREPARED 事务
  → 检查 Binlog，无对应 XID
  → 判定为未提交事务 → 执行回滚
  → 正确！数据一致性得到保证

场景2：在 Binlog COMMIT 之后、Redo Log COMMIT 之前崩溃

时间线:
  ✓ Redo Log PREPARED 已写入
  ✓ Binlog COMMIT 已写入
  ✗ Redo Log COMMIT 未写入
  
恢复策略:
  → 扫描 Redo Log，找到 PREPARED 事务
  → 检查 Binlog，有对应 XID
  → 判定为已提交事务 → 写 Redo Log COMMIT 标记
  → 正确！数据一致性得到保证

场景3：在 Redo Log COMMIT 之后崩溃

时间线:
  ✓ Redo Log PREPARED 已写入
  ✓ Binlog COMMIT 已写入
  ✓ Redo Log COMMIT 已写入
  
恢复策略:
  → 直接使用 Redo Log 前滚
  → 无需特殊处理
  → 正确！数据一致性得到保证

11.3 数据一致性验证 ​

sql
-- 验证 Binlog 与数据的一致性
-- 1. 检查 Binlog 中记录的事务是否都已提交
-- 2. 检查数据文件中的数据是否与 Binlog 一致

-- 工具: mysqlbinlog + diff

  mysql -e "SELECT COUNT(*) FROM users" > current_count

十二、日志配置最佳实践 ​

12.1 Redo Log 配置 ​

sql
-- 查看当前 Redo Log 配置
SHOW VARIABLES LIKE 'innodb_log%';

-- 推荐配置（OLTP 场景）
SET GLOBAL innodb_log_file_size = 2G;      -- 单个日志文件大小
SET GLOBAL innodb_log_files_in_group = 4;  -- 日志文件数量
SET GLOBAL innodb_flush_log_at_trx_commit = 1;  -- 每次提交刷盘
SET GLOBAL innodb_flush_method = 'O_DIRECT';    -- 使用 O_DIRECT

innodb_log_file_size 设置原则：

  • 太小（< 128M）：检查点过于频繁，性能下降
  • 太大（> 4G）：崩溃恢复时间过长
  • 推荐值：512M - 4G，根据业务写入量调整

innodb_flush_log_at_trx_commit 选择：

  • 1（推荐）：最安全，每次事务提交都刷盘
  • 2：折中方案，每秒刷一次
  • 0：最不安全，可能丢失 1 秒数据（不推荐生产环境）

12.2 Binlog 配置 ​

sql
-- 推荐配置
SET GLOBAL binlog_format = 'ROW';              -- Row 格式
SET GLOBAL binlog_cache_size = 4M;             -- Binlog 缓存
SET GLOBAL max_binlog_size = 1G;              -- 最大 Binlog 文件
SET GLOBAL expire_logs_days = 7;              -- 过期时间
SET GLOBAL sync_binlog = 1;                    -- 每次提交同步
SET GLOBAL binlog_rows_query_log_events = ON;  -- 记录原始 SQL

sync_binlog 选择：

  • 1（推荐）：每次事务提交都同步 Binlog 到磁盘
  • 0：性能高但可能丢失数据
  • N：每 N 次事务同步一次

12.3 Undo Log 配置 ​

sql
SET GLOBAL innodb_undo_directory = '/data/mysql/undo';
SET GLOBAL innodb_undo_tablespaces = 3;         -- 3 个 Undo 表空间
SET GLOBAL innodb_undo_log_truncate = ON;       -- 在线截断
SET GLOBAL innodb_max_undo_log_size = 2G;       -- 最大 Undo 日志大小

# 恢复
mysql -uroot -p < full_backup.sql
mysql -uroot -p mydb < mydb_backup.sql

关键参数：

  • --single-transaction：使用一致性快照，不锁表（推荐 InnoDB 表）
  • --master-data=2：在备份中记录 Binlog 位置
  • --routines：备份存储过程和函数
  • --triggers：备份触发器
  • --events：备份事件调度器
  • --flush-logs：备份前刷新日志
  • --delete-master-logs：备份后删除旧日志（谨慎使用）

13.2 物理备份（xtrabackup） ​

bash
# 全量备份
xtrabackup --backup --target-dir=/backup/full

# 准备备份（用于恢复）
xtrabackup --prepare --target-dir=/backup/full

# 恢复备份
xtrabackup --copy-back --target-dir=/backup/full

# 增量备份
xtrabackup --backup --target-dir=/backup/inc1 \
            --incremental-basedir=/backup/full

# 增量备份链恢复
xtrabackup --prepare --target-dir=/backup/full
xtrabackup --prepare --target-dir=/backup/full \
            --incremental-dir=/backup/inc1
xtrabackup --prepare --target-dir=/backup/full \
            --incremental-dir=/backup/inc2
xtrabackup --copy-back --target-dir=/backup/full

xtrabackup 工作原理：

  1. 备份 InnoDB 数据文件（页级别）
  2. 记录当时的 Redo Log 位置（LSN）
  3. 在备份过程中持续追踪 Redo Log 的新写入
  4. --prepare 阶段重放备份期间的 Redo Log，使数据页达到一致性状态

13.3 备份恢复演练 ​

定期进行恢复演练是保证备份有效性的唯一方法：

恢复演练流程:
┌─────────────────────────────────────────────────────┐
│  1. 在测试环境部署 MySQL                              │
│  2. 恢复最近的全量备份                                 │
│  3. 回放 Binlog 到指定时间点（PITR 测试）              │
│  4. 验证数据完整性和一致性                             │
│  5. 记录恢复时间和 RTO（Recovery Time Objective）      │
│  6. 验证 RPO（Recovery Point Objective）是否满足需求   │
│  7. 形成演练报告，归档                                 │
└─────────────────────────────────────────────────────┘

RTO 与 RPO：

  • RTO（恢复时间目标）：从故障发生到恢复完成的最大时间
  • RPO（恢复点目标）：允许丢失的最大数据量（时间或事务数）

总结 ​

MySQL 的日志体系是其数据安全的基石。通过深入理解各种日志的内部结构和工作机制：

  1. Error Log：诊断 MySQL 运行状态，快速定位错误
  2. General Log：审计所有数据库操作，用于安全审计
  3. Slow Query Log：发现性能瓶颈，指导 SQL 优化
  4. Binlog：实现主从复制和基于时间点的恢复
  5. Redo Log：保证事务持久性，支撑崩溃恢复
  6. Undo Log：实现事务回滚和 MVCC
  7. Relay Log：主从复制的中转站

两阶段提交（2PC）是日志一致性的核心保障，理解其原理有助于在故障场景下做出正确的恢复决策。定期进行备份恢复演练，是数据安全的最后一道防线。
