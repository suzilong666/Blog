查询优化器原理 ​

本文档从源码级别深入剖析 MySQL 查询优化器的工作原理，涵盖 SQL 解析、查询改写、索引选择、执行计划生成、统计信息、连接算法、子查询优化等核心模块。

一、优化器的总体架构 ​

MySQL 查询优化器是一个基于代价模型（Cost Model）的选择型优化器。它的核心任务是：接收经过解析的 SQL 语句，生成多个候选执行计划，并从中选择代价最低的一个。

1.1 优化器处理流程 ​

SQL 输入
    │
    ▼
┌─────────────────────┐
│  词法分析 (Scanner)  │  → 将 SQL 字符串拆分为 Token 序列
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  语法分析 (Parser)   │  → 构建抽象语法树 (AST)
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  语义分析 (Analyzer) │  → 检查表、列、权限
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  查询改写 (Rewriter) │  → 视图合并、子查询优化、等价变换
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  代价优化 (Optimizer)│  → 基于代价模型选择最优执行计划
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│  执行计划生成        │  → 生成最终的 QEP (Query Execution Plan)
└─────────┬───────────┘
          │
          ▼
    执行器 (Executor)

1.2 核心数据结构 ​

优化器的核心数据结构是 JOIN 对象和 QEP_TAB 链表。

c
// JOIN 对象 - 优化器的核心上下文
struct JOIN {
    THD* thd;                    // 线程描述符
    LEX* select_lex;             // SELECT 语句的语法树
    QEP_TAB* qep_tab;            // 查询执行计划的表链表
    QEP_TAB* order;              // 排序/分组后的表链表
    JOIN_TAB* join_tab;          // 旧版连接表结构（兼容）
    table_map_t const_tables;    // 常量表位图
    table_map_t all_tables;      // 所有表的位图
    uint join_tab_count;         // 连接表数量
    uint best_qep;              // 最佳执行计划
    Cost_estimates best_cost;    // 最佳代价估计
    // 子查询相关
    JOIN**  subjoin_map;
    // 代价模型
    Cost_model* cost_model;
};

// QEP_TAB - 查询执行计划中的表节点
struct QEP_TAB {
    TABLE* table;                // 物理表对象
    QEP_TAB* next;               // 下一个表
    QEP_TAB* prev;               // 上一个表
    // 访问方法
    enum access_method {
        AM_INVALID,
        AM_SYSTEM,              // 系统表
        AM_CONST,               // 常量查找
        AM_EQ_REF,              // 等值引用
        AM_REF,                 // 范围查找
        AM_REF_OR_NULL,         // 范围查找(含NULL)
        AM_INDEX_SCAN,          // 全索引扫描
        AM_INDEX_RANGE_SCAN,    // 索引范围扫描
        AM_TABLE_SCAN,          // 全表扫描
        AM_INDEX_MERGE,         // 索引合并
        AM_FT,                  // 全文搜索
        AM_MATERIALIZATION,     // 物化
        AM_LOOP,                // 循环
    } access_method;
    // 代价估计
    Cost_estimates cost;
    // 行数估计
    ha_rows rows;
    // 索引信息
    uint ref_key;                // 使用的索引键
    uint ref_len;               // 索引键长度
    unsigned char* ref_value;    // 索引值
    // 连接信息
    QEP_TAB* join;              // 连接目标
    uint join_tab_idx;          // 连接表索引
    // 条件
    Item* select;               // 附加选择条件
    // 半连接/反连接
    bool is_sj;                 // 是否为半连接
    bool is_anti_sj;            // 是否为反连接
};

二、SQL 解析与预处理 ​

2.1 词法分析 ​

词法分析器（Scanner）将 SQL 字符串拆分为 Token 序列。MySQL 使用手写的词法分析器（sql/sql_lex.cc），而非自动生成工具。

c
// 词法分析器的核心状态机
class Sql_scanner {
    const char* m_ptr;           // 当前位置
    const char* m_end;           // 结束位置
    int m_token;                 // 当前 Token
    // ...
    
    int lex_one_token(LEX_CSTRING* yylval) {
        // 跳过空白和注释
        skip_whitespace();
        
        // 读取下一个字符
        char c = *m_ptr;
        
        if (is_alpha(c) || c == '_') {
            // 标识符或关键字
            return lex_id();
        } else if (is_digit(c)) {
            // 数字
            return lex_number();
        } else if (c == '\'') {
            // 字符串
            return lex_string();
        } else {
            // 运算符、标点符号等
            return lex_operator();
        }
    }
};

Token 类型示例：

  • TOK_SELECT：SELECT 关键字
  • TOK_FROM：FROM 关键字
  • TOK_WHERE：WHERE 关键字
  • TOK_IDENT：标识符（表名、列名）
  • TOK_INT_NUM：整数常量
  • TOK_STR_NUM：字符串常量
  • TOK_EQ：等号
  • TOK_LT：小于号

2.2 语法分析 ​

MySQL 使用 Bison（yacc）生成的语法分析器（sql/sql_yacc.y）。语法分析器将 Token 序列构建为抽象语法树（AST）。

SELECT id, name
FROM users
WHERE age > 20
ORDER BY name
LIMIT 10;

对应的 AST:

2.3 语义分析 ​

语义分析（sql/sql_prepare.cc）验证 AST 中的每个元素是否合法：

  1. 表名解析：验证 FROM 子句中的表是否存在
  2. 列名解析：验证 SELECT、WHERE、ORDER BY 等子句中的列是否存在
  3. 类型检查：验证表达式中的类型是否兼容
  4. 函数解析：验证使用的函数是否存在且参数正确
  5. 聚合检查：验证 GROUP BY 和聚合函数的使用是否正确
c
// 语义分析核心函数
bool LEX::prepare(THD* thd) {
    // 1. 检查权限
    if (check_access(thd)) return true;
    
    // 2. 验证所有表
    for (TABLE_LIST* table : table_list) {
        if (open_and_process_routine(thd, table)) return true;
    }
    
    // 3. 解析所有列引用
    for (Item* item : all_fields) {
        if (item->fix_fields(thd, &item)) return true;
    }
    
    // 4. 类型检查和转换
    if (propagate_type(thd)) return true;
    
    return false;
}

2.4 权限检查 ​

权限检查在 mysql_check_permission() 中完成，检查用户是否对涉及的表具有 SELECT 权限。MySQL 8.0 中引入了新的权限检查机制：

  • 语句级权限：SELECT、INSERT、UPDATE、DELETE
  • 列级权限：特定列的访问权限
  • 动态权限：BACKUP_ADMIN、REPLICATION_SLAVE 等
  • 角色权限：基于角色的权限管理

三、查询改写阶段 ​

查询改写是优化器的"预处理"阶段，它对 SQL 进行等价变换，为后续的代价优化创造更好的条件。

3.1 视图合并 ​

当 SQL 语句引用了视图时，优化器会尝试将视图定义合并到外层查询中：

sql
-- 原始查询
SELECT v.age, COUNT(*) FROM (
    SELECT age FROM users WHERE status = 'active'
) AS v
WHERE v.age > 20
GROUP BY v.age;

-- 视图合并后的等价查询
SELECT age, COUNT(*)
FROM users
WHERE status = 'active' AND age > 20
GROUP BY age;
c
// 视图合并函数
bool LEX::merge_view(THD* thd, LEX* view_lex) {
    // 条件：视图必须简单（无聚合、无GROUP BY、无子查询）
    if (!is_simple_view(view_lex)) {
        // 不能合并，使用物化视图
        return false;
    }
    
    // 将视图的 FROM、WHERE 等子句合并到外层
    // 1. 合并 FROM 子句
    // 2. 合并 WHERE 条件
    // 3. 替换列引用
    merge_from_clause(view_lex);
    merge_where_clause(view_lex);
    replace_column_references(view_lex);
    
    return true;
}

视图合并的限制：

  • 视图不能包含聚合函数（COUNT、SUM 等）
  • 视图不能包含 GROUP BY 或 DISTINCT
  • 视图不能包含子查询
  • 视图不能包含 LIMIT

3.2 子查询优化 ​

MySQL 将子查询优化为半连接（Semi-join）或物化（Materialization）。这是查询改写中最关键的部分。

子查询类型：

  • IN 子查询：WHERE col IN (SELECT ...)
  • NOT IN 子查询：WHERE col NOT IN (SELECT ...)
  • EXISTS 子查询：WHERE EXISTS (SELECT ...)
  • 标量子查询：WHERE col = (SELECT ...)
sql
-- 原始SQL
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE total > 100);

-- 优化方式1: 半连接 (Semi-join)
-- 将 IN 转换为 EXISTS 形式
SELECT * FROM users
WHERE EXISTS (
    SELECT 1 FROM orders
    WHERE orders.user_id = users.id AND orders.total > 100
);

-- 优化方式2: 物化 (Materialization)
-- 先执行子查询生成临时表，再与外层查询连接
CREATE TEMPORARY TABLE tmp (user_id INDEX) AS
SELECT user_id FROM orders WHERE total > 100;
SELECT /*+ SEMIJOIN(tmp) */ users.* FROM users
JOIN tmp ON users.id = tmp.user_id;

3.3 等价变换 ​

优化器会对条件进行等价变换，使其更容易利用索引：

sql
-- 原始: WHERE 20 < age → 改写为: WHERE age > 20
-- 原始: WHERE id = 100 → 改写为: WHERE id = 100 (常量)

-- OR 条件转换为 UNION (如果无法使用索引)
SELECT * FROM users WHERE age = 20 OR age = 30;
→ (如果 age 没有索引)
SELECT * FROM users WHERE age = 20
UNION
SELECT * FROM users WHERE age = 30;

-- 隐式类型转换的处理
SELECT * FROM users WHERE id = '100';
→ 转换为: WHERE id = 100

3.4 常量传播 ​

常量传播将计算可以提前完成的表达式进行求值：

sql
SELECT * FROM users WHERE age > 20 + 3;
→ 常量传播: WHERE age > 23

SELECT * FROM users WHERE create_time > '2020-01-01' + INTERVAL 1 YEAR;
→ 常量传播: WHERE create_time > '2021-01-01'
c
// 常量传播函数
void propagate_type_constants(THD* thd, Item* item) {
    if (item->type() == Item::INT_ITEM_FUNC) {
        // 如果所有参数都是常量，直接计算
        if (item->const_item()) {
            item->val_int();  // 触发计算
        }
    }
    // 递归处理子表达式
    for (Item* arg : item->arguments()) {
        propagate_type_constants(thd, arg);
    }
}

四、索引选择优化 ​

4.1 范围扫描选择 ​

当 WHERE 条件中包含索引列的范围条件时，优化器会选择索引范围扫描：

sql
SELECT * FROM users WHERE age > 20 AND age < 30;
-- 如果 age 有索引，选择 range scan

范围扫描的选择逻辑在 Optimize_table_order::choose_table_order() 中完成：

c
void Optimize_table_order::choose_table_order() {
    // 对每个表，评估每种可能的访问方法
    for (QEP_TAB* tab : qep_tabs) {
        // 1. 尝试常量查找 (eq_ref)
        if (try_eq_ref(tab)) continue;
        
        // 2. 尝试范围扫描 (range)
        if (try_range_scan(tab)) continue;
        
        // 3. 尝试索引扫描 (index scan)
        if (try_index_scan(tab)) continue;
        
        // 4. 全表扫描
        set_table_scan(tab);
    }
}

bool Optimize_table_order::try_range_scan(QEP_TAB* tab) {
    // 收集所有可以使用索引的条件
    Key_range_keypart_map key_usage;
    collect_key_usage(tab, key_usage);
    
    // 计算范围扫描的代价
    Cost_estimates range_cost;
    range_cost = compute_range_cost(tab, key_usage);
    
    // 如果范围扫描的代价比全表扫描低，使用范围扫描
    Cost_estimates scan_cost = compute_scan_cost(tab);
    if (range_cost < scan_cost) {
        tab->access_method = AM_INDEX_RANGE_SCAN;
        tab->cost = range_cost;
        return true;
    }
    return false;
}

4.2 多列索引选择 ​

对于联合索引 (col1, col2, col3)，优化器遵循最左前缀原则：

sql
-- 可以使用索引 (col1)
SELECT * FROM t WHERE col1 = 1;

-- 可以使用索引 (col1, col2)
SELECT * FROM t WHERE col1 = 1 AND col2 = 2;

-- 可以使用全部索引 (col1, col2, col3)
SELECT * FROM t WHERE col1 = 1 AND col2 = 2 AND col3 = 3;

-- 只能使用 col1 (col2 之前断裂)
SELECT * FROM t WHERE col1 = 1 AND col3 = 3;

-- 不能使用索引 (跳过了 col1)
SELECT * FROM t WHERE col2 = 2;

优化器在 best_extension_by_limited_search() 中选择最佳的索引前缀：

c
void best_extension_by_limited_search(
    QEP_TAB* tab, uint key, uint max_used_keys,
    uint* used_keys, Cost_estimates* cost) {
    
    // 尝试使用索引的不同前缀长度
    for (uint i = 1; i <= max_used_keys; i++) {
        // 计算使用前 i 列的代价
        Cost_estimates current_cost;
        current_cost = compute_key_prefix_cost(tab, key, i);
        
        if (current_cost < *cost) {
            *cost = current_cost;
            *used_keys = i;
        }
    }
}

4.3 覆盖索引选择 ​

覆盖索引（Covering Index）是指查询所需的所有列都在索引中，不需要回表：

sql
-- 表有索引 (age, id)
-- 查询只需要 age 和 id，都是索引列
SELECT age, id FROM users WHERE age > 20;
-- → 可以使用覆盖索引，避免回表

优化器通过 check_cover_covering() 函数检查是否可以使用覆盖索引：

c
bool check_cover_covering(QEP_TAB* tab, uint key) {
    // 遍历查询需要的所有列
    for (Item* item : tab->query_columns) {
        // 检查列是否在索引中
        if (!is_column_in_key(item, key, tab->table)) {
            return false;
        }
    }
    return true;  // 所有列都在索引中，可以使用覆盖索引
}

五、执行计划生成 ​

5.1 代价模型（Cost Model） ​

MySQL 8.0 引入了新的代价模型，将代价分为单次操作代价和每行代价：

c
// 代价模型的核心参数
struct Cost_model_constants {
    // 单次操作代价
    double seq_page_cost;           // 顺序读一个页的代价
    double random_page_cost;        // 随机读一个页的代价
    double cpu_row_cost;            // 处理一行数据的CPU代价
    double cpu_eq_cond_cost;       // 处理等值条件的CPU代价
    double cpu_range_cond_cost;     // 处理范围条件的CPU代价
    
    // 行处理代价
    double cpu_row_compare_cost;    // 行比较代价
    double cpu_row_copy_cost;       // 行拷贝代价
    
    // 连接代价
    double cpu_join_create_cost;    // 创建连接的代价
    double cpu_join_record_cost;    // 连接记录的代价
};

代价计算示例：

c
Cost_estimates compute_table_scan_cost(TABLE* table, 
                                       Cost_model* model) {
    // 顺序扫描代价 = 页数 × 顺序页代价 + 行数 × CPU行代价
    double pages = table->file->stats.records / 
                   model->constants->records_per_page;
    double scan_cost = pages * model->constants->seq_page_cost;
    double cpu_cost = table->file->stats.records * 
                     model->constants->cpu_row_cost;
    
    return Cost_estimates(scan_cost + cpu_cost, 
                          table->file->stats.records);
}

Cost_estimates compute_index_scan_cost(TABLE* table, uint key,
                                       Cost_model* model) {
    // 索引扫描代价 = 索引页数 × 随机页代价 + 行数 × CPU代价
    double index_pages = table->file->stats.key_blocks[key];
    double scan_cost = index_pages * model->constants->random_page_cost;
    double cpu_cost = table->file->stats.records * 
                     model->constants->cpu_row_cost;
    
    return Cost_estimates(scan_cost + cpu_cost, 
                          table->file->stats.records);
}

5.2 选择最佳连接顺序 ​

对于多表连接，优化器需要选择最佳的表连接顺序。这是一个经典的排列组合问题——n 个表有 n! 种连接顺序。

动态规划算法 ​

MySQL 使用动态规划（Dynamic Programming）算法来选择最佳连接顺序，由 Optimize_table_order::choose_table_order() 实现：

以3个表 A、B、C 为例:

阶段1: 选择第一个表
  → A 的最佳访问代价
  → B 的最佳访问代价
  → C 的最佳访问代价
  
阶段2: 选择第二个表
  → A→B 的最佳代价（基于已选择A）
  → A→C 的最佳代价（基于已选择A）
  → B→A 的最佳代价（基于已选择B）
  → B→C 的最佳代价（基于已选择B）
  → C→A 的最佳代价（基于已选择C）
  → C→B 的最佳代价（基于已选择C）
  
阶段3: 选择第三个表
  → A→B→C
  → A→C→B
  → B→A→C
  → B→C→A
  → C→A→B
  → C→B→A
  
最后：从所有 3! = 6 种方案中选择代价最低的
c
void Optimize_table_order::choose_table_order() {
    uint n_tables = qep_tabs_count;
    
    // 动态规划: best_costs[mask] = 最佳代价
    // mask 是位图，表示已选择的表
    Cost_estimates* best_costs = new Cost_estimates[1 << n_tables];
    uint** best_orders = new uint*[1 << n_tables];
    
    // 初始化：选择单个表
    for (uint i = 0; i < n_tables; i++) {
        uint mask = 1 << i;
        best_costs[mask] = compute_initial_cost(qep_tabs[i]);
        best_orders[mask] = new uint[1]{i};
    }
    
    // 逐步添加表
    for (uint mask = 1; mask < (1 << n_tables); mask++) {
        for (uint next = 0; next < n_tables; next++) {
            if (mask & (1 << next)) continue;  // 已选择
            uint new_mask = mask | (1 << next);
            
            // 计算将 next 添加到当前顺序后的代价
            Cost_estimates new_cost = best_costs[mask] + 
                compute_join_cost(qep_tabs[best_orders[mask][count-1]], 
                                  qep_tabs[next]);
            
            if (new_cost < best_costs[new_mask]) {
                best_costs[new_mask] = new_cost;
                // 记录最佳顺序
            }
        }
    }
    
    // 找到最佳全表连接顺序
    uint full_mask = (1 << n_tables) - 1;
    best_qep_order = best_orders[full_mask];
}

贪心算法 ​

当表数量较多（超过 oprimizer_prune_level）时，MySQL 会切换到贪心算法以避免指数级的计算开销。贪心算法逐步选择当前代价最低的表加入连接序列。

c
// 贪心算法示意
void greedy_choose_table_order(QEP_TAB** tables, uint n) {
    QEP_TAB** order = new QEP_TAB*[n];
    bool* used = new bool[n]();
    
    for (uint step = 0; step < n; step++) {
        double best_cost = DBL_MAX;
        uint best_idx = 0;
        
        for (uint i = 0; i < n; i++) {
            if (used[i]) continue;
            
            // 计算将表 i 加入当前顺序的代价
            double cost = compute_greedy_step_cost(order, step, tables[i]);
            if (cost < best_cost) {
                best_cost = cost;
                best_idx = i;
            }
        }
        
        order[step] = tables[best_idx];
        used[best_idx] = true;
    }
    
    delete[] used;
    delete[] order;
}

5.3 剪枝策略 ​

为了加速动态规划的执行，MySQL 使用多种剪枝策略：

  1. prune_level 剪枝：当 optimizer_prune_level > 0 时，允许在搜索过程中剪枝
  2. search_depth 限制：optimizer_search_depth 限制动态规划的搜索深度
  3. 子查询优先：将子查询物化为临时表，简化主查询的优化
  4. 多范围读（MRR）：优化范围查询的 I/O 模式

八、连接算法 ​

8.1 嵌套循环连接（Nested Loop Join） ​

嵌套循环连接是 MySQL 最基本的连接算法，由 Nested_loop_join_executor 实现：

外层表: users (age > 20)
内层表: orders (user_id = users.id)

执行过程:
for each user in users where age > 20:  // 外层循环
    for each order in orders where user_id = user.id:  // 内层循环
        output user + order
c
// 嵌套循环连接执行器
class Nested_loop_join_executor : public Join_executor {
public:
    void read_rows() override {
        for (;;) {
            // 1. 读取外层表的一行
            if (!m_inner_row_ready) {
                if (!m_outer->read_row()) {
                    return;  // 外层表结束
                }
                m_inner_row_ready = true;
            }
            
            // 2. 在内层表中查找匹配行
            if (!m_inner->read_row()) {
                m_inner->rewind();  // 重置内层表
                m_inner_row_ready = false;
                continue;
            }
            
            // 3. 输出连接结果
            output_row();
        }
    }
};

代价：O(n × m)，其中 n 是外层表的行数，m 是内层表的平均匹配行数。

8.2 块嵌套循环连接（Block Nested Loop Join） ​

当内层表没有可用索引时，使用块嵌套循环连接。它将外层表的行缓存到 Join Buffer 中，批量扫描内层表：

Join Buffer (缓存外层表的行):
┌──────────────────────────────┐
│ user1 (id=1, age=25)         │
│ user2 (id=2, age=30)         │
│ user3 (id=3, age=22)         │
│ ...                          │
└──────────────────────────────┘
            │
            │ 批量扫描 orders 表
            ▼
    对于 orders 表的每一行:
        检查 user_id 是否在 Join Buffer 中
        如果在 → 输出连接结果
c
class Block_nested_loop_join_executor : public Join_executor {
    uchar* m_join_buffer;        // Join Buffer
    size_t m_buffer_size;        // Buffer 大小
    
    void read_rows() override {
        // 1. 填充 Join Buffer
        while (m_outer->read_row()) {
            store_row_in_buffer(m_join_buffer, m_buffer_size);
            if (buffer_full()) break;
        }
        
        // 2. 扫描内层表，与 Buffer 中的行匹配
        for (;;) {
            if (!m_inner->read_row()) {
                // 内层表扫描完毕，重新填充 Buffer
                refill_buffer();
                if (buffer_empty()) return;
                m_inner->rewind();
                continue;
            }
            
            // 3. 在内层 Buffer 中查找匹配
            for (each row in m_join_buffer) {
                if (match(row, m_inner_current_row)) {
                    output_row();
                }
            }
        }
    }
};

8.3 索引嵌套循环连接（Index Nested Loop Join） ​

当内层表有可用索引时，优化器会选择索引嵌套循环连接——对于外层表的每一行，通过索引查找内层表的匹配行：

外层表: users (通过 idx_age 索引查找)
内层表: orders (通过 idx_user 索引查找)

执行过程:
for each user where age > 20:  // 使用 idx_age 索引
    // 通过索引快速查找
    for each order where user_id = user.id:  // 使用 idx_user 索引
        output user + order

优势：每次内层查找的时间复杂度从 O(m) 降到 O(log m)。

8.4 哈希连接（Hash Join） ​

MySQL 8.0 开始支持哈希连接。哈希连接将外层表的行构建成哈希表，然后扫描内层表并在哈希表中查找匹配：

1. 构建哈希表 (使用 Join Buffer):
   users 表的所有行 → 构建哈希表 (以 id 为 key)
   
2. 扫描探测:
   for each order in orders:
       hash_table[order.user_id] → 查找匹配的 user
       如果找到 → 输出连接结果
sql
-- 哈希连接示例
EXPLAIN FORMAT=JSON SELECT /*+ HASH_JOIN(orders) */ 
u.name, o.total
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.age > 20;

哈希连接的使用条件：

  • 连接条件是等值连接（ON a.col = b.col）
  • 至少有一个表没有可用的连接索引
  • 优化器估算哈希连接的代价更低

8.5 半连接与反连接 ​

半连接（Semi-Join） ​

半连接只检查外层表的行在内层表中是否有匹配，不返回内层表的列。这是 IN 和 EXISTS 子查询的优化方式：

sql
-- 半连接
SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

MySQL 8.0 对半连接有 5 种执行策略：

  1. FirstMatch：找到第一个匹配就停止
  2. LooseScan：扫描内层索引，跳过重叠值
  3. Materialize：将子查询物化为临时表
  4. Semi-join：使用半连接执行器
  5. DuplicateWeedout：使用物化临时表去重
c
// 半连接策略选择
enum SemiJoinStrategy {
    SJ_FIRSTMATCH,
    SJ_LOOSESCAN,
    SJ_MATERIALIZE,
    SJ_SEMIJOIN,
    SJ_DUPLICATEWEEDOUT,
};

SemiJoinStrategy choose_semi_join_strategy(QEP_TAB* inner, 
                                            QEP_TAB* outer) {
    // 评估每种策略的代价
    Cost_estimates costs[5];
    
    costs[SJ_FIRSTMATCH] = compute_firstmatch_cost(inner, outer);
    costs[SJ_LOOSESCAN] = compute_loosescan_cost(inner, outer);
    costs[SJ_MATERIALIZE] = compute_materialize_cost(inner, outer);
    costs[SJ_SEMIJOIN] = compute_semijoin_cost(inner, outer);
    costs[SJ_DUPLICATEWEEDOUT] = compute_dupweedout_cost(inner, outer);
    
    // 选择代价最低的策略
    return arg_min(costs);
}

反连接（Anti-Join） ​

反连接检查外层表的行在内层表中没有匹配：

sql
-- 反连接
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

九、子查询优化 ​

9.1 物化子查询 ​

物化子查询将子查询的结果物化为临时表，然后与外层查询进行连接：

sql
-- 原始: IN 子查询
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE total > 100);

-- 物化后:
CREATE TEMPORARY TABLE tmp (user_id, INDEX(user_id))
    AS SELECT user_id FROM orders WHERE total > 100;
SELECT users.* FROM users JOIN tmp ON users.id = tmp.user_id;

物化的优势：

  • 子查询只执行一次
  • 物化临时表有索引，连接效率高
  • 外层查询可以使用多种访问方式

物化的劣势：

  • 物化临时表占用内存/磁盘空间
  • 如果子查询结果集很大，物化代价高

9.2 半连接优化 ​

半连接优化将 IN 子查询转换为 EXISTS 形式，使用半连接执行器：

sql
-- IN 子查询 → 半连接
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE total > 100);

-- 转换为:
SELECT * FROM users
WHERE EXISTS (
    SELECT 1 FROM orders 
    WHERE orders.user_id = users.id AND orders.total > 100
);

9.3 首次匹配策略 ​

首次匹配（FirstMatch）策略是半连接的一种优化，对于外层表的每行，只需要找到内层表的第一个匹配：

c
class FirstMatch_semi_join_executor : public Join_executor {
    void read_rows() override {
        for (;;) {
            // 读取外层表的一行
            if (!m_outer->read_row()) return;
            
            // 在内层表中查找第一个匹配
            if (find_first_match_in_inner()) {
                output_row();  // 找到匹配，输出
            }
            // 没找到，跳过该行（反连接时保留）
        }
    }
};

十、排序与分组优化 ​

10.1 filesort 优化 ​

当无法利用索引排序时，MySQL 需要使用 filesort（虽然叫 filesort，但可能在内存中进行）：

c
// filesort 执行流程
void filesort(FILE* file, TABLE** tables, uint* sortorder,
              uint nsortorder, uchar*排序键缓存) {
    
    // 1. 读取所有需要排序的行
    while (read_next_row(tables)) {
        // 2. 构建排序键
        sort_keys_buffer.push_back(current_row);
        
        // 3. 如果内存已满，进行外部排序
        if (sort_keys_buffer.is_full()) {
            external_sort(sort_keys_buffer, file);
            sort_keys_buffer.clear();
        }
    }
    
    // 4. 对内存中的数据排序
    std::sort(sort_keys_buffer.begin(), sort_keys_buffer.end(), compare_sort_keys);
    
    // 5. 合并多个已排序的块
    merge_sorted_blocks(file, sort_keys_buffer);
}

filesort 的两种模式：

  1. 双路排序（Two-Pass）：先读取行指针和排序键，排序后再回表读取其他列
  2. 单路排序（One-Pass）：直接读取所有列进行排序（推荐，使用 max_length_for_sort_data 配置）

10.2 利用索引排序 ​

如果 ORDER BY 子句中的列与索引顺序一致，MySQL 可以避免 filesort：

sql
-- 表有索引 (age, name)
SELECT * FROM users ORDER BY age, name;
-- → 可以直接利用索引排序，不需要 filesort

优化器通过 check_order_using_index() 函数判断是否可以利用索引排序：

c
bool check_order_using_index(QEP_TAB* tab, ORDER* order) {
    uint key = tab->ref_key;
    KEY* key_info = &tab->table->key_info[key];
    
    for (uint i = 0; i < order->n_item; i++) {
        // 检查排序列是否与索引列匹配
        if (!is_column_in_key(order->item[i], key_info)) {
            return false;
        }
    }
    return true;
}

10.3 分组优化 ​

GROUP BY 优化与排序类似，优先利用索引：

sql
-- 表有索引 (age, status)
SELECT age, status, COUNT(*) FROM users GROUP BY age, status;
-- → 可以直接利用索引进行分组

分组优化策略：

  1. 索引分组：利用索引顺序直接分组，无需额外处理
  2. 临时表分组：将数据放入临时表，再在临时表上分组
  3. 流式分组：在有序数据上进行流式分组（不需要临时表）
c
// 流式分组执行器
class Streaming_group_executor : public Join_executor {
    void read_rows() override {
        // 假设输入数据已按 GROUP BY 列排序
        // 读取第一行，作为当前组的开始
        read_first_row();
        init_current_group();
        
        for (;;) {
            if (!read_next_row()) {
                output_current_group();  // 输出最后一组
                return;
            }
            
            if (is_new_group()) {
                output_current_group();  // 输出当前组
                start_new_group();
            }
            
            accumulate_current_row();  // 累加到当前组
        }
    }
};

十一、Hint 的使用 ​

11.1 USE INDEX / IGNORE INDEX / FORCE INDEX ​

sql
-- 使用特定索引
SELECT * FROM users USE INDEX (idx_age) WHERE age > 20;

-- 忽略特定索引
SELECT * FROM users IGNORE INDEX (idx_age) WHERE age > 20;

-- 强制使用索引
SELECT * FROM users FORCE INDEX (idx_age) WHERE age > 20;

-- 组合使用
SELECT * FROM users 
USE INDEX FOR JOIN (idx_age) 
IGNORE INDEX FOR ORDER BY (idx_name)
WHERE age > 20 ORDER BY name;

11.2 JOIN_FIXED_ORDER / JOIN_ORDER ​

sql
-- 固定连接顺序
SELECT /*+ JOIN_FIXED_ORDER(u, o, p) */ *
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN products p ON o.product_id = p.id;

-- 指定连接顺序（优化器可以调整）
SELECT /*+ JOIN_ORDER(u, o, p) */ *
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN products p ON o.product_id = p.id;

11.3 MAX_EXECUTION_TIME ​

sql
-- 设置查询最大执行时间（毫秒）
SELECT /*+ MAX_EXECUTION_TIME(5000) */ *
FROM large_table;
-- 如果超过5秒，查询会被中止并返回错误

11.4 其他常用 Hint ​

sql
-- 半连接策略
SELECT /*+ FIRSTMATCH(user) */ * FROM users
WHERE id IN (SELECT user_id FROM orders);

-- 物化子查询
SELECT /*+ MATERIALIZE(orders) */ * FROM users
WHERE id IN (SELECT user_id FROM orders);

-- 索引条件下推
SELECT /*+ INDEX_CONDITION_PUSHDOWN(idx_age) */ *
FROM users WHERE age > 20 AND name LIKE 'J%';

-- 不使用索引条件下推
SELECT /*+ NO_INDEX_CONDITION_PUSHDOWN(idx_age) */ *
FROM users WHERE age > 20;

十二、可插拔优化器架构 ​

MySQL 8.0 引入了可插拔优化器架构，允许用户自定义优化策略和代价模型。

12.1 自定义代价模型 ​

c
// 自定义代价模型示例
class My_cost_model : public Cost_model {
public:
    double random_page_cost() const override {
        // 根据实际存储设备调整
        return 1.0;  // SSD 接近于 1.0
    }
    
    double seq_page_cost() const override {
        return 1.0;
    }
    
    double cpu_row_cost() const override {
        return 0.5;  // 调低CPU代价
    }
};

总结 ​

MySQL 查询优化器是数据库性能优化的核心引擎。通过从源码级别理解其工作原理：

  1. 掌握 SQL 解析流程：理解词法分析、语法分析、语义分析的每个步骤
  2. 理解查询改写策略：视图合并、子查询优化、等价变换、常量传播
  3. 深度理解索引选择：范围扫描、多列索引、覆盖索引的选择逻辑
  4. 掌握代价模型：理解单次操作代价与每行代价的计算方式
  5. 学习连接算法：嵌套循环、块嵌套循环、索引嵌套循环、哈希连接的适用场景
  6. 利用 EXPLAIN：通过 EXPLAIN 和 EXPLAIN ANALYZE 分析执行计划

在实际工作中，结合性能监控工具和优化器 Hint，可以精确控制查询的执行路径，实现从"写 SQL"到"写高效 SQL"的进阶。
